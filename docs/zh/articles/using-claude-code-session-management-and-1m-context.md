# 使用 Claude Code：会话管理与 1M 上下文
我们发布了 **`/usage`**，这是一个新的斜杠命令，帮助你了解自己在 Claude Code 中的用量。该功能源自与客户的多次交流。

在这些交流中反复出现的一点是，用户管理会话的方式差异很大，尤其是在我们刚刚将 Claude Code 的上下文更新到 100 万之后。

你是只用一个会话，还是在终端里保持两个会话？你会为每个提示词都开一个新会话吗？你什么时候使用 [compact](https://platform.claude.com/docs/en/build-with-claude/compaction)、rewind 或[子智能体](https://code.claude.com/docs/en/sub-agents)？什么会导致糟糕的 compact 或糟糕的会话？

这里的细节多得惊人，而且确实会塑造你使用 [Claude Code](https://claude.com/product/claude-code) 的体验，而几乎所有这些细节都来自[管理你的上下文窗口](https://code.claude.com/docs/en/how-claude-code-works)。

## **上下文、上下文压缩与上下文腐化的快速入门**



上下文窗口是模型在生成下一个回复时能一次性「看到」的全部内容。它包括你的系统提示词、到目前为止的对话、每一次工具调用及其输出，以及每一个被读取过的文件。Claude Code 的上下文窗口为 100 万 token。

遗憾的是，使用上下文会对性能产生轻微影响，这通常被称为上下文腐化。上下文腐化指的是这样一种现象：随着上下文增长，模型的注意力被分散到更多 token 上，较旧的、无关的内容开始干扰当前任务，从而导致模型性能下降。

上下文窗口是硬性上限，因此当你接近上下文窗口末尾时，你一直在处理的任务会被自动摘要成一段更简短的描述，模型则在新的上下文窗口中继续工作。我们称之为上下文压缩（compaction）。你也可以自行触发上下文压缩。



## **每一轮都是一个分叉点**

假设你刚让 Claude 做某件事，它已经完成了——现在上下文中有了一些信息（工具调用、工具输出、你的指令），而接下来该做什么，你有数量惊人的选项：

-   **继续** —— 在同一会话中再发一条消息
-   **`/rewind`（esc esc）** —— 跳回之前某条消息，从那里重新尝试
-   **`/clear`** —— 开启新会话，通常带上你从刚才所学中提炼出的简要说明
-   **Compact** —— 对到目前为止的会话做摘要，并在摘要之上继续
-   **子智能体** —— 把下一块工作交给一个拥有自己干净上下文的智能体，只把它的结果拉回来

虽然最自然的做法就是继续，但另外四个选项的存在是为了帮助你管理上下文。



## **何时开启新会话**

什么时候该保持一个长时间运行的会话，什么时候该开新的？我们的一般经验法则是：当你开始一个新任务时，你也应该开启一个新会话。

虽然 1M 上下文窗口意味着你现在可以更可靠地完成更长的任务，例如从零构建一个全栈应用，但上下文腐化仍可能发生。

有时你可能会做相关的任务，其中部分上下文仍然必要，但并非总是如此。例如，为你刚实现的功能编写文档。你固然可以开启新会话，但 Claude 将不得不重新读取你刚实现的那些文件，这会更慢也更贵。

## **用回退代替纠正**



在 Claude Code 中，双击 Esc（或运行 `/rewind`）可以让你跳回任意一条之前的消息，并从那里重新提示。该点之后的消息会从上下文中丢弃。

回退往往是更好的纠正方式。例如，Claude 读取了五个文件，尝试了一种方法，但没有成功。你的本能可能是输入「那样不行，改用 X 试试。」但更好的做法可能是回退到读取文件之后的那一刻，用你学到的东西重新提示：「不要用方法 A，foo 模块没有暴露那个——直接走 B。」

你也可以使用*「summarize from here」*或 `/rewind` 斜杠命令，让 Claude 总结它的经验教训并生成一条交接消息，有点像来自未来的自己给上一轮 Claude 的一条消息：它尝试了某件事，但没成功。

## **上下文压缩 vs. 开启全新会话**

一旦会话变长，你有两种方式摆脱多余的上下文：`/compact` 或 `/clear`（并重新开始）。它们感觉相似，但行为差异很大。

**Compact** 要求模型对到目前为止的对话做摘要，然后用该摘要替换历史记录。它是有损的，但你不必自己写任何东西，而且 Claude 在纳入重要的经验教训或文件时可能更周全。你也可以通过传入指令来引导它（`/compact focus on the auth refactor, drop the test debugging`）。



使用 `/clear` 时，由*你*写下重要的内容（「我们正在重构 auth 中间件，约束是 X，重要的文件是 A 和 B，我们已经排除了方法 Y」），然后干净地开始。这更费功夫，但得到的上下文是你自己认定相关的内容。

## **什么会导致糟糕的自动压缩？**

如果你运行大量长时间运行的会话，你可能注意到有时压缩会特别糟糕。在这种情况下，我们经常发现，糟糕的压缩会发生在模型无法预测你工作走向的时候。

在上面的例子中，自动压缩在一次长时间的调试会话之后触发，总结了调查过程，而你的下一条消息是「现在修复我们在 bar.ts 中看到的另一个警告。」

但由于该会话聚焦于调试，另一个警告可能已从摘要中被丢弃。

这尤其困难，因为由于上下文腐化，模型在压缩时正处于其最不智能的时刻。有了 100 万上下文，你有更多时间主动执行 /compact，并附上你想做什么的描述。

## **子智能体与全新的上下文窗口**

当你事先知道某块工作会产生大量你之后不再需要的中间输出时，[子智能体](https://claude.com/resources/articles/subagents-in-claude-code)往往效果很好。

当 Claude 通过 Agent 工具派生子智能体时，该子智能体会获得自己全新的上下文窗口。它可以根据需要做尽可能多的工作，然后综合其结果，只把最终报告带回给父级。



我们在 Anthropic 使用的思维测试是：*我还会需要这个工具输出，还是只需要结论？*

虽然 Claude Code 会自动调用子智能体，但你可能想明确告诉它这样做。例如，你可能想告诉它：

-   「派生一个子智能体，根据以下 spec 文件验证这项工作的结果」
-   「派生一个子智能体，通读另一个代码库并总结它如何实现 auth 流程，然后你自己以同样的方式实现」
-   「派生一个子智能体，根据我的 git 变更编写这个功能的文档」

**综合运用**

为了帮助你选择使用哪种上下文管理功能，我们整理了这个实用的表格，列出常见情况、该用哪个工具以及原因。

| 情况 | 考虑使用 | 原因 |
| --- | --- | --- |
| 同一任务，上下文仍然相关 | 继续 | 窗口中的所有内容仍在发挥作用；不要为重建它付出代价。 |
| Claude 走错了路 | 回退（双击 Esc） | 保留有用的文件读取，丢弃失败的尝试，用你学到的东西重新提示。 |
| 任务进行到一半，但会话被陈旧的调试/探索内容撑得臃肿 | /compact <提示> | 省力；由 Claude 决定什么重要。如有需要，用指令引导它。 |
| 开始一个真正的新任务 | /clear | 零腐化；你精确控制哪些内容被带过去。 |
| 下一步会产生大量输出，而你只需要其中的结论（代码库搜索、验证、写文档） | 子智能体 | 中间的工具噪声留在子级的上下文中；只有结果返回。 |
