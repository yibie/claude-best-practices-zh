# 在 Anthropic 重新设计源代码管理
_10 月 15 日更新，补充了关于那些率先采用我们在 Scion 中使用的许多技术的项目的更多细节。_

在 Anthropic，编码不再是构建系统或开展研究的瓶颈。Claude 能够自主地在研究循环中迭代、对复杂程序进行微优化，并以我们前所未见的速度和规模从零构建新服务。如今的瓶颈，是为人类规模构建的所有开发者基础设施：源代码管理、构建和 CI。

2026 年 5 月，Anthropic 平均每天合并约 2,500 次代码变更；截至 9 月，我们每天合并超过 30,000 次。我们不认为这一增长速度会在短期内放缓；合并代码的潜在需求几乎是无限的，而我们每消除一个瓶颈，都会立即带来代码产出量的进一步增长。

为了支撑这种增长，我们构建了 Scion——一个自研的版本控制系统——并在五个月内将我们的单体仓库从 git 完全迁移出来。在同一时期，我们还构建并上线了代码审查界面（名为 Antique）、代码搜索、一套丰富的源代码管理 IAM 系统、管理并落地大量已审查代码的新方法等等。本文中，我们将重点介绍我们具体是如何构建 Scion 的。这是一个有趣的案例研究：Claude 编写代码的能力既是最初让我们陷入这种处境的原因，_也_是我们能够快速构建出一个高质量、可扩展系统来应对它的原因。

### 扩展我们的单体仓库

在探讨我们构建了什么之前，我们应该承认我们的工作负载有多么不寻常。不出所料，Anthropic 使用 Claude 编写软件的程度远超几乎所有其他公司，因此我们常常是最先看到为人类规模构建的工具开始吃紧的一方。源代码管理只是其中一个例子。虽然我们不认为许多组织在短期内会遇到这些问题，但我们预计，用不了多久，其他使用 AI 编码工具的公司也会经历同样的压力点，这也是我们想分享我们构建了什么、学到了什么的原因。

Git 是一个去中心化系统：每个克隆都是一个完整、自包含的仓库，可以计算差异、读取历史和 blame，并在完全离线的情况下检出任意修订版本。对于绝大多数仓库来说，这是正确的设计，也是 git 成为标准的重要原因。

随着我们的单体仓库增长，它越来越不符合这一设计空间。仅主分支的历史就接近 100 GB，而_压缩后_的工作副本也超过 25 GB。我们每天为 CI 执行约 2,500 万次代码检出，这还不包括开发者环境、智能体沙箱和研究任务。如果朴素地拉取，那将是每天超过 600 PB 的 git 流量。

Git 提供了处理仓库一部分内容的工具，例如浅克隆、稀疏检出和 promisor 远程。除此之外，针对大型单体仓库还有标准的变通方法，比如内部 git 镜像和存放在 blob 存储中的仓库快照（种子）。这些我们都用过——在高峰期，我们运营着数百个内部 git 镜像来应对负载。这为我们争取了时间，但随着合并率的提高，它们的运维变得越来越困难。种子在每次刷新之间离主分支末端越来越远，而要让依赖历史记录的操作（如 diff 和 blame）在部分克隆上正常工作，需要越来越多的细心维护。

退一步看，我们注意到，和大多数公司一样，我们把 git 当作一个只有一个权威副本的集中式系统来使用，但我们的客户端几乎全是智能体和任务，而它们按定义是在线的。那些让 git 在分布式、离线工作中表现出色的特性，恰恰在仓库增长时削弱了我们的扩展能力。于是我们问自己：如果我们从一开始就考虑到智能体始终在线这一事实来设计源代码管理，它会是什么样子？

### 智能体规模源代码管理的原则

在智能体式编码中，许多关于软件开发方式的常见假设正在演变。我们在构建 Scion 时拥抱了这些变化，这让我们能够在几个核心原则上采取与 git 截然不同的方法。面向超大型单体仓库的源代码管理已有先例，尤其是 Google 的 [Piper](https://en.wikipedia.org/wiki/Piper_\(source_control_system\)) 和 Meta 的 [Sapling](https://sapling-scm.com/)，[2](#footnote-2) 因此我们能够借鉴它们来之不易的经验来构建 Scion。我们的原则是：

**客户端始终在线。** Git 假设客户端离线工作，并且需要仓库的完整副本。由于我们的客户端几乎全是智能体和任务，我们围绕一个始终可达的服务器来设计 Scion 的客户端和协议，客户端在需要时拉取数据。

**客户端-服务器不对称。** 在 git 中，每个客户端都能成为完整的服务器。在 Scion 中，服务器负责回答关于文件历史和 blame 的问题、创建提交、执行合并和变基等等。客户端维护一个有界的本地对象缓存，在磁盘上布置工作副本文件，监控文件系统变化，并为用户提供与服务器交互的顺手方式。它自身能计算的东西很少，但作为交换，它在本地需要的数据也少得多。

**一个全面的源代码管理服务可以支撑许多新颖的应用。** 在 git 中，一个需要向仓库提问的 CI 任务或工具——比如谁最后修改了某一行，或者两个提交之间是什么关系——必须维护一份仓库的本地副本，或者指望厂商特定的 API 能给出答案。在 Scion 中，客户端使用的所有源代码管理查询也都通过 API 暴露，因此在许多情况下，任务根本不需要本地仓库。许多内部工具，比如我们自动化的 bisect 和 revert 流水线，如果没有这种廉价、可编程的源代码管理访问方式，就无法在规模上实际运作。

**一切都必须能水平扩展。** 在高峰期，我们运行着数百个 git 镜像，这严重消耗了容量，而且一旦仓库超出了镜像的磁盘或内存限制，就不再能扩展。在 Scion 中，仓库的数据是分布式的，每个组件都可以独立扩展；任何地方都没有仓库的完整物化副本，即使在服务器上也没有。不存在 packfile（git 压缩的对象包）的等价物，因此不需要仓库维护。

**提交必须廉价、增量且无锁。** 在 git 中，你在本地提交，然后推送以分享你的工作。在 Scion 中，每次提交、变基或合并都在服务器上进行，因此没有什么需要推送，但每个操作都需要很快。创建提交并更新其下游数据结构的成本必须随变更的大小扩展，而不是随仓库的整体大小扩展，否则服务器就跟不上。Scion 的开发生命周期不鼓励使用 ref（指向提交的指针，如分支和标签），除了主 ref 或发布分支，因为每个服务器都必须达成一致的_全局_状态是一个迫在眉睫的扩展问题。

**工作副本是可选的，并且按设计就是稀疏的。** 由于我们的单体仓库如此之大，而且我们每天为 CI 检出代码数千万次，我们希望尽可能避免检出。在 Scion 中，一个需要某个提交与其合并基之间差异的 CI 任务，可以直接向服务器请求。写入也是如此：许多写入工作负载也可以跳过检出，完全通过 API 运作。Scion 的协议以稀疏检出（只包含客户端请求的目录）和虚拟化检出（按需物化文件）为中心，因此当任务确实需要磁盘上的文件时，客户端只为它实际读取的内容付出代价。

### Scion 如何工作

了解这些原则在构建 Scion 时如何在实践中结合是很有帮助的。这些洞见可以应用于其他源代码管理系统，或者更广泛地说，应用于软件开发生命周期的其他阶段。

#### 数据结构

在 Scion 中，工作单元是"changeset"，即预写日志中的一条记录。changeset 存储了你在 git 提交中预期的大部分内容。但 git 提交存储的是指向树的指针，而 changeset 存储的是相对于其第一个父提交发生变更的文件列表，[1](#footnote-1) 以及指向 blob 存储中压缩文件内容的内容寻址指针。changeset 在服务器端创建，并立即在所有地方可用。

这种结构让我们能够以极高的吞吐量接受 changeset，因为不需要接受 packfile，没有锁定或跨服务器协调，也没有需要移动的 ref。Scion 在技术上支持 ref，但由于创建和拉取提交都不涉及 ref，移动一个 ref 只是对单个 Spanner 行执行比较并交换，与创建 changeset 分开进行。

changeset 只记录变更的内容，因此单靠它无法快速回答诸如谁最后编辑了某一行、哪些提交影响了某个文件之类的问题。为了回答这些问题，Scion 从 changeset 构建额外的数据结构，包括专门用于文件 blame 和路径历史的结构，以及用于提交图的跳表。我们把所有不直接属于 changeset 的内容称为"派生数据"，并通过一个通用机制计算它们。每种派生数据都是递归定义的，因此某个 changeset 的值由该 changeset 各父提交的值计算得出。

这个机制有三个好处。第一，当新的数据结构能让某些操作更快时，我们可以轻松添加新的派生数据类型。第二，对于每种类型，我们可以选择是急切计算还是推迟计算，从而避免物化我们不需要的数据。第三，由于客户端永远看不到这些数据结构的内部，我们可以在不改变客户端的情况下优化它们。随着系统的发展，我们已多次添加新的派生数据类型，例如用于执行复制检测或基于路径的文件搜索的新索引。

#### 扩展 Scion

一小群 Scion 服务器为客户端所需的任何操作提供源代码管理 API，例如获取 changeset、计算差异、查找合并基和拉取 blob。所有源代码管理数据都是内容寻址的，因此一份数据一旦存储就永不改变，任何服务器都可以缓存它而无需与其他服务器确认。因此，服务器可以水平扩展，几乎不需要协调。它们本质上是大缓存，同时还能即时计算派生数据并将结果写回 Spanner。

Scion 的众多消费者不再需要维护自己的本地仓库。拉取和维护仓库过去是 CI 任务或需要向源代码管理提问（尤其是关于提交祖先关系和 blame）的工具的一项重大维护负担。在迁移早期，在我们拥有自己的客户端、仓库格式或协议之前，Scion 只回答这些"元数据"查询。拉取文件内容和物化工作副本是数据密集得多的操作，它们需要自己的设计。

Scion 的 scn 客户端在几个重要方面偏离了 git 的拉取协议，因此它适合一种高度可扩展的架构，所需的 CPU 远少于 git 服务器。Scion 的协商不会告诉服务器客户端已经拥有什么；相反，它只针对客户端想要的树和 blob 进行操作。从根树开始，客户端检查本地存储中缺失的树并递归请求它们，然后对 blob 重复该过程。每个请求都是针对一个永不改变的特定对象，因此任何缓存都能回答它，该架构与传统的分层缓存非常相似。这个过程也很高效且可恢复，因为不存在单个数 GB 的 packfile 响应。稀疏甚至虚拟化检出不需要特殊支持，因为客户端只是不去请求它不想要的树。

在这个服务器集群中，客户端通过套接字与一个守护进程 scion-daemon 通信，该守护进程为整个节点存储对象。我们的大多数节点需要访问单体仓库，同一节点上的任务会复用大部分相同的对象。每个守护进程从定期刷新的快照开始，然后只与其所在区域的树和 blob 缓存服务器（称为 scion-cache）通信。这些缓存服务器直接从内存中以守护进程将要消费的磁盘格式流式传输对象，因此它们不需要花时间计算客户端缺失的对象或执行增量压缩。当缓存缺少某个对象时，它会向权威的 scion-servers 请求，后者根据需要从 Spanner 或云存储读取。

scion-daemon、scion-cache 和 scion-server 都响应此协议的相同 RPC，因此客户端不需要知道缓存拓扑。理论上任何一层都可以与任何其他层通信，但我们严格强制分层以隔离故障域。我们希望避免区域性的 scion-cache 发生故障时压垮上游的 scion-servers 并拖垮整个系统的情况。

该系统的每一层都保持超过 99% 的缓存命中率，且不需要长期存活的状态，因此需要时可以轻松扩容。就 CPU 和内存需求而言，我们现在的 Scion 基础设施占用比之前的 git 镜像基础设施小 200 倍。CI 和研究任务检出代码的速度快了两个数量级（以秒计而非分钟计），这在整个集群中释放了相当可观的容量；仅 CI 就实现了 25% 的 CPU 容量收益。客户端和缓存都不需要执行仓库维护，这简化了我们任务的生命周期管理。

### 构建 Scion 的收获

我们开始构建 Scion 的时间，大约与 [Claude Mythos Preview](https://www.anthropic.com/claude/mythos) 和 [Claude Tag](https://www.anthropic.com/news/introducing-claude-tag) 在内部可用相同。这两个发布同时放大了对 Scion 的需求，也显著加快了我们构建它的速度。

这里有一个特别引人注目的例子。今年早些时候，我们基本上手写了 git 到 Scion 摄取流水线的第一版作为原型。我们认为它不错——直到我们拿到 Claude Mythos Preview 的早期内部快照。我们让它重写整个东西，在没有任何进一步指示的情况下，它产出了一个内存消耗减少 20 倍、速度快 4 倍的版本，同时保留了围绕摄取顺序和数据结构的所有隐式不变量。

我们在构建和运营 Scion 中学到的东西，为构建智能体规模软件可能是什么样子提供了一些有趣的教训。

**小团队的快速开发将变得更加普遍。** 一个七人团队同时构建了 Scion _和_ Antique（我们的代码审查工具，完全可以另写一整篇博客），更不用说还有六个相关系统，并在五个月内完全迁移到它们。我们完成这一切的同时，每天合并的代码量增长了 10 倍。过去，开发和部署这样一个源代码管理系统需要一家公司花费数年迭代迁移，并投入多得多的工程师。我们认为这种快速、灵活的迁移在未来会变得更加普遍。

**工程师的价值丝毫未减，但他们的工作正在改变。** 所有参与这个系统的工程师现在都会认为 Claude 在_编写_代码方面比他们更强。但我们的工程师仍然提供了对高层系统间组件和设计层面权衡的宝贵理解，围绕我们想解决的问题和我们知道需要达到的规模做出明智的选择。很多时候，我们发现工程师的角色是告诉 Claude"不行"。智能体有时会为了满足一个本就不该被允许的模式而违反核心系统约束。这在我们的迁移中尤为常见。例如，有多个系统试图通过线性读取提交日志来暴力查找某个变更何时合并到主分支，而不是询问我们的代码审查工具。Anthropic 还大量使用对抗性审查，虽然这在许多方面非常有效，但也可能目光短浅，因此熟练的工程师需要引导 Claude 不要为了应对假想的担忧而对系统的某些部分过度设计。例如，有一次这样的审查对信任另一个内部服务过于防御，导致 Claude 添加了过多的验证和复杂性。我们的团队成员仍然审查系统的每一个变更请求，但他们现在审视的是变更的_意图_，而不是逐行阅读代码。

**我们能够大幅改进优化和质量。** 得益于 Claude 能够以远超我们自己的速度编写海量代码，Scion 是我们参与过的最经过充分测试和充分防御的代码库之一。即使在我们紧张的时间表下，我们也能够为我们遇到过的每一个非平凡的基础设施和源代码管理交互构建封闭模拟，以及模糊测试和复杂的速率限制。Claude 还随手发现了重大的优化——例如，一项祖先关系查询的算法优化，它漏掉了我们的某个索引——这本需要专家花费数天或数周的分析和调优……然后第二天它又做了一遍。

**我们为单体仓库安全的新形式奠定了基础。** 在庞大的单体仓库中管理安全、安保和合规，与管理规模和体量同样重要。我们从一开始就考虑这些来构建 Scion。它支持对仓库的丰富访问控制，以及将权限应用于单个目录的能力，从而在不失去单体仓库优势的情况下保护最敏感的代码。此外，我们构建的代码审查工具可以对审批表达复杂的语义约束，这让我们能够区分仅注释变更和敏感逻辑变更这样简单的事情，使人类审查者能够专注于最重要的变更。

**可以实现新水平的运营卓越。** 我们的团队大量使用 Claude Tag，这帮助我们监控系统的每个组件。例如，我们创建了 Slack 频道，让 Claude 专注于单个组件的健康状况。我们称这些 Claude 为"超级粉丝"。我们有一个 scion-daemon 超级粉丝、一个 scion-cache 超级粉丝、一个 Antique 合并队列超级粉丝，等等。它们可以访问我们的遥测和日志，表现得像一位经验丰富的工程师，除了刷新图表和寻找任何异常之外无事可做。我们所有系统也都有传统告警，但我们的超级粉丝能够检测到微妙而新颖的问题，相比之下这些告警显得单一维度。

**我们正在彻底重新思考我们的先验假设。** 这个项目促使我们认真审视其他为人类规模设计的工作流。例如，一个正规的合并队列在智能体规模下没有太大意义。当数百甚至数千个变更可以在测试运行时合并，CI 到底意味着什么？我们一直无法有效地复制业界标准的合并队列全局仓库锁，因此我们转而投资于合并后和部署前的自动化测试。这确实意味着并发变更可能冲突，但 Claude 通常能比人类识别冲突更快地修复它们。

### 为更广泛的生态系统做贡献

我们认为 Scion 只是解决能力日益强大的 AI 智能体所引发的扩展问题的一部分答案。我们分享这些细节，是作为团队如何应对类似挑战的一个例子，尽管我们不认为我们的解决方案或我们的考量适合所有情况。

Scion 绝不是 git 在通用场景下的合适替代品。我们在这里概述的概念实际上只对真正庞大的单体仓库有意义，这些仓库要么有数万名工程师，要么有成群的智能体大量编写代码。此外，Anthropic 的独特之处在于，我们为内部使用花费 token 的能力远远超过任何其他企业现实上愿意花费的水平。我们这样做既是为了满足我们自己的软件开发需求，也是为了测试 Claude 的能力。

实际上，很难以一种对其他组织广泛有用的形式提供 Scion。它与 git 差异巨大，意味着公司需要迁移开发生命周期的每一个环节，而且它需要自己的代码审查、代码搜索和 CI。我们这些组件的内部版本高度定制化，因此其他组织难以采用，而且我们担心，试图构建一个试图取悦所有人的公开版本实际上不会很有用。

然而，我们预计这类问题在未来 6 到 12 个月内会变得更加普遍，而让每个使用 git 的公司独自面对类似挑战将是工程资源的低效利用。鉴于此，我们认为我们能做的最有影响力的事情就是分享我们的思考，以便其他开发者可以在不脱离整体模型的情况下，将 Scion 最成功的部分应用于 git。git 服务器不必以与 git 客户端相同的方式工作；存在能够带来显著扩展改进的新颖服务器架构。Git 平台可以提供像 Scion 那样全面的服务器端 RPC，甚至可能以一种标准化的方式跨各个 forge 提供，让 git 客户端学会与之通信。协商协议也不必看起来和今天完全一样，而且 git 中各种稀疏和浅克隆特性可以被组合得很好。

最后，我们要承认 git 社区花了近二十年时间为数百万开发者扩展这个平台。我们的贡献要狭窄得多：分享我们对智能体式软件开发如何与这些系统交互的早期看法，以便我们能够与 GitHub、GitLab 和 OSS 社区合作，支持开发者不断变化的需求。当软件开发生命周期与 AI 指数增长相交时，我们都在同一条船上。
