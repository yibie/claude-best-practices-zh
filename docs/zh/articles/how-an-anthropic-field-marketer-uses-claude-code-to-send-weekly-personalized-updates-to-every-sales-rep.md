# Anthropic 的一位现场营销人员如何用 Claude Code 每周向每位销售代表发送个性化更新

作为营销人员，我面临的最大挑战之一，是让销售团队随时了解现场发生的一切。大多数营销人员都熟悉这样的走廊对话：一位销售代表说，“哦，那个活动我从没听说过”（或者那份新白皮书、那场网络研讨会），然后你意识到自己错过了一个向销售代表、进而向客户分享最新工作的机会。

我最初的解决方案，是许多营销人员都熟悉的做法：周一早上与销售团队开 15 分钟的站会。我花周日晚上整理来自各业务线的更新，把它们做成可展示的幻灯片，然后在会上现场讲解信息，并把演示文稿分享到 Slack。大功告成，对吧？并不尽然：有了 Claude 之后，这一切都显得过于手工化，而且随着团队壮大、我开始支持多个销售团队，我的幻灯片流程也跟不上了。这些更新也变得越来越没用，因为我已经没有时间挑出适合每个团队的机会。

我希望让 Claude 来做这些工作，并为每位销售代表打造一个更好的“产品”：一份每周摘要，针对他们的客户量身定制，并与我们在营销侧推进的所有事项相匹配。

幸运的是，我们组织了一场营销黑客松：专门留出时间，用 Claude Code 重建可重复的流程和工作流。我和团队凑在一起，为这个问题投入了一个小时，而这带来了一切不同。像黑客松这样随性、往往由同伴主导的学习机会，能让你进行日常工作中不会专门腾出时间做的实验和探索，我们团队也不例外。

## **你不需要会写代码，你需要会讲清楚**

其他营销人员问我最多的问题之一是：“我该怎么开始用 AI？”我的方法，尤其是在 Claude Code 上，是先写一段提示词，向 Claude 说明：虽然我不是技术出身，但我有这样一个具体挑战，请 Claude 把我当作一位深刻理解业务问题的产品经理，和我一步步协作。我会把想法说出来，所以经常录下自己解释问题的过程，再把转录文本交给 Claude；这样 Claude 就掌握了全部业务上下文。

在我们团队的每周 AE 摘要这个例子里，我先向 Claude 概述目标：每周给每位代表发一条 Slack 消息，说明营销侧正在发生什么，以及这会如何帮助他们的客户。然后我写了一份假的每周更新，给 Claude 一个可参照的模板。我知道销售代表是行动导向的，所以我从“本周三件要事”清单开始，列出三个行动项，比如即将举行的活动或近期内容，供他们分享给客户。我还为经理汇总单独写了一个模板，因为经理通常想要的是团队的整体视图，而不只是单个客户。

接下来，我通过 MCP 把 Claude 连接到 BigQuery；BigQuery 是我们营销团队的可信数据源，能提供来自 HubSpot、Clay 和 Salesforce 数据的细粒度洞察。我想从简单处着手，所以先从我们活动和网络研讨会的唯一可信数据源开始。为了让每条更新个性化，我让 Claude 从我们的 CRM 中拉取该代表负责的区域，以及 Slack 中传达的相关客户更新。这样，Claude 就能把两者解析到一起，生成个性化的每周更新。

随着时间推移，我和营销侧的其他团队合作丰富了数据，所以现在简报中包含了博客文章、电子书、客户案例、网络研讨会，甚至来自我们合作伙伴生态的活动等新内容。

## **用户反馈才是真正的提示词工程**

为了向现场推广，我先从一个同意作为测试组的销售团队开始。发给 10 个人的小组感觉没那么吓人，万一出错也不至于影响太大，而且这个小组承诺提供反馈。首次发送之后，我做了一些调整。

有些问题只是错误。例如，某个活动在源表格中没有 URL，Claude 就编造了一个看起来合理、却打不开的链接。我们立即把它写成提示词中的硬性规则：绝不编造 URL。现在只有当地址逐字符来自源表格时，链接才会被渲染出来。后来的版本干脆把没有链接的活动从简报中完全去掉，因为我们意识到，销售无法为任何人报名的活动只是噪音。

到第一周结束时，提示词里已经有九条内容规则，每一条都对应来自某位销售或经理的一条反馈。有位销售指出，一个面向知识工作者的工作坊推荐了一位工程副总裁，所以现在联系人头衔会与活动的目标受众进行核对，不匹配的会被直接去掉、不作说明。一条行业门槛规则让零售客户不会收到金融晚宴邀请，而还没有客户的全新销售则会收到一段简短的欢迎语，而不是一条空白消息。

其他问题则是数据问题。营销圈的人都知道维护单一可信数据源有多难。比如现场活动表格的列在六周内被重新排列了三次。为了应对这一点，我们修改了提示词，让每次运行时先读取表格的表头行，在撰写任何内容之前先核对列映射。我们不再硬编码“看 C 列”，而是写成类似“看带有活动 URL 的那一列”。

## **在整个业务中推广这份摘要**

经过这些初始运行之后，我把这份摘要扩展到了我支持的每个团队，现在现场营销为整个销售组织运行它。每周一早上，Anthropic 多个销售分段的客户主管打开 Slack，就会看到一条私信，列出本周三项优先行动、其客户相关的现场活动、已注册即将举行的网络研讨会的联系人、可分享的相关营销内容，以及其他跟进建议。

每条消息都根据收件人自己的客户列表生成，所以没有两条消息是相同的。这份摘要确实有效；我们最近在一周内把一场高管晚宴的报名人数翻了一倍，纯粹是因为合适的销售代表在周一早上看到了合适的活动。

当 Anthropic 的业务拓展代表（BDR）想要他们自己版本的摘要时，我们为他们复制了提示词，只改动了一个字段，因为 BDR 在我们的 CRM 中通过不同于客户代表的关联关系映射到客户。提示词结构和内容规则原样沿用，BDR 在两天内就上线了。此后我也为客户成功团队和联盟团队做了同样的事，还为销售之外的其它跨职能伙伴提供所有营销活动的概览。

无论业务变化多快，我和我的团队在 Claude 的帮助下，都能确保销售代表在周一一开始就确切知道本周正在发生什么、该优先关注哪些客户和活动。每周一的发送都会完整归档，所以我可以调出任何销售在任何日期收到的确切内容，经理也能在一份汇总中看到整个团队的建议。我仍然会读发出的内容，不过系统已不再等待我的批准。几周前我去度假时，周一的发送自行发出，一切顺利。

## **开始使用 Claude 的最佳实践**

下面分享一些受我自己使用 Claude Code 经验启发的技巧和窍门：

1.  **从小处着手，从你已经在手工做的事开始。** 当关于人们用 AI 做什么的噪音太多时，起步可能很难。我的建议是：挑出你亲手花时间最多的重复性任务，让 Claude 重建它。这样你就能判断输出好坏，因为你已经知道什么算好。如果这个问题仍然感觉太大，就把 Claude 当作思考伙伴，把它拆成若干步骤。如果这件事是你和其他人共享的，先把早期运行结果只发给自己，这样你能在别人之前发现错误。
2.  **用平实的语言写指令，并给每份文档做版本管理。** 像给新同事交代工作那样向 Claude 交代，剩下的它会完成。指示 Claude 把每次更新保存为带编号的版本，并用一行说明改了什么，这样你就有记录，知道过去每次运行是由哪些提示词产生的。我们的版本是一个 Markdown 文件，同事们会为自己的销售分段运行它；我们最初从共享的 Google Doc 开始，后来在更多人需要编辑时迁移到了 GitHub。
3.  **用一个小而投入的群体做试点。** 我们最初的测试是和少数几位客户主管一起做的，我们知道他们愿意花时间给我们反馈、持续改进报告，帮我们发现问题或就如何扩大覆盖范围或个性化提出建议。
4.  **用反馈改进提示词，把每条修正都写成明确规则。** 当收件人开始给我们反馈、每条修正都成为 Claude 的一条明确规则时，这份营销简报才变得有用。
