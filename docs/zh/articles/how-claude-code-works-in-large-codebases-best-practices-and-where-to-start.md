# Claude Code 在大型代码库中如何运作：最佳实践与入门指南
[Claude Code](https://claude.com/product/claude-code) 已在数百万行的 monorepo、数十年的遗留系统、横跨数十个仓库的分布式架构，以及拥有数千名开发者的组织中投入生产使用。这些环境带来了更小、更简单的代码库所没有的挑战，比如每个子目录的构建命令各不相同，或者遗留代码分散在没有共同根目录的文件夹中。

本文涵盖了我们观察到的、促成 Claude Code 大规模成功采用的模式。我们用「大型代码库」指代各种部署形态：数百万行的 monorepo、历经数十年构建的遗留系统、分布在独立仓库中的数十个微服务，或上述形态的任意组合。这也包括团队通常不会与 AI 编码工具联系在一起的编程语言所编写的代码库，例如 C、C++、C#、Java、PHP。（在这些情况下，Claude Code 的表现超出大多数团队的预期，尤其是在近期的模型版本中。）虽然每个大型代码库部署都受其特定的版本控制、团队结构和积累的约定所塑造，但本文中的模式可以推广到这些场景，是考虑采用 Claude Code 的团队的良好起点。

## Claude Code 如何导航大型代码库

Claude Code 像软件工程师一样导航代码库：它遍历文件系统、读取文件、使用 grep 精确查找所需内容，并沿着代码库中的引用进行追踪。它在开发者的本地机器上运行，不需要构建、维护代码库索引，也不需要将索引上传到服务器。

由 RAG 驱动的 AI 编码工具通过嵌入整个代码库并在查询时检索相关片段来工作。在大规模场景下，这些系统可能失效，因为嵌入流水线无法跟上活跃工程团队的节奏。当开发者查询索引时，它反映的是代码库在数周、数天甚至数小时之前的状态。检索随后会返回团队两周前重命名的函数，或引用上一个冲刺中已删除的模块，而不会提示其中任何一项已经过时。

智能体式搜索避免了这些失效模式。无需在数千名工程师提交新代码时维护嵌入流水线或集中式索引。每个开发者的实例都基于实时代码库工作。

但这种方法也有取舍：当 Claude 拥有足够的起始上下文来知道该去哪里查找时，它效果最好。这意味着 Claude 导航的质量取决于代码库的设置是否良好，是否通过 CLAUDE.md 文件和 Skills（技能）分层组织上下文。如果你让它在十亿行的代码库中查找某个模糊模式的所有实例，工作还没开始就会触及上下文窗口限制。在代码库设置上投入的团队会看到更好的结果。

## 执行框架与模型同样重要

关于 Claude Code 最常见的误解之一是，它的能力完全由所使用的模型决定。团队关注模型的基准测试以及它在测试任务上的表现。而在实践中，围绕模型构建的生态系统——执行框架（harness）——对 Claude Code 表现的决定作用比模型本身更大。

执行框架由五个扩展点构成——CLAUDE.md 文件、钩子（hooks）、Skills、插件和 MCP 服务器——每个承担不同的功能。团队构建它们的顺序很重要，因为每一层都建立在前一层之上。另外两项能力——LSP 集成和子智能体——完善了整体设置。下面我们解释这些组件和能力各自的作用：

**[CLAUDE.md](https://code.claude.com/docs/en/memory) 文件排在第一位**。这些是 Claude 在每次会话开始时自动读取的上下文文件：根文件提供全局视图，子目录文件提供局部约定。它们为 Claude 提供做好任何工作所需的代码库知识。由于它们会在每次会话中加载，无论任务是什么，让它们专注于广泛适用的内容可以防止它们成为性能负担。

**[钩子](https://code.claude.com/docs/en/hooks-guide)让设置具备自我改进能力**。大多数团队将[钩子](https://claude.com/resources/articles/how-to-configure-hooks)视为防止 Claude 做错事的脚本，但它们更有价值的用途是持续改进。一个 stop 钩子可以在会话期间反思发生了什么，并在上下文还新鲜时提出 CLAUDE.md 更新建议。一个 start 钩子可以动态加载团队特定的上下文，让每位开发者无需手动配置就能获得适合其模块的正确设置。对于 linting 和格式化等自动化检查，钩子以确定性的方式执行规则，产生比依赖 Claude 记住指令更一致的结果。

**[Skills](https://code.claude.com/docs/en/skills) 让正确的专业知识按需可用，而不会使每次会话膨胀。** 在拥有数十种任务类型的大型代码库中，并非所有专业知识都需要在每次会话中出现。Skills 通过[渐进式披露](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)解决这个问题，将原本会争夺上下文空间的专门工作流和领域知识卸载，仅在任务需要时加载。例如，安全审查 Skill 在 Claude 评估代码漏洞时加载，而文档处理 Skill 在代码变更需要更新文档时加载。

Skills 还可以限定到特定路径，使其仅在代码库的相关部分激活。拥有支付服务的团队可以将其部署 Skill 绑定到该目录，这样当有人在 monorepo 的其他位置工作时，它永远不会自动加载。

**[插件](https://code.claude.com/docs/en/plugins)分发行之有效的方案。** 大型代码库的一个挑战是，_好的_设置可能停留在小圈子里。插件将 Skills、钩子和 MCP 配置打包成一个可安装的包，这样当新工程师在第一天安装该插件时，他们会立即拥有与已经在使用 Claude 的人相同的上下文和能力。插件更新可以通过[托管市场](https://support.claude.com/en/articles/13837433-manage-claude-cowork-plugins-for-your-organization)在整个组织内分发。

例如，我们合作的一家大型零售组织构建了一个 Skill，将 Claude 连接到其内部分析平台，使业务分析师无需离开工作流就能获取绩效数据。他们在向业务部门广泛推广之前，将其作为插件分发。

**语言服务器协议（LSP）集成让 Claude 拥有与开发者在 IDE 中相同的导航能力。** 大多数大型代码库的 IDE 已经运行着 LSP，支撑着「转到定义」和「查找所有引用」功能。将其暴露给 Claude 可赋予它符号级精度：它可以沿着函数调用追踪到定义、跨文件追踪引用，并区分不同语言中同名的函数。没有它，Claude 只能基于文本进行模式匹配，可能定位到错误的符号。我们合作的一家企业管理软件公司在 Claude Code 推广之前就在全组织范围内部署了 LSP 集成，专门为了让 C 和 C++ 的导航在大规模下可靠。对于多语言代码库，这是价值最高的投资之一。

**MCP 服务器扩展一切。** MCP 服务器是 Claude 连接其原本无法触及的内部工具、数据源和 API 的方式。最成熟的团队构建了 MCP 服务器，将结构化搜索作为 Claude 可直接调用的工具暴露出来。其他团队则将 Claude 连接到内部文档、工单系统或分析平台。

**[子智能体](https://code.claude.com/docs/en/sub-agents)将探索与编辑分离。** 子智能体是一个拥有自己上下文窗口的隔离 Claude 实例，它接受任务、完成工作，并仅将最终结果返回给父级。一旦执行框架就位，一些团队会启动一个只读子智能体来梳理某个子系统并将发现写入文件，然后让主智能体在掌握全貌的情况下进行编辑。



Claude Code 扩展层一览。

下表总结了每个组件的作用、加载时机以及我们看到的每种组件最常见的误区：

| 组件 | 是什么 | 何时加载 | 最适合 | 常见误区 |
| --- | --- | --- | --- | --- |
| CLAUDE.md | Claude 自动读取的上下文文件 | 每次会话 | 项目特定约定、代码库知识 | 将其用于应放在 Skill 中的可复用专业知识 |
| 钩子 | 在关键时刻运行的脚本 | 由事件触发 | 自动化一致行为、捕获会话学习成果 | 用提示词处理本应自动运行的事情 |
| Skills | 针对特定任务类型的打包指令 | 按需，在相关时加载 | 跨会话和项目的可复用专业知识 | 将所有内容都加载到 CLAUDE.md 中 |
| 插件 | 打包的 Skills、钩子、MCP 配置 | 配置后始终可用 | 在组织内分发可用的设置 | 让好的设置停留在小圈子里 |
| 语言服务器协议（LSP）\* | 通过语言特定服务器提供实时代码智能 | 配置后始终可用 | 类型化语言中的符号级导航和自动错误检测 | 以为它是自动的 |
| MCP 服务器 | 与外部工具和数据的连接 | 配置后始终可用 | 让 Claude 访问其原本无法触及的内部工具 | 在基础功能可用之前就构建 MCP 连接 |
| 子智能体\* | 针对特定任务的独立 Claude 实例 | 被调用时 | 将探索与编辑分离、并行工作 | 在同一会话中运行探索和编辑 |
| \*LSP 通过插件层访问。子智能体是一种委派能力，而非配置的扩展点。 |

## 成功部署中的三种配置模式

如何为大型代码库配置 Claude Code，很大程度上取决于该代码库的结构。尽管如此，在我们观察到的部署中，有三种模式反复出现。

### 让代码库在大规模下可导航

Claude 在大型代码库中提供帮助的能力受限于它找到正确上下文的能力。每次会话加载过多上下文会降低性能，而上下文太少则让 Claude 盲目导航。最有效的部署会预先投入，让代码库对 Claude 可读。以下几种模式反复出现：

-   **保持 CLAUDE.md 文件精简且分层。** Claude 在代码库中移动时会以叠加方式加载它们：根文件提供全局视图，子目录文件提供局部约定。根文件应只包含指针和关键陷阱；其他内容都会变成噪音。
-   **在子目录中初始化，而非在仓库根目录。** 当 Claude 被限定在代码库中实际与任务相关的部分时，它工作得最好。在 monorepo 中，这可能感觉反直觉，因为工具通常假定根目录访问权限，但 Claude 会自动向上遍历目录树，并加载沿途找到的每个 CLAUDE.md 文件，因此根级上下文永远不会丢失。
-   **按子目录限定测试和 lint 命令。** 当 Claude 只改动了一个服务时运行完整测试套件会导致超时，并在无关输出上浪费上下文。子目录级别的 CLAUDE.md 文件应指定适用于该部分代码库的命令。这对于面向服务的代码库效果很好，其中每个目录都有自己的测试和构建命令。在具有深层跨目录依赖的编译语言 monorepo 中，按子目录限定更难实现，可能需要项目特定的构建配置。
-   **使用 `.`**`ignore` **文件排除生成文件、构建产物和第三方代码。** 在 `.claude/settings.json` 中提交 `permissions.deny` 规则意味着排除项受版本控制，因此团队中的每位开发者都能获得相同的降噪效果，无需自行配置。在某些代码库中，生成文件本身就是开发工作的对象。从事代码生成器工作的开发者可以在本地设置中覆盖项目级排除项，而不影响团队其他成员。
-   **当目录结构无法胜任时，构建代码库地图。** 对于代码未整合在常规目录结构中的组织，在仓库根目录放置一个轻量级 Markdown 文件，列出每个顶级文件夹并用一行描述说明其中内容，可以为 Claude 提供一份在打开文件之前可以扫描的目录。对于拥有数百个顶级文件夹的代码库，这最好以分层方式实现：根文件仅描述最高层结构，子目录 CLAUDE.md 文件提供下一级细节，随着 Claude 在目录树中移动按需加载。对于更简单的情况，@ 提及 Claude 应引用的特定文件或目录也能起到同样的作用。
-   **运行 LSP 服务器，让 Claude 按符号而非字符串搜索。** 在大型代码库中对常见函数名执行 grep 会返回数千个匹配项，Claude 会消耗上下文打开文件来判断哪个重要。LSP 仅返回指向同一符号的引用，因此过滤发生在 Claude 读取任何内容之前。设置此项需要为你的语言安装[代码智能插件](https://code.claude.com/docs/en/discover-plugins#code-intelligence)以及相应的语言服务器二进制文件；Claude Code 文档涵盖了可用插件和故障排除。

**一个注意事项**：在某些边缘情况下，即使是分层 CLAUDE.md 方法也会失效，例如拥有数十万个文件夹和数百万个文件的代码库，或使用非 Git 版本控制的遗留系统。我们将在本系列的后续文章中讨论这些挑战。关于遗留系统，请参阅 AI 如何[_打破 COBOL 现代化的成本壁垒_](https://claude.com/resources/articles/how-ai-helps-break-cost-barrier-cobol-modernization)。

### 随着模型智能演进，主动维护 CLAUDE.md 文件

随着模型演进，为你当前模型编写的指令可能会对未来的模型产生反作用。那些曾引导 Claude 处理它过去难以应对的模式的 CLAUDE.md 文件，在下一个模型发布时可能变得不必要，甚至产生主动限制。例如，一条告诉 Claude 将每次重构拆分为单文件变更的 CLAUDE.md 规则，可能曾帮助早期模型保持正轨，但会阻止新模型进行它能够很好处理的跨文件协调编辑。

为弥补特定模型局限（无论是模型推理方面还是 Claude Code 自身工具方面）而构建的 Skills 和钩子，一旦这些局限不复存在，就会变成负担。例如，一个在 Perforce 代码库中拦截文件写入以强制执行 p4 edit 的钩子，在 Claude Code 添加原生 Perforce 模式后就变得多余了。

团队应预期每三到六个月进行一次有意义的配置审查，但在重大模型发布后如果感觉性能停滞不前，也值得进行一次审查。

### 为 Claude Code 的管理和采用分配归属

仅靠技术配置无法推动采用。做对了的组织也在组织层面进行了投入。

推广最快的部署在广泛开放访问之前就有专门的基础设施投入。一个小团队，有时甚至只是一个人，把工具链搭建好，使 Claude 在开发者第一次接触时就已融入其工作流。在一家公司，几位工程师构建了一套在第一天就可用的插件和 MCP。在另一家，一个专门管理 AI 编码工具的完整团队在推广开始前就准备好了基础设施。在这两种情况下，开发者的首次体验都是富有成效的而非令人沮丧的，采用由此扩散开来。



今天从事这项工作的团队通常隶属于开发者体验或开发者生产力部门，这通常是负责新工程师上手和构建开发者工具的职能。在多个组织中正在兴起的一个角色是智能体经理：一个混合 PM/工程师职能，专门管理 Claude Code 生态系统。对于没有专门团队的组织，最小可行版本是一个 DRI：一个人拥有 Claude Code 配置的归属权，有权对设置、权限策略、插件市场和 CLAUDE.md 约定做出决定，并负责保持它们与时俱进。

自下而上的采用会产生热情，但如果没有一个人来集中整合行之有效的做法，就可能变得碎片化。你需要一个人或一个团队来汇集并推广正确的 Claude Code 约定（例如标准化的 CLAUDE.md 层级结构或精选的 Skills 和插件集）。没有这项工作，知识将停留在小圈子里，采用也会停滞。

在大型组织中，尤其是受监管行业的组织，治理问题会早早出现，例如：谁控制哪些 Skills 和插件可用，如何防止数千名工程师各自独立重建同样的东西，如何确保 AI 生成的代码经过与人类生成代码相同的审查流程？为了尽早解决这些问题，我们建议从一组已定义的获批 Skills、必需的代码审查流程和有限的初始访问权限开始，并随着信心增强而扩展。

我们观察到，最顺畅的部署发生在那些早早建立跨职能工作组的组织中，这些工作组汇集工程、信息安全和治理代表，共同定义需求并制定推广计划。

## 将这些模式应用到你的组织

Claude Code 围绕常规软件工程环境设计，其中工程师是代码库的主要贡献者、仓库使用 Git、代码遵循标准目录结构。大多数大型代码库符合这一模式，但非传统设置——例如拥有大量二进制资产的游戏引擎、使用非常规版本控制的环境，或由非工程师贡献代码的代码库——需要额外的配置工作。我们的指导假设采用常规设置，我们描述的模式已在许多客户中奏效。任何剩余的复杂性都需要针对你的代码库、工具和组织进行具体判断。这正是 Anthropic 应用 AI 团队直接与工程团队合作，将这些模式转化为你组织特定需求的地方。
