# 构建智能体：何时将子智能体折叠进主智能体循环
_如果你在 Claude Platform 中构建了一个包含多个子智能体的智能体，可以看看哪些子智能体适合用我们的[迁移工具包](https://github.com/anthropics/single-agent-loop-kit)折叠进主智能体循环。它会运行一套引导式工作流，帮你识别现有模式、评估替代方案并验证最佳方案。其中包含一个演示，你可以先在模拟系统上试用，再应用到你的智能体上。_

子智能体——拥有自己的上下文窗口、工具和指令，[由协调器编排](https://claude.com/resources/articles/multi-agent-coordination-patterns)的智能体——是智能体设计的核心组成部分。它们在验证、并行工作和模块化权限控制方面很有效。我们在用 Claude Platform 构建的许多自有智能体中都在使用它们，例如我们的[多智能体研究系统](https://www.anthropic.com/engineering/multi-agent-research-system)。

然而，最近应用 AI 团队发现了一类企业智能体部署模式，它们从将路由器、规划器和领域子智能体折叠进主智能体循环中获益。在[我们对多个企业部署的对比](https://claude.com/resources/articles/the-anatomy-of-effective-commerce-agents#:~:text=In%20our%20comparisons%20across%20several%20enterprise%20deployments,latency%20per%20task)中，[带 Skills 的单一智能体](https://claude.com/resources/articles/building-agents-with-skills-equipping-agents-for-specialized-work)在质量上经常优于"一个提示词包打天下"的设计和子智能体设计，而且通常单任务成本和延迟更低。

例如，一家公司发现其面向客户的智能体中的十几个专家子智能体使得一致的品牌体验难以维持，并且增加了延迟，损害了用户体验。

我们也经常看到提出的智能体设计遵循一种熟悉的演进路径：一个意图分类器、一条固定的多步推理流水线、用户分群桶、独立的推荐分支，以及顶层的一个多智能体编排器。

在这些情况下，反馈往往是：这些结构中的大部分都在做模型已经不再需要它做的工作，而一个清晰的系统提示词、4-5 个轻量数据工具和严格的输出护栏就能覆盖大部分用例。

![子智能体设计](https://assets.claude.com/a7cb2cf08bfcef461166310c0c55f28b72c33b0d.gif)

需要明确的是，子智能体仍有其用武之地，包括在研究前沿。在以下情况下使用它们：

-   单一智能体循环因上下文膨胀而出现可测量的性能下降，或
-   多个任务需要并行处理，且各自使用全新的上下文窗口，任务完成后即可丢弃，或
-   单一智能体难以选择合适的工具，或系统提示词中存在相互冲突的指令。

但我们太常看到企业为每个团队或每种问题类型分配一个子智能体，结果智能体架构变成了其组织架构图的翻版（康威定律在起作用）。

本文解释了何时应考虑将子智能体折叠进主智能体循环，并分享了我们在大型组织中构建智能体时总结的最佳实践。

## 大型组织的智能体构建失败模式

公司通常希望构建一个智能体，将多个产品和能力统一到单一的客户界面中。

通常，每项能力由不同的团队负责，因此公司一开始让各个团队构建自己的智能体，然后由一个中央平台团队在其上构建编排器。这可以采取多种结构，包括编排器-子智能体结构，或将特定智能体作为 MCP 工具暴露的单一智能体结构。

这看起来是最简单的解决方案，但会立即引入以下复杂性：

-   **上下文管理：** 你需要决定智能体之间交换哪些上下文，而且往往在来回传递中丢失细节。
-   **子智能体泛滥**：每个团队都发布自己的子智能体，结果公司最终拥有数百个相互重叠的子智能体，既没有强制标准，也没有明确的负责人。
-   **弗兰肯提示词（Frankenprompt）**：每个团队都往系统提示词里加一句话，导致规则冲突、语气不一致。
-   **未经审查、过度本地化的评估（eval）**：每个人都添加自己的评估，且过度针对自己的子任务优化。没有人负责或维护整套评估，而管理层基于被稀释、过度本地化的分数做决策。
-   **延迟**：多智能体架构的复杂性会增加延迟。一位客户将其多智能体执行框架（harness）与单一智能体循环进行对比评估，发现后者的运行速度大约快 2 倍。

## 使用带渐进式披露的智能体循环

上述编排器-子智能体设计是协调跨团队构建的专家的一种合理方法，但通常更有效的方法是**通过 Skills 渐进式披露上下文**以及**通过工具搜索渐进式披露工具**。换句话说，智能体只看到 Skills 和工具的简短描述，只有在需要时才完整加载。

这种方法之所以合理，有三个原因：

-   **共享上下文能产生更好的答案：** 对于运行时间较长的智能体，我们希望来自多个不同任务的上下文都留在主上下文窗口中。一个看到过每个先前步骤结果的智能体可以将它们联系起来，从而产生比子智能体交回的一组摘要更丰富的输出和更好的洞察。这也意味着[更少的上下文窗口和更少的有损交接](https://claude.com/resources/articles/building-multi-agent-systems-when-and-how-to-use-them)。
-   **渐进式披露可防止上下文膨胀：** 这项技术让团队能够构建单一智能体来完成各种各样的任务，而无需将所有上下文立即加载到一个冗长的系统提示词中。这消除了团队此前将工作拆分到子智能体的主要原因。事实上，我们[将 Claude Code 面向更高级模型的系统提示词缩减了 80% 以上](https://claude.dev/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models/)，其中就包括与渐进式披露 Skills 和工具相关的删减。
-   **模型能力更强了：** 从 Opus 4.5 开始，模型在单一循环中能管理的内容远超大多数团队的预期。Opus 5.5 无法关闭思考，而 Fable 5.1 及近期模型越来越多地会叙述自己的进展并随时检查工作，这使得某些执行框架（harness）元素变得多余。每一个新模型都让你能把更多决策从执行框架（harness）转移到模型本身。更简单的循环也更容易迁移到下一个模型；在我们帮助客户进行的迁移中，僵化的多智能体结构往往是阻碍新模型承担更多工作的原因。

单一智能体循环设计需要纪律：精心管理的系统提示词、能在恰当时机触发的 Skill 和工具描述，以及对上下文窗口、记忆和笔记的刻意处理。本文将在后续章节深入探讨迁移和设计方面的考量。

应由一个中央团队负责端到端质量和系统提示词，在每个新工具和评估（eval）发布前进行审查。保持这个中央团队规模小有助于快速迭代，并降低大型组织内的协调成本。

如果你选择多智能体路线，从可能奏效的最简单模式（生成器-验证器、编排器-子智能体或其他）开始。有效地分解边界：**按上下文划分——给每个子智能体一项几乎不需要系统其余部分参与的工作，并让它交回一个紧凑的结果**（好的候选包括独立的研究路径、接口清晰的独立组件或黑盒验证）。当智能体按问题类型拆分时，它们会玩起"传话游戏"，来回传递信息，每次交接都会降低保真度。

## 如何将子智能体折叠进主智能体循环

许多团队已经在生产环境中拥有一个编排器和一组专家智能体。以下是我们建议逐步采用的单一循环设计：

-   一个模型和一个上下文窗口运行开放式工具循环，并在执行框架（harness）中设置限制（轮次和成本预算、写入闸门）。
-   每一轮，模型发出一批工具调用。执行框架（harness）并行运行它们，并将原始结果返回给同一个模型，由它决定下一步：再发一批、向用户提问，还是给出答案。
-   当模型给出答案或触及[预算](https://platform.claude.com/docs/en/build-with-claude/task-budgets)时，循环停止。答案之后可以选择运行目标检查或验证器检查。
-   模型在第一轮将计划写入上下文，并随着结果到达而修订计划。这是与编排器和专家智能体设置的主要区别：写计划的模型也是执行计划的模型，因此它可以在轮次中途改变计划。
-   上下文仍然会被加载，并由智能体自己管理：
    -   不再需要从规则目录重写计划的代码步骤，因为模型会决定每一步。
    -   排序和领域流程移入 **Skills。**
    -   硬性限制（验证、审批闸门）以及对话中途出现的其他任何内容（例如记忆查找）移入**工具。**
    -   代码仍可用于加载任何廉价且几乎总是相关的内容（例如实体解析步骤），以及在循环调用的工具内部处理任何机械性部分（载荷构造、流解析、恢复澄清）。

这种单一循环设计也有助于实现许多团队正在努力达成的最终状态（一个理解用户高层目标并代表用户行动的智能体），因为它将智能体学到的一切都保留在一个上下文中。

以下建议说明了团队如何分阶段从多智能体系统过渡到单一智能体循环，以及多个团队如何在此过程中持续为该智能体做出贡献。

### 任务完成度评估（eval）

第一步是创建一个评估（eval）集，帮助你判断是否应将某个子智能体折叠进主智能体循环。我们见过的有效评估结构是：一个由中央团队负责的共享端到端评估集，加上每个 Skill 由负责团队随附的较小评估集。即使只有 10 个黄金示例也足以起步。

根据评分标准对智能体的最终消息进行评分，是跟踪答案质量的良好起点。当你仍有编排器时，还应跟踪路由准确性（它是否选对了子智能体？）。一旦子智能体被折叠进来，则改为检查智能体是否加载了正确的 Skill 或调用了正确的工具。逐步转向任务完成度评估（eval）是有帮助的，因为在比较架构时这一点最为重要。

在内部系统难以重放、用户参与难以模拟的环境中，这可能很复杂。我们在内部行之有效的一种方法是：在重要事件上记录时间戳，以便日后重放作为有针对性的评估（eval）运行。

### 逐步减少子智能体

向单一智能体循环演进涉及将子智能体折叠为工具和 Skills。这可以通过合并领域子智能体、将它们作为工具调用，或用 Skills 和工具替换它们来实现。

![折叠子智能体](https://assets.claude.com/ed6bd97496ffdab88763806d9e14f1ec61ed9255.gif)

### 合并领域智能体

在第一次合并之前，先构建一个小型端到端评估（eval）。然后**按共享上下文折叠，从使用最多的子智能体开始。**

[合并](https://claude.com/resources/articles/building-multi-agent-systems-when-and-how-to-use-them)那些相互依赖彼此输出、接触相同数据或经常被一起调用的专家。例如，如果生产流量中有相当大一部分是先调用一个专家再调用第二个专家，那就是一对紧密耦合的组合，适合合并为一个领域智能体。

### 将子智能体作为工具调用

当上述三个条件之一适用且你保留某个子智能体时，让主智能体将子智能体作为工具调用可能很有效，这样它可以继续与用户保持对话。

我们只建议在子智能体需要直接与用户交谈时才进行完全交接（由子智能体接管对话）。其他一切都可以是主循环中的一个 Skill 加工具。

这将允许你为子智能体定义[共享响应模式](https://claude.com/resources/articles/structured-outputs-on-the-claude-developer-platform)，用主智能体对照真实数据验证结论，并精简任何最终综合步骤的输入。这是一个很好的第一步，因为你不需要**重写**子智能体。它还能让你在决定将任何子智能体折叠进主智能体之前，获得任务完成度评估（eval）的**基线**。

然而，某些失败模式仍会存在：

-   每个专家都有自己的提示词、上下文、负责团队和评估（eval）
-   每次调用仍然交回一个有损的摘要
-   每次调用都是一个嵌套的模型循环，会增加延迟

### 通过 Skills 和工具将子智能体折叠进主智能体

通过将每个子智能体的提示词转为 Skills、将 API 调用转为 MCP 工具，一次一个地将子智能体折叠进主智能体。比较有和没有该子智能体时的评估（eval）表现。然后决定保留哪些。

比较时，不要只看最终分数，还要看看哪些任务发生了翻转。当我们在一个示例支持智能体上测试时，将一个子智能体折叠进另一个子智能体降低了延迟，但也破坏了一个原本通过的流程。主智能体自己持有订单查询工具并直接作答，而没有向配送专家询问送达日期。

在每次更改之前，确保你的评估（eval）为生产环境中一起运行的每条智能体链、以及智能体绝不能违反的每条规则都设有任务，并且每个任务运行不止一次，因为像这样的破坏只在两次运行中的一次里出现。

## 多个团队如何为单一智能体做贡献

领域推理可以从知识库、Skills 和 MCP 工具中检索。各个团队可以将其职责从智能体转移到 Skills 和工具，由一个小型中央团队保留系统提示词和端到端质量的责任。这涉及在每个新 Skill、工具和评估（eval）发布前进行审查。

### MCP 工具

当智能体需要采取行动、从系统读取实时数据或以固定格式返回结果时，工具是合适的选择。你也可以在迁移期间用工具作为继续调用子智能体的方式。我们建议按用户意图对工具分组（而不是每个 API 一个工具），因为一旦系统提示词中的工具定义超过 30-50 个，工具选择往往会退化。

使用带延迟加载的[工具搜索](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)，限制硬性前置条件，并将任何必要的前置条件移入工具中。例如，如果 Y 需要 X 的输出，Y 的工具会检查它并返回一条模型可以据此行动的指令。按用户区分的权限也以同样方式工作。每个工具检查调用用户可以看到或做什么，并返回模型可以读取的明确拒绝，因此一个循环就能服务具有不同访问权限的用户，而无需为每个权限级别单独设置智能体。

### Skills

当智能体需要了解一个团队如何做事时——比如专家子智能体的提示词过去所承载的步骤、规则和判断——Skills 是合适的选择。

我们扩充 Skill 库的方法是，将维护工作交还给编写 Skills 的人。Claude 可以通过能够构建、测试和修剪其他 Skills 的 Skills 来完成繁重的工作。

为防止 Skill 泛滥，你可以让每个团队的 DRI 负责自己的 Skills，并确保它们精心制作、彼此区分，并随附适当的评估（eval）。

-   **/skill-creator** 允许你编写从一开始就格式良好的新 Skills，并审计现有 Skills 以进行修剪、去重和重构。
-   **/skill-doctor** 允许你查看库中每个 Skill 的成本以及实际使用频率，并删除无用负担。

### 知识库

知识库适合存放智能体只在部分时间需要的参考资料。事实和参考资料（政策、指标定义、产品规格）可以放在模型调用的搜索或查找工具之后，或作为 Skill 内的参考文件随附。避免让[代码检索并将这些上下文粘贴到提示词中](https://claude.com/resources/articles/seeing-like-an-agent)。

## 加速这项工作的方法

我们最近[发布](https://code.claude.com/docs/en/commands)了一组 Claude API Skills，可以帮助完成上述大部分工作。我们的[迁移工具包](https://github.com/anthropics/single-agent-loop-kit)将这些 Skills 串联成一个引导式工作流，用于评估多智能体系统并将其迁移到单一智能体循环。其中包含一个演示，你可以在应用到真实系统之前先试用：

-   **/claude-api build-eval：** 可以帮助创建由中央团队负责的首个端到端评估集，或每个团队随其 Skill 发布的小型评估
-   **/claude-api prompt-audit：** 可以标记出你的提示词、Skills 和工具描述中为旧模型编写的指令，并以 diff 形式提出修复建议。这可以在你的系统提示词上运行，找出任何为早期模型添加、如今却让智能体更慢或更僵化的规则。每个团队的 DRI 也可以在自己的 Skills 和工具描述上运行它。
-   **/claude-api hillclimb：** 可以针对现有评估（eval）迭代改进应用。这可以用于"折叠后 vs 保留"的对比（在将一个子智能体折叠为 Skill 加工具后，让它对 Skill 和工具描述进行迭代，看看折叠后的版本是否匹配或超越子智能体），也可以用于你的系统提示词。
-   **/claude-api cost-optimize：** 分析你的调用去向，并逐项提出来自提示词缓存、精简不必要的输入和输出 token、effort 和模型选择等选项的节省建议。这有助于降低给定设计的成本和延迟。

随着模型演进，我们对如何最好地使用它们的理解以及围绕最佳实践的指导也在演进。这使得任何单一架构都不如其背后的原则重要：测量、一次只改一件事，并保留经得起检验的部分。

这就是其中一例。随着模型能力增强、智能体运行时间变长，你更多的子智能体可以变成 Skills 和工具。不过，你不必一步到位。构建一个小型端到端评估（eval），折叠进一个子智能体，只有当折叠后的版本得分更差时才保留它为子智能体，然后重复这一过程。
