# 最大化你的 Claude Code 会话价值
## 摘要

-   **在任务之间运行 `/clear`。** 这可以防止先前无关的上下文被重新发送给模型，从而减少 token 用量。
-   **在开始之前设定好模型和努力级别。** 在对话中途更改其中任何一项都可能破坏提示词缓存，从而增加 token 成本。
-   **用 @ 提及文件，而不是直接写出文件名。** 文件会直接附加到你的消息上，从而省去一次 Read 调用，或者省去 Claude 不得不去寻找它时的一次搜索。
-   **给嘈杂的命令加上静默标志，或在子智能体中运行它们。** 命令输出会像文件一样被加入对话，并在会话剩余时间里一直留在那里。
-   **在一个全新会话中运行一次 `/context`。** 它会显示已加载的内容（`CLAUDE.md`、MCP 工具定义），这样你就可以删掉任何不必要的东西。
-   **在离开键盘休息之前运行 `/compact`。** 提示词缓存会在一小时后过期，而在对话仍被缓存时进行总结要便宜得多。

## 最大化价值

直到不久之前，你用来写代码的工具还是固定收费（或者免费）的。无论你那天下午是修好一个测试还是五十个，你的编辑器花费都一样，所以单个任务其实并没有自己的价格。

对于像 Claude Code 这样的智能体式编程工具来说，情况就不一样了。同一个完成的任务，也可能因为你的使用方式不同而产生不同的成本。

在一个会话中，Claude 读取测试和它覆盖的文件，做出修改，几个回合就完成了。在另一个会话中，它先在仓库里到处 grep，在找到同样那两个文件之前读了十几个文件，而每一个回合还会拖上从今天早上以来被读进对话的所有其他内容。

这是同一个修复，但你为此花费了不同数量的 token，而且整个过程中模型还得同时考虑十个它并不需要的文件。

高效使用 token 并不意味着总体上用得更少。它意味着确保你确实用掉的 token 都花在你真正要求的事情上。

所以，让我们先看看是什么决定了 token 的价格，然后看看是什么决定了一个会话发送多少 token，并在此过程中了解这对你如何运行会话意味着什么。

## **什么决定了 token 的价格**

你按 token 付费，但你实际支付的是推理：GPU（或 TPU，或模型碰巧运行在其上的任何硬件）在你的 token 上运行模型所需的时间。

有三件事决定了 token 需要多少这样的时间：你运行的是哪个模型、它是输入 token（进入）还是输出 token（输出），以及它是否被缓存。

### 模型

更大的模型在输入和输出 token 上都会做更多的工作。哪种模型对哪类工作值得，本身就是一个话题，我们在 [_Choosing a Claude model and effort level in Claude Code_](https://claude.com/resources/articles/claude-model-and-effort-level-in-claude-code) 中讨论过。

对于本文，你只需要知道，我们接下来要讲的一切都会被模型的价格所乘：当问题确实困难或模糊时使用更大的模型，当工作是常规性的时候使用更小的模型。

曲线仅用于示意。它们不代表真实的基准测试数据。

### 输入和输出 token

一个请求分两个阶段通过 GPU，它们的成本不同。

首先，在预填充（prefill）阶段，模型读取你的请求和上下文：系统提示词、你的 `CLAUDE.md`、你的消息，以及此后被加入对话的所有内容（Claude 读过的文件以及它运行过的命令的输出）。这些就是你的输入 token。

然后，在解码（decode）阶段，它写出输出 token：它的思考、它发起的工具调用，以及你看到的文本。这是一个 token 一个 token 地发生的；一个 200 token 的响应就是模型连续运行 200 次。按 token 计算，解码让 GPU 忙碌的时间要长得多，这就是为什么输出的定价大约是输入的 5 倍。

一个会话中大量的输出 token 是思考 token，而模型每回合思考多少正是由努力级别控制的。和模型一样，你用 `/effort` 选择的级别也会作为默认值延续到下一个会话。

> “提示：在一个全新会话中运行一次 /model 和 /effort，看看你实际处于什么设置。两者都会记住你上次的选择，而你希望这个决定是有意为之的。”

> “提示：如果你已经知道某个会话将是苦力活，MAX\_THINKING\_TOKENS=0 claude 会为该会话关闭思考（Fable 5 除外），这是比 /effort low 更低的一档。”

### 提示词缓存

如果一个请求的开头与服务器刚刚见过的某个请求的 token 完全相同，那么这段共享开头的状态就会完全相同，因此服务器可以保留上次的状态，只预填充它后面的内容。这被称为提示词缓存。

从缓存读取的成本是输入价格的 0.1 倍，因为服务器是加载状态而不是计算它。将 token 写入缓存的成本比普通输入略高，最高可达 2 倍，因为服务器之后还必须保留该状态。但写入对每个 token 只发生一次，而 0.1 倍的读取会在其后的每个回合发生。

Claude Code 会在每个请求上管理提示词缓存，无需开启任何东西。不过你可以破坏它，所以了解如何避免这些成本飙升很重要。

假设我们输入“fix the failing test in `utils.test.ts`”。以下是 Claude Code 为此发送的内容：

1.  Claude Code 用系统提示词（包含工具定义）、你的 `CLAUDE.md` 和你的消息组装出第一个请求，并发送出去（输入 token）。此时缓存中还没有任何内容，所以全部内容都会被预填充并写入缓存。
2.  模型无法修复它没见过的测试，所以它思考片刻，并响应一个针对 `utils.test.ts` 的 Read 调用（输出 token）。Claude Code 读取该文件，将其追加到对话中，并再次发送全部内容（输入 token）。这一次，请求 1 中的所有内容都以十分之一的价格从缓存中读回，唯一以全价预填充的是新增的内容：Read 调用和该文件。
3.  现在模型想要被测文件（输出）。又一次 Read，又一次追加，然后所有内容再次发出：请求 1 和 2 来自缓存，第二个文件以全价（输入）。
4.  模型响应一个 Edit（输出）。Claude Code 应用它，追加结果，并再次发送所有内容。情况相同：Edit 及其结果是新的，它们之前的一切都是缓存读取（输入）。
5.  模型运行 `npm test`（输出）。Claude Code 追加测试输出并再次发送所有内容，测试输出是唯一新增的部分（输入）。
6.  测试通过，模型响应一段简短的总结（输出）。没有工具调用意味着没有内容可追加，也就没有请求 6，所以我们完成了。

一个小修复就有五个请求，而每一个请求都包含了截至当时为止的整个对话。一个典型的回合是不均衡的：数万个 token 进入，几百个 token 出来。但只有该回合中新增的内容才会以全价预填充。

这就是每回合的全部账单：对历史记录进行缓存读取，对任何新增内容按全价输入计费，对响应按输出价格计费。

> “这也适用于订阅。你不会直接看到这些价格，但正是同样的请求在消耗你的限额。”

缓存必须从请求的最开头开始向前匹配，而请求总是以相同的顺序发出：工具定义，然后是系统提示词，然后是对话（`CLAUDE.md` 位于其最前面）。

如果该前缀中的任何内容发生变化，它后面的一切都会被重新预填充。追加到对话末尾的工具结果是最理想的情况，因为它后面没有任何内容。会丢弃缓存的是任何更靠近前端改变请求、或改变缓存键所依据内容的东西：

-   **`/model`**：每个模型都有自己的缓存，所以在下一个回合，整个对话都会以全价重新预填充。（这包括 opusplan，它会在你每次进入或退出计划模式时切换模型。）
-   **`/effort:`** 努力级别也是缓存键的一部分，所以情况相同。这就是为什么 `/model` 和 `/effort` 都会在你于对话中途切换时要求你确认。
-   **Fast mode**：也是键的一部分，而且重新预填充会以 fast mode 的价格发生，所以如果你要开启它，就在开始时开启。（关闭它则是免费的，就缓存而言。）
-   **`/compact`**：对话会被替换为更短的对话，所以其中没有任何内容再匹配（它前面的系统提示词会保留）。只要旧对话仍在缓存中，写入总结本身就很便宜，所以它在长时间休息之前比之后要便宜得多。
-   **时间：** 每个回合都会重置时钟，但缓存在订阅上于一小时后过期，在 API 密钥上于五分钟后过期（`ENABLE_PROMPT_CACHING_1H=1` 使其变为一小时）。超过这个时间再回来，下一个回合就会重新预填充整个对话。恢复旧会话几乎总是也会如此：到那时缓存通常已经消失，而且系统提示词在启动时本来就会被重建。

这并不意味着你永远不应该切换模型或努力级别。它意味着有便宜的时刻可以这样做，即会话开始时或刚运行完 `/clear` 之后，也有昂贵的时刻，即长对话的中途。

> “提示：如果最近几个回合走向了你不想保留的地方，用 /rewind 回到它们之前，而不是运行 /compact。回退只会从末尾切掉那些回合，所以它们之前的一切仍然被缓存，不产生任何成本。压缩会重写整个对话，所以它总是有成本的。”

## **什么决定了一个会话发送多少 token**

这里要知道的主要事情是，没有任何内容只发送一次。最终进入对话的所有内容，无论是 Claude 读过的文件还是它运行过的命令的输出，都会在其后的每个回合再次发送，直到会话结束。

它被缓存了，所以每次重新发送都很便宜，但便宜不等于没有成本，而且它还会占用模型在每个回合都必须在其周围思考的上下文空间。

这实际上就是一个会话的完整成本模型：有多少 token 最终进入上下文、它们在那里停留多少个回合，以及你同时运行多少个上下文。

### **什么最终进入了上下文**

上下文中的一部分内容在你输入任何东西之前就已经存在：工具定义、系统提示词、`CLAUDE.md`，以及启动时加载的其他任何内容。

> “提示：在一个全新会话中运行 /context，看看在你输入任何东西之前里面有什么。将 CLAUDE.md 保持在具体指令上，把工作流特定的指令移到 Skills 中，后者只在使用时才会被加载。如果有一个 MCP 服务器你在本次会话中不需要，用 /mcp 关掉它。”

会话期间被加入的几乎所有其他内容都是工具结果：Claude 读取的文件，以及它运行的命令的输出。

Claude 读取多少主要取决于它必须自己弄清楚多少。如果你说“测试失败了”，它首先必须找出哪些测试：一两次 grep，打开几个文件看看哪个相关，而所有这些结果在不再有用之后很久仍留在上下文中。

“Fix the failing test in `utils.test.ts`”跳过了搜索，只花费一次对该文件的 Read 调用，而“Fix the failing test in `@utils.test.ts`”连 Read 调用都不花费。

> “提示：当你引用一个文件时，用 @ 提及它，而不是输入路径。Claude Code 会在发送任何内容之前将文件附加到你的消息上，所以它就在第一个请求中，不需要为它进行 Read 调用。无论哪种方式，文件本身在上下文中占用的空间都一样，所以你只需要在每个对话中提及它一次：它会留在那里，而在之后的回合再次 @ 提及它通常会附加第二份副本。”

填满上下文的另一件事是 Claude 运行的命令的输出。每次它运行你的测试、构建或 git log，打印出来的任何内容都会像它读取的文件一样被追加到对话中，并停留同样多的回合。

非常大的输出实际上没问题：超过 30,000 个字符后，Claude Code 会将输出写入文件，只在对话中放入一段简短的预览和路径（如果你想更改，可用 `BASH_MAX_OUTPUT_LENGTH`）。

问题在于这个限制以下的一切。一个逐行打印 400 个通过测试的测试运行器在限制之内，而那 400 行现在成了每个剩余回合的一部分。

Claude 通常会通过标志和 tail 为你处理这一点，如果你不想把它留给 Claude，文档中有一个小钩子（hooks），可以在嘈杂的命令运行之前重写它们，这样只有重要的行才会返回。

> “提示：把你整天都在运行的两三个命令放进 CLAUDE.md，包括静默标志，就像你自己会输入的那样（“run a single test file with npx vitest run <file> --reporter=dot”）。这是一个小小的补充，但它能在之后的每个会话中节省一个回合和几百行输出。”

### 它在那里停留多少个回合

一个长会话比同样的工作分散在几个短会话中花费更多，而且超出你的想象，因为第 40 个回合也在重新读取之前的 39 个回合。你希望会话中的上下文简短且相关，所以不要把一项任务的上下文带入下一项：开始新事情时用 `/clear`，同一任务的早期部分完成时用 `/compact`。

> “提示：如果你以后还想找回该会话，在 /clear 之前先 /rename。当你 /compact 时，告诉它要保留什么，或者如果总是同样的内容，就在 CLAUDE.md 中放一个“Compact instructions”部分。如果你用的是 1M 模型，并且希望自动压缩的安全网回到原来的位置，/autocompact 200k 可以把它放回去（需要 Claude Code v2.1.221+）。”

也要留意那些在你没有输入时发生的回合。一个 `/loop` 会在你设置它的会话中作为完整回合触发，每次都带着整个对话，而且如果距离上一个回合已超过一小时，还会叠加一次缓存未命中。在另一个终端中启动一个全新会话，并从那里运行循环。

### 子智能体

让某些内容不进入你的上下文的另一种方式是让它在另一个上下文中发生，这正是子智能体的用途。子智能体有自己的上下文窗口，有自己的系统提示词、工具和你的 `CLAUDE.md`，但没有你的对话。它运行自己的回合，只有它的答案会回到主会话。其他一切在完成后都会被丢弃。

没有你的对话的缺点是，子智能体有时必须重新读取主会话已经有的内容，而且它在这样做时还要为自己的回合付费。对于小任务来说，这只是额外开销。

当一项任务产生大量你不需要保留的输出时，它就值得了，比如浏览日志。对于这类事情，Claude 通常会自己去找一个子智能体，而当它不这样做时，你可以直接要求一个（“go through this log in a subagent”）。只需记住，主会话只能拿回子智能体选择报告的内容。

> “提示：如果你有一个反复交出去的嘈杂任务，给它一个自己的子智能体定义，使用 model: haiku（或 sonnet）。否则它会运行在你的主会话所用的任何模型上。”

## 首先看哪里

在上述所有内容中，有四件事值得留意，大致按它们的成本高低排序：
