# Cresta 如何将 CX 专业知识转化为基于 Claude Agent SDK 的智能体构建器
_在我们的系列文章 **How startups build with Claude** 中，我们关注 AI 产品背后的决策。本文中，我们探讨 [Cresta](https://cresta.com/) 如何将其构建 AI 原生客户体验的专业能力带入 [Conductor](https://cresta.com/blog/cresta-conductor-the-agent-for-ai-agent-development)——一个帮助开发者构建和改进其他智能体的智能体。_

| 快速概览 |
| --- |
| 名称 | Cresta |
| 成立时间 | 2017 |
| CEO | Ping Wu |
| 增长情况 | 融资超过 2.7 亿美元。ARR 超过 1 亿美元。帮助 United Airlines、CVS Health 和 Marriott 等组织提供卓越的客户体验 |

为客户体验用例构建企业级 AI 智能体，需要理解广泛客户交互中蕴含的上下文。例如，客户可能会：

-   要求退款，却没有说明指的是哪笔购买，
-   在同一条消息中同时报告账单问题和登录问题，或
-   在退货窗口关闭后要求退款。

要正确回应，智能体可能需要核查客户购买了什么、退款政策、其账户历史或支付状态。

Cresta 大规模地见证着这些交互。其平台为客户体验提供支持：AI 智能体可以自行处理对话、为与之协作的人工坐席提供实时指导，并呈现对话智能，向企业展示应在何处改进。

构建和维护客户体验智能体，要求组织在运营需求上做出关键决策：智能体需要知道什么、必须访问哪些系统，以及其行为应在何处保持灵活或确定性。Cresta 希望让更多团队获得这种判断力，而不必每个团队都从零开始。

Conductor 正是这一目标的成果：一个自然语言智能体构建器，帮助团队将复杂的业务上下文转化为可投入生产的智能体。用户描述他们想要构建的内容，Conductor 则引导工作从有依据的蓝图推进到实现、评估和优化。

Cresta 最初使用 Claude Sonnet 和 Claude Opus 构建了 Conductor 的早期版本，帮助内部团队支持客户部署。悬而未决的问题是，Cresta 能否将该系统转化为客户可以直接在平台*内部*构建智能体的产品。

为执行开放式开发工作，Conductor 使用 Claude Agent SDK 作为通用执行框架（harness），用于收集上下文、使用工具、编写并运行代码，并根据结果进行调整。

“我们在内部将 Claude Code 作为开发工具使用，因为它在构建智能体的软件开发方面非常有效，”Cresta Conductor 工程负责人 Renjie Li 表示。“Claude Agent SDK 让我们能够以编程方式使用同一套智能体式开发执行框架。借助 Conductor，我们将其与 Cresta 深厚的对话智能、CX 专业知识、评估和运行时连接起来，为用户提供我们从第一天起就希望拥有的智能体构建体验。”

Cresta 报告称，在 Cresta 及其合作伙伴的早期用例中，Conductor 将初始部署时间缩短了大约一半。



Conductor 是一个自我改进的元智能体，基于 CX 智能体开发的成熟最佳实践构建。随着团队使用它构建和优化更多智能体，他们会积累自己经过验证的模式、工作流和专家判断。这形成了一个知识飞轮，使未来的开发更快、更一致。

上线后，生产交互、工作流结果和反馈会成为下一轮改进的新信号。

Conductor 帮助构建者将智能体构建过程中的所学转化为可复用的记忆产物，捕获模式、业务规则和评估方法。随后，他们可以将其作为一项技能与团队其他成员共享，让其他人能够基于同样经过验证的实践进行构建。

### **让重要决策更容易做出**

编写第一个提示词只是构建有用智能体的一部分。更难的抉择之一是：对话应在何处保持灵活，在何处需要明确的业务规则和受控的工具行为。

“你不希望过于确定性，否则你会创建一个巨大的决策树，试图映射出每一个可能的分支……但有些企业关键工作流你必须确保始终正常运行，尤其是对于风险容忍度低的高度监管行业，”Renjie 表示。“Conductor 帮助发现并加固这些确定性需求及其实现，同时保留灵活性以改善整体体验。”

Conductor 利用历史对话帮助团队识别哪些环节应保留人工介入，哪些环节可以给模型留出适应空间。一旦设定了这些边界，开发者仍需针对这些确定性部分所应满足的需求进行测试，并在底层业务规则变化时修订这些测试。

## **Cresta 如何评估 Conductor**

Conductor 的衡量标准是它构建智能体的能力。为此，Cresta 让 Conductor 完成一组构建任务：

-   构建一个新智能体
-   为其编写一个测试用例
-   修改一个已存在的智能体
-   执行根因分析

完成任务并不是唯一的标准。团队还会考察结果、Conductor 如何达成目标，以及过程中使用了什么。

| 评估 | 它回答的问题 |
| --- | --- |
| 结果 | Conductor 是否产出了所请求的、可用的产物？ |
| 执行路径 | 它是否使用了适当的工具和所需的上下文？ |
| 质量 | 结果与精心整理的参考相比如何？ |
| 资源使用 | 该任务需要多少时间和模型用量？ |

这些相同的任务也充当安全网。当新的 Claude 模型发布或 Conductor 框架更新时，Cresta 会重新运行其评估。它使用相同的任务和相同的评分，以在任何人提交变更之前识别哪些方面有所改进、哪些仍需完善。







同样的评估纪律也内置于 Conductor 中，使其用户能够检查自己的智能体是否按预期运行。Conductor 将构建阶段捕获的需求和边缘情况转化为其评估模块中的测试。

随后，团队可以在政策、连接系统和对话模式变化时，监控那些必须始终正常运行的工作流。这为他们提供了一种实用方式，随着业务变化更新智能体，同时不失去已经加固的工作流的可靠性。

## **在 Claude Agent SDK 上构建 Conductor**

Cresta 将 Conductor 设计为面向智能体开发的 CX 专用控制平面。它汇集对话数据、领域专业知识和开发实践，然后通过策略、可观测性、验证和反馈驱动的改进来治理每一次智能体运行。

Claude Agent SDK 作为通用执行框架位于 Conductor 之下。它管理收集上下文、调用工具以及编写和运行代码的工作；Conductor 则在其上叠加 Cresta 的 CX 工作流、工具和领域上下文。

团队针对 Conductor 需要执行的工作对 SDK 进行了评估：多步骤任务、大量上下文和重复的工具调用。其审查涵盖了数据隐私、租户架构、组织级密钥分发、控制措施以及整个实现过程中的可观测性。

“Anthropic 为智能体式软件开发提供了强大、通用的基础。这让我们能够将工程投入放在 Cresta 创造最持久客户价值的地方，”Cresta 工程副总裁 Xiangru Chen 表示。

## **将 Cresta 的工程专业知识直接交到客户手中**

Conductor 始于 Cresta 内部，帮助其自己的前向部署团队了解哪些开发任务可以变得可重复、上下文在何处最重要，以及构建者在过程中需要检查什么。它在内部工作中的成功让团队有信心将同样的能力带给客户和合作伙伴。

对于任何产品部署自定义智能体的速度快于工程师手工构建速度的团队来说，Cresta 的方法是一个有用的参考：无论是智能体还是元智能体，初始构建之后的工作往往是最难的部分。

了解 [Conductor](https://cresta.com/blog/cresta-conductor-the-agent-for-ai-agent-development) 如何将业务上下文转化为更好的智能体设计、实现和持续改进。

| 来自 Cresta 团队的最佳实践 |
| --- |
| 内部试用（Dogfood）你的产品 | Conductor 最初作为内部工具运行，只有当其产出与具备深厚 AI 专业知识的工程师所构建的成果相匹配时，才成为产品。 |
| 专注于你的独特优势 | Cresta 在只有他们能带来的专业知识（他们的对话数据和对客户体验的理解）与可以从 Agent SDK 直接采用的部分之间划出了明确界线，并拒绝在错误的一侧构建任何东西。 |
| 你的智能体哪些部分需要确定性 | 加固那些绝不能出错的企业关键工作流，其余部分保持灵活，否则你最终无法获得想要的交互式智能体体验。 |
| 投入生产是容易的部分 | 初始构建只占大约 20% 的工作量，另外 80% 是随后的测试、优化和持续改进，因此应围绕迭代循环而非发布来设计你的工具。 |
