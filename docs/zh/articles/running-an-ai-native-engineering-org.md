# 运营一个 AI 原生工程组织

多年来，工程人力一直是构建应用中最昂贵的部分。我们围绕软件规划与交付所建立的每一套流程——先是瀑布式，后是敏捷——都是围绕这一成本构建的。

我在 2000 年代初开始职业生涯，当时在做 Visual Studio。那时候我们用 CD-ROM 交付软件，有着严格的制造截止日期。后来我们能够在线分发软件，便开始逐步转向持续交付更新。现在我们又在改变工作方式，这一次改变的是编写软件所需的时间与人力。

在 Claude Code 团队，编写代码、编写测试和重构已经很少再拖慢我们的节奏。但当智能体式编程消除了实际敲代码的需求后，瓶颈并没有消失。验证、代码审查和[安全](https://claude.com/resources/articles/how-anthropic-secures-its-ai-native-software-development-lifecycle)取代了它们的位置。

现在我们都能够非常快速地生成大量代码，但这也带来了新的问题：这些代码正确吗？如何维护？以及我从其他工程负责人那里最常被问到的问题之一：“你们团队的人是怎么跟上代码审查节奏的？”

## 那些悄然失效的流程

我们建立每一套流程都有其原因，是为了填补某个缺口或让事情运转得更好。但当那个缺口不再存在、这些流程变得过时，它们很少会自行消失。当 Claude Code 团队开始将智能体式编程作为默认工作方式时，我们许多现有流程都失效了。以下是我们重写的规范，以及原因。

### 规划：将路线图转向即时规划

旧的规范是花大量时间做前期规划，因为编码时间很昂贵。我刚加入 Claude Code 团队时，我们写了一份相当不错的六个月路线图，然后*因为* Claude Code，变化太多，到第三个月它就过时了。

工程的节奏和吞吐量如今已不同，所以我们规划冲刺的方式也变了。我称之为即时（JIT）规划，几乎就像 JIT 编译：如何在正确的时间做正确数量的事？我们的规划仪式从设计文档转向了 PR 或原型中的讨论。这个领域变化很快，所以我们不做太多产品评审。我们现在的流程是：先做原型，让大量内部用户用起来，然后开始根据他们的反馈行动。

### 上下文收集：问 Claude，而不是问作者

当工程师编写代码时，大多数问题的第一步是找到写代码的那个人。现在，由于我们所有的 PR 都有 Claude 辅助，“这是谁改的？”已经不够了。我们的新规范是再深入一层：你实际需要知道什么？例如：你是在找谁导致了回归？找专家回答客户问题？还是需要某个决策的背景？你向 Claude 提出这个问题，并考虑 Claude 是否能直接回答，同时借助更多数据和上下文。

在 Claude Code 团队，无论问题是什么，我们的流程还包括问一句“有没有办法把它自动化？”例如，让 Claude 每天早上总结客户反馈渠道，这件事从过去我喝着咖啡手动完成的仪式，变成了我在后台自动运行的东西。

### 代码审查：信任但验证

我们大量使用 [Code Review](https://code.claude.com/docs/en/code-review)。Claude 处理所有风格和 lint 问题、PR 反馈请求、在完整提交前发现并修复 bug，以及添加测试。我们仍然明确需要人类的地方是专业判断。

新规范是在关键之处进行人工审查：对于法律审查，我总是希望我的法务伙伴参与风险容忍度的判断。对于信任边界和安全敏感的代码，我需要领域专家。产品经理和设计师也需要参与产品感和品味相关的判断。

不过，持续评估很重要，因为随着模型进步，信任与验证之间的正确平衡会不断变化。今天你需要人类做的事，在下一个模型下可能看起来不同。

### 团队构成：角色模糊化

Claude 和 AI 重塑了团队中的角色。我们的 PM 现在写很多代码，这看起来很有趣。有了 Claude，非传统编码者现在能做更多工程工作，而工程师也承担起内容和设计这类传统上不属于技术侧的工作。

在 Claude Code 工程团队，我重点看重两类人。一类是有产品感的创造性构建者：那些梦想家，对交付解决问题的产品充满好奇和热情。另一类是拥有深厚系统专业知识的工程师。例如，我加入团队时注意到我们缺少有系统背景的专家，而在构建 [Claude Code on the Web](https://www.anthropic.com/news/claude-code-on-the-web) 时我们需要这类人，以确保我们能在任何地方运行 Claude。

另一方面，我不那么看重的是原始吞吐量；模型会处理这些。更重要的问题是你仍然需要人类专业判断的地方在哪里，那才是我会关注的重点。

|  | 之前 | 之后 |
| --- | --- | --- |
| 规划 | 六个月产品路线图。 | 即时（JIT）规划：做原型，让内部用户使用，并根据他们的反馈行动。 |
| 上下文收集 | 找到写代码的人并问他们。 | 先问 Claude。然后问你所问的事情能否自动化。 |
| 代码审查 | 人类审查一切。 | Claude 处理风格、bug 和测试。人类在领域专业判断重要的地方进行审查。 |
| 团队构成 | 固定角色：工程师写代码，PM 做规划，设计师做设计。 | 角色模糊：PM 做原型，工程师承担设计和上下文工作。招聘创造性构建者和深厚系统专业知识的人。 |

## 我们如何推广新规范

随着这些规范变化，有些方面被规定为团队原则，另一些我们让小规模子团队（pod）自行摸索。Claude Code 核心团队有一套不可协商的“必须做”原则：

-   **不遗余力地内部试用（dogfood）你的产品：** 每个 Claude Code 团队成员，包括跨职能伙伴，都使用 Claude Code（也使用 Claude Cowork）。我们一直在思考如何让 Claude 帮助我们更快、更高效地完成工作。
-   **尽可能保持团队扁平。** 我加入 Claude Code 时，希望每个管理者都先以个人贡献者（IC）身份开始，通过交付学习如何成为团队中有效的工程师，真正经历并理解在 Anthropic 做工程师是什么感觉。我们在 Claude Code 和 Claude Cowork 上有一个整体团队使命。管理者支持各个工作 pod，同时保持团队敏捷，让人们能流向工作所在之处。
-   **毫不犹豫地砍掉不再有效的流程：** 最后，我们不断质疑为什么我们这样做事情。当某些事情不再合理时，团队成员有明确许可去质疑并砍掉旧流程。

不过，在这几条规则之内，每个 pod 有很大的自主权。他们有余地调整如何使用 Claude 做分诊、如何运行任何规划仪式或站会，以及哪些工作流先被“Claude 化”。

## 如何知道你的新流程在扎根

以下是每位工程负责人在推广变革时现在就应该开始追踪的三个数字。

-   **上手（onboarding）加速时间下降：** 一个工程师、设计师或 PM 多快能开始有效工作？在我们团队，这比一年前快得多，工程师现在第一周内就能交付真实代码。
-   **PR 周期时间下降：** 这个值得深入挖掘，因为它可能帮你识别流水线在哪里难以扩展。由于我们生成多得多的代码，有时构建系统和持续集成（CI）可能难以跟上。
-   **Claude 辅助的提交上升**：对我们来说，默认每个提交都是 Claude 辅助的。过去四个月里我不记得见过一个非 Claude 辅助的提交。

关于第三点，不要把吞吐量与成功混淆。吞吐量是一个指标，但真正的指标是衡量你试图解决的问题。有了正确的对齐，吞吐量能帮你更快地解决问题。

## 开始行动

如果我只留给你一件事：**挑出你最嘈杂的工作流。** 那可能是你最昂贵的工作流、你可能害怕的那个，或者你团队不期待的那个。然后问：它还在服务于它的目的吗？如果是，你能把它自动化吗？

我曾经在一个团队，每周有一次昂贵的评审，会议室里坐了一大群人。我注意到除了轮到做状态汇报时，每个人都在自己的笔记本电脑上。他们会抬起头，说状态，然后又低头回到笔记本电脑。我问了一个简单的问题：“我们为什么还要开这个会？这似乎是在昂贵地使用我们的时间。”就这一个问题让所有人意识到它并不需要。于是我们取消了它。

所以，问问自己：你的工程工作流中，有哪一部分你可以考虑自动化，甚至干脆去掉？
