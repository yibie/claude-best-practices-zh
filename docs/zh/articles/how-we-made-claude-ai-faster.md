# 我们如何在两周内让 claude.ai 提速 3 倍
今年八月，我们在为期两周的冲刺中，让 claude.ai 和 Claude 桌面应用的核心用户体验提速了约 3 倍。用户一直告诉我们它很慢，他们说得对。我们在一个 Slack 频道里运行一切，每个线程里都有 Claude。

我们聚焦于占用户活动 95% 的四条旅程。在第 75 百分位，全新加载 claude.ai 到页面可输入的时间从 3.1 秒降至 0.55 秒，启动新的 [Claude Code](https://claude.com/product/claude-code) 会话从 0.8 秒降至 0.3 秒，加载 [Claude Cowork](https://claude.com/product/cowork) 云会话从 2.6 秒降至 0.73 秒。总体而言，我们估计这每天为用户节省了数万小时的等待时间。

我们使用了 [Claude Tag](https://claude.com/product/tag)（beta），运行一个大致相当于 Opus 5.5 的内部研究模型。Claude 发现瓶颈、构建基准测试、发布改进，并监控每一次部署。我们通过设定目标、做出权衡、批准每一项变更来掌舵。借助这种方法，我们合并了三千多项变更，没有出现任何面向客户的事故或回滚。本文介绍我们发布了什么、如何衡量，以及我们与 Claude 共同构建的安全循环。

## 任务简报

冲刺开始前，我们创建了一个 Slack 频道，并附上以下[常驻指令](https://claude.com/docs/claude-tag/users/getting-started#give-claude-standing-instructions)：

> @Claude 你的工作是促进与 claude.ai 网站和桌面应用性能相关的所有事务。你的职责包括监控部署的性能回退、评估现有遥测的准确性和全面性、维护精心策划的可观测性仪表盘、主动为观察到的问题和低垂果实实施解决方案、提出性能项目机会，以及与人类队友沟通。\[…\]
>
> 这个频道的最终目标是让你尽可能自主，但今天我们清楚这还不可能。

我们让 Claude 通过 Datadog MCP server 分析使用数据。它识别出四条影响最大的用户旅程：启动应用、开始对话、加载已有对话，以及发送消息。在 Web 和桌面端之间，以及跨我们的产品，这些旅程合计为十三项不同的测量。为了建立基线，我们添加了埋点，直到它们可以直接比较：每项测量都从一次用户交互开始，在结果渲染后结束，并区分客户端和服务端的工作。

我们以约二十个精心挑选的项目启动了冲刺，每个项目针对一条特定旅程。Claude 以毫秒为单位估算每个项目的影响，我们将这些估算汇总以设定冲刺目标。有些项目相当大，但我们认为很可能在两周内完成大部分。

到第三天，我们已达成十三个目标中的十二个。

计划中的项目提前落地。为了加快启动，我们将静态输入框烘焙进 HTML，让用户可以在 React 初始化期间输入，并预编译 V8 代码缓存，使桌面壳的主进程无需从头重新编译。为了加快导航，我们在对话之间保持输入框挂载，在用户悬停时预取会话，并将侧边栏重渲染减少了 90%。

我们还留出了空间，让 Claude 识别机会并提出新的工作流。这些工作流迅速成长为各自完整的项目，远超我们最初的目标。于是我们设定了新目标，然后寻找更多可衡量的东西：

> @Claude 我们最终资助了原始项目列表中的几乎每个项目，甚至更多。让我们刷新一下 \[…\] 我们还没探索什么，我们可以在什么上爬山，现在最大的机会在哪里？\[…\] 我对 WACKY 的想法持开放态度

十一分钟后，五个线程在运行，每个聚焦于不同的测量：指令数、V8 调用数、React commit 数、样式重计算和 DOM 变更。

我们对每个新基准测试都持一些怀疑态度。每个都有两项职责：第一，一个 Claude 可以在实验室中推动的指标；第二，CI 中一个只能单向下降的护栏数字。如果基准测试不稳定，或者它实际上与用户延迟不相关，我们就丢弃它，而不是让 Claude 爬错山。

> @Claude 请证明针对每个基准测试爬山都能带来可衡量的墙钟性能提升。对于任何无法证明这一点的候选，我们将撤下这些基准测试

墙钟时间是用户感受到的，但它有噪声，毫秒太不稳定，不能用作 CI 门禁。指令数很有吸引力，因为它们是确定性的，但我们仍然需要 Claude 证明它们能跟踪墙钟时间。

于是我们让 Claude 在两条热路径上降低计数：组装对话消息树的例程，以及 Claude Code 输出中状态行的扫描器。Claude 用 Valgrind 对两者进行了性能分析，发现第一条路径四分之一的指令是巨态字典查找，将同一个消息 ID 解析了三次。

一小时后，它将两条路径的指令数分别减少了 48% 和 31%，墙钟时间分别下降了 78% 和 44%。我们签入了两个新的棘轮。从那时起，任何提高这些路径指令数的 PR 都会使 CI 失败，并且每天有一个任务在计数下降时降低每个上限。

这引出了冲刺的核心教训。**借助 Claude，衡量某事物使其变得可处理。**

衡量过去是第零步：你会添加一个指标，等待数据流入，然后才开始理解问题。借助 Claude，它是爬山的第零步。一旦 Claude 有了要击败的数字，它就可以开始优化。这意味着我们能做的最高杠杆的事情是找到更多可衡量的东西。

## 循环，逐个线程

所有这些都在同一个 Slack 频道中运行，多位工程师和 Claude 在每个线程中即兴协作。从那里，冲刺进入了一个[循环](https://claude.com/blog/getting-started-with-loops)：

1.  有人会就旅程中某段缓慢的部分开一个线程，通常附带截图或录屏。
2.  Claude 会追踪流程，然后找到或构建一个能证明问题的基准测试。
3.  一旦在实验室中有了有希望的结果，Claude 会带着 PR 回来——通常有多个，按风险和审查规模分级，任何用户可见的内容都放在功能标志后面。
4.  发布后，Claude 监控部署并读取现场数据。
5.  如果性能改善，Claude 通过降低基准测试上限来锁定胜利；如果没有，它关闭标志并迭代。
6.  然后它在同一旅程中寻找下一个慢点。

循环中的一个线程

有人开一个线程；Claude 从那里接手

一个例子：有人分享了一段屏幕录制，显示侧边栏行在页面加载后弹出。Chat 和 Cowork 行在不同时间解析，让页面感觉卡顿。我们现有的监控都没有检测到它。我们最接近的是[累积布局偏移](https://web.dev/articles/cls)，但每次偏移只得分约 0.008——远在 0.1 的良好阈值之内。

Issac 有了直接引用底层 [Layout Instability API](https://wicg.github.io/layout-instability/) 的想法。Claude 创建了一个遥测事件，将每个 `layout-shift` 条目的 `sources` 映射到命名区域（例如侧边栏、对话记录）和阶段（例如首次绘制前、可输入后）。它添加了一个集成测试，打开一个侧边栏已填充的页面，将侧边栏数据保持到首次绘制之后，并在任何命名区域发生任何偏移时失败。Claude 以此作为基准测试来证明修复：该测试在 main 上 20 次运行中 20 次变红，在 PR 上 20 次运行中 20 次变绿。

事件部署后，Claude 读取现场数据，发现 31% 的 Web 页面加载在页面可用后移动了某些东西，而没有任何用户交互。从那里，Claude 按名称逐一处理原因：一个迟到的标题行、一个在用户姓名加载后横向滑动的光标、一个在滚动条弹出时移动的列表。Claude 将最严重的问题批量修复，当它们消失后，它找到下一批。

## 横向扩展

一旦循环在一个线程上奏效，在更多线程上运行它只是开线程的问题。Claude 不会在原始请求完成后关闭线程，而是会_继续前进_。单个线程会提交五十个，有时一百个优化 PR。越来越多地，是 Claude，而不是我们中的某个人，开启新线程来追逐它自己发现的机会，作为单独调查或夜间任务的一部分。频道中的一位工程师 Shelley 观察到，“\[这个模型\] 是个数字恶魔。”

每个测量都找到了可改进之处。Claude 运行了一次 React hook 普查，发现输入框打字路径中有 6,900 个 hook 和 900 个 store 订阅，每次击键都重渲染。Claude 统计了样式重计算，发现单个 `:root:has()` 选择器为每次 DOM 变更增加了 24 毫秒。Claude 追踪了首次绘制后的代码路径，发现一个遗留的 `location.reload()` 导致每天五十万次隐藏重载，而我们没有任何加载指标能看到。Claude 读取了空闲标签页的 profiler 样本，发现相同的缓存快照每分钟被克隆到 IndexedDB 两次，全在主线程上。

我们很少知道一个线程会引向何处。在一次 CPU 卡顿扫描中，Claude 注意到高亮一个已完成的代码块可能让页面冻结约一秒。它在实验室中深入调查，找到了罪魁祸首：长破折号。如果回复的 markdown 包含任何非 Latin-1 字符，比如长破折号或弯引号，V8 会将整个字符串存储为 UTF-16，这会让每个语法高亮正则表达式走上较慢的双字节路径。Claude 用一个二十行的变更修复了它，在突出显示每个代码块之前将其复制到单字节字符串中。

到第二周，我们几乎无法将产出总结成每日更新。在最忙的日子，超过两百项变更落地。Claude 不断提出新的基准测试；约三分之一的 PR 包含额外的遥测或护栏，每个新工具都产生更多线程和更多机会。

在一个频道中工作意味着一切都在公开进行。我们跳进彼此的线程，辩论决策并庆祝胜利。消息传开了：其他团队开始将他们的变更带入频道，进行性能审查。由于引入了所有护栏和 Claude Skills，新项目以微妙更高效的方式编写。

## 护栏

我们为这个节奏做好了准备。因为我们接触的几乎所有东西都是热路径（首次绘制、输入框、对话记录），我们预先建立了安全机制。每个 PR 都经过[自动审查](https://claude.com/blog/code-review)并至少有一位人工批准，单元测试总是先于优化，任何可能导致用户可见问题的内容都放在短期功能标志后面发布。

当标志开始堆积时，我们开了一个线程来协调它们的推广和清理。Claude 将每个标志分类为终止开关或渐进发布，并在安全后立即退役每一个。两周内，我们引入了近两百个标志，其中一半以上在结束时已经清理完毕。

我们也知道性能胜利在快速移动的代码库中会衰减，而且[Anthropic 的代码发布很快](https://claude.com/blog/agentic-coding-is-straining-ci-heres-how-we-scaled-test-impact-analysis-at-anthropic)。一旦项目证明了胜利，我们就投资于保护它的方法。例如，静态输入框在设计上就是脆弱的。我们几乎立即向用户展示页面的 HTML 副本，并让 React 直接在其上绘制。

如果 React 渲染哪怕差一个像素，魔法就消失了。所以 Claude 构建了数十个护栏：

-   静态标记通过在实际 React 组件于 jsdom 中渲染来生成，测试保证它们永不漂移。
-   一个集成测试套件在十四个视口尺寸下将静态页面与 React 渲染进行比较，并断言在 1 像素内对齐。
-   一个击键测试直接穿过交接过程打字，并在任何丢失或重排的按键上失败。
-   在现场，每次交接报告到十分之一像素的偏移。Claude 为任何非零移动的事件开一个线程。

并非一切都能在实验室中捕获，所以我们也利用了书中最古老的护栏：渐进式推广。高风险变更先推广给员工，然后 1% 的用户，然后所有人。我们在内部发布静态输入框四小时后，一位队友分享了一段布局偏移的屏幕录制，我们的指标都看不到。当他在新标签页中打开 claude.ai 时，输入框会下沉——但这不是我们的代码。

## 掌舵

循环富有成效，但不是自主的。保持它快速、安全和在轨道上是我们的工作，它有三个部分。

**雄心。**默认情况下，Claude 对范围很谨慎。它把发现记成工单，对可行性持保留态度，并给估算留有余地。但我们对护栏有信心。我们所做的很多事情，尤其是早期，是鼓励 Claude 更大胆。

当我们开始达到设定的目标时，我们注意到线程会慢下来。Sam 一个线程一个线程地传达同样的信息：“让我们继续推动下降，目标不是停止点。下一步是什么？要有雄心。”

**品味。**每个线程都有一个指定的人类负责人，Claude 用前后截图或录屏突出任何用户可感知的变更，供他们裁决。表格应该逐格填充，还是等每行完整？加载骨架应该立即显示，还是只在半秒后？流式文本的逐词淡入是否值得它花费的五分之一帧预算？Claude 寻找削减毫秒的方法，我们权衡取舍。

**方向。**我们故意让每个线程保持狭窄，聚焦于一个基准测试或旅程，并要求 Claude 只在该范围内寻找改进。我们把线程看作一百五十把寻找钉子的锤子。我们的大部分决定是关于排序和用户影响：优先哪些界面、如何合并相互冲突的线程，以及何时关闭已达到收益递减的线程。一个 900 行的 PR 得到了一行回复：“我裁定每次发送 2 毫秒不值得维护这个构建插件的复杂性。”
