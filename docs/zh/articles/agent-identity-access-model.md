# Claude Tag 中的智能体身份：面向自主、团队级 AI 的全新访问模型

要让 AI 智能体在[人机团队](https://claude.com/resources/articles/building-effective-human-agent-teams)中发挥最佳表现，它需要访问与人类相同的工具、文档和上下文。

在“单人”AI 体验中（一个人与一个助手对话），这很直接：你连接自己的账户，智能体代表你行事。但在像 [Claude Tag](http://anthropic.com/news/introducing-claude-tag) 这样的“多人”AI 体验中，Claude 与许多人同时身处同一个共享频道，它使用的是属于_工作区_的工具和上下文，而非任何个人。

要让多人体验运转起来，Claude 需要在这些工具中拥有自己的账户，由管理员设置并绑定到工作区。我们把这种访问模型称为**智能体身份（agent identity）**。

本文中，我们将解释智能体身份如何运作、它如何将权限从按用户转移到按频道，以及如何在你自己的工作区中妥善划定其范围。

## **为什么“以用户身份行事”行不通**

当你把 AI 当作个人助手使用时，你可以连接 Google Drive、GitHub 和日历等平台，让模型使用_你的_访问权限在其中读写。

这一模型对 Claude Tag 不适用，原因有二：

-   **智能体自主性不断提升。** AI 智能体能够独立可靠完成的任务时长大约[每四个月翻一番](https://www.anthropic.com/institute/recursive-self-improvement)。智能体现在会为自己安排后续任务，并在提出请求的人早已登出很久之后响应事件。虽然用户会设置例程，在特定情况下触发智能体行动，但智能体在很大程度上是自主工作的。
-   **多人团队。** Claude Tag 将 Claude 置于[团队已经在其中工作的共享空间](https://claude.com/resources/articles/claude-tag-guide-for-startups)——例如一个三名工程师和一名 PM 一起调试的频道。但当不止一个人参与指挥时，该应用谁的权限？不存在任何时候都正确的单一人员选择。这使管理员能够独立于参与的人类，定义智能体在 Slack 中可以做什么，并对 Slack 中所做的事进行独立追踪。

### Claude 以自身身份行事

在 Claude Tag 活跃的频道中，Claude 并不代表单个用户行事。它在所接触的每个系统中都有自己的账户：它以 Claude 应用的身份在 Slack 中发帖，以 Claude GitHub App 的身份发起拉取请求（PR），并在管理员配置的服务账户下查询你的数据仓库。

而且由于不涉及任何个人用户凭证，共享频道永远不会成为通往某人私人文档的后门。

### 继承权限

在智能体身份模型中，管理员在工作区层面定义一个身份——即 Claude 在所有地方持有的连接和 Skills（技能）的基线集合——每个频道默认继承它。然后，在合理之处，管理员可以在频道层面覆盖它，例如授予工程频道访问 GitHub 和数据仓库的权限，或将某个 CRM 连接限制在单个私有频道内。

除凭证外，管理员还定义：

-   **仓库访问权限：** Claude 可以读写哪些仓库。
-   **Connectors：** Claude 用来完成工作的工具和 API 密钥。在整个组织中，不同的 API 密钥可以以不同的权限级别连接同一服务（例如，Claude 在通用频道中可能被授予数据仓库的只读访问权限，而在数据团队的私有频道中被授予写入权限）。
-   **Skills 与插件：** Claude 动态加载以提升特定任务表现的指令、脚本和资源文件夹。
-   **常驻指令：** 每个频道的自定义指令和上下文。

由于这一模型围绕独立的 Claude 身份运作，撤销该身份即可终止 Claude 在所有使用过该身份的地方的访问权限。这比跨数十个用户账户审计单个智能体的操作要省力得多。

## 智能体身份模型如何运作

智能体身份将“这个用户能做什么？”这一问题替换为“这个智能体在这个隔间里能做什么？”这是对按用户访问控制列表（ACL）的背离：它意味着，即使某个频道成员没有该仓库的直接访问权限，只要该频道的配置授予了 Claude 该权限，该成员就可以让 Claude 读取该仓库。

这并不寻常，但我们认为这是迈向适用于自主、多人智能体的访问模型的必要一步。下面，我们概述如何考虑划定这些边界。

### 身份边界如何运作

Claude Tag 为每个私有频道创建独立身份；工作区中的公共频道共享一个工作区级身份。Claude 在法律频道的身份无法触及未在那里授予的代码，其在工程频道的身份也无法读取未在那里授予的法律文档。记忆和访问权限都遵守这些边界：Claude 在私有频道中学到的内容永远不会出现在更广泛的工作区中。

身份属于频道，因此默认情况下频道中的任何人都可以 @ 提及 Claude，管理员可以将每个频道的配置范围限定为权限最低的成员。在 Enterprise 计划中，基于角色的访问控制让管理员可以更进一步，决定哪些成员能够调用 Claude，因此频道同时管辖智能体能触及什么以及谁能发起请求。

### 对工具和上下文的宽泛默认访问

团队在 Claude Tag 中如何划定 Claude 的工具访问范围：宽泛、低风险的集成在共享频道中以智能体身份运行，而个人或团队专属工具留在私信中并以用户身份运行。

在 Anthropic 内部运行 Claude Tag 时，我们发现其价值会随着工具和上下文访问的增加而叠加。每接入一个系统都会让其他系统更有用，因为 Claude 可以跨系统组合上下文——从 Slack 拉取一个讨论串、从 Drive 取一份文档、从工单系统取一张工单、从数据仓库取一个查询，汇成一个任何单一工具都无法提供的答案。

从 Claude 中获益最多的团队，是那些从一开始就授予其慷慨访问权限、再根据组织的管理员偏好逐步收缩访问的团队。智能体身份为管理员提供了足够宽泛的范围，让 Claude 能完成有用的跨系统工作，同时边界足够牢固，使访问权限永远不会流向未被授予的地方。我们的建议是：先在少数频道中从基线配置开始，查看审计轨迹，然后在工作足以证明其合理性时扩展访问权限，一次一个审慎的授权。

对于需要更细粒度的组织，管理员可以在特定频道中禁用 Claude Tag。管理员还可以应用基于角色的访问控制（RBAC），将 Claude Tag 的访问限制为特定用户。

### 私信

在 Claude Tag 中，私信的工作方式与共享频道不同。私信运行在用户各自的 claude.ai 账户上——使用他们的 Connectors、凭证，结果中也显示他们的名字。这使私信成为与 Claude 处理那些永远不应出现在频道中的任务和工具的正确场所，例如邮件草稿或只有你拥有许可证的软件。

### 安全与审计

当管理员向频道配置添加连接时，凭证会被独立存储并映射到该频道的身份，然后在请求时于网络边界注入。发往管理员未允许的任何主机的出站流量会被直接阻断。在审计方面，使用智能体凭证进行的每一次例程、记忆写入和网络调用都会被记录，而且由于 Claude 以自己的服务账户行事，这些操作也会落入每个所连接系统自身的日志中。

## 后续计划

智能体身份是 Claude Tag 访问模型的基础。未来，我们计划加强 Claude Tag 的安全能力，包括即时凭证授予——让用户可以在当下批准单个敏感操作，而无需永久扩大智能体的范围——以及面向权限结构更复杂的组织的身份感知叠加层。这将在智能体的范围之上增加用户级检查，使 Claude 仅在频道配置和请求用户自身的权限都允许时才行动。

在 Claude Tag 等产品中从单人 AI 向多人 AI 的转变，使长时程、基于团队的工作成为可能。智能体身份确保 Claude 对工具的访问足够宽泛以发挥作用，同时范围足够受限以在企业规模下保持安全。
