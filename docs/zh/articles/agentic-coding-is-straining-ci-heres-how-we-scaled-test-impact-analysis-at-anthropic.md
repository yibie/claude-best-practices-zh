# 智能体式编码正在给 CI 带来压力。我们如何在 Anthropic 扩展测试影响分析
## AI 正在改变 CI

Anthropic 的工程师现在平均每季度交付的[代码量是 2021-2025 年期间的 8 倍](https://www.anthropic.com/institute/recursive-self-improvement)。其中 [80% 的代码由 Claude 编写](https://www.anthropic.com/institute/recursive-self-improvement)，Claude 在[审查和批准 PR](https://claude.com/resources/articles/how-anthropic-secures-its-ai-native-software-development-lifecycle)方面也发挥着重要作用。



编写代码不再是瓶颈，而一旦 PR 审查加速，CI 就开始感受到压力。

除此之外，我们代码库中的测试数量增长了 10 倍，而我们只增加了少量工程师。这一切导致 CI 任务量在六个月内增长了 25 倍（如果你想算一算：并非每个测试都会在每个 PR 上运行，我后面会解释）。

这多次威胁到我们的测试影响分析服务过载。为了避免成为下一个瓶颈，我们彻底拆解了整个服务，重新构想了它的架构。但走到那一步的过程并不平坦，起点是三次快速修复，它们分别撑了 70 天、29 天，以及不到一天。

随着智能体持续加速代码生成和审查，扩展 CI 是更多工程团队很可能很快就要面对的挑战。关于合并的配套文章，请参阅[重新设计 Anthropic 的源代码控制](https://www.anthropic.com/engineering/redesigning-source-control)。我预计，随着运行智能体的团队产生更多 PR 和更多测试，水平扩展的测试选择架构将成为行业标准。



在本文中，我将讨论我们如何在 Anthropic 扩展测试影响分析服务，以及我以惨痛代价学到的教训：始终为指数增长做规划。具体的扩展技巧——购买更大的机器、并行化进程，或重启服务（没错，这一招仍然出奇地有效）——都很常见，**并不是本文要传达的洞见。**

关键在于，这些技巧中的每一个所能争取到的时间，都只有一年前的零头。另一方面，彻底改造并完全重新设计一个服务所需的时间同样只有零头，而且在编写代码不再是瓶颈的今天，这种做法要可持续得多。

你越能预见这种压力并规划好架构将如何随之演进，你在半吊子措施上浪费的时间就越少。

## 测试影响分析架构

我的许多同行所在的组织**仍然**在每次变更时运行每一个测试。这种做法在某个临界点之前是可行的，但无法扩展：CI 门禁会变得越来越长、越来越贵，也越来越不可信。

此外，人类很擅长判断哪些测试失败与自己无关，而智能体则需要更多上下文和指引。当它们拿到一组具体的有效测试时，就能更有效地自我验证和迭代。

在 Anthropic，我们构建了一个确定性的测试影响分析（即测试选择）服务，它根据历史表现和包相关性来决定每次变更运行哪些测试。这并非罕见做法，市面上也有一类厂商提供这方面的产品。

我们的服务依赖两个保持同步的确定性组件：

-   **一个“监听器”**记录每次 CI 运行中的测试结果。
-   **一个“选择器”**读取测试结果历史，并决定哪些已打开的 PR 运行哪些测试。

这很有效，但当每秒都有多个 CI 任务运行时，监听器会越来越落后于 PR 队列。对于 [AI 原生的 SDLC](https://claude.com/resources/articles/the-ai-native-sdlc-playbook) 而言，小小的滞后也可能产生巨大影响。例如，监听器滞后 20 分钟，可能意味着数万条测试更新未能应用到选择器上。

-   **如果一次糟糕的变更被合并**，那么某个测试会开始对其他人持续失败，导致多次不必要的排查。
-   **如果某个依赖开始不稳定**，那么不稳定的失败就会开始阻塞合并。
-   **如果某个测试被修复或新增了测试**，在监听器追上进度之前它不会运行，从而带来回归风险。

这一切都作为单个进程运行，因为要为每个测试维护运行历史，就需要由单个写入者来应用结果。这种 v0 设计使我们无法进行水平分片。

## 重新设计的坎坷之路

到去年十月，该服务已经显现出压力迹象，我们连续两天被呼叫。

### 补丁 1：更大的机器

第一个修复很简单：我们把运行该服务的核心数翻了一倍。我们也知道这只是暂时的。



对话为重新构建。基于真实事件。

即使趋势线已经很明显，归属仍然模糊。没有人愿意再负责一套基础设施。而且，CI 团队还有更重要的事要忙。

### 补丁 2：分片

此时，由于该服务监听器中不断累积的滞后，我们相当频繁地被呼叫。为了推动一些长期修复，我在内部版本的 Claude Tag 中启动了一个长期会话，专门用于监控该服务。每当监听器滞后超过 50,000 个任务时，Claude 就会通知我，并继续我们关于下一步的对话。

这持续了数月，而且不必不断提醒它过去的努力或上下文，这很有帮助。Claude 经常主张彻底改造，但我们通常还是选择了另一个补丁。



在内部版本 Claude Tag 上的逐字对话，部分内容已隐去。

二月，CI 任务的指数增长再次开始给该服务带来压力。这一次，我们决定并行化。

监听器并不需要单个写入者来正确排序测试结果，它需要的是每个包一个写入者，以正确排序代码库每个部分的测试结果。Claude 为我们生成了代码，将每个包的状态拆分到各自拥有工作进程的分片中。

我们也知道这个修复只是暂时的，但我们没意识到它只为我们争取了 29 天。

### 补丁 3：每日重启



三月，该进程在大多数工作日的下午中段就达到了内存上限。我们再次寻找快速修复方案，但是：

-   我们只发现了四个 bug。
-   作为权宜之计更换内存分配器毫无效果。我们试图优化垃圾回收，但那并不是真正的解决方案。
-   我们不想冒险对一个已经处于高负载下的单例进行内存分析。
-   重启只为我们争取了不到一天。

我们还发现，每日重启导致该服务逐渐越来越落后。当它落后超过一小时（这种情况发生过好几次）时，大量任务结果没有被监听器记录。

需要说明的是，这并不意味着那些 PR 上从未运行过 CI，也不意味着未经测试的代码被推到了生产环境。它的意思是监听器没有接收到部分结果，这意味着我们的测试选择组件在用陈旧数据决定 PR 上运行什么、不运行什么。这主要导致我们运行了一些本来就极不稳定或普遍失败的测试。

### 重新设计

是时候（早就该）重新设计该服务了，我们采纳了 Claude 的建议：我们给测试选择服务配了一个数据库，准确地说是一个内存数据存储。通过这样做，我们有效地卸载了单例过去在内存中处理的一大块工作。

现在，任何监听器工作进程都可以处理任何结果，将其追加到内存存储中的日志，然后继续处理，而无需在内存中保留任何东西——无状态，因而可水平扩展。一个独立的小型消费者进程每隔几秒将日志汇总为每个测试的历史记录，选择器则可以快速查找相关的结果历史。



这种分布式架构的运行成本更高，但比一个摇摇欲坠的单例更容易扩展和进行内存分析。这个项目由一名工程师花了三周完成。一年前，这需要接近一个季度。



排队中、未处理的任务结果事件，每小时最大值。之前：大多数日子都会积压，且逐周增长。切换并调优后：持平。

有一些微调（确定日志大小和工作进程数量），主要由 Claude 自主完成，但此后我们的服务一直保持稳定。

## 我会做出哪些不同的选择

如果我能被送回 2025 年 10 月，我会用现在所知的方式处理这个项目和其他项目。

第一个不同之处是，我会把 AI 的指数增长考虑进去。随着每位工程师平均智能体数量的上升，以及加速的 PR 批准变得更加成熟，CI 任务量会呈指数增长。

随着时间的推移，这改变了 Anthropic 中 PR 的形态，因为 Claude 偏好更小、更细粒度的 PR（这也是不要对每个 PR 运行所有测试的另一个好理由）。这导致每天产生更多 CI 任务。此外，活动水平的下限被抬高了，因为智能体会在夜间和周末推送，但它仍然呈突发性，因为人类工程师仍然驱动并批准大量 PR。

我对工程团队的建议是：无论自建还是采购，都要假设你的架构在两个季度内会承受 25 倍的负载。过度工程化这个概念正开始略微消退，或者至少门槛正在大幅提高。只要预算允许，你现在就可以在 v0 设计中考虑 10-20 倍的预期规模。

为你的服务加上可观测性，让它们成为 Claude 的眼睛和耳朵。这让 Claude 能够比我们手动做得更好、更快地爬山式优化并逐步修复问题。特别要确保进来的 CI 任务数量与出去的数量相等。

从一开始就让状态远离进程。我还建议不要将任何关键服务作为单实例运行，除非你能对它进行度量并做金丝雀变更。CI 演进得太快，任何其他做法都行不通。
