# 在 Claude Code 中使用 Claude Opus 4.7 的最佳实践
_编者注：本文中 2026 年 10 月 30 日之前提及的 Max，包含如今称为 Max 和 Ultra 的套餐。_

[Opus 4.7](https://www.anthropic.com/news/claude-opus-4-7) 是我们迄今为止面向编程、企业工作流和长时程智能体任务的最强通用可用模型。它比 Opus 4.6 更能处理模糊性，在发现 bug 和代码审查方面能力大幅提升，跨会话携带上下文更可靠，并且能以更少的指引推理模糊任务。

在我们的[发布公告](https://www.anthropic.com/news/claude-opus-4-7)中，我们提到两项变化会影响 token 用量：更新后的分词器，以及在更高 effort 级别下倾向于思考更多的特性，尤其是在较长会话的后续轮次中。因此，在用 Opus 4.7 替换 Opus 4.6 时，可能需要一些调优才能达到最佳性能。对提示词和执行框架（harness）做一些微调就能带来很大差别。

本文梳理了有哪些变化，以及如何在 Claude Code 中最有效地使用 Opus 4.7。

## 组织交互式编程会话

Opus 4.7 的 token 用量和行为会有所不同，取决于你部署的是更自主、异步、只有单个用户轮次的编程智能体，还是更交互、同步、有多个用户轮次的编程智能体。在交互式场景中，它在用户轮次之后会进行更多推理：这提升了它在长会话中的连贯性、指令遵循和编程质量，但也倾向于消耗更多 token。

要在 Claude Code 中充分发挥 Opus 4.7 的潜力，我们发现把 Claude 当作一位你能干、可以委派任务的工程师，而不是逐行指导的结对程序员，会更有帮助：

-   **在第一轮就明确任务。** 包含意图、约束、验收标准和相关文件位置的、描述清晰的任务说明，能为 Opus 4.7 提供交付更强输出所需的上下文。在多轮中逐步传达的模糊提示词，往往会降低 token 效率，有时还会降低整体质量。
-   **减少所需的用户交互次数。** 每个用户轮次都会增加推理开销。把你的问题批量提出，并给模型提供它继续推进所需的上下文。
-   **在合适的时候使用[自动模式](https://claude.com/resources/articles/auto-mode)。** 对于你信任模型能安全执行、无需频繁确认的任务，自动模式能缩短周期时间。它尤其适合你已在前置提供完整上下文的长时程任务。自动模式现已面向 Claude Code Max 用户提供研究预览——你可以用 Shift+Tab 开启。
-   **为已完成的任务设置通知。** 让 Claude 在完成任务时播放声音，它可以自行创建基于钩子（hooks）的通知。

## Opus 4.7 的推荐 effort 设置



Opus 4.7 在 Claude Code 中的默认 effort 级别现在是 `xhigh`。这是一个介于 `high` 和 `max` 之间的新 effort 级别，让用户能更好地控制难题上推理与延迟之间的权衡。我们推荐大多数智能体式编程工作使用 xhigh，尤其是对智能敏感的任务，如设计 API 和 schema、迁移遗留代码，以及审查大型代码库。

以下是针对每个 effort 级别的一些额外指引：

-   **`medium` 和 `low`**：适用于对成本敏感、对延迟敏感或范围严格限定的工作。模型在更难的任务上不如在更高 effort 级别时能力强，但仍优于以相同 effort 级别运行的 Opus 4.6——有时还消耗更少的 token。
-   **`high:`**：平衡智能与成本。如果你在运行并发会话，或想花更少的钱而不大幅牺牲质量，选择 high。
-   **`xhigh`（默认，推荐）**：大多数编程和智能体式用途的最佳设置。它具备很强的自主性和智能，又不会像 max 在长时程智能体运行中那样产生失控的 token 用量。
-   **`max`**：在真正困难的问题上榨取额外性能，但收益递减，且更容易过度思考。请有意识地将其用于在评估（eval）中测试模型能力上限，以及对智能极度敏感且对成本不敏感的场景。

如果你要升级到新模型，我们建议试验不同的 effort，而不是直接沿用旧设置。你可以在同一任务中切换 effort 级别，以更有效地管理 token 用量和推理。

我们将 Opus 4.7 的默认 effort 级别设为 xhigh，是因为我们相信它是大多数编程任务的最佳设置。如果你是现有 Claude Code 用户但尚未手动设置 effort 级别，你将被自动升级到 `xhigh`。你仍然可以手动调整 effort。

## 使用自适应思考（adaptive thinking）

**Opus 4.7 不支持带固定思考预算的扩展思考（Extended Thinking）。** 取而代之的是，Opus 4.7 提供自适应思考。这让思考在每一步都是_可选的_，并允许模型根据上下文决定何时使用更多思考。它可以快速响应简单查询，在某个步骤不会从思考中获益时跳过思考，并把思考 token 投入到最可能有用之处。在一次智能体运行中，这可以累积成更快的响应和更好的用户体验。

自适应思考在此次发布中有显著改进——尤其是 Opus 4.7 更不容易过度思考。

如果你想对思考频率有更多控制，可以直接在提示词中要求：

-   **如果你想要更多思考**，可以试试类似这样的话：“在回复前仔细地、一步一步地思考；这个问题比看起来更难。”
-   **如果你想要更少思考**，可以试试类似这样的话：“优先快速回复，而不是深入思考。拿不准时，直接回复。”你会节省 token，但在更难的步骤上可能会损失一些准确性。

## 值得了解的行为变化

Opus 4.6 和 4.7 之间有一些默认行为发生了变化，如果你曾针对旧模型仔细调优过提示词或执行框架，这些变化值得了解。

**回复长度按任务复杂度校准。** Opus 4.7 不像 Opus 4.6 那样默认冗长。你可以预期简单查询得到更短的回答，开放式分析得到更长的回答。如果你的用例依赖特定长度或风格，请在提示词中明确说明。我们发现，给出你想要的语气的正面示例，比“不要这样做”之类的负面指令更有效。

**模型调用工具更少，推理更多。** 这在许多情况下能产生更好的结果。如果你想要_更多_工具调用（比如在智能体式工作中更积极地搜索或读取文件），请提供明确说明何时以及为何应使用该工具的指引。

**它默认生成的子智能体更少。** Opus 4.7 倾向于更审慎地决定何时把工作委派给子智能体。如果你的用例受益于并行子智能体（例如，跨文件或独立条目分发），我们建议明确写出来。例如：

不要为你可以在单次回复中直接完成的工作生成子智能体（例如，重构一个你已经能看到的函数）。当跨条目分发或读取多个文件时，在同一轮次中生成多个子智能体。

## 接下来可以尝试什么

Opus 4.7 在长时程任务上的表现优于以往模型。这使它很适合那些过去以监督为瓶颈的任务，比如复杂的多文件改动、模糊的调试、跨服务的代码审查，以及多步骤的智能体式工作。

我们建议把 effort 保持在 `xhigh`，看看你的第一轮能走多远。
