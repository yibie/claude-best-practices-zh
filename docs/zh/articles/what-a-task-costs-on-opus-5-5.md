# Opus 5.5 上完成一项任务的成本
## 任务的成本，以及重试的成本

你不会一开始就打算买几百万个 token。你的目标是构建一个功能、完成一次迁移，或者跑完一项任务。token 数量只是模型达成目标所需的量。

两个每 token 成本相同的模型，在同一个任务上的花费可能相差很大。一个模型只读一遍代码。另一个读了代码、尝试修复、又读了一遍代码。其中每一步都是一轮（turn），而每一轮都会重新发送此前的对话。所以需要更多轮次的模型花费更高，即使单价相同。

读完本文，你应该能回答关于自己工作的三个问题：

-   在 Opus 5.5 上，我典型任务的花费是多少？
-   哪些设置会改变这个数字，改变多少？
-   我如何查看自己会话的用量？

我想先说明的权衡是：每一种减少 token 消耗的方式，也可能让你付出「任务没做完」的代价。降低 effort、换用更小的模型、减少上下文，这些当然都能省 token。但一次重试的花费比这些节省更多。本文试图为每一项权衡标上价格。

这里有些数字是标价，有些是基于标价构建的示例。这些数字是可交互的，你可以在阅读时修改输入。这些都是尽力而为的示例，请务必核对我们的文档和你自己的计算。

## 一项任务要花多少钱？

[Claude Code](https://claude.com/product/claude-code) 中的一项任务是一个循环。模型读取对话、调用工具、读取结果，然后再次循环，直到完成。循环中的每一趟就是一次请求。有四件事决定了这个循环的成本。

**轮次。** 每一轮都会重新发送此前的对话。轮次越少，处理的输入越少。

**缓存读取。** 一轮重新发送的内容，大部分是模型在上一轮已经见过的文本。这部分按缓存读取计费，价格只是输入价格的一小部分。

**输出 token 类型。** 最贵的 token，价格是输入的五倍。[思考](https://platform.claude.com/docs/en/build-with-claude/extended-thinking)按输出计费，所以一个在得出答案过程中思考更少的模型，花费更低。

**模型。** 每个模型都有自己的价格，列在定价页面上，所以你选择的模型决定了每个 token 的价格。

我们的示例使用 Opus 5.5 的 API 标价：每百万输入 token 4 美元，每百万输出 token 20 美元，每百万缓存读取 0.20 美元。与下文计算器一样，示例将缓存输入按读取价格计费，其余按输入价格计费，并且不计缓存写入。token 数量均为示例。

### 轮次

假设一项任务开始时上下文为 20K token，随着模型读取文件和工具结果增长到 120K。按 40 轮计算，平均每轮发送约 70K token。这项任务大约处理 2.8M 输入 token，尽管对话从未超过 120K。若其中 90% 从缓存读取，输入成本约为 1.62 美元。同样的任务若用 25 轮完成，处理约 1.75M token，输入成本约为 1.02 美元。

一轮的成本高于它新增的 token，因为它会重新发送之前的所有内容。所以最便宜的一轮，是你不需要的那一轮。

一个能减少轮次的做法，是给模型[一种检查自己工作的方式](https://claude.com/resources/articles/building-verification-loops-in-claude-code-with-skills)。例如，一个可以运行的测试、一次构建，或者一个调用该端点的脚本。能检查自己工作的模型会更早发现自己的错误。

一次就能收集到所需信息、并批量执行工具调用的模型，需要重新发送的次数也更少。

### 缓存读取

同样的 2.8M 输入 token，如果没有任何缓存，成本为 11.20 美元。命中率 90% 时成本为 1.62 美元，96% 时约为 0.99 美元。没有其他设置能如此大幅地影响输入成本。一个持续进行的会话本身就能保持较高的命中率。我在本文后面会介绍一些需要避免的、会破坏缓存的操作。

### 输出 token

在 Opus 5.5 上，一个输出 token 的成本是一次缓存读取的 100 倍。一项典型任务的 60K 输出 token 花费 1.20 美元，相当于从缓存读取 6M token。输出包含思考。即使 Claude Code 只向你展示摘要，你也要为全部内容付费。这就是为什么 effort（主要改变模型思考多少）对账单影响如此之大。

### 模型

缓存读取更便宜的模型，主要有利于长会话。输出更便宜的模型，主要有利于需要大量推理的任务。

## OPUS 5.5 有哪些变化

有两件事变了：价格，以及模型完成的工作量。

**每一项价格都更低了。** 输入和输出 token 比 Opus 5 便宜 20%。缓存读取便宜 60%。输入价格下降，读取费率也随之下降，从输入价格的十分之一降到二十分之一。图 A 比较了两个模型每百万 token 的价格。这些是 API 标价。在 Pro、Max 或 Team 套餐上，Opus 5.5 更低的价格会传递到你的限额上，包括缓存上下文，因此限额大约比 Opus 5 多出 25%。缓存读取的额外折扣属于 API 价格变化。

另外，Pro、Max、Team 以及按席位计费的 Enterprise 套餐的五小时限额提高了，符合条件的订阅用户还会获得一次限额重置，可自行选择何时使用。你可以在网页版或 Claude Desktop 的 Settings > Usage 下找到它，而不是在终端里的 Claude Code 中。重置会应用于你的整个账户，包括 Claude Code。

使用 API key 时，缓存读取降价对 Claude Code 影响最大。一个长时间的智能体式会话，大部分输入都花在缓存读取上。在下文图 B 计价的会话中，缓存这一行从 1.00 美元降到 0.40 美元，是账单上降幅最大的一项。

你能省多少取决于工作的形态。一个以缓存读取为主的会话，输入最多可省 60%。一个没有缓存、答案很长的简短提问，最多可省 20%，因为输出占了大头。大多数 Claude Code 任务介于两者之间。下面的计算器可以显示你的任务处于哪个位置。

你可能看到过 Opus 5.5 的运行成本比 Opus 5 低 40%。这是我们对按 token 计费、使用默认设置的典型工作负载的估计。它假设 Opus 5.5 在其默认的 medium 档位上每项任务使用的 token 更少，再加上更低的价格，所以这并不是 token 价格降低了 40%。token 价格就是图 A 中的那些，图 B 展示了价格变化本身带来的影响。

Opus 5.5 在一个答案上可能使用更多 token，因为它在回复前总是先思考。我们预计人们用 Opus 5.5 能完成更多工作，但这因任务而异，所以请在你自己的工作上进行测量。图 C 比较了两个模型每项任务的成本。这部分对你自己工作的依赖远大于对价格的依赖。

在一项范围明确的任务上，两个模型完成的轮次大致相同，你得到的就是价格下降。差距应该在开放式任务上最大，因为模型可能把很多轮花在错误的想法上。没有哪个单一数字适用于所有代码库，所以要测量（见最后一节）。

**长时间运行以报告收尾。** Opus 5.5 在长时间运行结束时，会说明它改了什么、发现了什么，以及需要你做什么。这也能省钱，因为当你能看到发生了什么时，你重跑会话的次数会更少。

## 最大化会话价值的技巧

Opus 5.5 更低的价格让每个 token 更便宜。你如何运行会话决定了你使用多少 token，以下步骤会有帮助。

### 先提高 effort，再考虑换模型

Effort 为模型每一轮花多少 token 设定一个总体倾向：它的思考、它写的文本，以及它的工具调用。在较低的 effort 下，它发起的工具调用更少，也更简短。Opus 5.5 有四个档位（low、medium、high 和 xhigh），外加用于单次会话的 max。选择一个档位，看看何时使用它以及设置它的命令。

Medium：用于范围明确的日常工作

范围清晰的日常工作。它每轮思考比 high 少，所以每轮成本更低。

当任务范围明确时，从这里开始。

-   `/effort medium`
-   `/effort status`
-   `/model`
-   `/usage`

**图 D**档位从每轮思考最少到最多。

Claude Code 为每个模型设定默认档位，/effort status 会显示你的档位。对于范围明确的日常工作，试试 **medium**。当 medium 卡住时，试试 **high**。它每轮的花费比 medium 多，但比换用更大的模型少。对于机械性工作，比如重命名或在多个文件中应用已知模式，使用 **low**。

在 Opus 5.5 上默认是 medium，比 Opus 5 的默认档 high 低一档。档位在不同模型上并不意味着相同的思考量。在给定档位下，Opus 5.5 每轮思考比 Opus 5 更多，在 xhigh 和 max 上尤其明显。所以不要沿用你为 Opus 5 选择的档位。从 medium 开始，把 xhigh 和 max 留给你已测量到收益的工作。

一个粗略理解 effort 定价的方法：假设 high 在一项任务中增加了 20K 思考 token。在 Opus 5.5 上那是 0.40 美元。一个十轮的重试循环，100K 缓存上下文，总共 10K 输出 token，成本大致相同。所以 high 在一项能省下一次重试的任务上就值回票价。在一项 medium 本来第一次就能完成的任务上，它就是浪费。

#### 当 medium 只修好一层时

需要更高 effort 的最明显信号，是一个只修到一层的修复。

假设一个字段在 API handler 中被重命名。在 medium 下，模型更新了 handler，handler 的测试通过了，但客户端仍在发送旧字段。它做了被要求做的事。它只是没有读得足够远，没找到第二个调用方。在 high 下，它在写之前花更多轮读取调用点，并在一次操作中修改两层。

一个检查也能抓住同样的 bug。如果模型能运行一个经过客户端的测试，旧字段在被写入的那一轮就会让该测试失败，即使在 medium 下。所以在提高 effort 之前，先检查模型是否有办法检查自己的工作。一次测试运行花费一轮及其输出。更高的 effort 会给每一轮都增加思考。

如果提高 effort 档位和增加检查都不奏效，那就换用更大的模型。

#### 在会话中途改变 effort

在 Claude Code 中，运行 /effort 加一个档位，例如 /effort high。/effort status 会打印当前档位。你可以在任务中途更改，新档位会应用于下一个请求。

在 Opus 5.5 上使用 API key 或 Claude 订阅时，改变 effort 会保留缓存。你可以为一个困难步骤提高它，然后再降回来，而无需重写对话。在 Amazon Bedrock、Google Cloud 的 Agent Platform 或 Claude apps gateway 上，改变 effort 仍会清除缓存的对话，下一个请求要为全部内容支付缓存写入价格。Opus 5.5 的思考始终开启，所以没有思考设置可以更改。

### 为你的工作选择合适的模型

[模型选择](https://claude.dev/blog/which-claude-model-should-you-build-with/)决定了会话中每个 token 的价格，所以它对账单的影响比 effort 更大。它的影响也更远。每个继承主模型的子智能体也继承它的价格。大多数日子需要三个模型：一个小的用于查找，Opus 5.5 用于你密切监督的工作，一个更大的用于最难的任务。

![三个模型按成本排序，柱状条仅表示成本顺序：Haiku 或 Sonnet 用于查找和子智能体，Opus 5.5 作为日常主力，Fable 5.1 用于最难的工作，各自附有适合的工作类型。](https://claude.dev/media/f08757b9a91bce794fda0b6e3cd0deacede7783ce9db0097a67a47606e6900a4.png)

#### Opus 5.5 作为日常主力

用 Opus 5.5 做你监督的工作：跨几个文件的功能开发、调试，以及带后续修改的代码审查。你会阅读它做了什么，并在它偏离时介入，所以循环保持简短。

#### 升级到 Fable 5.1

**当结果比 token 价格更重要时，升级到 Fable 5.1。** 例如你不会监督的长时间运行、代码库中没有现成模式的问题，以及协调多个子智能体的大型变更。不要等到第三次失败。如果 Opus 5.5 在 xhigh 下两次遇到同一个问题，就切换，问题解决后再切回来。对于交互式工作，Opus 5.5 更合适，因为它延迟更低、成本更少。

Fable 5.1 标价为每百万输入 token 10 美元、每百万输出 50 美元，是 Opus 5.5 价格的 2.5 倍。它的缓存读取为每百万 0.25 美元，仅为 Opus 5.5 费率的 1.25 倍，因为按输入价格的 0.025 倍计费。所以差距在长时间、缓存密集的运行中最小，在写入量大的任务上最大。

在自然的断点切换。缓存属于前一个模型，所以预计在新模型上的第一轮要为整个对话支付写入价格。先运行 /compact，或者用一个简短的书面计划开启新会话，让那一轮更小。运行 [/model](https://code.claude.com/docs/en/model-config) 加别名或模型名来切换。/model 还会把你的选择保存为新会话的默认值，所以困难部分完成后要切回来。

#### 为查找而降级

**为查找而降级到 Sonnet 或 Haiku，而不是为写代码：** 搜索和总结的子智能体、读取日志和测试输出，以及「这个在哪里定义」的问题。对于跨多个文件的机械性编辑，保留 Opus 5.5 并把 effort 设为 low。编辑仍留在写你其余代码的模型上，每轮成本更低。

要把[子智能体](https://code.claude.com/docs/en/sub-agents)放到更小的模型上，在其定义中设置 model: haiku 或 model: sonnet。要把所有子智能体放到同一个模型上，设置 CLAUDE\_CODE\_SUBAGENT\_MODEL 环境变量。子智能体定义中指定的模型会覆盖该变量。没有模型设置的子智能体在你的主模型上运行，除非设置了该变量。

每个子智能体在自己的上下文窗口中运行并交回一份摘要，所以它的文件读取不会进入你的主对话。它仍要为自己的 token 付费，所以模型设置决定了这笔花费的成本。

智能体团队（agent teams）是一项实验性功能，会放大这一点。每个队友是一个独立的 Claude Code 实例，有自己的上下文窗口，并且会持续使用 token 直到退出。我们的[成本文档](https://code.claude.com/docs/en/costs)估计，当队友在计划模式下运行时，一个团队的 token 用量约为标准会话的七倍。保持团队规模小，让每项任务自成一体，并在队友的部分完成后将其关闭。

权衡在于：一个误读搜索结果的小模型，会让主模型去找错误的文件，而主模型要为这段弯路付费。让小模型做那些错误容易被发现的工作，比如查找文件、运行测试和读取日志。

把需要判断的决策留在主模型上。opusplan 别名以另一种方式拆分工作：Opus 在计划模式下做计划，Sonnet 执行计划。这把代码编辑放在 Sonnet 上，与上面的建议相反。在把它设为默认之前，先在你自己的任务上测量。

### 迁移时检查你的提示词

为旧模型写的指令可能让 Opus 5.5 写得更多并重复工具调用。在 Claude Code 中运行 /claude-api prompt-audit，检查你的 Claude Code 设置（例如你的 skills 和 CLAUDE.md 文件）是否存在这些[提示词反模式](https://claude.com/blog/reducing-cost-and-improving-performance-with-claude-platform)。它也会检查你在 Claude Platform 上构建的应用的代码。

我们在一次从 Opus 4.8 到 Opus 5.5 的迁移中测试了这一点，使用一个包含 44 个工单的内部客户支持基准测试，其提示词包含其中若干模式。迁移到 Opus 5.5 并使用 low effort，使该基准测试的成本降低约 18%。运行 prompt-audit 又降低了 9%，比 Opus 4.8 的起点低约 25%。审计移除了让模型写得更多并重复工具调用的仪式性指令：一个强制性的六步流程、一条草稿纸规则、一条验证两次的规则，以及相互矛盾的指令。

这个结果来自一个基准测试，所以把它当作示例，而不是可以预期的数字。运行审计，然后比较一项真实任务前后的 /usage（见 Measure it yourself）。

### 缓存与压缩

Claude Code 为你处理缓存和压缩。你如何运行会话决定了它们能省多少。

#### 缓存如何工作

Claude Code 会缓存请求中重复的部分，例如系统提示词、工具定义，以及此前的对话。

在 Opus 5.5 上，一次缓存读取的成本是新输入 token 的 5%。写入缓存的成本高于一次新读取，按当前定价，五分钟缓存为输入价格的 1.25 倍，一小时缓存为输入价格的两倍。每次命中都会免费重置有效期。

在 Claude Code 中，有效期取决于你的付费方式。在 Claude 订阅上是一小时。在 API key 或云提供商上默认是五分钟，而订阅一旦开始动用用量额度，也会降到五分钟。

在 120K token 上下文时，Opus 5.5 上一次五分钟写入约花费 0.60 美元，一次读取约 0.02 美元。一次写入的成本相当于 25 次读取。在 API key 上，六分钟的咖啡休息会把下一次 0.02 美元的读取变成 0.60 美元的写入。同样大小的一小时写入约花费 0.96 美元，在 API 上你可以支付这个溢价来覆盖一天中的空档。

#### 会话形态与命中率

缓存存储的是一个前缀，所以它只能复用请求中从开头起与上一次匹配的部分。

一个持续进行的会话在每一轮都向对话末尾追加内容，从而保持较高的命中率。任何改变请求较早部分的操作都会降低命中率。改变工具定义会清除整个缓存，而改变系统提示词会从该点起清除缓存，那几乎是全部内容。

在实践中，以下情况预计会发生缓存写入：

-   你暂停的时间超过缓存有效期；
-   你在 Amazon Bedrock、Google Cloud 的 Agent Platform 或网关上改变 effort，在这些地方档位是缓存匹配内容的一部分；
-   你在对话中首次开启 fast mode，这会改变缓存匹配内容的一部分；
-   你连接或断开一个 MCP server，这可能改变每次请求开始时加载的内容；
-   你切换模型，因为新模型从空缓存开始；以及
-   对话被压缩，这会重写缓存所匹配的历史。

所以在会话开始时就把这些设置好，并在它工作期间不要改动。

#### 为什么长会话每轮成本更高

每一轮都会重新发送整个上下文，所以随着上下文增长，一轮的成本也更高，即使缓存是热的。在 20K token 上下文时，一轮的缓存读取在 Opus 5.5 上约花费 0.004 美元。在 150K 时约花费 0.03 美元，在这个大小下 30 轮仅读取就要花 0.90 美元。同样的 30 轮在 20K 时约花费 0.12 美元。在 Claude 4.6 及之后的模型上，更大的上下文窗口不会改变每 token 的价格，所以成本完全来自重新发送对话。

这些上下文中有很多是早前工作的残留：一小时前的堆栈跟踪、一个你已经处理完的文件、一次你已经修复的测试运行的输出。这些内容在每一轮仍会被发送。

#### 压缩、/compact 和 /clear

当会话接近其上下文限制时，Claude Code 会总结较早的历史，让后续轮次发送更少内容。运行 /autocompact 加一个 token 数，可以改变在此之前上下文达到多满。

有两个命令让你自己来做这件事。/clear 清空对话，不产生费用，所以当你转向无关工作时使用它。/compact 保持连续性，花费一次请求。它会读取要总结的对话，你可以说明要保留什么，例如 /compact keep the failing test names and the schema change。

在 150K token 时压缩的大致价格约为 0.25 美元。这包括读取、几千输出 token 的摘要，以及在更短上下文上的一次新缓存写入。之后每一轮在读取上节省约 0.025 美元，所以压缩大约在十轮内回本。在你快完成时做压缩，花费会超过它节省的。

这个价格假设缓存是热的。缓存热时，摘要请求从缓存读取对话，所以在休息前压缩，而不是休息后。在超过缓存有效期的休息之后，同样的 /compact 会再次读取整个对话并把它写回缓存。在五分钟缓存、150K token 时，仅输入就约 0.75 美元。如果你已经走上一条想放弃的路径，改用 /rewind 回到较早的一轮。缓存热时，这会回到一个已经缓存的前缀。

摘要也会丢失细节。在调试会话中途压缩，可能丢掉那条重要的日志行。在自然的断点压缩，当下一步依赖某个具体内容时，在 /compact 指令中说明。

#### 在你输入之前加载的内容

你的 [CLAUDE.md 文件](https://code.claude.com/docs/en/memory)会在每个会话开始时加载到上下文中，所以其中的每一行都是每一轮重新发送内容的一部分。[成本文档](https://code.claude.com/docs/en/costs)建议将其保持在 200 行以内。MCP 工具定义是延迟加载的。开始时只加载工具名称和服务器指令，完整定义在工具被使用时加载。运行 /mcp 查看哪些服务器已连接，并关闭你不使用的那些。

## 自己测量

本文中的数字都是示例。你的代码库、提示词和习惯都不同，所以要在你自己的任务上测量成本。以下是检查方法。

1.  **在会话中运行 [/usage](https://code.claude.com/docs/en/costs)。** /cost 做同样的事。Session 区块显示 token 使用量和按标价估算的美元成本。提示词缓存一行显示你的输入中有多少来自缓存。在 Pro、Max、Team 或 Enterprise 套餐上，同一屏幕会显示你的套餐用量条。美元数字是在你的机器上按标价计算的，所以在订阅上它是你做了多少工作的参考，而不是账单。
2.  **把同一项任务跑两次。** Opus 5.5 需要 Claude Code v2.1.280 或更高版本，所以先运行 `claude update`。从你的待办事项中挑一项，而不是玩具示例。用 /model 在 Opus 5 和 Opus 5.5 之间切换。记录每次运行的轮次、输出 token 和成本。做三到四项任务后再下结论。
3.  **对于团队，使用用量和成本报告。** [Claude Code Analytics API](https://platform.claude.com/docs/en/manage-claude/claude-code-analytics-api) 给出每位用户的估算成本。[Usage and Cost API](https://platform.claude.com/docs/en/manage-claude/usage-cost-api) 按模型以及缓存与非缓存 token 拆分支出。
4.  **试试 effort 阶梯。** 把一项困难任务先在 medium 下运行，再在 high 下运行。把一项机械性任务在 low 下运行。

### 阅读一个会话

在任务结束时检查 /usage 中的三件事。

-   **缓存占比。** 对于长会话它应该很高。如果很低，找找是否有长时间暂停、模型切换、中途连接的 MCP server，或者在云提供商或网关上改变了 effort。提示词缓存一行通常会指出最近一次未命中的可能原因。
-   **输出与输入之比。** 一个小改动却产生大量输出，通常意味着 effort 档位对该任务过高，或者模型在重试。
-   **总输入与对话大小之比。** 如果总量是对话大小的许多倍，说明会话经历了很多轮，值得读一读对话，找出循环在哪里重复了。

作为基准，Claude Code 成本文档给出企业部署的平均值：每位开发者每个活跃日约 13 美元，90% 的用户每个活跃日低于 30 美元。一个成本远高于你自己正常水平的会话值得回顾。

## 请记住

-   范围明确的日常工作使用 medium effort。
-   给模型一种检查自己工作的方式，并在计划模式下开始跨文件的变更。
-   当 medium 卡住时，把 effort 提高到 high。使用 API key 或订阅时，更改会保留你的缓存。在云提供商或网关上，在断点处更改。
-   如果 xhigh 两次遇到同一个问题，切换到 Fable 5.1。解决后再切回来。
-   把搜索和读日志的子智能体放在 Sonnet 或 Haiku 上。代码编辑留在 Opus 5.5 上。
-   让长会话保持推进，这样它的缓存保持热。
-   在无关任务之间使用 /clear，在断点处使用 /compact 并注明要保留什么。
-   **最重要的一点：** 在每个模型上运行一项真实任务，比较 /usage 报告的内容。你自己的数字才是可信的。
