# 有效电商智能体的解剖学指南
过去一年里，我们与电商行业的众多团队合作——包括零售商、市场平台、旅游、娱乐和电信服务商——使用 Claude 构建电商智能体。

这些智能体已投入生产，企业客户在使用后看到了更大的购物车和更高效的卖家运营。它们也共享一个简单的架构：Claude 处于一个智能体循环中，配备一组 Skills（技能）、工具和一套强大的评估（eval）套件。

本文面向构建这类（或其他面向消费者的）智能体的工程师和工程负责人。第 1 部分讲架构，这是你只需决定一次的事。第 2 部分讲延迟与成本。第 3 部分讲生产环境：记忆、安全、评估，以及在组织内推广这项工作。

## 01 架构

一个模型处于标准智能体循环中，用 Skills 覆盖长尾需求，用工具调用你已经在运行的系统。这个决定只需做一次。

### **什么是电商智能体？**

我们将电商智能体定义为一种简化在线商品目录中买卖流程的智能体。

有些智能体面向消费者：它们搜索、比较、替换并组装订单。这可能是一个零售购物车、一份旅行行程、一次移动套餐变更，或为某场演出预留的座位。有些智能体面向企业：它们回答关于销售的问题，运行促销和营销活动，并管理库存和定价。

核心架构是一个模型处于[标准智能体循环](https://www.anthropic.com/engineering/building-effective-agents)中：围绕目标进行推理、探索上下文、通过工具采取行动、通过 Skills 学习流程、提出澄清性问题，并观察结果，直到目标达成。

它前面没有意图路由器来对对话进行分段，后面也没有一组领域特定的智能体。

### **工程上下文**

#### **用 Skills，而不是子智能体**

电商智能体必须覆盖众多品类和意图的广泛能力，这让人很想为每个领域创建一个子智能体。

实践中这被证明并非最优，因为电商对话是一个跨多个意图和轮次、紧密耦合的会话，需要大量共享上下文。

在子智能体架构中，编排器持有购物车或暂存变更、用户偏好以及对话历史。

每次移交给子智能体都是有状态损失的操作，这往往会影响子智能体响应的质量，进而影响整体响应。除此之外，每次移交可能消耗数倍的 token，并增加数秒延迟。

各领域也很少能干净地分离。退货流程可能需要订单历史、当前购物车和商品目录，这意味着按领域划分的子智能体方案要么在各处重复这些访问，要么在任务中途移交。

随着模型变得更智能，它们也能处理更长的上下文、更多的 Skills 和更多的工具，因此当今这些放置规则背后的限制会随着每一代模型而放宽。

相反，[智能体 Skills](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview) 为你提供了类似的按领域模块化和上下文控制，却没有移交的代价，因为技能指令会加载到已经持有完整历史的主智能体中。

在我们对多个企业部署的比较中，带 Skills 的单一智能体在质量上始终优于「一个提示词包打天下」的设计和子智能体设计，而且通常单任务成本和延迟更低。

子智能体真正有价值的地方，是编排器可以将其作为工具调用，用于一个狭窄或自包含、且能受益于自己专属上下文窗口的任务。

一个常见的生产示例是深度研究子智能体：子智能体搜索并阅读文档、编写并运行代码、遍历数据模型，并走进死胡同。所有工作都在一个或多个子智能体内部完成，只有一份精简的答案返回给编排器。

另一个例外是已经拥有自己专用智能体的领域。如果你的药房或金融服务体验运行着一个带有自身合规面的专用智能体，正确的做法可以是移交（hand-off），由该智能体接管任务，通过自己的循环直接与用户协作，直到任务完成。

区别在于对话的所有权。移交让领域智能体成为用户的对话方，而委托则保留编排器，在单个轮次内让领域智能体进进出出，并在每次交互中劣化。

#### **系统提示词还是 Skill：按频率决定**

决定把一组指令放在系统提示词还是 Skill 中的主要因素，是智能体需要它的频率。加载一个 Skill 要花费一个模型轮次，因此智能体在大多数轮次都需要的内容通常放在系统提示词中。

不过，这取决于你的流量分布，以及你的评估所显示的智能体行为。一个好的起点是：任何与你三分之一或更多流量相关的内容——无论是发布前预判的还是生产中观察到的——都放在系统提示词中，其余放在 Skills 中。

如果一个 Skill 可以从你已有的信号中预测出来，例如用户来自哪个页面，我们建议在执行第一次模型调用之前由执行框架（harness）注入它，跳过加载该 Skill 的额外轮次。

关键指令，例如安全和法律规则、品牌约束，以及关键用户事实（如过敏），始终放在系统提示词中。

对电商智能体而言，这意味着商品搜索放在提示词中，因为几乎每个会话都会涉及它，而 Skills 承载长尾功能。

在我们的[参考实现](https://github.com/anthropics/commerce-agents)中，购物智能体的提示词包含事实依据、购物车和结账语义以及展示规则，以下 Skills 覆盖其余部分：search-discovery、purchase-research、planning-goals、customer-care 和 memory-personalization。

商家智能体也以同样方式拆分，其 Skills 为 performance-insights、catalog-listings、inventory-operations、pricing-promotions 和 marketing-campaigns，每个运营领域一个。

### **工程化智能体工具**

我们关于[为智能体编写有效工具](https://www.anthropic.com/engineering/writing-tools-for-agents)的文章涵盖了通用的工具设计。在电商领域，有两点最为重要：

**在核心系统和逻辑之上构建智能体工具。**

一家电商公司已经拥有搜索和排序、购物车、偏好与资料存储、库存系统、促销和营销活动引擎、销售分析等等，每一个都编码了多年调优的逻辑，并能看到模型永远不会看到的信号。

智能体的工具应该调用这些系统，而不是重新实现它们，工具边界正是它们的逻辑结束、模型的判断开始的地方。

例如，当智能体调用 `search_products` 时，结果应当已经排好序到达；它的工作是决定哪些结果服务于用户的目标、展示多少个以及如何展示。

**工具结果就是上下文。**

只返回模型用于推理的字段，丢弃其余部分。每一行搜索结果都带图片 URL 是常见的罪魁祸首。

如有需要，在工具内部重塑原始响应，包括在数据本身不明显时追加下一步操作。

这在错误场景中尤其相关，模型从指令中获益而非错误码。例如，添加错误指令「查询可用性时请包含产品 ID」，而不是一个通用的 403。

#### **UI 组件就是工具**

大多数电商智能体的响应是 UI 组件而非散文，无论是商品轮播、行程、座位图还是图表。这意味着智能体必须输出 schema 而不是文本。

团队有时会先提示模型输出自定义标签，然后在客户端解析。随着界面增长，这种做法会失效，因为：

-   模型对你的标记语言的训练程度不如对工具调用，因此随着嵌套组件增加，可靠性会下降。仅靠提示并不能保证数据格式良好。
-   标签定义位于系统提示词中，因此每个新组件都会膨胀上下文，每次编辑都有在提示词其他地方引入回归的风险。
-   过去的对话最终以只有你的解析器能读的格式存储，因此加载历史意味着要么在客户端解析原始消息，要么以非模型 API 原生格式保留第二份副本。

经得起考验的模式是让每个 UI 组件成为一个工具。模型用类型化参数调用 `present_products`、`present_itinerary` 或 `present_plan_comparison`；你的服务器验证并丰富该调用并发出事件；你的客户端渲染它。

由于这些组件是工具调用，它们已经以原生格式存在于消息数组中，因此重新加载旧对话时无需重新解析。下面以及[参考仓库](https://github.com/anthropics/commerce-agents)中展示了一个展示工具契约的示例。

代价是流式粒度。工具调用的每个顶层参数都会在服务器上缓冲以进行验证，因此即使开启流式，展示工具的子组件也会分步到达。这会影响感知延迟。

要获得 token 级流式，在工具定义上设置 `eager_input_streaming:` true，这会跳过缓冲，同时也跳过服务器端的 schema 保证。

在我们的评估中，在 Claude Sonnet 级及以上的模型上 schema 违规非常罕见，但请将调用包裹在重试中，以应对偶尔漏网的情况。

展示工具还让智能体获得屏幕上内容的记录。当客户说「第一家酒店」或「左边第三个」时，布局就在消息数组中，位于最后一次展示调用的参数里。

为此，参数必须反映渲染后的布局，因此要按 UI 的结构来组织它们，即有序的行和轮播，而不是客户端会重新排列的扁平列表。

## 02 让它又快又便宜

从端到端和感知两个战线攻击延迟，让缓存承担成本。这一切都不应以牺牲智能为代价。

延迟在电商中很重要，而消费者界面是最不宽容的。然而，在智能体式界面上，我们持续看到能推动留存、参与度和购物车规模等指标的是结果的质量。

答案是否相关、任务是否真正完成，相比边际延迟收益，对这些指标更为关键。

因此从两个战线攻击延迟。通过良好的工程最小化端到端延迟，并配合降低感知延迟（因为观看智能体工作的时间会被感知为进展）。

每个用户都有一个延迟预算，下面的技巧让智能体保持在其内，而不牺牲智能。

### **最小化任务完成延迟**

任务完成延迟是各模型轮次上「到最后一个 token 的时间」加上工具处理时间的总和。这给你三个可努力的方向：更少的轮次、更快的工具和更快的 token。这些杠杆有时相互竞争，因此要最小化的是总和，而不是其中任何一个。

#### **更少的轮次**

查询复杂性会增加轮次，这通常不在你的控制范围内。模型智能和相关上下文帮助智能体以更少的轮次完成任务。我们在这一领域的一些关键经验包括：

-   **预先加载可能的上下文。** 如果用户从商品页面打开助手，或商家从营销活动仪表盘打开它，就把该页面的数据放入会话上下文。对话很可能与之相关，从上下文回答不花费额外轮次。
-   **提高模型智能。** 更智能的模型可以减少完成任务的总轮次，因为智能体能更高效地规划并发出工具调用。这通常超过其较慢 token 的劣势。如果你的查询偏复杂，或生产显示每个任务超过约五轮，更智能的模型往往也是更快的那个。具体是哪个取决于你的流量，因此按下文「选择模型」所述进行扫描来选择。
-   **让模型并行调用独立工具。** 电商用例通常需要许多并行操作：搜索多个商品、查询许多政策文档，或从许多销售数据源获取记录。并行工具确保多个独立查询不会消耗额外轮次。提示模型在一个轮次内调用多个工具，并在一条用户消息中以工具结果数组的形式返回结果（参见[并行工具调用文档](https://platform.claude.com/docs/en/agents-and-tools/tool-use/parallel-tool-use)）。

#### **更快的工具**

-   **优化工具自身的后端。** 有时一个工具确实需要扇出——一个带有「获取今日快照」查询的商家智能体通过三个独立调用读取销售、库存和营销活动状态。但我们经常看到工具边界成为拼接缺失后端逻辑的地方：一个可用性检查调用目录获取 SKU、按门店调用库存服务、调用履约服务获取截止时间，然后在工具自己的代码中应用替换规则和自提资格，再作答。这个工具现在被领域知识压得超载，随着规则变化难以保持正确，并承载了本应位于上游系统的逻辑。当你发现自己在工具中编写这种逻辑时，解决办法是一个回答该问题的后端端点，并用一个智能体工具调用它。
-   **尽早派发工具。** 工具参数像其他 token 一样从模型流出，因此执行框架可以在每个工具的参数完成时执行其调用，并在模型仍在流式输出其他并行工具或内容块时处理它。我们见过这将数秒的间隔缩短到几百毫秒，而 [Claude Agent SDK](https://code.claude.com/docs/en/agent-sdk/overview) 默认就这样做。你应该提示模型先发出最慢的调用，以获得最大的延迟收益。

### **感知延迟**

感知延迟是用户感到屏幕做出反应之前的时间。它在面向消费者的用例中尤为关键，因为任何交易摩擦都会影响结账率和收入。有两种技巧可以在不触碰模型的情况下缩短它：

-   **组件形成时即流式输出。** 一个渲染后的电商响应通常有 500–700 个输出 token，不流式的话就是五秒以上的加载圈。将展示工具的每个参数在流式输出时发送给客户端，并逐步渲染页面。
-   **展示工作过程。** 当智能体在收集上下文时，为每个步骤用平实的语言渲染一行简短进度（例如「正在寻找水边酒店」）。你可以从工具已有的参数（如商品搜索的查询）构建它，或添加一个额外的 user\_facing\_message 参数工具，提示模型编写该行文字。

上面两个面板运行相同的智能体、相同的工具和提示词；只有执行框架不同。总时间大致相同，但用户看到内容的时间差别很大。

### **提示词缓存**

提示词缓存是你最大的成本削减候选，而电商流量非常适合它。缓存的输入 token 读取成本是新鲜 token 的十分之一，虽然缓存写入带有约 1.25 倍溢价，但缓存前缀在第二次使用时就能收回成本。在流量巨大的面向消费者应用中，你有独特的机会使用最便宜的默认 5 分钟缓存过期来达到非常高的缓存水平。

我们见过的最好的电商部署运行在 90–99% 的缓存命中率，这就是你从一开始就应设计的范围。我们的经验表明，在约 100k token 时，缓存 token 读取也快约 1.5 到 2 倍，token 越多，扩展大致呈线性。

缓存基于前缀。请求从缓存读取直到第一个与之前请求不同的字节，因此重要的不仅是上下文里有什么，还有它的顺序。把请求视为三个段，按变化频率排序：

-   **全局**：大部分系统提示词和工具定义，在每个会话中完全相同。这是你最热的缓存，在规模下很可能不会过期。保持它在各轮次和会话间字节一致，并在其末尾放置一个缓存断点。
-   **会话**：每用户上下文和对话历史，跨会话不同但在单个会话内保持稳定。这一段位于全局段之后。
-   **易变**：会话内任何变化的内容，例如当前时间或当前页面。把它放在请求的最末尾，要么作为最新用户轮次中的标记块，要么在支持[对话中途系统消息](https://platform.claude.com/docs/en/build-with-claude/mid-conversation-system-messages)的模型上，作为追加到消息数组的系统角色消息。我们见到的最常见错误是把时间戳或当前页面放在系统提示词顶部，这会静默地在每个请求上破坏缓存。

这里有两个实现细节要记住。第一，Skills 应作为工具结果加载，而不是追加到系统提示词。技能正文随后落入对话前缀，并随之被缓存。

第二，在每一轮中向前滚动你的断点：一个请求允许有限数量的断点，因此把最新的一个移到每个用户轮次的末尾。这样每一轮都能从缓存读取累积的历史，包括搜索响应等长工具结果。

### **选择模型及其配置**

[模型规模和努力程度设置](https://claude.com/resources/articles/claude-model-and-effort-level-in-claude-code)是同一个权衡——智能对延迟和成本——你应该通过测量来选择两者：

1.  **选定你的指标和下限。** 选定你业务所依赖的质量指标（任务完成、答案相关性、有依据的准确性）、你不会低于的评估分数，以及你的 p50 和 p99 延迟与成本预算。
2.  **扫描。** 在你考虑的所有模型和努力程度上运行整个评估套件。我们建议商家智能体从 Opus 开始，其任务偏重分析；消费者智能体从 Sonnet 开始，那里延迟权重更大。如果你有生产流量，按真实查询组合对结果加权。然后让数字决定。有时 Opus 在推动购物车任务上的提升足以证明其相对 Sonnet 的成本差，有时则不然。**‍**
3.  **仔细解读结果。** 有两件事经常让团队意外。第一，提示词是针对某个模型调优的，因此用一个提示词跑的扫描可能在其他并非为其编写的模型上表现不佳。较小的模型通常需要当前模型自行推断的指令，而较大的模型会严格遵循较小模型所忽略的指令。在排除任何候选之前，对每个候选的失败案例进行几轮迭代是廉价的一步。第二，更智能的配置有时在延迟上胜出（最常见于 p90 和 p99），尽管 token 更慢，因为它更好地规划工具调用，在最复杂的请求上需要更少的轮次。

衡量每个已完成任务的成本，而不是每次模型调用的成本，因为一个需要更多轮次或更频繁失败的更便宜模型并不更便宜。当结果接近，且成本符合你的单任务经济性和延迟时，选择智能。质量是推动采用和留存的因素，并为未来 6 个月随着模型变好而构建留出空间。

## 03 在生产环境中运行

记忆、安全、评估，以及在组织内推广这项工作：让智能体通过生产并保持在那里的要素。

最后，我们谈谈让智能体通过生产的要素：记忆、安全、评估，以及在组织内推广这项工作。

### **能跨越会话的记忆**

你与客户的关系和互动很重要。记忆让智能体从上次对话中断的地方继续，而不是从零开始。一位在三月提到坚果过敏的购物者不应该在六月重复它，一位每周一查看同样三个营销活动的商家不应该每次都说出它们的名字。长期记忆——应该跨会话保留的事实——是一个你构建的系统，它有三个部分：事实如何存储、如何写入以及如何读取。

#### **存储记忆**

记忆属于你的系统，而不是模型。

当资料很小且智能体是唯一读者时，一个扁平的 markdown 资料文件就行。大多数生产电商智能体会超出它，实际的替代品是你已经在运营的数据库。一个事实是一条小的类型化记录：一个键（如 shoe\_size、default\_store、preferred\_report\_cadence）、一个短值、一个类别，以及它来自的会话。有些键你预先决定，每个用户都有；其余由提取器发现。数据库随着存储增长仍可查询，让你能在特定属性上构建确定性行为，并连接到你已有的用户数据。

对于面向商家的智能体，按人而不是按账户来键控记忆。商家登录名通常在操作员之间共享，因此每个操作员需要自己的资料，读取必须尊重该操作员的权限：门店经理的智能体不应回忆起区域经理陈述的事实。

在电商领域，智能体记忆持有个人数据。值得记住的事实往往是最受监管的，而不同司法管辖区的规则不同。把记忆当作数据处理设计问题，而不仅仅是存储问题。实践中这意味着四件事：

-   **决定你愿意持有哪些类型的记忆**。在写入路径上强制执行，用一个每次保存都必须经过的验证器，而不是仅在提示词中。
-   **给用户一种查看、更正和删除已存储内容的方式。** 将删除接入你的账户删除和数据请求流程。
-   **设置保留期。** 几年前的偏好很可能已过时，因此保留期有助于保持记忆事实的新鲜。
-   **记忆应该是一个按部署的开关**。这让无法承担这些义务的地区可以在没有它的情况下运行。

#### **写入记忆**

异步写入记忆。在每个轮次结束时，或在长会话中每隔几轮，一个位于单独线程或进程中的智能体读取对话，并在存储中创建、更新或删除事实，随着会话进行保持自己的工作上下文。

它不给对话增加任何延迟，并在我们的内部电商记忆评估套件上实现了高出 13% 的事实召回率。

显而易见的替代方案——一个智能体调用来保存事实的工具——对延迟敏感的电商智能体来说是错误的选择。每次保存都是面向用户轮次内的工具调用，除非整个存储在上下文中，否则保存需要先读取以更新或去重，这本身就是一轮。

它还在每一轮给智能体多一个决策，而在我们的评估中，这种对注意力的竞争表现为遗漏的记忆。

分离提取器还让你能精确地提示它。它只读取用户和助手的文本，从不读取工具结果，因此商品描述或评论不能成为关于用户的事实。它的提示词说明什么算作事实——陈述的尺码、饮食限制、履约偏好、商家常用的物化视图——以及什么不算，例如来自商品列表的任何内容或一次性细节。

#### **读取记忆**

分三层读取记忆。

由于记忆是每用户上下文，它全部进入会话段，位于全局缓存断点之下。

### **安全：执行位于执行框架中**

提示词是安全行为的起点，但在电商中它不能是安全被执行的地方。失败是财务性的且往往不可逆，而一条提示词规则距离被跳过只差一次注入或一个坏样本。下面的每条规则都在代码中执行，在消费者和商家智能体上都一样，并且只定义一次，以便每个运行时共享它。

#### **模型暂存；由人或策略应用**

没有任何模型工具调用会移动资金或改变业务。下单、支付、退款、价格变更和营销活动启动最终都落在执行框架控制而非模型控制的动作上。

在消费者侧这是结构性的：结账工具渲染购物车并带有一个下单按钮，而智能体调用的后端接口根本没有扣款方法。

在商家侧，每个写入工具产生一个带有服务器生成 ID 的暂存变更，而 `apply_change` 只对通过真实界面批准的 ID 成功：操作员门户中的按钮、CLI 中的确认，或当智能体运行在 Managed Agents 上时平台自己的工具批准提示。

护栏在应用时针对当前限制重新检查，而不是变更暂存时生效的限制。无论界面如何，形态都一样：模型最危险的动作是提议，而批准通过你业务中已用于该类变更的 maker-checker 流程进行。

#### **写入和渲染只接受服务器签发的 ID**

执行框架保留一份服务器已交给模型的每个 ID 的按会话记录，该记录是任何写入或渲染唯一接受的键。

购物车只接受服务器返回给本会话的商品 ID，商家工具只接受智能体实际读取过的商品列表和营销活动 ID。以任何其他方式到达的 ID——幻觉的、用户粘贴的、植入评论中的——在后端看到它之前就被拒绝。

同样的规则覆盖 UI。展示工具接受 ID，服务器自己填充商品、订单或变更记录，因此卡片只渲染服务器自己填充的记录。

它也覆盖委托：商家分析子智能体读取数据，但从不添加到智能体可写入的 ID 集合中。

对于费用、披露和其他受监管内容，模型选择披露哪个商品，服务器从批准的文案中提供每一个字。相同的费用字段在商家智能体的保护列表上，因此柜台两侧都不能更改或转述它们，而评估逐字节检查渲染后的字符串。

#### **有上限的交易必须对重复请求保持**

大多数电商界面限制一个用户能买多少件商品——用于票务分配、促销定价或欺诈控制——而智能体会以人类点击按钮从未有过的方式重试、改写和并行化。

因此上限按写入后的行状态执行，这样第二次「再加两个」不能叠加超过它，并且一个会话的购物车写入被串行化，因此单个轮次中的并行工具调用不能组合起来超过它。

商家变更以同样方式对照价格变动、折扣深度、补货规模和营销活动预算的上限进行检查，外加一份任何变更都不得触碰的保护字段列表。该规则可以推广：对结果状态而非请求执行每个限制，并按会话串行化写入。

#### **第三方内容经过净化**

在电商中，大部分上下文是由不是你的人写的——卖家、评论者、竞争对手——因此每次后端读取都是不可信输入，并经过同一个净化器。

每个由第三方编写的工具结果，例如商品列表、评论、政策、卖家消息和存储的记忆，在模型看到之前都经过净化并包裹在带有固定标签的围栏中。

净化器剥离控制字符和双向字符，移除任何模仿围栏标记的内容，化解模仿对话轮次或工具调用的文本，并限制大小，旨在阻止恶意商品列表冒充系统或填满上下文。

提示词承载契约的另一半：围栏文本是要报告的材料，绝不是要据以行动的内容。

### **评估：交付一个非确定性系统**

从小的提示词更改到新工具，任何东西都可能以难以预测的方式改变智能体行为，而你交付的变更往往不是导致回归的那个。评估是你在部署前发现这一点的方式。我们之前关于[智能体评估](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)的博客文章涵盖了通用实践。本节涵盖电商智能体的具体内容。

**评估快照，而不是对话**

模型的 API 是无状态的，因此智能体输出是系统提示词、工具和消息数组的函数。这意味着电商对话能到达的任何状态都可以直接构造。因此创建一个评估用例意味着构造测试状态、追加测试用户消息，并让智能体从那里运行。

然后对结果评分：最终状态和渲染后的响应，包括最后一次写入的参数。在大多数情况下，我们建议不要对智能体到达那里的路径评分，因为这类测试用例脆弱且限制性强。

模拟用户评估，即第二个模型扮演用户、评判者对整个对话评分，是糟糕的测量工具。两个非确定性系统交互需要更大的样本、每次试验成本更高、更难评判，并产生难以归因的失败。它们对发现覆盖缺口和对智能体做总体感觉检查有用，因此用它们来发现用例，然后把每个用例写成快照。

#### **针对艰难条件下的行为进行评估**

大多数团队未能正确测试注入的状态。一个用例应该编码失败的前提条件，而不仅仅是任务。如果一个行为只在繁忙的第一轮之后（带有若干工具调用）才出现，或在会话早期出现矛盾之后才出现，那么从干净状态开始的用例会在每个配置上通过，提供不了有意义的数据。

我们观察到大多数套件偏重这类干净状态用例，因此确保你的一部分用例从长、混乱或矛盾的历史开始。

#### **覆盖不同类型的电商智能体评估**

有效的评估需要测试期望和不期望的行为。

对每个正向用例，写出其负向对应物：每个「应该提供」对应一个「应该拒绝」，每个「应该直接做」对应一个「应该询问」。缺失的负向用例是我们在套件中发现的最常见缺口。

针对以下内容评估：

-   **构成你大部分流量的核心请求**，因为这里的失败影响大多数会话。这些包括简单查询、多约束请求、商品和套餐问题，以及多意图消息。对于问题，检查每个价格、可用性和属性都能追溯到返回的数据，并且智能体在数据缺失时说明而不是编造。
-   **依赖上下文的请求**，例如对屏幕上内容的引用、从早期轮次延续的约束，以及对现有购物车的写入。评估记忆也归入这一类。检查记忆是否被提取、检索并改变了答案。
-   **安全和品牌用例**，这里的失败会损失金钱或信任。这些包括尝试注入、尝试读取另一个用户的数据，以及受监管语言（逐字节检查）。将注入拆分为两个用例：用户编写的注入，指令来自用户自己的消息；以及数据平面注入，它被植入商品名称、评论或通过工具结果到达的网页片段中。
-   **界面评估**，确保渲染正确的组件、遵守商品上限，并且面向用户的文本中没有内部标识符。也要测试超时和空结果。
-   **同时属于多个能力的请求。** 一位操作员问「如果我把这个降价 15%，我有足够库存覆盖需求吗？」这同时是定价问题和库存问题。正确答案会暂存降价并附上库存预测；错误答案只做其中一个而跳过另一个。按能力编写的评估不会捕捉到这一点，因为每个只评自己那一半。为需要两个相邻能力一起的请求编写用例，并对答案的两半都评分。

#### **与领域专家一起编写评估并使用真实事件**

与亲眼看到失败的领域专家合作——例如产品、法务、商家运营、客户关怀和品类管理团队的成员——来设计测试用例。真实失败能造出最好的评估，每个用户流程 50-100 个评估用例是一个好的起点。

确保用例多样，如上所述。生产对话记录是获取新用例的绝佳来源，尤其是棘手的那些。编码智能体擅长生成额外用例和对抗性变体。[参考仓库](https://github.com/anthropics/commerce-agents)包含一个 Claude Code 插件，带有一个按我们推荐方法构建的评估编写技能。

#### **在大型组织中交付**

在一家电商企业里，智能体由许多工程团队构建。搜索、结账、定价、营销技术、客户关怀和商品目录平台各自拥有智能体依赖的系统，各自按自己的节奏交付，并且各自都想添加或更改一个工具、一个 Skill 或一条提示词规则。

与服务不同，智能体没有严格的模块边界保护其他部分：定价团队所做的更改与结账共享同一个上下文窗口。

诱人的解决办法是把系统拆成许多子智能体，每个业务单元一个。如第 1 部分所述，出于质量原因我们不建议这样做。相反，我们概述降低多团队协作风险的流程：

-   **所有权跟随系统。** 每个 Skill 和工具都有单一的所有者团队。例如，定价拥有促销工具和定价 Skill，客户关怀拥有订单和退货工具以及 customer-care Skill。共享提示词有一个平台级所有者负责公共部分，领域所有者负责领域特定部分。
-   **变更随其用例一起交付，CI 运行为其选定的一组用例。** 贡献一个 Skill 的团队也贡献其用例，包括负向用例和针对相邻 Skill 的边界用例。在每个拉取请求（PR）上运行完整套件太慢、太贵，无法持续，因此从中构建一个 CI 集。该集将包含一组核心用例，涵盖最高流量请求和每个安全用例。在此基础上，运行变更所触及内容的用例。对于一个 Skill，这意味着它自己的用例和邻居的边界用例。对于一个工具，是每个调用它的用例。对于共享提示词，是完整评估套件，因为一切都读取系统提示词。我们建议对若干次试验的通过率设门，并对缓存命中率和每轮成本设门。每晚和每次发布前运行完整套件也是好做法。跨团队回归在这些运行中被捕获。
-   **智能体也应该在发布日历之内。** 它是一个部署单元，因此一个坏变更会同时到达每个用户。先将提示词和 Skill 变更推广到金丝雀队列，保留一个无需部署即可关闭某个 Skill 的开关，并像冻结其他系统一样在高峰时段前冻结智能体。

关于这一安排的人力方面，参见[构建有效的人机团队](https://claude.com/resources/articles/building-effective-human-agent-teams)。

## 04 展望未来

本文描述的大部分内容与模型无关。工具调用你已经在运行的系统，Skills 编码你已经在遵循的流程，评估是你的产品需求文档写成测试，执行框架执行你会对任何客户端执行的政策。模型会持续改进，当更好的模型发布时，我们描述的架构会将其作为配置变更加一次评估扫描来采纳。其他一切继续工作。

思考你的产品界面路线图也很重要。架构会比聊天面板更长久。同一个智能体可以通过语音工作，也可以在用户询问之前主动对票价下降采取行动。对于一个已经拥有评估和工具的团队，那些是展示层项目。更远一些，你店面的一部分流量将来自代表用户购物的智能体。让你自己的智能体保持在边界内的同样的来源、暂存和批准规则，正是让你能安全地向那些智能体开放工具的东西。

电商一直奖励让购买过程尽可能顺畅。智能体让这容易得多。查看[完整参考实现](https://github.com/anthropics/commerce-agents)，包含消费者和商家智能体，以及零售、旅游、电信和娱乐的可运行示例。
