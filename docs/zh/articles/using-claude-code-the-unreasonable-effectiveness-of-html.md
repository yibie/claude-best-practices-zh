# 使用 Claude Code：HTML 的惊人效力

Markdown 已成为智能体与人类沟通时使用的主流文件格式。它简单、可移植、具备一定的富文本能力，而且易于编辑。Claude 甚至已经相当擅长在 Markdown 文件里用 ASCII 字符绘制示意图。

但随着智能体变得越来越强大，我发现 Markdown 逐渐成为一种限制性越来越强的格式。具体来说，我发现自己很难读完一个超过一百行的 Markdown 文件；我希望用 Claude 生成更丰富的可视化、颜色和图表；我也希望能更轻松地分享这些成果。

而且我越来越不亲自编辑这些文件，而是把它们当作规格说明和参考文件来使用。当我确实需要修改时，通常也是提示 Claude 去改，这就消除了 Markdown 最大的优势之一。

于是，我开始更倾向于用 HTML 而不是 Markdown 作为输出格式，并且越来越多地看到 Claude Code 团队的其他成员也在采用这种模式。在本文中，我将分享我们团队为何以及如何使用 HTML 来产出更丰富、更易读的 Claude Code 输出。如果你想跟着实践，也可以直接使用这些针对常见用例的 [HTML 文件模板](https://thariqs.github.io/html-effectiveness/#code-review)。

## 为什么使用 HTML？

对于我现在用 Claude Code 所做的这类工作，有几方面因素让 HTML 比 Markdown 更合适，包括那些需要或涉及以下内容的任务：

### 信息密度

![单个 HTML 文件可以承载的八类信息：表格、设计、插图、代码、交互、工作流、空间布局和图像。](https://claude.dev/media/2adbcc628e8e032bd17f932e46641d462fb8409cc534d8383eff51b578b75c88.png)

与 Markdown 相比，HTML 能传达丰富得多的信息。它当然可以做简单的文档结构，比如标题和格式，但它还能表示各种其他信息，例如：

-   用表格呈现的表格数据
-   用 CSS 呈现的设计数据
-   用 SVG 呈现的插图
-   用 script 标签呈现的代码片段
-   用 HTML 元素配合 JavaScript + CSS 实现的交互
-   用 SVG 和 HTML 呈现的工作流
-   用绝对定位和 canvas 呈现的空间数据
-   用 image 标签呈现的图像

在我看来，几乎不存在 Claude 能读到、而你无法用 HTML 高效表示的信息集合。这使得 HTML 成为模型向你传达深度信息、以及你审阅这些信息的一种极其高效的方式。

我发现，在无法做到这一点时，模型在 Markdown 里可能会做一些效率更低的事情，比如 ASCII 图表，或者我最喜欢的——用 unicode 字符来估算颜色。

![在 Markdown 代码块中以 ASCII 形式渲染的调色板：十六进制色码旁边是用阴影字符块代替的色块。](https://claude.dev/media/518a129fc56fba5dedb9a99265322c521997219a152349f2bdb2fd6a8a307425.png)

**图 A** 当 Markdown 是唯一选项时，调色板看起来是什么样子。

### 视觉清晰度与易读性

![同一个支付服务规格说明的两种呈现。作为 Markdown：一个 240 行的标题与段落文件，需要不断滚动。作为 HTML：一个带有概览、API 和上线（rollout）标签页的页面，包含一个延迟目标提示框、一张按区域划分的流量图表，以及一份待解决问题列表。](https://claude.dev/media/ba99cabcc8425efafb8240517951542dd40c825d1b902bc4ccdae9cef3981a22.png)

随着 Claude 能够处理更复杂的工作，它也能写出越来越长的规格说明和计划。我发现我实际上通常不会读完超过 100 行的 Markdown 文件，我也完全没法让我组织里的其他人去读。

但 HTML 文档要易读得多，因为 Claude 可以在视觉上组织结构，用标签页、插图和链接让它非常适合浏览。它甚至可以做到移动端响应式，让你根据设备形态以不同方式阅读。

### 易于分享

Markdown 文件相当难以分享，因为大多数浏览器无法原生地良好渲染它们。你往往不得不把它们作为附件添加到邮件或消息中。

而只要上传 HTML 文件，你就可以[轻松分享链接](https://claude.com/resources/articles/artifacts-in-claude-code)。你的同事可以在任何他们方便的地方打开它，并轻松引用。

如果你的规格说明、报告或 PR 说明是 HTML 格式，那么有人真正去读它的可能性会高得多。

### 双向交互

![一个 checkout-button.html 页面，带有用于悬停动画时长、缩放和阴影模糊的滑块，一个弹簧缓动开关，以及一个“复制为提示词”按钮；复制出的值被粘贴到 Claude Code 中，后者据此更新 CheckoutButton.tsx。](https://claude.dev/media/6bd2866c31e53bad12b2d70bf74e4ad0de4067f464ecc6b33bc00d5d7ae4a8e6.png)

HTML 还能让你[与文档交互](https://x.com/trq212/status/2017024445244924382)；例如，你可能会要求它添加滑块或旋钮来调整设计，或者让你调整算法中的不同选项以观察结果。你还可以要求它让你把这些改动复制成提示词，再粘贴回 Claude Code。

在有用的时候，这能让你针对正在处理的具体问题创建单独的编辑环境。

### 数据摄取

使用 Claude Code 而不是 Claude.ai 或 [Claude Design](https://claude.com/product/design) 来生成 HTML 文件的最大原因之一，是 Claude Code 能够摄取的所有上下文。例如，在写这篇文章时，我让 Claude Code 通读我的代码文件夹，找出我生成的所有 HTML 文件，对它们进行分组和分类，然后生成一个 HTML 文件，用图表表示每一种类型。你在本文中看到的图表正是这一过程的直接产物。

除了文件系统，Claude Code 还能利用你的 MCP（如 Slack、Linear 等）、你的网页浏览器（借助 [Claude in Chrome](https://claude.com/claude-in-chrome)）以及你的 git 历史来找到额外的上下文。

## 入门

有一点值得注意：你不需要做太多事情就能让 Claude 生成这样的 HTML。你只需提示它“_生成一个 HTML 文件_”或“_生成一个 HTML artifact_”。关键在于知道你想让这个 artifact 做什么，以及你可能如何使用它。随着时间推移，[围绕反复出现的模式构建一个 Skill](https://claude.dev/blog/lessons-from-building-claude-code-how-we-use-skills/) 可能是合理的，但从头开始提示是一个很好的方式，可以让你感受它在不同用例中的运作方式。

## 用例

为了让这种方法更具体，下面列出了一些[示例用例](https://thariqs.github.io/html-effectiveness/)，在这些场景中我认为使用 HTML 文件比 Markdown 更合理。你也可以在[这里](https://github.com/anthropics/html-effectiveness)查看这些用例的 GitHub 画廊。

### 规格说明、规划与探索

HTML 是 Claude 深入探究问题的丰富载体。当我开始处理一个问题时，我不再只做一份简单的 Markdown 计划，而是预期会形成一张由 HTML 文件构成的网。例如，我可能会先让 Claude Code 头脑风暴，并针对不同选项做一些探索。然后我会让它深入展开其中一个，也许为这类界面做一些线框图或示例。最后，当我感觉不错时，我会让它写一份实现计划。当我对计划满意时，我会新建一个会话，把所有这些文件传进去让它实现。

在验证时，我也会让验证智能体读取这些文件，它就能对所需内容有更广泛的上下文。

![一个标题为“Pick an approach”的 HTML 页面，将防抖搜索的三种方案以卡片 A、B、C 并排展示，每张卡片都包含代码和优缺点；B 被选中。](https://claude.dev/media/d4f2739204ee8c10555643038abdbf5783144dc4da089051100d49efd93da15f.png)

**图 B** 探索：在一个页面中并排展示多种方案及其权衡。

**示例提示词：**

-   _我不确定引导屏幕该往哪个方向做。生成 6 个截然不同的方案——在布局、语气和密度上有所变化——把它们以网格形式排布在一个 HTML 文件中，方便我并排比较。为每个方案标注它所做出的权衡。_
-   _在一个 HTML 文件中创建一份详尽的实现计划，务必包含一些线框图，展示数据流，并添加我可能想审阅的重要代码片段。让它易于阅读和消化。_

**适用于：**

-   探索在代码中实现某事的其他方式
-   同时试验多种视觉设计

### 代码审查与理解

代码在 Markdown 文件中可能难以阅读，但借助 HTML，我们可以渲染差异、注释、流程图和模块。用 HTML 来理解智能体编写的代码、审查代码，或向审阅你代码的人解释一个 PR。。

![PR #482 的 HTML 代码审查，展示 lib/session.ts 的差异，带有附加到特定行的边注，标记为 blocking、nit 和 nice。](https://claude.dev/media/73ee6f9cc3027b599d59b0c54dce81a62bc02fc9d1c22474d6909f22c68752fe.png)

**图 C** 代码审查：渲染出的差异，带有按严重程度标记的边注。

**示例提示词：**

_通过创建一个描述该 PR 的 HTML artifact 来帮我审查这个 PR。我对流式/背压逻辑不太熟悉，所以请重点关注那部分。渲染实际的差异，并附上行内边注，按严重程度对发现进行颜色编码，以及任何其他有助于清晰传达概念的内容。_

**适用于：**

-   创建 PR
-   审查 PR
-   理解代码中的某个主题

### 设计与原型

Claude Design 基于 HTML，因为 HTML 在设计方面极具表现力，即使你的最终界面不是 HTML。Claude 可以用 HTML 勾勒出设计，然后用你选择的语言编写，无论是 React、Swift 等。

你还可以为交互制作原型，比如动画、操作等。可以考虑让 Claude 制作滑块、旋钮等，来精确调出你想要的效果。

![一个 Web 应用的设计 token 页面：带名称和十六进制色码的色块、一套字号层级、一套间距层级，以及主要、次要和幽灵按钮。](https://claude.dev/media/e63f469938d9231d5081a2a5b0a654d1dfe1e714cca971b71e81781255a99904.png)

**图 D** 设计：按实际外观渲染的 token 和组件。

**示例提示词：**

_我想为一个新的结账按钮制作原型，点击时它会播放动画，然后迅速变成紫色。创建一个 HTML 文件，包含若干滑块和选项，让我尝试这个动画的不同方案，并给我一个复制按钮，用来复制效果好的参数。_

**适用于：**

-   创建设计系统 artifact
-   调整组件
-   可视化组件库
-   为动画制作原型

### 报告、研究与学习

Claude Code 非常擅长跨多个数据源综合信息，并将其转化为易于阅读的报告。你可以提示 Claude 搜索你的 Slack、代码库、git 历史或互联网，并用它生成易于阅读的报告。

你可以将其组装成一份长 HTML 文档、一个交互式讲解页面，甚至一个幻灯片/演示文稿。让 Claude 用 SVG 绘制图表来帮助可视化。

![一个标题为“How rate limiting works”的讲解页面，包含目录、TL;DR、四个可折叠的请求路径步骤（链接到源码行）、一份已读文件列表，以及带标签页的配置片段。](https://claude.dev/media/8190e029a7a24a3b92f02ec719cd7a76c6d21323abe0a878e34b1bf883dad609.png)

**图 E** 报告：一个带导航、可折叠步骤和带标签页片段的讲解页面。

**示例提示词：**

_我不理解我们的限流器实际上是如何工作的。阅读相关代码，生成一个单独的 HTML 讲解页面：一张令牌桶流程的图表、3–4 个带注释的关键代码片段，以及底部一个“注意事项”部分。针对只读一遍的人进行优化。_

**适用于：**

-   撰写功能总结
-   生成讲解材料
-   起草每周状态报告
-   创建事故报告
-   制作 SVG 插图、流程图和技术图表

### 自定义编辑界面

有时很难纯粹在文本框里描述你想要什么。对于这种用例，我常常让 Claude 为我正在处理的具体内容构建一个一次性的编辑器：不是产品，也不是可复用的工具，而是一个单独的 HTML 文件，专为这一份数据量身定制。

诀窍始终是以导出收尾：一个“复制为 JSON”或“复制为提示词”按钮，把我在 UI 中所做的一切转回可以粘贴到 Claude Code 或提交到文件中的内容。你始终参与其中，但这个反馈循环变得紧密得多。

![一个渲染为表单的 flags.yaml 编辑器，开关分组在 streaming 和 billing 下，某个开关上带有依赖警告，还有一个“复制差异”按钮；剪贴板中只有两个被改动的键，以及一段可粘贴到 Claude 的提示词。](https://claude.dev/media/b8592b3b6ec79401ee1f46ac6aa9da9b96fb4b6ecd630c03eacf255211da9067.png)

**示例提示词：**

-   _我需要重新排定这 30 个 Linear 工单的优先级。给我做一个 HTML 文件，把每个工单做成可拖拽的卡片，分布在 Now / Next / Later / Cut 四列中。按你最好的猜测预先排序。添加一个“复制为 Markdown”按钮，导出最终排序，并为每个分组附上一行理由。_
-   _这是我们的功能开关配置。为它构建一个基于表单的编辑器，按区域对开关分组，显示它们之间的依赖关系，如果我要启用某个前置条件未开启的开关就警告我。添加一个“复制差异”按钮，只给我改动的键。_
-   _我正在调优这个系统提示词。做一个并排编辑器：左侧是可编辑的提示词，变量槽位高亮显示；右侧是三个示例输入，实时重新渲染填充后的模板。添加一个字符/token 计数器和一个复制按钮。_

**适用于：**

-   重新排序、分诊或分桶任何内容（工单、测试用例、反馈）
-   编辑结构化配置（功能开关、环境变量、带约束的 JSON/YAML）
-   带实时预览地调优提示词、模板或文案
-   整理数据集——批准/拒绝行、为示例打标签、导出所选内容
-   为文档、转录稿或差异添加注释并导出注释
-   挑选难以用文本表达的值：颜色、缓动曲线、裁剪区域、cron 调度、正则表达式

## 常见问题

以下是我最常被问到的关于在 Claude Code 中使用 HTML 的问题，并附上我最终形成的实用日常习惯：

### 这样不是效率更低吗？

虽然 Markdown 通常使用的 token 更少，但我发现 HTML 增加的表达力，以及我阅读它的可能性大大提高，意味着我总体上得到更好的输出。借助 Opus 4.7 的 1MM 上下文窗口，增加的 token 用量在上下文窗口中并不明显。

### 那你现在什么时候还用 Markdown？

老实说，我几乎在所有事情上都已经完全不用 Markdown 了，不过我大概属于 HTML 极端主义者那一端。

### 这就是你替代规划的方式吗？

我发现，与其只有一份计划，我倾向于为计划的不同部分/阶段准备几个不同的 HTML 文件。例如，我可能会用 HTML 做一份实现计划，然后为 UI 的探索再做另一个文件，最后再做一个列出每个设计的 HTML 组件。我倾向于把这些文件保留下来，作为未来的参考，也用于验证。

## 与 Claude 保持同步

以上所有内容都说明，我使用 HTML 而不是 Markdown 的真正原因是，它让我感觉与 Claude 更加同步。随着 Claude 承担更多工作，我注意到自己读计划越来越不仔细，我想要一种方式持续关注它的选择，而不是直接把它们交出去。HTML 恰好就是这样的方式。我现在感觉自己比以往任何时候都更与 Claude 保持同步。
