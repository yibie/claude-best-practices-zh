# Anthropic 如何保障其 AI 原生软件开发生命周期的安全
在 Anthropic，代码量和部署速度都呈指数级增长。我们的软件工程师平均每季度交付的代码量是 2021 至 2025 年期间的 8 倍。

我们的审查、监控和其他安全流程需要与这一加快的节奏同步扩展。否则，它就会变成瓶颈的成因（[阿姆达尔定律](https://en.wikipedia.org/wiki/Amdahl%27s_law)）。

我们的软件开发流程也发生了翻天覆地的变化。Claude 已从编码助手演变为主要的创建者和审查者。[Claude 编写](https://www.anthropic.com/institute/recursive-self-improvement)了如今合并进我们代码库的约 80% 的代码。

超过一半的代码由我们内部版本的 [Claude Tag](https://www.anthropic.com/news/introducing-claude-tag) 合并，而人类工程师则专注于指导、设定意图并负责最终审批。

这意味着我们的安全团队必须防御一个快速扩张的攻击面，并加固一个以非确定性、不断演进的智能体为核心的开发周期。在本文中，我将介绍保障软件开发生命周期（SDLC）安全的策略。

_（本文旨在与我们近期发布的[面向智能体的零信任](https://claude.com/resources/articles/zero-trust-for-ai-agents)框架结合使用；本文中的一切内容在实现时都采用了该框架中的安全设计理念。）_

我们针对的威胁是具体的：被攻陷或被提示词注入的智能体引入恶意变更；供应链和依赖投毒被智能体当作可信输入摄入；以及如今以更高数量出现的、更为人熟知的各类应用漏洞。下文中的每一项控制措施都至少对应其中一种威胁。

为了在不显著拖慢开发速度的前提下实现这一目标，我们部署了几项总体策略，包括：

-   将安全左移，并与代码开发阶段完全集成；
-   使用严格的访问和身份边界来限制影响范围；
-   在生产前后结合自动化的确定性审查和智能体式审查；以及
-   在杠杆效应最高的环节引入人工介入。

在本文中，我们将介绍我们在软件开发生命周期特定阶段实施的安全流程，以及这些流程背后的核心原则。这些原则更具持久性，因为随着模型能力演进，安全团队必须重新审视、并且往往要重新设计其流程。

## **不断演进的软件开发生命周期**



我们的开发团队已经[详细介绍了](https://claude.com/resources/articles/running-an-ai-native-engineering-org)其软件开发生命周期的变化，因此在深入每个阶段之前，这里先做一个简要的入门介绍。

从高层来看，我们的软件开发生命周期被压缩了。它更多由原型和内部采用（dogfooding）驱动，而非漫长的规划周期。创意来自组织的各个角落，传统角色（前端、后端、设计）之间的界限变得模糊。审查和审批仍然有人类介入，但也由智能体循环驱动。

尽管每个阶段都已被 [Claude Code](https://claude.com/product/claude-code) 和 Claude Tag 从根本上改变和加速，但各阶段的名称和目的对于来自更传统组织的开发者来说并不陌生。这些是自然的关卡，我们也将其作为 AI 原生 SDLC 安全流程的一部分。

## **规划**

我们最早的安全自动化之一，是一个由 Claude Opus 驱动的简单 PSR（项目安全审查）Web 应用。它摄入项目设计文档，并依据 [MITRE ATT&CK 框架](https://attack.mitre.org/)进行分析，以识别潜在漏洞并提出缓解建议。

我们通过将其连接到一个内部知识索引，显著增强了该系统，该索引提供了跨组织范围政策、过往决策和相关系统的更深入上下文。



Anthropic 内部自动化 PSR 的流程。

这让我们更好地理解潜在风险，同时也捕获了 PSR 中缺失的信息。这一项实现就节省了 AppSec 团队的大部分时间。一旦我们确信 Claude 在风险评估上是准确的，我们就允许团队在 Claude 判定发布风险足够低的情况下自行批准其项目。

这里我们可以看到对 AI 原生 SDLC 的首批关键适应之一。PSR 最初的设计目的是在漫长且昂贵的编码过程之前发现安全问题。在这一阶段发现问题可以节省数月的重新开发。

如今，重大功能的多个原型可以在数小时内创建出来，这使得详细的架构审查成为一个不那么关键的关卡。将我们的 PSR 应用连接到知识索引，可以捕获否则可能被遗漏的上下文，而不会造成不必要的减速。创建一个 Claude Code skill 使 Claude 能够进一步扩展，并在任何存在上下文的地方捕获额外的上下文。

**持久原则**：将安全智能体连接到组织上下文。随着规划周期被压缩，将这些智能体带到上下文已经存在的地方——聊天线程、过往审查、代码库——要比在可能不再需要详细文档的阶段强制要求详细文档有效得多。无论哪种方式，智能体都需要代码本身之外的上下文。

## **编码**

AI 原生工程组织中的安全专业人员拥有一个新的杠杆：他们可以直接塑造代码的创建方式，帮助从源头预防漏洞。

过去，团队观察到反复出现的漏洞并制定安全编码指南来应对，但这些指南难以执行，也很少被标准化。

在 Anthropic，这些指南被编码在 CLAUDE.md 文件和对组织范围 Skills 的引用中，因此代码在生成的那一刻就遵循这些最佳实践。这是作为闭环的一部分来完成的。一旦智能体发现某一类 bug，相关文件就会被更新，以防止它在未来的代码中再次出现。

当然，这并不意味着所有代码都是完美的。我们的团队从一个 CLAUDE.md 文件开始，指示智能体在打开 PR 之前作为最后一步运行 [/security-review](https://support.claude.com/en/articles/11932705-automated-security-reviews-in-claude-code)。这个普遍可用的命令是我们团队内部审查工作流的产品化版本，它会查找潜在攻击者可控输入的进入点，扫描可疑链接，然后验证其发现。

如今，这些审查在 Claude 生成代码的同时进行。一旦安装了[安全指导插件](https://code.claude.com/docs/en/security-guidance)，Claude 就会在生成过程中审查对话和代码。它会在生成代码的同一会话中提出安全改进建议并处理常见漏洞。

PR 阶段的其他提示会推动内部非技术团队将其应用托管在我们的低代码应用托管平台上，从而避免传统上困扰安全团队的影子 IT。

我们的一些客户选择将 [/security-review](https://support.claude.com/en/articles/11932705-automated-security-reviews-in-claude-code) 与 PreToolUse 钩子（hooks）集成，使这一步成为更严格的关卡。这同样有效，但我们的团队选择在周期的测试/CI 阶段纳入我们严格的代码审查关卡。

除了塑造和审查代码之外，限制影响范围是我们在这一阶段的主要关注点之一。我们通过围绕身份设置硬边界（更多内容见监控部分）以及让开发人员在虚拟机上编码来实现这一点。

将我们的编码迁移到远程 VM 是一个相对无痛的转变，与仅使用笔记本电脑相比，它为我们提供了更强的控制力和可见性。这些 VM 上的智能体流量采用出站允许列表。

当智能体读取可能携带提示词注入载荷的不可信输入时，这些严格的出站控制尤为重要。被注入的指令无法到达互联网上的任意目的地：数据外泄路径被限制在一小组受监控的服务中。

这里你同样可以看到对 AI 原生 SDLC 的明确适应。远程编码过去主要用于保护知识产权，而如今我们看到更成熟的 AI 编码团队采用这些环境作为限制智能体的一种手段。

**持久原则**：在 AI 原生工程组织中，左移意味着闭合漏洞发现与更新指令之间的循环，以定制 Claude 生成代码的方式。限制影响范围（最小代理原则）以及智能体在适当情况下通过硬边界可以访问的内容。

## **测试（CI）**

根据我的经验，在 AI 原生转型过程中，测试或 CI 阶段很快就会成为工程团队最痛苦的瓶颈。在 Anthropic，一旦大多数开发人员都在使用智能体式编码工具并同时运行多个智能体，团队很快就意识到，他们的推进速度只能与人类审查代码的速度一样快。

让我们明确一点：人类问责仍然是我们流程的核心。我们所做的是通过结合自动化的智能体式审查和确定性审查来加速审查过程，同时将人工审查保留给受监管或真正关键的代码。

历史上，人工代码审查一直被视为标准，然而[实证证据](https://link.springer.com/chapter/10.1007/978-3-642-36563-8_14)表明它并不完美。安全漏洞经常随世界各地的软件一起发布。我们的审查流程能够审查更多代码并捕获特别复杂的问题，有助于降低这些风险。

随着我们通过要求智能体为其发现的有效性编写证明而对发现结果建立信心，获得实质性审查评论的 PR 占比[已从 16% 增长到 54%](https://claude.com/resources/articles/code-review)。我们还确定，过去 claude.ai 事件背后约[三分之一的 bug 本可以被](https://www.anthropic.com/institute/recursive-self-improvement)我们现在已实施的自动化流程捕获。

并非只有我们一家组织发现了这一点。[Intercom 已分享](https://www.intercom.com/blog/ai-is-approving-our-pull-requests-heres-how-we-made-it-safe/)其自动批准了 19% 的 PR。部署量翻了一番，而由破坏性代码变更导致的停机时间下降了 35%。CircleCI 在构建 Chunk（一个基于 Claude 的自主智能体，用于解决 CI/CD 维护问题并在人类看到之前[验证其自身的修复](https://claude.com/customers/circleci)）时得出了类似的结论。该方法使智能体任务转化为已完成拉取请求的速率翻了一番。

在 Anthropic，当一个 PR 被打开时，多个智能体会自动审查它。每个审查智能体都被设计和限定为特定、狭窄的焦点，并利用 RAG 获取围绕过往事件的额外上下文和记忆。

这比一个巨型提示词或超级安全智能体有效得多，原因有几个：

-   它们不共享偏见和盲点
-   如果其中一个被攻陷或犯错，可以被其他审查者捕获
-   精力不会在多个焦点领域上被摊得太薄

需要明确的是，智能体并非在无人监督的情况下将代码合并到生产环境。我们按风险对代码库进行分层，并对哪些部分自动化做出审慎决策。整个代码库都有严格的人工审批流程。

对于由 Claude 审查和合并的代码，人类问责仍然是核心。每次批准都会记录其背后的信号和推理，并按风险加权抽样由人工审查。另一轮测试聚焦于诸如「用户 A 永远无法读取用户 B 的数据」这类不变量，并触发额外的人工审查。我们还将智能体式扫描与 SAST 工具结合，后者直接在 PR 上发布结果。

大多数扫描方法，无论是智能体式还是确定性，都是基于用量计费的。成本会随着代码吞吐量的增加而增加，团队需要决定适合自身的覆盖水平。

在 Anthropic，我们接受这里的成本会随着代码速度的提升而增长，但预计单位成本会下降。如今的模型在编码方面比几年前的所有模型都好得多，我们预计这一模式将持续下去。

**持久原则**：自动化审查是一种不同类型的风险，需要以不同方式控制（通过多个关卡和具有独立上下文窗口的智能体）。人类保持在循环中，但根据代码库的性质，可能处于生命周期中的不同位置。

> 「当 CI 确实出现故障时，Claude Tag 充当我们应对 CI/CD 故障的第一响应者。」

## **部署（CD）**

Anthropic 维护着一个稳健的预发布环境，我们在其中执行常见的安全最佳实践，例如针对重大发布的外部渗透测试，以及定期的 DAST 扫描，以捕获静态扫描遗漏或无法看到的逻辑 bug。

与其他 SDLC 阶段一样，AI 为安全团队带来了新的挑战和解决方案。一方面，到达这一阶段的漏洞更少。另一方面，幸存下来的漏洞属于最隐蔽、最难捕获的那一类。

再加上更大数量的代码被更频繁地交付，定期动态测试似乎不再那么动态了。

好消息是，AI 模型在能够捕获更大比例此类复杂漏洞的多步骤、跨组件推理方面表现更好。例如，今年二月，我们披露 Claude 发现并帮助修复了超过 [500 个高危 OSS 漏洞](https://www.anthropic.com/research/zero-days)。

在 Anthropic，我们正在预发布环境中实施持续的 AI 驱动 DAST 扫描。这些扫描在系统层面查找两个或多个服务之间的假设不成立时的漏洞。如今有许多供应商提供这些能力。

**持久原则**：动态测试应与部署节奏相匹配。

## **监控**

任何优秀的安全团队都知道，代码推送到生产环境并不意味着工作结束。我们可以假设任何漏洞都会被日益复杂的攻击者迅速识别。

我们的安全团队在这里实施了标准实践项目，例如[公开漏洞赏金计划](https://hackerone.com/anthropic)、红队模拟攻击，以及针对我们的依赖、密钥、供应链、云态势和容器的定期漏洞扫描。

Claude 在这些方面发挥着重要作用，但我们将重点关注因 AI 原生 SDLC 而对我们监控工作带来的较大变化：告警分诊和代码迁移。

当 Anthropic 触发告警时，Claude 会开始：

-   审查生产日志
-   对 bug 进行根因分析；
-   撰写事后复盘；以及在某些情况下
-   编写修复该 bug 的代码变更。

这个智能体不能做的是自动部署修复。它是一个单用途的系统账户智能体，拥有三项权限：它可以编写新文档、在公司频道中发帖，以及访问生产日志。

修复必须来自一个独立的智能体-人工审查系统。原因归结为管理身份、权限和硬边界：在将代码推送到生产环境时，限制影响范围很重要。分离智能体至关重要，因为一个（或多个）智能体充当对另一个的检查。

这对 CISO 来说也是一个重要的教训，也是我不得不通过惨痛教训才学到的。在考虑智能体的硬边界时，你需要将其对其他智能体的访问权限也纳入其中。

在一次模型升级之后，事件响应智能体主动通过 Slack 联系了另一个 Claude 实例。它要求那个能够编写代码的智能体推送修复。**这按设计在人工审查关卡被捕获了**，但这次经历教会我们，要围绕访问和操作来划定边界，而不是围绕模型的指令或我们认为模型能做什么。如今在 Anthropic，Slack 上的智能体间通信已是常态，我们对[智能体身份模型](https://claude.com/resources/articles/agent-identity-access-model)进行了大量思考。

第二个重大变化是我们的团队如何处理迁移。每个安全工程团队都经历过这样的时刻：他们意识到需要进行代码迁移，以修复公司运营方式中的某些系统性缺陷。过去，CISO 需要开始游说，并请求各部门连续多个季度提供一小部分工程资源来修复它。

迁移的经济成本已经下降，跨公司协调的成本也同样下降。Claude [在数天内自动化了迁移过程，涉及数万行代码](https://claude.com/resources/articles/ai-code-migration)。

**持久原则**：为每个智能体赋予一个单用途身份，并授予其完成工作所需的最低权限。如果你确实让智能体进行协调，就让它们通过与人类相同的渠道进行。

## **治理**

我们已经自动化了许多安全流程，但人类仍然是确保安全软件开发生命周期不可或缺的一部分。但我们的注意力不再集中在审查代码和 bug 报告上，而是集中在 Claude Tag、循环和仪表板上。

这凸显了强有力治理的重要性。如果一个 skill 过时了、一个已发现的 bug 类别从未回到 CLAUDE.md 中，或者一个智能体的决策从未被抽样，整个结构就会退化。我们通过以下方式避免这种情况：

-   **按风险对代码库进行分层**，然后基于该级别自动化审查。
-   **对所有新的 AI 审查者采用影子模式**。新智能体发布评论供人工批准，直到赢得信任。我们的团队还会对它们进行「红队」测试，尝试插入恶意变更。
-   **抽样**一定比例的所有自动批准。
-   **关注我们的生命体征**。我们维护并密切监控一个仪表板，汇总每个安全流程和工作流的关键指标。
-   **将每个智能体操作路由到 SIEM**。每次自动批准、工具调用和智能体间消息都会连同其使用的信号一起记录，并进入我们的 SIEM，因此任何决策事后都可归因、可审计。我们使用这些数据，并将这些智能体视为一种新型内部威胁，当它们行为偏离对齐时发出告警。

**持久原则**：安全工程师的工作从监控 bug 演变为监控循环。

_关于这些控制措施背后的评估框架，请参阅 [CISO 的智能体式 AI 指南](https://claude.com/resources/articles/ciso-guide-to-agentic-ai)。_

## **在模型演进过程中保持 AI SDLC 的安全**

软件开发生命周期及其加固手段的演进速度之快，怎么强调都不为过。模型能力每月都在进步，既带来新的挑战，也带来新的解决方案。

今天不太可行或不太经济可行的，很可能很快就会变得可行。对你的团队来说，正确的问题不是「我们负担得起扫描所有内容吗？」而是「如果扫描几乎免费，我们会运行什么？」为此做好规划。
