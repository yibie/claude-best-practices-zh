# 多智能体协调模式：五种方法及适用场景

在之前的一篇文章中，我们探讨了多智能体系统何时能带来价值、何时单个智能体是更好的选择。本文面向的是已经做出这一判断、现在需要决定哪种协调模式适合自身问题的团队。

我们看到过不少团队根据哪种模式听起来更高级来选择，而不是根据哪种模式适合手头的问题。我们建议从可能奏效的最简单模式开始，观察它在哪些地方吃力，再由此演进。本文考察五种模式的机制与局限：

-   **生成器-验证器（Generator-verifier）**，适用于有明确评估标准、对质量要求严苛的输出
-   **编排器-子智能体（Orchestrator-subagent）**，适用于任务分解清晰、子任务边界明确的情况
-   **智能体团队（Agent teams）**，适用于可并行、相互独立、长时间运行的子任务
-   **消息总线（Message bus）**，适用于事件驱动、智能体生态不断扩张的流水线
-   **共享状态（Shared state）**，适用于智能体在彼此发现的基础上协作推进的工作

## 模式 1：生成器-验证器

这是最简单的多智能体模式，也是部署最广泛的模式之一。我们在上一篇文章中将其介绍为验证子智能体模式，这里采用更宽泛的「生成器-验证器」表述，因为生成器不必是编排器。

### 工作原理



‍

生成器接收任务并产出初始输出，将其交给验证器评估。验证器检查输出是否满足所需标准，要么接受其完成，要么带反馈拒绝。若被拒绝，反馈会被送回生成器，生成器据此产出修订后的尝试。该循环持续进行，直到验证器接受输出或达到最大迭代次数。

### 适用场景

设想一个为客户工单生成邮件回复的支持系统。生成器利用产品文档和工单上下文产出初始回复。验证器对照知识库检查准确性，依据品牌指南评估语气，并确认回复回应了提出的每个问题。未通过的检查会带着明确指出问题的反馈返回生成器，例如某项功能被错误归到某个定价层级，或某个工单问题未获答复。

当输出质量至关重要且评估标准可以明确表达时，使用此模式。它适用于代码生成（一个智能体写代码，另一个编写并运行测试）、事实核查、基于评分标准的评分、合规验证，以及任何错误输出的代价高于额外一轮生成的领域。

### 局限

验证器的水平取决于其标准。如果只告诉验证器检查输出是否「好」而不给出进一步标准，它就会对生成器的输出一路放行。团队最常犯的失败，是在未定义「验证」含义的情况下就实现了这个循环，从而制造出质量控制的假象而无其实质。（我们在上一篇文章中讨论过这个「早期胜利」问题。）

该模式还假设生成与验证是可分离的技能。如果评估一个创意方案与生成它同样困难，验证器可能无法可靠地发现问题。

最后，迭代循环可能停滞。如果生成器无法回应验证器的反馈，系统就会来回震荡而无法收敛。设置最大迭代上限并配备兜底策略（升级给人类、返回带说明的最佳尝试）可以防止其变成无限循环。

## 模式 2：编排器-子智能体

层级结构定义了这种模式。一个智能体充当团队负责人，负责规划工作、分派任务并综合结果。子智能体承担具体职责并回报。

### 工作原理



主智能体接收任务并决定如何着手。它可能直接处理部分子任务，同时将其他子任务分派给子智能体。子智能体完成工作并返回结果，由编排器综合为最终输出。

[Claude Code](https://claude.com/product/claude-code) 就采用这种模式。主智能体自己编写代码、编辑文件、运行命令，在需要搜索大型代码库或调查独立问题时，在后台分派子智能体，使工作在结果陆续返回的同时继续进行。每个子智能体在自己的上下文窗口中运行，并返回提炼后的发现。这让编排器的上下文专注于主要任务，同时探索并行进行。

### 适用场景

设想一个自动化代码审查系统。当拉取请求（PR）到达时，系统需要检查安全漏洞、验证测试覆盖率、评估代码风格并评价架构一致性。每项检查彼此独立，需要不同的上下文，并产出清晰的输出。编排器将每项检查分派给专门的子智能体，收集结果并综合为统一的审查意见。

当任务分解清晰且子任务之间相互依赖极少时，使用此模式。编排器保持对整体目标的一致视角，而子智能体专注于具体职责。

### 局限

编排器会成为信息瓶颈。参见[何时将子智能体收回主智能体循环](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop)。当某个子智能体发现了与另一个子智能体工作相关的内容时，该信息必须经由编排器回传。如果安全子智能体发现了一个影响架构子智能体分析的认证缺陷，编排器必须识别出这一依赖关系并恰当地转发信息。经过几次这样的交接后，关键细节往往被丢失或概括掉。

顺序执行也限制了吞吐量。除非显式并行化，子智能体一个接一个运行，这意味着系统承担了多智能体的 token 成本，却没有获得速度上的收益。

## 模式 3：智能体团队

当工作可分解为能够长时间独立推进的并行子任务时，编排器-子智能体模式可能变得不必要地受限。

### 工作原理



协调器将多个工作智能体作为独立进程启动。团队成员从共享队列中领取任务，在多个步骤中自主工作，并发出完成信号。

与编排器-子智能体的区别在于工作者的持久性。编排器为一个边界明确的子任务启动子智能体，子智能体返回结果后即终止。团队成员则在多次任务分配中持续存活，积累上下文和领域专长，从而随时间推移提升表现。协调器分配工作并收集结果，但不会在任务之间重置工作者。

### 适用场景

设想将大型代码库从一个框架迁移到另一个框架。团队成员可以独立迁移每个服务，各自拥有依赖、测试套件和部署配置。协调器将每个服务分配给一个团队成员，每个团队成员自主完成迁移：依赖更新、代码修改、测试修复、验证。协调器收集已完成的迁移，并在整个系统上运行集成测试。

当子任务相互独立且受益于持续的多步骤工作时，使用此模式。每个团队成员会积累关于其领域的上下文，而不是每次分派都从头开始。

### 局限

独立性是关键要求。与编排器-子智能体不同——在那里编排器可以在子智能体之间居中协调并转发信息——团队成员自主运行，无法轻易共享中间发现。如果一个团队成员的工作影响另一个，双方都不知情，其输出可能相互冲突。

完成检测也更困难。由于团队成员自主工作且时长不定，协调器必须处理部分完成的情况：一个团队成员两分钟就完成，另一个却要二十分钟。共享资源会加剧这两个问题。当多个团队成员操作同一代码库、数据库或文件系统时，两个团队成员可能编辑同一文件或做出不兼容的更改。该模式需要仔细的任务划分和冲突解决机制。

## 模式 4：消息总线

随着智能体数量增加、交互模式变得复杂，直接协调变得难以管理。消息总线引入一个共享通信层，智能体在其中发布和订阅事件。

### 工作原理



智能体通过两个原语交互：发布和订阅。智能体订阅自己关心的话题，路由器投递匹配的消息。具备新能力的新智能体可以直接开始接收相关工作，而无需重新连接现有连接。

### 适用场景

一个安全运营自动化系统展示了该模式的优势所在。告警从多个来源到达，分诊智能体按严重程度和类型对每条告警分类，将高严重程度的网络告警路由给网络调查智能体，将凭据相关告警路由给身份分析智能体。每个调查智能体可能发布富化请求，由上下文收集智能体满足。发现结果流向响应协调智能体，由其决定适当的行动。

这条流水线适合消息总线，因为事件从一个阶段流向下一阶段，团队可以随着威胁类别的演变添加新的智能体类型，并且团队可以独立开发和部署智能体。

当工作流由事件涌现而非预定顺序决定，且智能体生态很可能扩张时，使用此模式处理事件驱动的流水线。

### 局限

事件驱动通信的灵活性使追踪（trace）更加困难。当一条告警在五个智能体之间触发一连串事件时，理解发生了什么需要细致的日志记录和关联。调试比跟踪编排器的顺序决策更难。

路由准确性同样关键。如果路由器错误分类或丢弃了事件，系统会静默失败——什么都不处理，但也从不崩溃。基于 LLM 的路由器提供了语义上的灵活性，但也引入了自身的失败模式。



前几种模式中的编排器、团队负责人和消息路由器都集中管理信息流。共享状态移除了中间人，让智能体通过一个所有智能体都能直接读写的持久化存储来协调。

### 工作原理

智能体自主运行，读写共享的数据库、文件系统或文档。没有中央协调器。智能体检查存储中的相关信息，对发现的内容采取行动，并将自己的发现写回。工作通常始于一个初始化步骤向存储中写入问题或数据集，终于某个终止条件被满足：时间限制、收敛阈值，或某个指定智能体判定存储中已包含足够的答案。

### 适用场景

设想一个研究综合系统，多个智能体调查一个复杂问题的不同方面。一个探索学术文献，一个分析行业报告，第三个查阅专利申请，第四个监测新闻报道。每个智能体的发现都可能为其他智能体的调查提供线索。学术文献智能体可能发现一位关键研究者，而行业智能体应更仔细地考察其所在公司。

有了共享状态，发现直接进入存储。行业智能体可以立即看到学术智能体的发现，无需等待协调器转发信息。智能体在彼此的工作基础上推进，共享存储成为一个不断演进的知识库。共享状态还消除了协调器这一单点故障。任何一个智能体停止，其他智能体仍继续读写。在编排器和消息总线系统中，协调器或路由器故障会使一切停摆。

### 局限

没有显式协调，智能体可能重复工作或采取相互矛盾的路径。两个智能体可能独立调查同一条线索。智能体交互产生的是系统行为而非自上而下的设计，这使结果的可预测性降低。

更棘手的失败模式是反应式循环。例如，智能体 A 写入一条发现，智能体 B 读取后写入一条后续内容，智能体 A 看到后续内容又作出回应。系统持续在无法收敛的工作上消耗 token。重复工作和并发写入有已知的工程解决方案（加锁、版本控制、分区）。反应式循环是行为问题，需要一等公民的终止条件：时间预算、收敛阈值（连续 N 个周期没有新发现），或一个专门负责判断存储中是否已有足够答案的指定智能体。把终止当作事后考虑的系统，往往会无限循环，或在某个智能体上下文填满时任意停止。

## 在模式之间选择与演进

正确的模式取决于关于系统的几个结构性问题。在上一篇文章中，我们主张以上下文为中心的分解，即按每个智能体需要什么上下文来划分工作，而不是按它做哪类工作来划分。这一原则在这里同样适用。这些模式的差异在于它们如何管理上下文边界和信息流。

### 编排器-子智能体 vs. 智能体团队



两者都涉及协调器向其他智能体分派工作。问题在于工作者需要维持其上下文多久。

-   **选择编排器-子智能体**，当子任务短小、聚焦且产出清晰输出时。代码审查系统在此适用，因为每项检查运行其分析、生成报告，并在一次边界明确的调用内返回。子智能体无需跨多个周期携带上下文。
-   **选择[智能体团队](https://claude.dev/blog/safely-scaling-multi-agent-teams-with-fable-5-2/)**，当子任务受益于持续的多步骤工作时。代码库迁移在此适用，因为每个团队成员会对其分配的服务形成真正的熟悉度：依赖图、测试模式、部署配置。这种积累的上下文以一次性分派无法复制的方式提升表现。

当子智能体需要在多次调用之间保留状态时，智能体团队是更合适的选择。

### 编排器-子智能体 vs. 消息总线



两者都能处理多步骤工作流。问题在于工作流结构有多可预测。

-   **选择编排器-子智能体**，当步骤顺序事先已知时。代码审查系统遵循固定流水线：接收 PR、运行检查、综合结果。
-   **选择消息总线**，当工作流由事件涌现且可能因发现的内容而变化时。安全运营系统无法预测会到达哪些告警，或它们需要哪些调查路径。可能出现需要新处理方式的新告警类型。消息总线通过将事件路由给有能力的智能体而非遵循预定顺序，来适应这种可变性。

随着编排器中积累越来越多处理各种情况的条件逻辑，消息总线使这种路由变得显式且可扩展。

### 智能体团队 vs. 共享状态



两者都涉及智能体自主工作。问题在于智能体是否需要彼此的发现。

-   **选择智能体团队**，当智能体在不相互交互的独立分区上工作时。代码库迁移在此适用，因为每个团队成员处理其服务，协调器在最后合并结果。
-   **选择共享状态**，当智能体的工作是协作性的、发现应实时在它们之间流动时。研究综合系统更匹配，因为学术智能体对一位关键研究者的发现会立即与行业智能体的调查相关。

一旦团队成员需要彼此通信，而不仅仅是共享最终结果，共享状态会让这更自然。

### 消息总线 vs. 共享状态



两者都支持复杂的多智能体协调。问题在于工作是作为离散事件流动，还是累积成共享知识库。

-   **选择消息总线**，当智能体在流水线中对事件作出反应时。安全运营系统逐阶段处理告警，每个事件在完成前触发下一个。该模式在将事件路由给有能力的智能体方面很高效。
-   **选择共享状态**，当智能体在随时间累积的发现基础上推进时。研究综合系统持续收集知识。智能体反复回到存储，查看他人发现了什么并调整自己的调查。

消息总线仍有路由器，这意味着有一个中央组件决定事件去向。共享状态是去中心化的。如果消除单点故障是优先事项，共享状态能更彻底地提供这一点。

如果消息总线系统中的智能体发布事件是为了共享发现而非触发动作，共享状态更合适。

## 入门建议

生产系统常常组合多种模式。一种常见的混合方式是用编排器-子智能体处理整体工作流，用共享状态处理协作密集的子任务。另一种是用消息总线进行事件路由，用智能体团队风格的工作者处理每种事件类型。这些模式是构建块，而非互斥的选择。

下表总结了每种模式的适用场景。

| 情况 | 模式 |
| --- | --- |
| 质量至关重要、评估标准明确 | 生成器-验证器 |
| 任务分解清晰、子任务边界明确 | 编排器-子智能体 |
| 并行工作负载、独立的长时程子任务 | 智能体团队 |
| 事件驱动流水线、智能体生态不断扩张 | 消息总线 |
| 协作研究、智能体共享发现 | 共享状态 |
| 要求无单点故障 | 共享状态 |

对大多数用例，我们建议从编排器-子智能体开始。它以最少的协调开销处理最广泛的问题。观察它在哪些地方吃力，然后在具体需求明确时向其他模式演进。
