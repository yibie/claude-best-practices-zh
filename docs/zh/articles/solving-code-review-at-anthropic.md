# Claude Code 团队如何进行代码审查
我们之前说过，Claude Code 自身约 90% 的代码由 Claude 编写。那么，面对这样的产出规模，我们如何审查代码？现在还有人读代码吗？如果出了问题，谁来发现？

本文介绍 Claude Code 团队的代码审查流程及其演变过程。从六月到九月，合并进 Claude Code 代码库的拉取请求（PR）数量翻了一倍多，而需要回滚的比例下降了 40% 以上。

我们并没有取消审查。但我们把大部分阅读工作交给了机器，把优化目标放在人的时间与注意力上，并大力投入让撤销错误变得快速而简单。

## 重新思考代码审查的目的

当智能体编写代码时，变更数量会快速上升。在 Anthropic 的 monorepo 中，每天落地的变更从今年[五月的约 2,500 个增长到九月的 30,000 多个](https://www.anthropic.com/engineering/redesigning-source-control)。

Claude Code 位于独立于 monorepo 的自己的代码库中，但也承受着巨大压力。以这样的速度交付时，逐行的人工代码审查极其困难，甚至不可能。

代码审查承担两项职责：

1.  在代码发布前发现并修复问题
2.  在团队内建立共享上下文和对代码库的理解

本文主要关注发现和修复问题，但最后我们会回到第二项职责。

我们认为，「有没有人读过这段代码？」并不能准确代表「这次变更可能出什么问题，哪项检查——自动的还是人工的——才是发现它的正确方式？」

追问这个问题也改变了审查发生的*时机*。以前，审查是道路尽头的关卡：写代码、开 PR、等同事。现在，审查持续进行，更像是写作时的拼写检查。大多数变更在请人查看之前，已经至少被 Claude 审查并修复过一次。这能抓住大多数常规错误，把团队的注意力留给更高层次的问题和审视。

## 稀缺资源：人的时间与注意力

我们希望把人的时间和注意力留给只有人类才能解决的问题，并确保自动检查抓住其余问题。以我们当前的变更速度，人类仍有大量工作要做，团队几乎每天都会遇到新的、前所未有的挑战。

人的时间涵盖审查成本的两端：人们花在审查上的时间，以及花在修复坏代码造成的问题上的时间。如果削减前者只是让时间出现在后者，那就没有帮助。

因此目标是：Claude Code 各代码库（CLI、桌面端和 Web 应用、移动应用）中的大多数拉取请求，在最多只有一个人参与的情况下合并（这个人可以是作者），同时回滚率或事故率不上升。为了衡量人的时间，我们追踪每个 PR 的人工批准数（中位数和第 95 百分位）、人工评论数，以及 PR 等待某人的时长。回滚率和事故率是护栏：如果它们上升，我们就没有节省人的时间，只是把它转移了。

### 1. 在任何人查看之前先验证工作

现在大多数审查发生在 PR 存在之前。我们给 Claude 一些它可以运行的东西——比如测试、构建，或一张用来与设计稿对比的截图——并要求它展示输出，而不是只说完成了。然后一个子智能体用全新的上下文审查 diff。这两个习惯都来自我们的[最佳实践指南](https://code.claude.com/docs/en/best-practices)。

在开 PR 之前，我们中许多人还会运行几个[内部 Skills（技能）](https://claude.dev/blog/lessons-from-building-claude-code-how-we-use-skills/)：一个搜寻 bug，一个简化 diff，一个端到端检查行为。UI 变更还会对照我们的设计规范进行检查。

Claude Code 的创造者 Boris Cherny 曾说，给 Claude 一种验证自身工作的方式，是获得好结果[大概最重要的一件事](https://x.com/bcherny/status/2007179861115511237)。他估计这能让最终结果好上两到三倍，并写道：「验证在每个领域看起来都不同。它可能简单到运行一条 bash 命令，或运行一套测试，或在浏览器或手机模拟器中测试应用。」

**当自动审查器反复标记同一件事时，我们从源头修复：**在 Skill 中、用 lint 规则，或更新指导性文件，例如：

-   `CLAUDE.md` 告诉 Claude 项目是什么：技术栈、约定、目标和非目标。每次审查都会加载它，所以在大型代码库中我们保持它简短，并从那里指向其他文档。审查器还会标记违反其中约定的代码，以及让其中某一行过时的变更。
-   `REVIEW.md` 由代码所有者编写，告诉审查器在他们负责的那部分代码中什么重要。我们会单独检查审查器是否真的遵循它。好的 `REVIEW.md` 都很短。它们说明在该仓库中失败是什么样子（对文档来说是「它在撒谎」，对配置来说是「它路由错了」），限制吹毛求疵的数量，列出要跳过的路径，并要求以文件和行号作为证据，而不是从名字猜测。它们还要求摘要以计数开头，并在没有需要修复的问题时明确说明。

### 2. 每个拉取请求都进行 AI 审查

每个拉取请求在有人查看之前都会先得到 Claude 的审查。它对照整个仓库和 PR 声明的意图阅读 diff，并追问：这次变更解决了它的问题吗，契合系统吗，还是破坏了别的东西？

在 bug 修复上，它会寻找根本原因。公开版本 [Code Review for Claude Code](https://code.claude.com/docs/en/code-review) 现已在 Team 和 Enterprise 计划上正式可用，`/code-review` 可在本地运行一个更轻量的版本。

当我们[推出研究预览版](https://claude.com/resources/articles/code-review)时，获得实质性审查评论的内部 PR 比例从 16% 上升到 54%。大多数超过 1,000 行的 PR 会得到发现项，而大多数小 PR 则干净通过。管理员可将每个仓库设为 Quick、Standard 或 Deep。在漏掉一个 bug 的代价高于额外审查时间的地方，Deep 值得一用。

**发现项在人工审查之前会由其他智能体验证。**多个智能体同时寻找 bug。然后另一组智能体对每个发现项投票，只有足够多的智能体同意它是真的，才会被发布。仅涉及风格、诊断或清理的发现项会被丢弃。我们在自己的 PR 上对这些过滤器做了 A/B 测试后才保留它们。剩下的以按严重程度排序的行内评论呈现。每条都标记为 Important、Nit 或 Pre-existing，这样 PR 没有引入的 bug 就不会看起来像是作者的错。

**每个发现项都必须得到回应。**你要么修复它，要么附上理由解决该讨论串。通常一个智能体会在夜间接手修复，所以作者回来时会看到一个已经过了一轮审查的 PR。

### 3. 可以阻断合并的安全审查

安全也有自己的自动审查。只要 bug 审查或安全审查中还有任何发现项未关闭，PR 就不能合并。你要么修复它，要么附上简短理由关闭讨论串，这就是清除误报的方式。

如果后续提交修复了该问题，发现项会自动清除。你可以用开源的安全审查 GitHub Action 或 `/security-review` 命令设置同样的流程。设置方法见 [Claude Code 中的自动安全审查](https://support.claude.com/en/articles/11932705-automated-security-reviews-in-claude-code)。

### 4. 可以阻断合并的自动检查

常规的那些：lint、类型检查、各平台上的测试，以及构建。（我们[在这里](https://claude.com/resources/articles/agentic-coding-is-straining-ci-heres-how-we-scaled-test-impact-analysis-at-anthropic)写过如何为这样的规模扩展 CI。）一个典型的 CLI 拉取请求在任何人查看之前可能会运行几十项检查。PR 模板会询问变更如何测试、如何撤销。Claude 可以填写，但提出变更请求的人要为此签字确认。

### 5. 按风险分级的人工批准

文档修复和自动更新器变更的风险不同，所以审查方式也不同。

| 风险 | 示例 | 人工批准 |
| --- | --- | --- |
| 低 | 文档、文案、仅内部功能、开关后的增量变更 | 自动审查和安全检查通过后无需人工批准 |
| 中 | 普通产品变更，以及对缓存、自动更新器或系统提示词等敏感区域的变更 | 一人 |
| 高 | 风险最高的代码，以及一小部分始终需要两人的路径 | 两人 |

**由变更决定层级，而非作者。**一个分类器读取变更并选择其风险层级。第二个分类器追问：即使层级表明不需要，这次特定变更是否需要另一个人。有些路径始终需要人，包括所有者列为敏感的任何内容，以及任何 CI 工作流文件。

**只有受信任的作者才能走更轻的路径。**只有仓库受信任名单上的作者才能走更轻的路径，主要是拥有该仓库的团队。其他所有人都需要第二个人批准。智能体的批准也永远不算作人的批准。自动审查可以放行低风险变更，但它不能填补需要人的位置。

**谁发起变更，谁就负责。**在智能体编写的 PR 上，指挥智能体的人算作所需审查者之一，就像代码是他们自己敲的一样。

**一次批准只覆盖一个特定提交。**如果落地了系统无法担保的新提交，比如智能体的推送或有人手动解决的合并，批准必须重新给出。

### 6. 合并队列、开关和渐进发布

合并队列会在应用变更的情况下针对 main 重新运行每一项检查，这样两个单独通过的 PR 不会组合出损坏的 main。新行为通常先通过开关发布给 Anthropic 员工，我们的重度使用往往会在用户之前暴露回归。公开发布先进入 `latest` 渠道。`stable` 渠道随后跟进。

### 7. 快速检测，快速回滚

有些错误仍会漏过去，所以最后一层是快速抓住它们。开关无需部署即可关闭。Claude Code 有每周轮值的 on-call，事故复盘会追问哪一层本应抓住该问题。

发现坏的合并仍依赖作者和 on-call，以及回滚和事故仪表盘。我们还没有在这些数字变动时收紧审批的熔断机制；这里的工程师希望在更多代码转向零人工合并之前拥有它们。

一位同事说，放慢速度确实会降低错误率，但主要是因为你在所有事情上都做得更少。我们宁愿更快地发现和修复问题。

## 我们如何改进审查器

我们的代码审查流程在一个循环中不断改进。

**任何事故现在都是一个评估（eval）。**团队收集了过去导致事故的 PR，连同它们的修复前滚和回滚，并让了解那段代码的工程师确认每个 bug 及其所在位置。审查器每天针对该集合运行。

**图 C**评估随每次事故增长，审查器的每次变更都会针对全部评估打分。

**我们通过观察人们如何处理评论来衡量噪音。**如果你不介意标记大量非 bug，抓住更多 bug 很容易，所以我们需要对此加以检查。我们按 PR 上的人如何回应来对审查器留下的每条评论分类：他们修复了它、说它错了、说该行为是有意为之，或认为它无关紧要。我们还会在已知干净的 PR 上运行审查器，统计它报告了多少次本会引导人做出有害变更的问题。我们写下的优先级是：首先抓住真正的 bug，其次减少审查轮次。

当作者是智能体时，噪音的代价更高。人可以几秒钟内挥开一个吹毛求疵的问题。智能体会修复它，这意味着又一次提交和又一轮审查。

**审查必须收敛。**智能体作者和智能体审查器可以让彼此无限忙碌。一个 CLI PR 在一夜之间经历了五十多轮审查和修复，直到其作者叫停。

当我们对审查器反复标记的内容运行 git blame 时，约 59% 是审查器第一轮就已存在的代码。审查器很少发现新 bug，它每轮都在发现一些更旧的 bug。

我们自己让它变得更糟。我们习惯了默认运行几轮，因为每一轮都能抓住新东西。这在有风险的变更上可能值得，但不是每个 PR 都值得。团队现在将一次通过所需轮次与召回率一起追踪，并改变了重新审查方式：

-   **轮次上限。**三轮之后，审查器请作者退后一步，重新考虑方案。
-   **仅 diff 重新审查**，在最初几轮之后。
-   **标记 bug 类别，**让作者修复每一个实例，而不是一行。
-   **不重复**已发布的发现项。

审查智能体还会每晚对现有代码运行，帮助我们在旧 bug 出现在别处之前抓住它们。

## 人类留在环中的地方

把一位资深工程师从深度工作中拉出来去抓一个常规错误，代价远高于一次自动审查。团队中的人仍然负责：

-   **决定是否要做。**方向、品味和范围。一个宣称已解决审查瓶颈的团队，仍然对来自团队外部的变更保留人工审查，以便有人问「我们到底该不该做这个？」
-   **审查有风险的代码**，如计费、自动更新器和 CI 工作流。
-   **审查架构**，即会为他人树立范式的架构。
-   **阅读证据。**测试输出、运行的命令及其返回结果、截图、审查器的发现项。如果你说不出这些检查会漏掉什么，就要求一次真正的审查，而不是快速批准。
-   **对结果负责。**每一次发布的变更都有人负责，无论代码是谁敲的。

## 在团队内共享上下文

代码审查的第二项职责一直是传播对代码库的理解。阅读队友的 diff 是你了解发生了什么变化、各部分如何拼合的方式。如果大部分阅读由机器完成，人们如何学习代码？

我们没有为此设立正式流程。团队里没有人脑中保有 Claude Code 的完整心智模型，我们也不认为有人需要。当有人想理解代码库的某一部分时，他们让 Claude 为那个确切的切片写一份讲解。这只需几分钟，并反映代码今天的样貌。

![标题为「如果大部分阅读由机器完成，人们如何学习代码？」的示意图。左侧一个网格代表代码库，其中几个方块高亮为 managed settings，即你想理解的部分；没有人在脑中保有它的完整心智模型。一个标有「就那个切片问 Claude」的箭头，附带示例问题「Claude Code 如何检索 managed settings？」，指向两个结果：Claude 写一份讲解，只需几分钟，并反映代码今天的样貌；以及，对一些人来说，Claude 构建一个小工件，将该部分代码可视化，并按那个人喜欢的学习方式教学。底部：逐行阅读琐碎的 diff，一行文案改动几乎教不了你什么；为你即将修改的模块写一份讲解，则能教你很多。](https://claude.dev/media/d4fafcbf3d2137bc64eb7f0707ba91809ff1ed4d098785e36d7422b3b07f6c40.png)

我们中有些人更进一步，让 Claude [构建一个小工件](https://claude.dev/blog/using-claude-code-the-unreasonable-effectiveness-of-html/)，将该部分代码可视化，并按那个人喜欢的学习方式教学。

如果目标是把人的注意力花好，这胜过逐行阅读琐碎的 diff。一行文案改动几乎教不了你什么。为你即将修改的模块写一份讲解，则能教你很多。我们默认在开放的 Slack 频道中工作的文化也有帮助，因为你能在他人构建时看到他们在做什么。

## 「你落地的，你负责」

如果你落地了一个小或中等变更，而仍然出了问题，团队规范通常是由你来修复。有几件事防止这变得糟糕：

-   **变更很小，**所以容易审查、调试和回滚。
-   **一切皆可逆。**开关、回滚和分阶段发布能在几分钟内撤销大多数错误。
-   **影响范围决定标准。**代价高昂的代码需要更多人和更多检查。
-   **回归会快速浮现**，通过遥测和内部使用。
-   **这不是追责。**负责修复意味着你拥有最多上下文；事故复盘看的是系统。

责任也是共享的。团队中许多人在[开放频道](https://claude.com/product/tag)中工作，任何人都能看到他人在构建什么、接手一个讨论串，或让 Claude 去填补一个缺口，反馈也来自不拥有该代码的人。这种开放性是质量在没有逐行关卡的情况下依然保持高水平的重要原因。

## 当我们改变方向时

智能体让启动事情变得廉价，所以有些工作不该落地。通常频道里会有人问为什么、指出早先的决定，或建议更简单的路径，然后作者关闭或重塑 PR。

既然代码写得快，关闭 PR 不会让人觉得是损失。诀窍是在讨论串中尽早提出不同方向，而不是作为对已完成 PR 的阻断性评论。

## 你如何采纳这一流程

与团队一起做这件事的大部分组件今天都已存在。

### 在拉取请求之前

-   给你的智能体一些它可以运行的检查，列在简短的 `CLAUDE.md` 中，再加上运行格式化和 linter 的钩子（hooks）。
-   在本地运行 `/code-review` 和 `/security-review`，或进行一次全新上下文的子智能体审查。
-   添加 `REVIEW.md`，并把重复的审查评论移入其中。

### 在每个拉取请求上

-   要求 CI，并在 PR 模板中加入「测试」「风险」和「如何回滚」。
-   在一个仓库上添加 AI 审查器（Code Review for Claude Code，或 Claude Code GitHub Action），用几周时间调整 `REVIEW.md`，然后扩大范围。
-   添加自动安全审查，并要求合并前解决每个审查讨论串。
-   让审查投入与风险匹配：常规变更快速过一遍，漏掉 bug 代价高昂的地方深入审查（Code Review 中的 Quick、Standard 或 Deep）。
-   限制审查轮次；最初几轮之后，只重新审查新的 diff。

### 批准

-   写下风险层级，由变更而非作者设定；从严开始，凭证据放宽。
-   为你信任的作者保留更轻的批准路径。
-   使用 CODEOWNERS 和分支保护，让认证、计费、CI 和发布工作流以及安装程序始终需要人。
-   绝不让机器人的批准替代所需的人工批准；在新提交上撤销批准。

### 合并及之后

-   使用合并队列、功能开关、先内部使用、分阶段发布和一键回滚。
-   把事故和回滚转化为评估集，每当审查器的提示词、工具或模型变更时重新打分。
-   衡量人的时间，以回滚率和事故率作为护栏。

## 这将走向何方

Code Review 的[公告](https://claude.com/resources/articles/code-review)说，批准拉取请求仍然是人的决定；该产品发布发现项，而非批准。我们自己的仓库走得更远，让所有者决定哪些低风险变更仅凭自动检查即可合并，而这条线还在不断移动。

当审查漏掉某些东西时，我们会问模型面前缺了什么，并把修复写进 `CLAUDE.md`、一个 Skill 或一项新检查。目标没有改变：每次变更花更少人的时间，回滚不比以前多。

如果你的团队让智能体开拉取请求，我们想听听你自动化了哪些检查、哪些仍需要人，以及你认为我们哪里做错了。
