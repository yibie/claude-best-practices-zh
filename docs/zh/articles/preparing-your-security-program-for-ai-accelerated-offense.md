# 为 AI 加速的攻击做好安全项目准备

本周早些时候，我们宣布了 Project Glasswing——这是我们的一项紧急尝试，旨在将我们最新的前沿模型 Claude Mythos Preview 强大的网络安全能力用于防御目的。在[公告](https://www.anthropic.com/glasswing)以及[配套的技术博客文章](https://red.anthropic.com/2026/mythos-preview/)中，我们描述了 AI 模型如何正在迅速降低发现和利用软件漏洞所需的资源、时间和技能。

着眼于 AI 的飞速进展，我们也指出，用不了多久，具备类似能力水平的模型就会广泛可用。在未来 24 个月内，大量可能多年来一直潜伏在代码中无人注意的缺陷，将被 AI 模型发现并串联成可用的漏洞利用。事实上，目前已经出现这样的情况：公开可用的、低于 Mythos 水平的模型能够[发现严重漏洞](https://www.anthropic.com/news/mozilla-firefox-security)，而这些漏洞在很长时间内都被传统审查所遗漏。

幸运的是，这对双方都是如此：虽然攻击者可以用 AI 加快速度，但采用 AI 工具来保护自己的防御者同样可以。在本文中，我们基于安全团队和研究人员在使用前沿 AI 模型保护真实代码库和系统过程中的观察与经验，提供安全建议和实用技巧。我们希望安全团队及其他相关人员在迈入 AI 驱动的网络安全时代时，能觉得这些建议有所帮助。

下文中的许多建议已经是现有安全共识的一部分；我们根据哪些控制措施经受了考验、哪些已经退化，对它们进行了优先级排序。如果你的组织按照 SOC 2 和 ISO 27001 进行报告，这些建议将直接对应到你已经在跟踪的控制项。

随着我们和 Project Glasswing 合作伙伴继续开展网络安全工作，我们将持续更新本指南。

## **现在该做什么**

### **1\. 弥合补丁缺口**

AI 模型非常擅长识别未打补丁系统中已知、已修补漏洞的特征。将补丁逆向还原为可用的漏洞利用，正是这些模型所擅长的机械式分析。这意味着从补丁发布到漏洞利用出现之间的窗口正在缩小。

-   _立即修补 [CISA 已知被利用漏洞（KEV）目录](https://www.cisa.gov/known-exploited-vulnerabilities-catalog)上的所有内容。_ 该目录包含已确认正在被积极利用的漏洞。此列表中任何可从网络访问的内容都应被视为紧急情况。
-   _使用 [EPSS](https://www.first.org/epss/) 对其余漏洞进行优先级排序。_ 漏洞利用预测评分系统（EPSS）提供每日更新的概率，预测某个通用漏洞与暴露（CVE）在未来 30 天内被利用的可能性。先修补 KEV 列表，然后修补所有超过选定 EPSS 阈值的内容，将帮助你把手头数千个未解决的 CVE 转化为一个可管理的队列。
-   _缩短暴露在互联网上的系统的补丁时间。_ 我们建议在漏洞利用出现后 24 小时内修补面向互联网的应用，其他漏洞则在数天内完成修补。
-   _在自动更新导致中断的风险可接受的情况下，自动化补丁部署和重启。_ 手动审批步骤会增加延迟，而延迟现在是主要风险。

**实用技巧：** 大多数云和操作系统供应商已经提供补丁自动化；启用它通常只是一个简单的配置更改。对于容器镜像和依赖清单，有多个开源扫描器可以作为单个持续集成步骤运行，并用来自 KEV 目录和 EPSS 的数据标注 CVE，因此优先级排序是内置的。

### **2\. 准备好处理数量大得多的漏洞报告**

在大约未来两年内，你用于接收、优先级排序和修复漏洞（包括你自己代码中的漏洞和你从供应商处购买的软件中的漏洞）的流程将面临比现在大得多的压力。你的漏洞管理流程应该为来自供应商和上游的大量补丁做好准备。

-   _为发现数量增加一个数量级做好规划。_ 接收、分类和修复跟踪等方面需要跟上不断暴露的漏洞数量。如果你的安全会议仍然围绕电子表格和每周例会展开，你不太可能跟得上。值得考虑一定程度的自动化——当然，要有人员在环，以应对如此庞大的数量。
-   _检查开源依赖的安全性。_ 大多数软件供应链主要是开源的。大多数开源项目没有服务级别协议或对维持高水平安全的承诺。[OpenSSF Scorecard](https://securityscorecards.dev/) 会根据分支保护、模糊测试覆盖率、签名发布和维护者活跃度等信号自动为每个依赖评分。它在 CI 中运行，有助于识别无人维护的软件包。
-   _对你的供应商应用同样的期望。_ 你的第三方风险管理流程应询问供应商，他们自己如何为加速的漏洞利用时间线做准备，以及他们是否在扫描自己的代码。

‍**实用技巧：** 研究能够评估易受攻击代码可达性的开源软件和第三方服务。构建自动化流程，持续向你的 IT 和生产基础设施交付新的软件更新，通过对更新进行回归测试来建立信心，确保你能快速部署它们。

上面我们提到了这些流程的自动化。AI 可以通过多种重要方式提供帮助：

-   _加速分类。_ 分类是一个瓶颈，因为它需要专家审查和分类。前沿模型可以将发现与现有积压去重，利用对你资产的了解来估计暴露程度，并在受影响的代码路径已预先识别的情况下起草修复工单。
-   _检查依赖的冗余。_ 大多数大型代码库会积累多个做同样工作的库（多个 HTTP 客户端；多个 JSON 解析器）。这给攻击者提供了更多机会，而对你来说没有任何功能上的收益。让 LLM 查看一个 lockfile，询问哪些依赖存在重叠（以及迁移和整合会是什么样子），这是一个一小时的练习，往往会有回报。
-   _AI 升级自动化。_ 前沿模型越来越有能力生成补丁，随漏洞报告一起提供。当报告清晰且详尽，甚至可能带有概念验证时，模型可以直接测试补丁以确认漏洞利用路径已被关闭。它还可以直接自动化接受上游补丁的过程，验证升级不会破坏测试或内部系统。
-   _AI 自建依赖（vendoring）。_ 一些小依赖在 OpenSSF Scorecard 上得分较低——也许是因为它们没有被积极维护。你不应继续依赖这些；相反，你应该考虑让 LLM 自己编写代码来重新实现你实际使用的功能。

### **3\. 在发布前发现缺陷**

预防总是胜于治疗。你应该假设到达生产环境的缺陷最终会被发现，因此你的安全测试需要远远提前进行。

-   _将静态分析和 AI 辅助代码审查添加到你的持续集成流水线中，_ 并在高置信度的发现上阻止合并。如果误报使这变得不切实际，你应该保留检查，但解决工具问题。[OWASP 应用安全验证标准](https://owasp.org/www-project-application-security-verification-standard/)定义了在三个不同严格级别下"通过"测试是什么样子。
-   _将自动化渗透测试添加到你的持续交付流水线中。_ 你可以对预发布环境运行攻击者将对你的生产系统运行的相同扫描。
-   _保护构建流水线。_ 能够在提交和部署之间注入代码的攻击者不需要发现漏洞。[SLSA](https://slsa.dev/) 安全框架提供了一条分级路径：较低级别确定哪个提交产生了哪个制品，较高级别使构建本身可验证。
-   _采用[安全设计（Secure by Design）](https://www.cisa.gov/securebydesign)实践。_ CISA 的承诺事项（默认多因素认证；无默认密码；透明的漏洞报告）是一个合理的最低标准。
-   _新代码优先使用内存安全语言。_ 很大一部分严重漏洞是内存安全缺陷，这些缺陷不会在 Rust、Go 或托管运行时中出现。CISA、NSA 和 [NCSC](https://www.ncsc.gov.uk/) 已经[发布了有用的路线图](https://www.cisa.gov/resources-tools/resources/case-memory-safe-roadmaps)。现有的 C/C++ 代码不需要重写，但新的 C/C++ 代码应该需要理由。AI 辅助的重写也越来越可行。

**实用技巧：** 作为 CI 操作运行的静态应用安全测试（SAST）工具，带有 OWASP Top 10 和特定语言规则集，广泛可用，既有开源的，也有内置于代码托管平台的（GitHub 上的 CodeQL 是最常见的起点）。要评估构建来源，OpenSSF 发布了一个[可复用工作流](https://github.com/slsa-framework/slsa-github-generator)，可以从 GitHub Actions 生成 SLSA Level 3 证明；采用它比 SLSA 规范所暗示的工作量要少得多。

和之前一样，AI 在加速这项工作方面有一些明显的机会：

-   _AI 漏洞扫描。_ 这里的逻辑很直接：你应该在攻击者之前，用他们会使用的那类模型扫描你自己的代码和系统。这种方法只需要一个隔离的智能体、一个过滤噪音的验证步骤，以及一条进入你现有分类流程的路径。你今天就可以用 LLM 做到这一点。**_如果你只从本节实施一件事，就实施这个。_**
-   _补丁生成。_ 当 SAST 或扫描器产生一个发现时，前沿模型通常可以为其提出补丁。这并不消除审查的需要，但它将开发者的工作从"理解缺陷并编写修复"转变为"验证提议的修复是否正确"。后者更快。同样的方法适用于内存安全迁移：LLM 可以将一个自包含的 C 模块连同测试移植到 Rust；审查者可以验证等价性，而不是从头编写整个东西。

### **4\. 发现代码中已有的漏洞**

打补丁解决的是你所依赖软件中的已知漏洞。但你自己的代码库中包含未知漏洞。大多数长期运行的生产代码已经被人类审查过很多次，但从未被前沿模型检查过，而这种分析[往往会揭示新的、以前被忽视的问题](https://www.youtube.com/watch?v=_IDbFLu9Ug8)。主动扫描可以在攻击者自己发现之前，识别出现代 LLM 能力范围内的漏洞。

-   _按暴露程度排序优先级。_ 从解析不受信任输入、执行认证或授权决策、或可从互联网访问的代码开始。这些是发现最可能产生影响的路径。
-   _包括遗留代码。_ 早于当前审查实践的代码，或原作者已经离开的代码，往往受到的审查最少。这正是你从新一轮检查中获益最多的地方。
-   _为修复预留预算。_ 对较旧代码进行结构良好的模型扫描通常产生的发现比 SAST 推广少，但其中真实问题的比例更高。规划工程时间来修复这些缺陷。

**实用技巧：** 选择一个当前负责人较少的面向互联网的服务，扫描其输入处理和认证逻辑。在隔离环境中运行智能体，并添加验证步骤，以便你基于已确认的发现采取行动。正确完成一个服务是估算更广泛项目成本的合理基础。

### **5\. 为被入侵而设计**

攻击者会试图在某处建立立足点。你需要限制他们从那里能触及的范围。

那些价值来自摩擦——使攻击变得_繁琐_——而非硬性屏障的缓解措施（额外的跳转节点、速率限制、非标准端口、基于短信的 MFA），对于能够磨过这些繁琐步骤的对手来说效果要差得多。我们下面的建议倾向于那些即使攻击者有无限耐心也能保持有效的控制措施：硬件绑定的凭证、过期令牌，以及不存在的网络路径而非仅仅是不方便的路径。

-   _采用零信任架构。_ 对服务之间的每个请求进行认证和授权，就像它来自互联网一样。CISA 的[零信任成熟度模型](https://www.cisa.gov/zero-trust-maturity-model)和 NCSC 的[零信任原则](https://www.ncsc.gov.uk/collection/zero-trust-architecture)都提供了分阶段的采用路径。
-   _将访问权限绑定到经过验证的硬件而非凭证。_ 生产系统和敏感内部工具应只能从具有经过认证的硬件身份的受管员工设备访问，并配合抗钓鱼的 2FA（FIDO2 或 passkeys）。仅凭被盗凭证绝不应足以获得访问权限。甚至生产服务之间的调用也应植根于硬件身份。
-   _按身份隔离服务。_ 被入侵的构建服务器不应能够查询生产数据库。被入侵的笔记本电脑不应能够访问构建基础设施。在接收端强制执行这一点：每个工作负载都应携带自己的加密身份，每个服务应只接受来自其策略名称所指定的特定调用者的连接。网络分段仍然可以减少影响范围和噪音，但它是一个后备措施。
-   _用短期令牌替换长期密钥。_ 静态 API 密钥、嵌入的凭证和共享的服务账户密码是攻击者借助模型辅助代码分析最先发现的东西之一。使用由身份提供商签发的短期、范围狭窄的令牌。

**实用技巧：** 完整的零信任是一个多年期的项目，但身份感知访问代理可以在不从根本上改变内部服务架构的情况下，将设备验证、MFA 门控的访问置于内部服务之前。每个主要云提供商都提供原生选项，对于本地或多云环境，也有多个开源和商业替代方案。对于密钥，每个主要云都有托管密钥存储；将最广泛共享的单个凭证移入其中一个并轮换它，对其余部分是一个有用的推动力。

### **6\. 减少并盘点你所暴露的内容**

本节基于两个重要原则。第一，你无法防御你不知道的系统。第二，暴露面越小，可攻击的东西就越少。

-   _维护一份最新的清单，_ 涵盖你系统中每个面向互联网的主机、服务和 API 端点。攻击者可以运行自动化侦察；你的清单至少应同样准确。将这些系统纳入你的渗透测试和红队演练。
-   _停用未使用的系统。_ 没有明确负责人的遗留服务通常也没有打补丁。
-   _最小化每个服务暴露的内容。_ 默认拒绝网络入口，并将 API 表面积限制在实际需要的范围内。

**_实用技巧：_** 互联网范围的扫描索引是公开可搜索的；查询一个索引中你自己的 IP 范围和域名，就能看到攻击者侦察时看到的内容。对于云资产，原生清单工具（AWS Config、Azure Resource Graph、GCP Asset Inventory）已经存在；工作在于查询它们。

AI 也可以在这里直接提供帮助：

-   _清理过时的代码和系统。_ 识别未使用的代码很繁琐——但如上所述，AI 模型擅长繁琐的任务。一个对代码库和流量日志有读取权限的模型可以列出没有调用者且未收到流量的端点；然后，它可以解释移除每个端点会影响什么。
-   _自主外部红队演练。_ 从外部将 AI 攻击性智能体指向你自己的边界，没有凭证，也没有源代码访问权限。然后，让它做攻击者会做的事：弄清楚什么是可达的，对其进行指纹识别，并尝试将发现的东西串联成立足点。这种自动化红队演练可以捕捉源代码扫描看不到的东西：被遗忘的主机、暴露的管理界面、默认凭证和配置错误的存储。以与清单刷新相同的节奏运行它。

### **7\. 缩短事件响应时间**

漏洞利用可能在补丁发布后数小时内出现。需要数天的响应流程太慢了。以下是一些关于如何缩短事件响应时间的想法：

-   _在警报队列前端放置一个模型。_ 每个入站警报都应在人类看到之前得到自动化的第一轮调查。这种"分类智能体"对你的安全信息和事件管理（SIEM）平台有只读访问权限，并拥有一组范围明确的查询工具，可以将你的注意力引导到最需要人类判断的警报上。
-   _将入侵者驻留时间和覆盖率置于其他一切之上。_ 这是 AI 自动化最有能力推动的两个指标；当漏洞利用窗口缩短时，两者都最为重要。
-   _自动化事件相关的记录工作。_ 在活跃事件期间，模型应做笔记、捕获制品、推进并行调查线索，并起草事后总结和根因分析。另一方面，_人类_ 应做出遏制决策、披露决策和客户沟通决策。事件期间的人类决策速度绝不应因为那些更适合交给 AI 的方面（如证据收集或撰写报告）而受到速率限制。
-   _让模型驱动检测飞轮。_ 摄取[威胁情报](https://platform.claude.com/cookbook/tool-use-threat-intel-enrichment-agent)、生成候选检测规则、搜寻匹配项以及调整触发规则，这些现在都在前沿模型的能力范围内，它们可以端到端地运行这个过程。
-   _为五个同时发生的事件进行桌面演练。_ 标准演练假设一个带有可用漏洞利用的严重 CVE 在周一袭来。鉴于我们看到的 AI 能力提升，这可能不明智。要真正压力测试你的响应，你应该运行五个事件在同一周袭来的版本。
-   _将检测覆盖率映射到 [MITRE ATT&CK](https://attack.mitre.org/)。_ ATT&CK 提供了大多数检测工具已经在使用的攻击者技术标准词汇表。知道你能够检测哪些技术（以及哪些不能），比"改进检测"的笼统目标更有用。你应该优先考虑横向移动和凭证访问的覆盖率。
-   _提前建立紧急变更程序。_ 生产补丁的两周变更审批周期本身就是一种安全风险。紧急遏制行动（如使服务下线、轮换凭证或阻断网络路径）也是如此。你应该提前决定谁可以授权这些行动以及多快。

**实用技巧：** 选择一个已知误报率高的嘈杂规则。将前沿模型接入其警报流，对底层数据有只读访问权限，让它为每次触发生成结构化的处置结果。与人类审查者进行两周的一致性测量。如果一致率可以接受，就扩展到下一个规则。不值得试图一次性自动化整个队列。另外，[Atomic Red Team](https://atomicredteam.io/) 是一个开源库，包含映射到 ATT&CK 技术的小型安全测试；运行几个并检查你现有的日志记录实际检测到了哪些，是一个下午的练习，可以产生具体的覆盖率地图。

以下是 AI 可以帮助缩短响应时间的一些方式：

-   _100% 覆盖率的第一轮分类。_ 一个范围明确的分类智能体可以调查每个警报（而人类可能只看高于给定严重性阈值的那些），并生成人类可以接受、拒绝或升级的结构化处置结果。使其奏效的机制是给你的模型一个最小的工具集（查询、思考、报告），让它选择自己的调查策略，并根据运营指标衡量输出。
-   _事件记录员和并行调查员。_ 在活跃事件期间，模型可以同步做笔记、在收集制品时为其打时间戳、推进响应者尚未顾及的独立调查线索，并在事件结束后根据记录起草事后总结。这是前沿模型应用于安全工作中最不起眼的应用——但它可能是影响最大的一个。
-   _针对你自己环境的主动搜寻。_ 能够在源代码中发现漏洞的那类智能体，也可以在你的遥测中搜寻配置错误和入侵指标。你可以以与外部攻击面扫描相同的节奏运行它。

## **向他人提交漏洞报告的建议**

如果你在扫描代码——你自己的依赖、开源项目或供应商产品——并向上游报告发现，这些报告的质量决定了是否有人会采取行动。开源维护者已经在接收大量低质量的自动化报告，许多人已经开始忽略任何看起来像 AI 生成的东西。在不增加信号的情况下增加数量，会让每个人的问题更糟，包括你自己。

只有在人类已验证并愿意署名的情况下，才应发送报告。具体来说：

-   _用平实的语言说明缺陷及其影响。_ 维护者应该能够从第一段就理解出了什么问题以及为什么重要，而不需要运行任何东西。
-   _走一遍代码路径。_ 展示输入在哪里进入、在哪里被错误处理、后果在哪里发生。这是区分真实发现和模式匹配的部分。
-   _提供可用的复现。_ 维护者可以运行的概念验证，或一个失败的测试用例，比任何数量的解释都更可信。
-   _包含一个补丁_，如果你是维护者，_你会接受它_。补丁表明报告者足够了解代码库，能够以符合项目惯例的方式修复问题。
-   _预先披露 AI 参与。_ 如果模型发现了缺陷或起草了报告，在第一行说明。维护者无论如何都会发现；隐瞒比披露损失更多可信度。
-   _尊重维护者的判断。_ 如果他们拒绝了报告，你应该接受。易于合作的善意比在一个缺陷上赢得争论更有价值。

**实用技巧：** 在发送漏洞报告之前，一个有用的自我检查是关闭编辑器，凭记忆解释这个缺陷。如果你不能在不回看模型输出的情况下描述出了什么问题，你对它的理解还不够充分，不足以报告它。

## **如果你没有安全团队**

上述大部分建议假设你的组织有专门的安全职能。如果你是一个小型组织、独立开发者或开源维护者，同样的风险适用，但行动更简单：

-   _打开自动更新_，适用于你的操作系统、浏览器和每个提供此功能的应用。这是最有效的单一行动，不需要持续努力。
-   _优先选择托管服务而非自托管。_ 让有安全团队的提供商运行数据库、认证和电子邮件，将补丁负担转移给他们。这样的托管服务成本几乎总是低于一次事件的成本。
-   _在每个支持该功能的账户上使用 passkeys 或硬件安全密钥。_ 短信验证码可以被拦截，密码会被重复使用；硬件密钥无法被钓鱼。
-   _启用代码托管平台上的免费安全工具。_ GitHub 的 Dependabot、密钥扫描和 CodeQL 对公共仓库免费，能捕获企业工具所捕获的相当一部分问题。启用它们只需几分钟。

_如果你维护一个开源项目，发布一个 `SECURITY.md`_，说明联系谁以及联系后可以期望什么。AI 辅助扫描意味着你将收到比以前更多的漏洞报告。有些会有价值；有些会是自动化噪音。清晰的接收流程有助于你区分它们，并向善意的报告者表明他们的努力不会白费。
