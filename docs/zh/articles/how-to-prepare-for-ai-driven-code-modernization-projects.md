# 如何为 AI 驱动的代码现代化项目做好准备
_在我们的 **Notes from the Field** 系列中，Anthropic 的前置部署工程师分享源自真实客户部署的最佳实践。在本文中，我们分享管理大型代码现代化项目的经验。_

[代码现代化](https://claude.com/resources/articles/how-ai-helps-break-cost-barrier-cobol-modernization)曾经被规划为耗时数年、全员投入的工作，如今可以在几个月（甚至[几周](https://claude.com/resources/articles/ai-code-migration)）内完成，但两侧的组织工作往往保持不变。

例如，对关键银行系统的每一次变更都必须经过变更管理、审查和批准。这是一个稳健的流程，因为监管机构、审计人员和业务方都要求如此。

正是这些流程让关键系统值得信赖，而它们建立在这样一个假设之上：由人编写每一处变更，由人审查每一个 diff。一旦智能体加速了变更的编写，瓶颈就从产出变更转移到围绕变更调动组织资源。

本文涵盖企业在现代化开始之前必须完成的工作：定义“完成”意味着什么、变更必须携带哪些证据、经过认证的变更如何进入生产环境，以及必须预先准备好哪些条件才能启动运行轮次（run）。

我们将这一过程分为六个步骤：

1.  **定义目标：** 现代化后的代码必须具备的技术栈和行为。
2.  **创建证书：** 变更在目标状态下被视为正确所必须满足的条件。
3.  **设定推广策略：** 经过认证的变更以产出速度进入生产环境的路径。
4.  **准备前置条件：** 环境、CI/CD、审查能力和审批。
5.  **构建并完善智能体式工作流：** 定制的 Claude Code [动态工作流](https://claude.com/resources/articles/introducing-dynamic-workflows-in-claude-code)，将现代化工作分配到许多更小的并行子智能体工作流中，由它们产出变更。它围绕目标、证书和推广策略构建。
6.  **运行现代化：** 在代码库的一小部分上端到端验证工作流，然后扩展。

## **第 1 步：定义目标**

**目标**是现代化的最终状态。期望的最终状态决定了你要进行三种现代化中的哪一种，详见下表。

### **确定现代化类型**

| 类型 | 是什么 | 何时选择 | 目标是 |
| --- | --- | --- | --- |
| **升级（Uplift）** | 同栈版本升级（例如 C++11 → C++20）。 | 技术栈没问题，但版本已落后：运行时已停止支持、存在未修补的安全问题、依赖项无法再升级。 | 一个运行时版本和包集合。 |
| **转换（Transform）** | 跨栈重写，保持行为不变（例如 COBOL → Java）。 | 技术栈是需要解决的问题，而行为是可信的。 | 升级所需的一切，加上新代码必须遵循的语言、框架和架构约定。 |
| **重构（Reimagine）** | 在新架构上进行全新重建，并修改行为。 | 行为需要与代码一起改变。 | 转换所需的一切，加上新系统的书面行为规格。 |

选择进行哪种类型的现代化，往往会在组织内部引发争论。根据我们的经验，最贴近生产的人希望替换技术栈并保持行为不变以控制风险（转换式现代化）。另一方通常是长期与代码库共处的工程师，他们希望现代化能偿还技术债务，以及其他希望借此机会提出新需求的业务利益相关方（重构式现代化）。

两种立场都合理，但如果这个问题悬而未决，它日后会重新浮现，变成关于某项变更是否“正确”的争论。就选择哪条路径达成共识会增加初始摩擦，但能让整个项目更顺畅。

### **梳理代码库并创建行为规格**

理解当前系统通常是定义目标的一个良好起点。提取旧代码实际做了什么，并创建当前行为的清单，可以让你轻松决定哪些部分应该修改或舍弃，从而判断现代化是转换还是重构。这通常还能揭示未知的业务逻辑和边缘情况。

Claude 可以通过[梳理依赖关系并记录无人记得构建过的工作流](https://claude.com/resources/articles/how-ai-helps-break-cost-barrier-cobol-modernization)来完成大部分发现工作。[代码现代化插件](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/code-modernization)的 _assess_、_map_ 和 _extract-rules_ 命令会挖掘业务规则，并附上可供工程师审查的源引用。

然而，仅靠 Claude 的发现可能无法完整捕捉遗留系统的行为方式。与业务用户和开发者的访谈，以及内部文档，可以填补这些空白。上下文收集在前期可能需要一些时间，但上下文的质量会塑造工作流之后做出的每一个决策。

对于重构式现代化，定义目标需要额外的工作：应写下详细的行为规格，并与用户群体达成一致。

### **确立项目的理由与目标**

在定义目标的同时，组织还应考虑现代化究竟为何值得进行。现代化遗留系统可以降低持续的维护和运营成本，但根据我们的经验，降低成本并不是大多数现代化项目的主要目标。

> “降低风险往往是现代化最重要的收益。在讨论是否要开展项目时，请考虑不进行现代化的风险。”

例如，一个带有未修补漏洞的系统可能意味着网络入侵或严重到足以让企业本身陷入风险的中断。不受支持的运行时，或理解该系统的工程师群体不断萎缩，都会加剧风险。

像 Claude Code 这样的智能体式编程工具缩短了现代化的时间线，但预算仍然难以估算，这导致了惰性。我们公布了一些[大规模现代化](https://claude.com/resources/articles/ai-code-migration)的成本，[其他公司](https://claude.com/customers/lg-cns)也是如此。这些可以作为粗略的基线，我们在本指南末尾还提供了关于预算预测的额外指导。

启动这些项目的主要挑战，通常是建立内部共识，并获得拥有该系统的团队以及依赖该系统的团队的承诺。构建商业论证并设定项目目标（通常在领导层层面）能让这一部分过程更容易。这也有助于为后续证书和推广策略中的权衡提供依据。当利益相关方对一项变更可以承载多少风险存在分歧时，不进行现代化的风险就是制衡因素。

## **第 2 步：定义证书**

**证书**是每一项现代化变更都必须满足的一组条件或测试。选择那些能提供最强累积证据、证明变更相对于目标而言是正确的条件。

每个条件都应能在无需人工介入的情况下检查，这样智能体式工作流就可以反复迭代变更，直到它满足证书；如果无法满足，则将其标记出来交由人工审查。

证书的内容取决于目标，但通常会从以下列表中选取：

-   原始测试套件通过
-   现代化期间编写的 Claude 生成的测试全部通过
-   测试覆盖率达到约定阈值
-   性能基准测试保持在约定范围内
-   由 Claude 在各自全新的上下文窗口中进行的独立对抗性审查未发现阻塞性问题
-   对于用户界面，Claude 驱动的计算机使用未发现回归
-   当前版本和目标版本对相同输入产生相同输出，输入可以是实时的、录制的或 Claude 生成的
-   持久化状态和线格式在当前版本和目标版本之间可往返转换
-   变更在预发布环境中运行约定时长，错误率、延迟或告警均无回归
-   静态分析和安全扫描未显示新的发现
-   对于编译型目标，构建干净且类型检查通过

> “与将要审查变更并将其推广到生产环境的人一起编写证书。在证书和智能体式工作流仍在设计时，就引入当前依赖该代码库的开发者、用户群体和业务负责人。”

他们的专业知识塑造了证书所衡量的内容，而他们的早期参与正是他们在变更进入审查时给予支持的原因。对完成的证书进行一项良好的检验是：他们是否愿意仅凭证书的证据就放心合并。如果他们在其中看到了自己的标准，那么第 3 步中的推广策略就可以更轻量。

证书对照什么进行检查、如何检查，取决于现代化类型。

-   **对于升级式现代化**，对照的是原始代码库，原始测试套件可以作为证书的核心。
-   **对于转换式现代化**，同样对照原始代码库，但原始测试套件很少能在新栈上运行。取而代之的是，生产流量回放、新旧版本之间的差分测试，以及生产并行部署承担了大部分工作。
-   **对于重构式现代化**，证书锚定在行为规格上。这是最困难的情况。规格不如现有系统那样客观可供比对，因此涉及更大程度的模型判断，可能导致结果更加多变。在这里，证书依赖于根据规格编写的测试、由 Claude 进行的独立对抗性审查（对照规格检查每一项变更），以及在新系统保持旧系统行为之处进行的差分检查。随着规格逐渐明确，预计需要修订证书：规格中的缺口会首先在这里显现。

较旧的系统往往测试覆盖率低、测试不稳定，且遥测很少。定义证书的一部分工作就是识别这些缺口。如果难以支撑一个强有力的证书，那么在这一步最有用的做法之一，就是使用 Claude 构建缺失的证据，无论是搭建生产并行环境、构建回放执行框架（harness），还是编写更多测试。

智能体产出变更的速度将远超任何人类团队逐 diff 审查的速度。推广策略是一条分层的审查路径——事先写下并达成一致——它设定了一项变更的人工审查深度，使现代化能够在可接受的时间线上完成。

与证书一样，这一步要与审查者共同完成，并尽可能将其融入组织现有的变更管理流程。细节会因组织和其面临的风险权衡而异，但有几条规则放之四海而皆准：

-   **按影响范围和智能体置信度对变更分层。** 如果组织有自己的变更或风险分类，就使用它。对关键路径保留完整的人工审查。
-   **从源头修复反复出现的标记。** 随时间推移对标记的变更进行分组和分析。当同一类标记反复出现时，在智能体式工作流或证书中修复原因，而不是逐一审查。
-   **与审查者共同设计输出格式。** 就哪些信息和格式能让审查最快达成一致，以及哪些信号比其他信号更能带来信心。让他们在第 5 步审查早期样本输出。
-   **有效分配 SME 时间。** SME 不会阅读每一个最终 diff，但他们的判断仍然是稀缺的输入。让他们能直接跳到最高风险层级的变更，以及每一层级中被标记的智能体决策，而无需费力浏览大量 diff。这样少量专家工时就能覆盖风险最高的变更。

这些规则中有许多通过让 SME 在项目早期参与，将他们的工时前置。他们的反馈会在全面现代化开始之前调整证书和智能体式工作流。

他们对样本的签字确认，也成为在信心很高之处采用更轻量审查路径的进一步依据。这与传统的、非智能体式的模式相反，后者审查发生在最后。



一项变更从生成到生产的路径。

推广策略还应反映现代化在速度与审查深度之间的谱系上所处的位置。一场赶向硬性截止日期（例如运行时失去支持）的现代化，需要更快的策略、更轻的人工审查，并明确同意每项变更承担更多风险。

时间线较长的现代化则能够承受更深的人工审查和更慢的切换。利益相关方会根据自身的风险偏好和约束落在这一谱系的不同点上，因此值得在工作开始前就锁定。

在受监管的环境中，对任何变更采取更轻的人工审查路径都可能引起真实的不适。个别审批者不愿签字，因为他们承担着不良变更的风险，而领导层则承担着系统老化的更大风险。

根据我们的经验，最好让推广策略的指令来自组织最高层。事先达成一致也更好，这样到达生产环境的 bug 的责任就是共担的，而不是被钉在批准该变更的人身上。

> “所有这些仍然取决于一份足够详细、能作为真实证据的证书，以及理解 Claude 如何得出某项变更、从而足以信任它的审查者。”

## **第 4 步：准备前置条件**

这一步的许多工作要经由现代化之外的团队完成：主机所需的平台或基础设施、测试容量所需的 QA 或发布工程、审批所需的安全与合规。这些团队通常各有自己的待办事项或审批流程，因此要尽早开启对话，一旦确定需求就开始，往往在第 1 至第 3 步仍在进行时。

### **环境**

-   一台专用的远程主机，用于运行工作流，且 Claude 可访问代码库和其他相关来源
-   证书所需的测试容量
-   任何能强化证书的东西：生产遥测、生产并行环境，或用于回放的生产数据

### **代码库与 CI/CD**

-   代码库的依赖关系图，基于构建和编译日志、导入分析或运行时追踪（trace）。注意：插件的 _map_ 命令是一个很好的起点，但取决于代码库的规模和年代，可能需要做更多的前期工作
-   作为目标定义的一部分，对任何依赖项或包的预定处理方式
-   如有需要，准备好添加到 CI/CD 的兼容性检查
-   如果就地现代化，需有约定的代码冻结策略
-   面向活跃开发者的沟通计划，涵盖任何代码冻结和新的兼容性要求

### **团队与审查**

-   与依赖该代码库的其他团队就他们如何参与达成一致，例如签署证书或按推广策略进行审查，并预留审查者时间

### **安全与合规**

-   一条获批用于源代码的 Claude Code 模型访问路径
-   智能体式工作流的最小权限访问：仅写入现代化分支，无生产凭据
-   从现代化分支中清除或掩蔽机密信息和 PII
-   每项变更可追溯，PR 链接到智能体转录记录和证书证据
-   对新依赖项进行许可证和漏洞检查

## **第 5 步：构建并完善智能体式工作流**

使用 Claude Code 开发一个定制的[动态工作流](https://claude.com/resources/articles/introducing-dynamic-workflows-in-claude-code)，用于现代化代码库。

我们建议从[代码现代化插件](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/code-modernization)开始，并将工作流可能需要的一切放在文件系统上或通过 MCP 提供，让 Claude 能够访问。这包括目标、证书、推广策略、代码库、文档，以及证书所需的任何数据源或工具。你也可以将本文作为上下文提供给 Claude。这构成了项目的中央知识库。

有了这些，[构建现代化工作流](https://claude.com/resources/articles/ai-code-migration)就是容易的部分。让 SME 按需审查 Claude 的工作，包括任何代码库特定的 Skills（技能）或提取的规则，然后再让下游的任何东西依赖它。

通过将你构建的东西应用于代码库的小部分来完善它，由 SME 审查它产出的变更、智能体的过程，以及满足证书的证据。

> “当问题浮现时，你应该修改工作流，而不是修改每一项变更。目标是确信：一旦扩展，变更几乎在所有地方都能满足证书，审查者也会愿意按推广策略合并。”

## **第 6 步：运行现代化**

首先，在代码库的一小部分上端到端完成现代化，包括通过推广策略审查并落地变更。在成本仍然低廉时修复任何不奏效的地方，重复该过程直到你有信心，然后扩展到整个代码库。

转换式和重构式现代化涉及在现有系统旁边构建目标系统，并在完成后一次性切换；而升级式现代化还有第二个选项：在开发继续进行的同时，在活跃代码库上就地现代化。

当系统不能停机，或代码库变化太快以至于难以保持一个单独的现代化副本最新时，这通常是常规选择。在这种情况下，我们看到行之有效的做法是：从叶子向内将代码库拆分为逻辑分区；一次冻结并现代化一个分区；并对 CI/CD 设门禁，使新提交无法撤销已经现代化的分区。



## **关于成本的说明**

我们经常被问到这样一次现代化会消耗多少 token。每次现代化工作都不同，但主要的成本驱动因素包括：

-   代码库中有多少需要读取而非修改；
-   证书有多复杂（在受监管环境中，验证通常比编写变更占更大份额）；
-   证书要求编写多少新测试和修复多少测试；以及
-   运行轮次进行期间，其他团队在你周围合并代码带来了多少协调工作。

> “在代码库的一小部分上完成现代化时，测量 token 用量，并用它来推算整个运行轮次的用量。将试点无法看到的一切（例如活跃代码库上的协调工作）视为未知。这样你就能得到全面现代化的成本下限估算。”

试点的测量结果还能显示在哪里针对成本优化智能体式工作流。找出工作流中消耗 token 最多的部分，并考虑如何让它们更高效。将计算密集型的验证信号移到更便宜的关卡之后，使它们只在更简单的检查通过后才运行。

考虑对证书能完全检查的机械性、高量工作使用像 Sonnet 这样平衡成本与能力的模型。将更智能的模型留给困难的转换和验证正确性的对抗性审查。

当较便宜的模型未能满足证书时，你也可以升级到更昂贵的模型，但在试点期间要仔细分析重试率，因为多次廉价尝试的成本可能高于一次昂贵尝试。如果你让 Claude 同时访问工作流和试点数据，它可以与你一起完成大部分分析。

## **超越现代化本身**

现代化后的代码库是其中一项产出。其他产出包括：产出它的工作流、一份关于何为正确的书面证书、一份你的变更管理流程已经接受的推广策略，以及每一项已落地变更的证据轨迹。将这套实战手册（playbook）固化为可复用的资产，这样下一次升级或重写时模式就已经就位。
