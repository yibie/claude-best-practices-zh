# 构建 Claude Code 的经验：提示词缓存就是一切

工程界常说「缓存统治我周围的一切」，这条规则对智能体同样适用。

像 Claude Code 这样长时间运行的智能体式产品之所以可行，靠的是[**提示词缓存**](https://x.com/RLanceMartin/status/2024573404888911886)，它让我们能够复用此前往返请求中的计算，显著降低延迟和成本。

在 Claude Code，我们整个执行框架（harness）都是围绕提示词缓存构建的。高提示词缓存命中率能降低成本，也帮助我们的订阅方案给出更宽松的速率限制，因此我们对提示词缓存命中率设置了告警，一旦过低就宣布 SEV。

以下是我们在规模化优化提示词缓存过程中学到的（往往反直觉的）经验。

## 为缓存而布局你的提示词

![系统提示词布局，自上而下：基础系统指令与工具（全局缓存）、CLAUDE.md 与记忆（按项目缓存）、会话状态如 env、MCP 与输出风格（按会话缓存），以及每轮都会增长的消息。](https://claude.dev/media/8234c2ef7c2f5624440f380ddbd14ca13d87d3c3827148968c1a83a7d86b73f6.png)

**图 A** Claude Code 的系统提示词经过组织，使稳定的部分保持缓存，只有对话本身逐轮增长。

提示词缓存通过前缀匹配工作——API 会缓存从请求开头到每个 `cache_control` 断点之间的所有内容。这意味着你放置内容的顺序极其重要，你希望尽可能多的请求共享同一个前缀。

提示词的组织方式不仅影响缓存命中，也影响输出质量——[提示词工程基础](https://claude.com/blog/best-practices-for-prompt-engineering)是这门手艺的另一半。

最好的做法是静态内容在前、动态内容在后。对 [Claude Code](https://claude.com/product/claude-code) 来说，这看起来是：

1.  **静态系统提示词**与工具（全局缓存）
2.  **CLAUDE.md**（在项目内缓存）
3.  **会话上下文**（在会话内缓存）
4.  **对话消息**

这样我们就能最大化共享缓存命中的会话数量。

但这种方法可能出人意料地脆弱。我们曾因各种原因破坏过这个顺序，包括：在静态系统提示词中放入精确到秒的时间戳、以非确定性的方式打乱工具定义顺序、以及更新工具的参数（例如 Agent 工具可以调用哪些智能体）。

## 用消息传递更新

有时你放进提示词的信息会过时，例如时间变了，或者用户修改了文件。你可能会想更新提示词，但这会导致缓存未命中，最终对用户来说可能相当昂贵。

考虑一下能否改为在智能体的下一轮中通过消息传入这些信息。在 Claude Code 中，我们在下一条用户消息或工具结果中加入一个 `<system-reminder>` 标签，把更新后的信息带给模型，这有助于保住缓存。

## 不要在会话中途更换模型

提示词缓存是模型独有的，这会让提示词缓存的账算起来相当反直觉。

例如，如果你和 Opus 的对话已经进行到 100k token，想提一个相当容易回答的问题，切换到 Haiku 实际上比让 Opus 回答更贵，因为我们需要为 Haiku 重建提示词缓存。

如果你需要切换模型，最好的方式是通过子智能体；沿用上面的例子，你可以部署一个子智能体，让它提示 Opus 为另一个模型准备一条「交接」消息，说明需要完成的任务。我们经常用 Claude Code 的 Explore 智能体这样做，它们使用的是 Haiku。

## 绝不在会话中途增加或移除工具

在对话中途更改工具集是人们破坏提示词缓存最常见的方式之一。这看起来很直觉——你只应该给模型它此刻需要的工具。但由于工具是缓存前缀的一部分，增加或移除一个工具会使整个对话的缓存失效。

### 用计划模式围绕缓存做设计

[计划模式](https://code.claude.com/docs/en/common-workflows)是围绕缓存约束设计功能的一个绝佳例子。直觉的做法会是：当用户进入计划模式时，把工具集换成只包含只读工具，但这会破坏缓存。

相反，我们始终在请求中保留*所有*工具，并把 EnterPlanMode 和 ExitPlanMode 本身作为工具使用。当用户开启计划模式时，智能体会收到一条系统消息，说明它处于计划模式以及相关指令：探索代码库、不要编辑文件、在计划完成时调用 ExitPlanMode。工具定义从不改变。

这还有一个额外好处：因为 EnterPlanMode 是模型自己可以调用的工具，它可以在检测到难题时自主进入计划模式，而不会造成任何缓存中断。

### 用工具搜索来延迟加载而非移除

同样的原则也适用于我们的[工具搜索工具](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)。Claude Code 可能加载了数十个 MCP 工具，把所有这些工具都放进每个请求会很昂贵，但在对话中途移除它们又会破坏缓存。

我们的解决方案：`defer_loading`。我们不移除工具，而是发送轻量的存根（只有工具名，带 `defer_loading: true`），模型可以在需要时通过工具搜索「发现」它们。完整的工具 schema 只在模型选择它们时才加载。这样缓存的前缀保持稳定，因为相同的存根始终以相同的顺序存在。

你也可以通过我们的 API 使用[工具搜索工具](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)来简化这一点。

## 在不破坏缓存的前提下做上下文压缩

![上下文压缩与提示词缓存如何配合。压缩前：系统与工具加上许多轮次，上下文窗口几乎占满。一次分叉的压缩调用复用相同前缀，以十分之一的价格获得缓存命中，追加「总结这段对话」，并返回约 20k token 的摘要。压缩后：系统与工具、一个 compact\_boundary、对话摘要、重新附加的文件与上下文，以及新对话的空间。](https://claude.dev/media/75fb66a792d269a2b47976ee5eda71cdd4e8e17aa3fb7ff4049b836113000dfc.png)

**图 B** 当上下文窗口填满时，Claude Code 分叉一次带缓存的调用以总结对话，然后用摘要替代原始消息继续。

[上下文压缩](https://platform.claude.com/docs/en/build-with-claude/compaction)是上下文窗口用尽时发生的事。我们总结到目前为止的对话，并用该摘要继续一个新的会话。

上下文压缩与提示词缓存的交互方式很容易出错。要压缩一段对话，你必须把完整对话发给模型，它才能写出摘要。最简单的做法是发起一次单独的 API 调用，使用自己的系统提示词（类似「总结这段」）且不附带任何工具，但这正是成本陷阱所在。提示词缓存只在请求的前缀与已缓存内容从头开始逐字节匹配时才生效。你的主对话是在一个系统提示词和工具集下缓存的；而总结调用使用不同的系统提示词且没有工具，因此前缀在第一个 token 处就分叉了，缓存完全用不上。结果你要为发送的整段对话支付全额、未缓存的输入费率——而且对话越长（也就是你越需要压缩），这一次调用就越昂贵。

### 解决方案：缓存安全的分叉

当我们执行上下文压缩时，我们使用与父对话*完全相同*的系统提示词、用户上下文、系统上下文和工具定义。我们在前面接上父对话的消息，然后在末尾追加压缩提示词作为一条新的用户消息。

从 API 的角度看，这个请求与父对话的最后一次请求几乎完全相同——相同前缀、相同工具、相同历史——因此缓存的前缀被复用。唯一新增的 token 就是压缩提示词本身。

不过这意味着我们需要预留一个「压缩缓冲区」，以便上下文窗口中有足够空间容纳压缩消息和摘要输出的 token。

上下文压缩很棘手，但幸运的是，你不需要自己去踩这些坑——基于我们在 Claude Code 中的经验，我们把[上下文压缩](https://platform.claude.com/docs/en/build-with-claude/compaction#prompt-caching)直接构建进了 API，这样你就可以在自己的应用中套用这些模式。

## 经验总结

以下是我们发现在构建智能体时优化提示词缓存有用的几个模式：

1.  **提示词缓存是前缀匹配。** 前缀中任何位置的任何改动都会使其后的所有内容失效。围绕这一约束设计你的整个系统。把顺序搞对，大部分缓存就免费生效了。
2.  **用消息代替系统提示词改动**。你可能会想编辑系统提示词来做诸如进入计划模式、更改日期等事情，但把这些插入到对话中的消息里实际上更好。
3.  **不要在对话中途更改工具或模型。** 用工具来建模状态转换（如计划模式），而不是更改工具集。延迟加载工具，而不是移除工具。
4.  **像监控正常运行时间一样监控你的缓存命中率。** 我们对缓存中断设置告警，并将其视为事故。[几个百分点的缓存未命中率](https://claude.dev/blog/what-a-task-costs-on-opus-5-5/)就能显著影响成本和延迟。
5.  **分叉操作需要共享父级的前缀。** 如果你需要运行一个旁路计算（上下文压缩、总结、技能执行），使用相同的缓存安全参数，这样你就能在父级前缀上获得缓存命中。

Claude Code 从第一天起就是围绕提示词缓存构建的；为了在构建智能体时获得最佳效果，我们建议你也这样做。
