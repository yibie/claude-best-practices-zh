# 使用 LLM 保护源代码安全
模型能力正在快速且不均衡地进步。我们一直[与安全团队合作](https://www.anthropic.com/glasswing)，在他们自己的代码和开源软件中寻找并修复漏洞，这项工作让我们更好地理解了如何使用模型来保护源代码安全。**我们的主要结论是：发现漏洞如今很容易并行化，瓶颈已经转移到验证、分类和修复上**。

为了说明这种差距，作为我们[自身扫描](https://www.anthropic.com/research/glasswing-initial-update)开源软件工作的一部分，截至 2026 年 5 月 22 日，我们已披露 1,596 个漏洞。据我们所知，其中 97 个已被修复。

本指南将介绍如何与 Claude Opus 协作构建威胁模型、在你的代码库中发现漏洞，然后验证、分类并修复它们。虽然我们并非掌握所有答案，但会分享各团队如何扩展发现规模，以及在后续阶段哪些做法有帮助。_立即从[配套仓库](https://github.com/anthropics/defending-code-reference-harness)开始_，其中包含用于交互式工作流的 Skills（技能）以及用于自主扫描的演示执行框架（harness）；阅读时我们会指出实现每个步骤的 Skill。

## **发现与修复循环**

发现并修复漏洞最多的团队，最终都收敛到现有最佳实践的一种变体上。我们将其提炼为六个步骤：

1.  **威胁模型：** 在开始扫描之前，先确定什么算作漏洞。
2.  **沙箱：** 构建沙箱环境，隔离智能体并验证漏洞可利用性。
3.  **发现：** 让模型在你的源代码中寻找漏洞。
4.  **验证：** 独立确认哪些发现确实可利用。
5.  **分类：** 对发现去重、评定严重程度，并确定修复优先级。
6.  **修复：** 应用修复，确认漏洞已被消除，并搜索变体。

在威胁建模和沙箱上的一次性投入，为防御者的循环提供动力——这是一个由发现、验证、分类和修复组成的重复循环——其中瓶颈不是发现漏洞，而是之后的一切。

前两个步骤——构建威胁模型和沙箱——是循环其余部分的准备工作。这些通常每个代码库做一次，并在底层系统发生变化时重新审视。接下来的四个步骤是你要针对源代码运行的循环：发现、验证、分类和修复。

对代码库的首次运行通常发现的漏洞数量最多。后续运行往往发现的漏洞更少——但通常更复杂——因为较简单的漏洞已在之前的运行中被修复。不过，不要指望第 _n_ 次运行就没有新发现。模型具有随机性，大型代码库可能有一条长尾漏洞，即使代码未变也会持续零星出现。

在代码库的第一次迭代中，你应该多次运行该循环，根据净新增发现的数量以及你对该系统的风险容忍度来决定何时停止。在第一次迭代之后，继续扫描：（1）定期扫描，或（2）每当代码发生实质性变化时扫描。

接下来，我们将详细讲解每个步骤，解释它为何重要、产出什么，以及如何实现。

## **1\. 威胁模型：定义什么算作漏洞**

误报最常见的原因是模型对你的信任边界缺乏良好理解。模型可能将代码标记为存在漏洞，因为它假设客户端可能发送损坏的值，或攻击者可能控制配置，而这些输入在你的环境中实际上是_受信任的_。反过来，模型可能假设一个面向互联网的服务仅限内部使用，从而漏报真实漏洞。在这两种情况下，模型对威胁模型的理解有误，而非代码有误。

> “一个团队注意到其发现中的一个模式：模型在拥有完善记录的威胁模型、系统设计文档、需求和约束的系统上表现最好。当威胁模型定义清晰时，模型的发现‘有 90% 的情况下是可利用的’。”

你可以与 Claude 分两步构建威胁模型：

**首先，从代码、文档和漏洞历史中引导生成。** 把你会交给一位新入职安全工程师第一天的材料喂给模型：架构文档、wiki、入口点、git 历史和过往漏洞。这有助于克服仅从代码推断隐性知识、权衡和设计决策的挑战。然后，让模型创建一个包含系统上下文、资产、入口点和信任边界的威胁模型。最后，让模型对过往缺陷进行聚类，并列出相关的漏洞类别。确保威胁模型记录了你关心和不关心哪些漏洞，以及原因。

> “一个团队审查了数百个过往 CVE 和安全修复提交，将它们提炼为‘缺陷形态’提示，并向模型提出两个问题：修复是否完整，以及是否已应用到其他所有地方？他们在一小时内发现了三个可利用的问题。正如他们所说：‘“过去人们利用过什么”有时比“在这个代码库中帮我找漏洞”更容易成为通往成功的捷径。’”

**其次，让模型采访一位熟悉该系统的人。** 可以考虑 [Shostack 的四个问题](https://github.com/adamshostack/4QuestionFrame)：_我们在构建什么？可能出什么问题？我们正在如何应对？我们做得怎么样？_ 先运行引导生成步骤，这样受访者不必从零开始。这样，他们不必花数小时研究并从零构建威胁模型，而是可以从草稿开始。虽然采访步骤是可选的，但它增加了模型无法从代码或文档中获得的上下文，从而改进威胁模型。

一些实践可以带来很大差别：

-   **考虑依赖项的安全策略。** 许多开源项目会发布此类策略。例如，vLLM 的 [`security.md`](https://docs.vllm.ai/en/latest/usage/security.html)、SQLite 的[“Defense Against the Dark Arts”](https://www.sqlite.org/security.html)以及 [ImageMagick 的安全策略](https://github.com/ImageMagick/ImageMagick/security/policy)。你的威胁模型应直接考虑它们，而不是从零重建策略。
-   **明确什么是受信任的。** 如果你信任配置文件或已认证的客户端，请在威胁模型中记录这一点。这些假设有助于将不可利用的缺陷与实际漏洞利用区分开来。
-   **随代码包含一个 `THREAT_MODEL.md`。** 将其放在仓库中，并随代码变化更新。发现智能体随后可以在搜索前阅读它，跳过已知的非问题。

你将在两个地方使用威胁模型。在发现阶段，作为范围界定：划分代码、确定目标优先级，并跳过范围之外的内容。这有助于处理你无法完全扫描的大型代码库。在分类阶段，作为过滤器：在广泛扫描之后，使用威胁模型更好地校准严重程度，使其符合你的系统和环境。

> “一个团队在扫描一个大型项目时误报率达到 40%，并深入调查了原因。这些发现是可复现的，PoC 也证明了可利用性。但拥有该代码的开发团队将其视为误报而驳回，因为这些缺陷不符合项目的威胁模型。另一个团队的首席信息安全官（CISO）一语中的：‘[模型]对代码有良好的上下文，但对我们没有良好的上下文。’”

**试试 [threat-model Skill](https://github.com/anthropics/defending-code-reference-harness/tree/main/.claude/skills/threat-model)。** 它涵盖本节描述的两个步骤——`bootstrap` 从你的代码、CVE 和 git 历史中推导出草稿，interview 则通过 Shostack 的四个问题引导系统负责人完善它。输出是一个 `THREAT_MODEL.md` 文件，用于发现和分类步骤。

## **2\. 沙箱：安全运行智能体并验证可利用性**

**沙箱的一个目的是保护你的系统。** 为了让模型能够安全、自主地运行，你需要一个强大的隔离层。没有它，智能体可能超出目标范围，做出意料之外的事情。

> “一个团队告诉模型它没有网络访问权限——而实际上它有——模型发现它仍然可以从 GitHub 获取内容。另一个团队观察到智能体在扫描中途回答了一个 GitHub issue。这两个行为都不是恶意的，但都表明需要通过代码和配置来强制执行约束。”

让隔离程度与你的威胁模型相匹配。容器对于阅读代码的发现智能体来说足够了，但要在 microVM（如 Firecracker）或完全锁定了出站流量的完整 VM 中运行目标及其 PoC，这样任何东西都无法触及你的生产系统。并且绝不要让凭据（`~/.aws`、`~/.ssh`、`.env`）对智能体可用。

仅在设置沙箱时给予网络访问权限。拉取依赖项、构建、安装工具、部署目标，并运行现有测试以确认一切正常。然后，对环境做快照并移除其网络访问权限。在扫描期间，仅允许发往模型 API 的流量，并通过本地代理路由。在每次运行开始时加载快照，使每次扫描都从相同的干净状态开始。

**沙箱的另一个目的是证明可利用性。** 在静态扫描期间，模型阅读代码并推测什么可能出问题，但它无法测试某条路径是否可达，或是否存在补偿性控制。因此，模型可能标记出你实际上并不关心的、不可利用的代码正确性缺陷。当团队构建了一个沙箱，让智能体能够编译代码、运行测试并引爆概念验证时，不可利用的发现显著减少。

> “一个进攻性安全团队构建了一个执行框架（harness），为智能体提供测试台，并采用简单的验证规则：只有当智能体能够构建概念验证并在测试台上运行时，才算真正的阳性。他们六周后的评估是：‘最大的效能杠杆是给模型提供测试台、实时系统和运行 PoC 的能力。’”

构建沙箱时，尽可能固定一切，使每次运行都在相同环境中使用相同代码：镜像标签、提交 SHA、依赖项和构建命令。缓存本地副本，使构建无需网络，并力求容器持久化，以便多个测试循环可以直接加载它。

> “一个团队的扫描标记了一个漏洞，结果发现这是智能体下载了旧版本库而非实际部署版本所导致的副产品。一位工程师阅读了记录，发现正在下载的是不同的依赖项，从而发现了这一点。他们现在构建 Docker 容器时，将依赖项固定为与生产环境匹配，这样发现智能体和验证智能体操作的就是攻击者会面对的相同产物。”

构建足够忠实于生产环境的沙箱很重要。排除依赖项（如队列或数据存储）可能导致漏报生产环境中可能存在的缺陷。反过来，忽略生产防御措施（如 WAF 或认证网关）会导致模型报告你的生产环境已经缓解的不可利用发现。

尽管如此，如果由于云依赖、数据存储或其他现实复杂性而无法构建有代表性的沙箱，请从发现步骤（见下文）开始。你不一定需要在沙箱中运行 PoC。前沿模型擅长仅通过分析源代码来发现漏洞。包括我们自己在内的多个团队都发现这很有效。权衡在于验证阶段，没有运行中的目标，我们无法用 PoC 证明发现，因此要为验证预留更多时间。你也可以稍后投资沙箱，等发现的数量足以证明其合理性时再做。

**参考[执行框架 `README.md`](https://github.com/anthropics/defending-code-reference-harness/tree/main/harness) 了解参考沙箱。** 在此实现中，智能体和目标运行在 gVisor 隔离的容器中，出站流量锁定到模型 API。目标从固定到特定提交的 Dockerfile 构建，由 [`setup_sandbox.sh`](https://github.com/anthropics/defending-code-reference-harness/blob/main/scripts/setup_sandbox.sh) 处理设置阶段。

## **3\. 发现：提供丰富的上下文、更短的提示词和有用的工具**

让发现智能体能够按需加载上下文，例如威胁模型、架构文档和过往扫描结果。当智能体理解你的信任边界以及系统实际如何部署时，它就能更好地识别你系统特有的漏洞。

我们发现，前沿模型在发现阶段受益于越来越简单的提示词。与直觉相反，更具规定性的提示词会让发现效果变差——冗长的检查清单往往会降低模型的创造力，产生更少的新颖缺陷。以下是一些在发现阶段有帮助的提示技巧：

-   **提供目标和上下文。** 说明“为什么”和“是什么”——为什么扫描、什么样的发现才算重要、正在扫描什么系统——把“如何扫描漏洞”留给模型。前沿模型在安全任务上越来越擅长，过度规定可能会限制它们尝试的范围。
-   **尝试要求特定的漏洞类别。** 如果你想聚焦于由过往 CVE 或代码库语言引导的特定类型漏洞，就明确说出来。描述该漏洞类别、它的作用以及它通常存在于何处，以便模型能在你的代码库中识别它。
-   **定义输出。** 要求提供带有预定义字段的结构化报告，并安排字段顺序，使模型的推理建立在每个字段之上。示例字段包括理由、发现、影响、严重程度等。包含一个退出机制，让模型可以针对弱发现提前退出。

给模型提供搜索和阅读代码库的工具，例如 grep、glob 等。还要让模型使用你团队可能使用的安全专用工具，例如 SAST 扫描器或模糊测试器。询问模型特定任务需要哪些工具，并提供它们。最后，让模型按需构建工具：近期的前沿模型越来越擅长编写它们所需的工具。

> “除了源代码，一个渗透测试团队还给发现智能体提供了发送请求、检查响应和查询流量日志的工具。结果，智能体无需猜测某条路径是否可达，可以在进行过程中针对运行中的应用测试每个候选，将其真阳性率提高到接近 100%。”

让模型先对系统做一遍梳理，以划分搜索空间，例如按攻击面、端点或组件划分。然后，将这些分区喂给并行的发现智能体，使它们不会收敛到相同的浅层缺陷。最后，运行一次系统级梳理，将分区级发现作为上下文来搜索漏洞。

> “试图暴力破解发现的团队很快遇到了收益递减。一个团队说：‘我们最初只是尝试水平扩展并发送更多智能体，但看到了有限的回报。’另一个团队增加了关注区域和并行智能体的数量，得到了‘大量问题’，其中大多数彼此重复。”

如果你有运行目标的沙箱，请让发现智能体为发现构建 PoC，例如脚本、导致崩溃的输入或失败的测试。构建 PoC 有助于智能体迭代并确定发现，而产物为验证智能体提供了具体证据来评估。尽管如此，智能体无法复现的发现仍然可以报告，标记为未证实，以保持高召回率。

**[`vuln-scan` Skill](https://github.com/anthropics/defending-code-reference-harness/tree/main/.claude/skills/vuln-scan)** 在此阶段很有帮助。它读取你的 `THREAT_MODEL.md`，将目标划分为关注区域，并为每个区域分派并行的审查智能体。输出是结构化发现，供后续步骤直接使用。

## **4\. 验证：过滤掉不可利用的发现**

发现优化的是召回率；验证优化的是_精确率_。换句话说，发现应尽可能多地找到漏洞——即使是不太可能的漏洞——而验证应排除实际上不可利用的发现。当智能体试图在同一步骤中同时做_两件事_时，它可能会自我审查，排除可利用的真阳性。我们吃过这个苦头：让发现智能体同时验证发现，导致它们过滤掉了单独的验证步骤本会确认的真阳性。

验证智能体应独立于发现智能体。在没有共享文件系统或对话历史的全新容器中运行验证器。如果验证器接触到发现智能体的推理，它可能只是同意而不是测试该主张。因此，只给验证器（1）概念验证或书面发现，以及（2）代码库，以便它可以搜索发现者遗漏的缓解措施（例如上游验证、认证网关、类型约束或不可达代码）。

如果单次验证仍让太多不可利用的发现通过，尝试运行多个独立的验证器。它们可以考虑不同角度或使用不同模型运行。然后，采取多数投票。还可以考虑设置一个单独的裁判来决定发现智能体和验证智能体结果之间的取舍。

提示验证智能体去证伪发现智能体的发现。让验证器假设每个发现都是误报，并寻找该发现错误的理由。包含明确的标准，供验证智能体判断发现是否为真阳性。当发现智能体的输出不包含 PoC 时，这一点最为重要。目标是尽可能排除不可利用的发现，以减少人工审查的工作量。

> “在我们合作过的团队中，添加对抗性验证器大致将发现阶段的不可利用发现率减半。要求验证器同时构建确认漏洞利用的概念验证，将误报率降至接近零。这两个步骤共同显著减少了下游的分类和修复负担。”

如果你能在沙箱中充分复现生产环境（见步骤 2），请提示验证智能体构建并执行可复现的概念验证（PoC）。如果 PoC 有效，你可以断定该发现可利用。注意反过来并不成立——未能生成有效的 PoC 并不能证明是误报。

> “一个扫描开源软件包的团队构建了一个帮助闭环的验证步骤：扫描软件包、生成概念验证，然后部署一个使用该软件包并触发 PoC 的模拟应用。他们的看法是：‘验证是最大的瓶颈，而 PoC 就是验证。’”

## **5\. 分类：按根本原因去重，按前置条件和影响排序**

验证确认发现可利用，而分类评估修复优先级。以前，当发现需要更多精力时，发现缺陷的工程师也负责分类。如今，模型能在午饭前找到上百个候选，分类已成为瓶颈。

恰当的分类有助于防止告警疲劳。如果你提交太多重复或严重程度虚高的缺陷，产品工程师可能会不再阅读它们，即使是需要立即修复的也不例外。开源维护者尤其可能被未分类的发现淹没，因为他们会收到来自许多依赖其软件的不同用户的报告。

> “多个团队分享了同样的教训：如果我们给产品工程师发送一堆发现，其中大多数不可利用，他们就会对报告失去信任并放弃。他们还会优先处理严重和高危发现，以避免让下游工程师不堪重负。其他团队通过让模型处理现有积压——来自先前扫描器、先前模型、漏洞赏金接收的未解决发现——在几天内清理了数百个陈旧条目，从而取得了成功。”

要对发现去重，考虑根本原因。扫描器通常会在多个调用点标记同一个缺陷，或报告单一根本原因的多个症状。这里有一个实用方法：首先，使用廉价的确定性处理：同一文件、同一类别、漏洞行号彼此相差十行以内。然后，让模型对剩余项应用定性规则：

-   **视为重复**：同一根本原因的不同表述；同一漏洞在多个调用点被报告；缺失的全局保护（如认证检查）按端点分别报告；或同一路径中标记的原因及其后果。
-   **视为不同**：同一文件中的不同漏洞类别；不同变量到达不同汇聚点；一个辅助函数内的两个独立缺陷；两个端点上相同的缺失检查，但各自需要自己的修复。

如果你的执行框架为每个发现生成 PoC 和补丁，另一种去重方法是检查一个发现的补丁是否也解除了其他发现的 PoC。

去重后，根据以下方面评定每个发现的严重程度：

-   **可达性。** 攻击者能否从真实入口点到达此代码，还是只能从内部代码和端点到达？
-   **攻击者控制。** 不可信输入是否完整到达汇聚点，还是上游有东西对其进行了净化或约束？
-   **前置条件。** 缺陷触发需要具备什么条件：非默认设置、特定功能标志、攻击者必须命中的狭窄时间窗口？
-   **认证。** 未认证的攻击者能否触发它，还是需要已登录用户或管理员？
-   **读与写。** 攻击者只能读取数据，还是也能修改数据？
-   **影响范围。** 如果 PoC 触发，谁受影响？一个用户还是所有用户，一个租户还是整个平台，用户态还是内核？

要将评分标准转化为分数，让模型在分配严重程度之前先写出对每个问题的回答。先梳理证据可以防止模型锚定在缺陷类别上（“SQL 注入，所以是严重”），然后为了匹配而抬高严重程度。作为起点：零前置条件且未认证的远程访问是严重或高危。一两个前置条件，或需要认证的路径，是中危。三个或更多，或仅限本地，是低危。根据你的系统调整阈值。

模型可能因为上下文不足而抬高严重程度。它们可能不知道攻击者实际控制哪些输入，或者看不到补偿性控制。前者的一个例子：SQL 注入如果由未认证请求触发则是严重的，但如果由仅管理员可用的配置文件触发则不是问题。对于后者，阻止漏洞利用的上游 WAF 或认证可能仅从源代码中看不到。

解决方案是在分类期间提供威胁模型，告诉模型你在系统中关心和不关心哪些类型的漏洞。例如，澄清“我们信任已认证的客户端”可以简化或消除一整类严重问题。

> “一个团队发现，除非有可验证的依据，或对某事物是否属于威胁模型的预期有更多上下文，模型往往过度自信。他们的解决办法是给分类智能体提供与发现智能体相同的威胁模型。”

**试试 [`triage` Skill](https://github.com/anthropics/defending-code-reference-harness/tree/main/.claude/skills/triage)。** 它同时进行验证和分类：对每个发现进行多轮投票验证、跨运行去重，并按推导出的可利用性重新排序。输出是一份简短、排序、有归属的列表，而不是原始堆砌。

## **6\. 修复：闭环并为下一轮改进上下文**

修复是你闭环并修复漏洞的地方。它还有助于根据已验证的发现改进威胁模型——更新需要更多审查的信任边界或组件——并将过往发现作为下一次扫描的上下文。每个循环都会强化代码库，并使下一次扫描信息更充分。

在修复之前，编写一个在现有代码下会失败的新测试。然后，实施修复并确认同一测试现在通过，且没有破坏其他任何东西。（是的，这是测试驱动开发）。如果你不添加测试，修复可能会悄悄回归，而且事后很难证明该缺陷是真实的。

> “一位渗透测试人员发现他们生成的补丁不一致——有些好，有些坏——直到执行框架告诉模型通过针对已修复代码重新运行概念验证来验证补丁。通过给模型提供可迭代的反馈，补丁质量大幅提升，节省了人工审查时间。”

模型可能只狭隘地处理特定调用点的发现，而不是根本原因。简单地提示模型识别并修复根本原因可能很有效。然后，让模型在两个层面寻找变体：（1）相同模式，即其他地方存在其他调用点或同一缺陷代码的副本；（2）相同类别，即存在一个 SQL 注入漏洞的代码库往往有更多 SQL 注入漏洞。用已验证的发现和补丁更新威胁模型以闭环。

在发布补丁之前，运行对抗性检查。让一个新的发现智能体以攻击者身份探查补丁，以确认补丁是全面的。然后，简化生成的补丁，以处理过于侵入性的补丁。最小化补丁更易于审查，也更不可能引入新缺陷。提示要求做出修复根本原因的最小改动——不重构、不顺带清理、不重新格式化。

> “一个团队关于他们最常见的补丁失败：‘推荐的补丁往往尽可能严格，以至于会破坏与其他服务的连接。它能解决问题，但会破坏让服务正常工作的依赖关系。’”

你可以通过一系列检查来验证每个补丁，从最廉价的开始：

1.  **构建。** 补丁编译通过，新测试通过。
2.  **尝试复现。** 原始 PoC 应停止工作。这能捕获无效补丁。
3.  **检查回归。** 原始测试套件仍然通过。这能捕获损坏或过度严格的补丁。
4.  **重新攻击。** 一个新的发现智能体运行对抗性检查。这能捕获不完整的补丁。

最后，虽然模型可以编写补丁，但仍需人类负责。生成的补丁可能以可预测的方式失败——修复症状而非根本原因、阻止合法输入，或移除对依赖服务的访问。目标是尽可能验证每个补丁，使人工审查所需精力更少。目标是帮助开发团队专注于模型可能不了解的细微之处（例如即将到来的变更、代码风格），同时只需最少的审查和补丁更新。

**试试 [`patch` Skill](https://github.com/anthropics/defending-code-reference-harness/tree/main/.claude/skills/patch)。** 它消费分类输出，为每个发现生成候选差异，并由独立的审查智能体检查每一个。

## **开始使用**

试着自己运行这个循环。克隆 [`defending-code-reference-harness`](https://github.com/anthropics/defending-code-reference-harness)，并在 Claude Code 中运行 `/quickstart`。它会引导你完成一个交互式工作流，从威胁建模到扫描再到分类，针对一个演示目标。该仓库还包含一个自主执行框架和一个 /customize Skill，用于为你的环境更新执行框架。

然后，在你自己的代码上运行它。选择一个服务或软件包。从代码和文档引导生成威胁模型，并完成采访。投入精力构建你环境的沙箱。扫描。用独立的智能体验证发现。根据你的标准分类，并审查所有评为高危及以上的项。修复。然后定期重新扫描。

你的第一次扫描会暴露比你预期更多的发现。大多数需要验证和分类。在预算更多扫描之前，先为扫描_之后_的流水线做预算。

一些你可能会觉得有用的资源：

-   [`defending-code-reference-harness`](https://github.com/anthropics/defending-code-reference-harness)：配套仓库，包含用于交互式工作流的 Skills 以及用于自主运行的演示执行框架。
-   [`claude-code-security-review action`](https://github.com/anthropics/claude-code-security-review)：GitHub action，让 Claude 在每个拉取请求（PR）上担任安全审查员。
-   [Threat Intelligence Enrichment Agent](https://platform.claude.com/cookbook/tool-use-threat-intel-enrichment-agent)：构建智能体以根据威胁情报源丰富入侵指标的 Cookbook。

## **展望未来**

我们相信，模型在代码中[发现和利用漏洞](https://red.anthropic.com/2026/exploit-evals)正变得越来越容易。因此，我们作为防御者的工作，是在对手利用之前发现并修复我们代码中的漏洞。一些团队甚至已将他们的执行框架连接到事件：漏洞赏金报告触发自动变体分析，安全审查触发扫描并附上候选发现，或已验证的漏洞更新静态分析工具以防止未来再次发生。

这项工作至关重要且风险很高。但如果做得好，它是一场更大、更有希望的转变的开端——我们将_能够_在攻击者利用漏洞之前发现并修复它们。
