# 用 Claude 自动化评估设计与爬山优化

评估（eval）能提供信号，说明你的应用或 skill 在特定任务上表现如何。但设计评估，并在评估上提升表现而不自欺欺人，是件难事。我们已在 [claude-api skill](https://github.com/anthropics/skills/tree/main/skills/claude-api) 中为这两件事都加入了指导。

借助该 skill，你可以运行 `/claude-api build-eval` 在你的代码库中构建一个评估，并运行 `/claude-api hillclimb` 针对该评估改进你的应用，一次只做一处改动，并用一组留出的示例来捕捉过拟合。

在本文中，我们先重点介绍良好评估设计与爬山优化的原则，然后展示 [Claude Code](https://claude.com/product/claude-code) 配合 `claude-api` skill 如何应用这些原则。最后，我们会展示这些命令的几个示例。

## 评估设计

设计良好的评估有几个共同要素（图 1）：

1.  **评估任务反映生产环境。** 从你在"生产环境"中关心的任务里采样，也就是你正在测试的能力或应用将被使用的场景。有时任务之所以被选中，是因为它们容易生成或容易评分。但重要的是确保任务分布代表你_真正_关心的内容。
2.  **性能随更强的模型和更多的思考而提升**。能力更强的模型和[更高的 effort 设置](https://claude.dev/blog/spending-your-effort/)通常应该在评估上表现更好。如果不是这样，那么往往是模糊的任务或校准不当的评分器拖累了性能。
3.  **前沿存在"可通过"的余量**。能力最强的模型在最高 effort 下应该明显低于 100%，否则你无法可靠地判断改动如何影响性能。重要的是，这一差距不应由不可能或模糊的任务来解释：一个常见的迹象是某个任务在每次评估运行中都失败，无论重复多少次。好的任务是两位领域专家会得出相同结论、且评分器检查的所有内容都在任务中明确陈述的任务。
4.  **运行间方差低**。高方差通常源于设计不佳、模糊的任务，或对相同输出给出不同判定的评分器。方差也可能隐藏在配置中。例如，effort 可能没有被一致地应用。此外，环境也会影响评估结果：早期试验遗留的状态（一个文件、一段 git 历史）可能把答案直接交给智能体。

### 对抗性采样

模型能力是参差不齐的。如果你因为今天的模型在这些案例上失败而挑选它们，你就是在对某个模型能力曲面的低谷进行采样（图 2）。评估最终可能衡量的是该模型的失败指纹，而不是你的应用在本质上困难或有价值的事情。

![两个面板，绘制任务空间上的能力分布，每个面板中今天的模型是一条参差不齐的曲线，下一个模型是位于其上方的更平滑的曲线。左侧，在今天的模型失败处采样的案例只落在其低谷中；右侧，由人判定为困难的案例分布在波峰和波谷之间，并带有少量不应触发的案例。](https://claude.dev/media/6a014fa959cbc13b3026ca0f2ac1cb8754d541bd07da79bb4c61d81af428024a.png)

**图 2** 对抗性采样

挑选困难案例，是因为人判定它们困难：一个有用的测试是，在纳入某个任务之前，你能说出它为什么困难。纳入那些源自生产流量、bug 报告或工单的、你应用中的具体失败案例。然而，不要盲目信任用户流量：用户有时会尝试他们预期能奏效的东西，因此严格从用户流量中抽取的任务分布可能偏简单。

## /CLAUDE-API BUILD-EVAL

claude-api skill 中的 `build-eval` 命令将这些原则转化为一个引导式工作流。当你在 Claude Code 中运行 `/claude-api build-eval` 时，Claude 会采访你，在你的代码库中构建评估，并在特定节点暂停等待批准。

### 设计示例

Claude 按以下顺序帮助你采样输入以构建评估：

1.  生产对话记录，在询问留存与敏感数据相关事宜之后。
2.  bug 报告和支持工单。
3.  你手写的五到十个案例。
4.  从你的代码库合成的案例。

该 skill 优先使用生产流量，但也可以基于你提供的少量真实示例生成合成数据。该 skill 指示 Claude 生成一个简单页面，向你展示每一个输入，并等待你确认。作为示例，下面我们展示该 skill 可能要求用户审阅的一组电子邮件路由应用的输入示例（图 3）。

### 验证评分器

在输入之后，Claude 会提出最适合你应用输出的最廉价评分器：

-   **程序化验证**：如果输出可能性受限，它使用基于代码的检查（精确匹配、来自固定集合的标签、符合 schema 的 JSON、通过的测试）。
-   **LLM 作为评判者**：如果输出空间是开放式的，有许多有效答案但有明确的质量标准，它会默认使用这类检查。在这种情况下，第二个模型读取输入、输出和以可检查断言形式编写的评分标准（而不是 1 到 5 的评分量表），并返回分数及其推理。如果你有可比较的基线，评判者则改为以随机顺序读取两个输入，不被告知哪个是基线，然后选出更好的那个。评判模型由你选择，且不应是你正在测试的模型。

Claude 会对少量案例评分，并询问你是否会对其中任何案例给出不同的评分（图 4）。一般来说，在相信你的评估器之前，[阅读一部分已评分的对话记录](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)很重要；评分失败是评估配置错误最常见的方式之一。

当你验证完评分器后，该 skill 会告诉你评估集的规模（案例数 × 重复次数 × 模型，以及大致耗时），运行基线，并打印带有置信区间的分数。你会得到：案例、评分器、运行器、每个案例一行 JSON 和一份完整对话记录，以及一个列出每个案例分数并附有其对话记录链接的普通页面。如果你想要该页面之外的内容（例如图表），直接提出即可，Claude 会在旁边作为额外页面构建它。默认情况下，这些额外页面是本地打开的静态文件，不从网络加载任何内容。

![该 skill 为收件箱路由评估生成的结果页面：基线在 24 个案例上的平均正确率为 0.681，然后是一个逐案例分数表，附有每次重复的链接。一个重复链接会打开该案例的原始 JSON 追踪记录，并排显示。](https://claude.dev/media/9c7c2f00ebdd0f9e6b8ad0d3de8cdcc6ebb162c9d2fa5b4f4950ac36b736aef8.png)

**图 4** 生成的结果页面示意图，附有每个输入的推荐评分。

### 诊断检查

在上述基线运行期间，Claude 会检查若干事项：

-   **评分器**：Claude 对同一输出运行评分器两次，并报告判定是否发生变化。
-   **基础设施**：Claude 检查超时、API 错误和答案截断，以确保基础设施噪声不会被当作模型方差。
-   **余量**：如果基线已经得分约 95% 或更高，该 skill 会警告用户，并提示爬山优化应着眼于探索成本或延迟，而非质量。

## 爬山优化

现在你有了可靠的手段来评分你的应用在任务上的表现，你可以尝试改进它。爬山优化是调整 effort 或提示词等参数的有效方式，这些参数在成本与性能之间权衡。关于选择在何处应用它，有一些通用建议：

-   **廉价迭代** - 修改你专注于爬山优化的那个表面，应该成本低廉（就时间、成本和精力而言）。许多内部工作和客户都将爬山优化聚焦于文本，例如提示词和 skills。这些容易修改和回退。相比之下，在爬山优化期间对智能体执行框架（harness）进行开放式修改可能涉及大量代码改动。
-   **可归因** - 评估分数的变化应可归因于你在爬山优化期间修改的表面。例如，若干成功的爬山优化应用聚焦于 [skill 触发](https://claude.com/resources/articles/improving-skill-creator-test-measure-and-refine-agent-skills)。评估指标（该 skill 的触发率）与被修改的 skill 描述直接耦合。
-   **目标范围明确** - 一种常见的失败模式是开放式地要求提升性能，而不仔细考虑评估中可用的余量；接近饱和的评估或范围界定不佳的表面（例如开放式地要求更新执行框架）更可能停滞。在各种工作中一个普遍有力的目标是成本：即使评估已饱和，你也可以要求 Claude [寻找降低成本的方法](https://claude.com/blog/reducing-cost-and-improving-performance-with-claude-platform)，同时保持性能持平。

### 过拟合

即使是设计良好的评估，也很少能精确匹配你在生产环境中关心的任务分布。因此，"过拟合"到评估上是一个常见问题，会导致系统在评估上的表现优于生产流量。

评估有多种方式"泄漏"进你的执行框架（模型周围的代码，包括提示词、工具和调用 Claude 的循环）。例如，考虑一个受益于 OCR 的评估任务，但 OCR 在你的生产任务中很少有益。评估执行框架可能会向你的应用添加一个 OCR 工具，这在基准测试上有所提升，但对生产毫无影响。更广泛地说，爬山优化可能会向该执行框架添加功能，以处理你所选特定评估示例中的边缘情况。这些执行框架的添加提升了你的评估分数，但不会转化为生产中的改进（图 5）。

![左侧是基准测试的特征，每个特征在右侧塑造了执行框架中对应的添加：需要 OCR 的任务组合添加了 OCR 工具，/app 中的任务添加了"始终 cd /app，运行 pytest"，独特的措辞得到了调优的提示词，你读过的失败各得到一个补丁。一条虚线箭头标记了彻底的泄漏：一个带有答案的公开仓库让执行框架可以 curl 参考解决方案。](https://claude.dev/media/a328a3f4d5bfd0967174ef2ca79bc8f094d8db3c12af71be3189891bf40d0e53.png)

**图 5** 执行框架过拟合的常见原因。

有三件事可以帮助解决这个问题：

-   **拆分案例**。使用爬山优化器可以读取的训练集，以及从未见过的测试集。如果训练集分数提升而测试集分数持平，那么这是一个常见的过拟合警告信号。
-   **绝不把失败粘贴进提示词**。如果爬山优化器读取了失败的对话记录，它绝不应把失败内容粘贴进提示词。
-   **在结构上让答案处于模型触及范围之外**。模型有时会通过直接找到评估答案来进行"奖励黑客"。

如下文所述，claude-api skill 会为你应用这些原则。

## /CLAUDE-API HILLCLIMB

claude-api skill 中的 hillclimb 命令将这些原则转化为一个引导式工作流。当你在 Claude Code 中运行 `/claude-api hillclimb` 时，Claude 会迭代以针对给定评估进行改进。你选择它可以做哪些改动，包括：

-   你的系统提示词
-   Skills 或指令文件
-   工具描述
-   模型选择、effort 级别和其他 API 参数
-   你的执行框架代码

在开始之前，Claude 会询问你想优化什么（例如性能，或在保持性能的同时降低成本），然后随机将评估集拆分为测试集和训练集。若目标是成本，它会考虑[几个常见的成本驱动因素](https://claude.com/blog/reducing-cost-and-improving-performance-with-claude-platform)，包括提示词缓存、审查提示词与所选模型的兼容性，以及挑选模型和 effort 设置。

在第一轮之前，Claude 会检查评估的噪声（仅凭偶然分数可能波动的幅度）是否小于你会采取行动的最小改进；如果不是，它会说明并建议增加重复次数或案例。

每一轮，Claude 读取上一轮的训练对话记录，并作为补丁提出一处改动。它每轮都瞄准一个效果能在评估噪声之上显现的改动：它从根源上修复失败行为（例如重写导致该问题的章节或添加缺失的规则），而不是改写某一行。然后它运行带有该补丁改动的评估。此时，Claude 会应用一项检查：如果 `train` 集提升但 `test` 集持平，Claude 怀疑过拟合并回退该补丁。如果出现退化，Claude 回退。如果训练集和测试集都提升，它保留该补丁（图 6）。

![爬山优化循环：被编辑的对象（例如提示词）馈入一个固定的模型和执行框架，后者在留出的测试集和训练集上评分。分析器只读取训练集失败，并每轮提出一个 diff；当训练集和测试集都上升时保留该 diff，当只有训练集上升或任一分数下降时回退。](https://claude.dev/media/dafbc5fb0edf5aeed96af8984ec09f6a0f8ebd753274c305ccf3043e1640d75a.png)

**图 6** 爬山优化器使用的流程。

当分数停滞两到三轮时，Claude 读取每个剩余的失败案例并按原因分类。如果没有任何单一修复能带来超过评估噪声的收益，它也会提前这样做，并建议增加重复次数或案例，而不是把轮次花在太小而无法衡量的改动上。这一步可以捕捉模糊的评估案例、执行框架错误或运行间方差。

只有合法的失败才会被纳入更多爬山优化轮次。

爬山优化完成后，Claude 会将你的代码留在针对你的目标在测试集上表现最好的版本。它会报告测试结果相对于基线的置信区间（图 7）。如果收益在噪声范围内，它会说明并建议不要合并。

![爬山优化后的收件箱路由结果页面，在训练集和测试集分数上比较三个变体。变体 v1 定义了每个队列并添加了平局决胜规则，在两者上均以 0.875 标记为最佳；变体 v2 添加了两个示例，因训练集上升而测试集持平而被回退。](https://claude.dev/media/8c9b0ffdf9d75df81ec451ccb55feb091693fb7eb88ad9c20f3911387e3ec4e1.png)

## 示例

### 为降低成本而爬山优化

我们在一个[内部客户支持基准测试](https://claude.com/blog/reducing-cost-and-improving-performance-with-claude-platform)上运行了 `/claude-api hillclimb`，目标是降低成本并提升性能。该基准测试包含 44 个工单，其中 30 个用于搜索，14 个留出。它从 Opus 4.8 在默认（高）effort 设置下开始，在搜索工单上的决策准确率为 74.4%，每个工单的 token 成本为 4.6 美分。

爬山优化首先审查了提示词，[移除](https://claude.com/blog/reducing-cost-and-improving-performance-with-claude-platform)了强制性的工具调用仪式、一个草稿步骤和相互矛盾的规则。然后它尝试了低 effort 的 Opus 5.5。这以 87.8% 越过了基线准确率门槛，并将成本降至每个工单 1.9 美分，不到起始成本的一半。

其中一部分节省来自 [Opus 5.5 的定价](https://claude.dev/blog/getting-the-most-out-of-opus-5-5/)：输入和输出 token 比 Opus 4.8 便宜 20%，缓存读取便宜 60%。由于 Opus 5.5 越过了门槛，爬山优化随后降一档，检查更便宜的模型是否也能越过。低 effort 的 Sonnet 5 得分大致相同，为 88.9%，成本约为一半，每个工单 1 美分（图 8）。

### 为提升性能而爬山优化

另一个例子是我们的 [claude-api](https://github.com/anthropics/skills/tree/main/skills/claude-api) skill，它提供关于使用我们 API 的指导以及使用 Claude 的通用技巧（包括本文讨论的子命令）。我们希望确保我们的 skill 能正确实现使用我们 API 的代码，并构建了一个源自我们文档的评估集来测试该 skill。

在我们的评估上，该 skill 起始为 66%。我们让爬山优化器访问文档和我们的 SDK，使 Claude 能够识别错误并自我纠正（图 9）。Claude 发现该 skill 缺少对八项功能的覆盖。

在 skill 中为它们添加章节将性能提升至 74%。随后它发现 C# 和 Java 类型表中的错误，将性能提升至 77%。

claude-api skill 评估

在三个阶段的工作中从 66.1% 提升至 87.9%

**图 9** 以性能为重点的爬山优化。

在分数停滞两轮后，Claude 分析了剩余的失败并按根因分类。普通轮次针对最常见的失败做一处编辑。这一步不做编辑；它只按原因对每个剩余失败进行分类。这一反思步骤在几个方面很有用：

-   通过跨一组失败进行反思，爬山优化器发现 skill 内容存在，但 Claude 只是写出了较旧的 API 形态（例如来自其训练先验）。为解决这个问题，爬山优化器在 skill 顶部附近添加了一个表格，引导 Claude 从它记忆中的形式转向当前形式：例如，从使用固定 token 预算的扩展思考（API 现在在最近的 Opus 模型上会拒绝这种形式）转向自适应思考，以及从旧版本的 web search 和 web fetch 工具转向当前版本。它还将针对固定预算思考的 C# 和 Java 警告移到了其自适应思考示例之上。这将性能提升至 80%。
-   尽管解决了明显的内容缺口，性能却从未提升的任务，是示例或评分器有缺陷的迹象。一个任务要求捕获一种错误类型的代码，而其评分器想要至少三种的链条。Claude 改写了该任务。另一个评分器的指令与我们的文档相矛盾，测试真实 API 表明文档是正确的。解决这些问题，再加上更多 skill 编辑，将性能提升至约 88%。

## 开始使用

**注意：** 先运行 `claude update`。claude-api skill 随 Claude Code 一起提供，因此更新即可获得这些命令的最新版本。

```shell
claude update
```

然后，在 Claude Code 中：

PROMPT

```shell
/claude-api build-eval
/claude-api hillclimb
```

这些子命令可以通过 [claude-api skill](https://github.com/anthropics/skills/tree/main/skills/claude-api) 直接在 Claude Code 中使用：

如果你想为某个特定问题生成评估集，运行 `/claude-api build-eval`。你可以通过提供对示例（例如追踪记录）的访问来引导它。Claude 将运用本文分享的指导来设计示例和评分器，并确保你批准示例和评分器。

如果你已有评估并希望 Claude 在此基础上改进，运行 `/claude-api hillclimb`，由你的目标引导（例如更好的性能，或在保持性能的同时降低成本）。Claude 将运用本文分享的指导，在爬山优化过程中检查过拟合，并检查评估本身的 bug，例如把看起来正确的答案标记为错误的评分器或执行框架错误，这些检查既在首轮之前进行，也在分数停滞时进行。
