# ABC Legal 如何借助 Claude Managed Agents 让每位员工都成为构建者

今年早些时候，美国法律文书送达公司 ABC Legal 的 CTO Brandon Fuller 向公司 1,100 名员工推广了 [Claude Enterprise](https://claude.com/solutions/enterprise)，结果立刻产生了共鸣。公司各部门的团队（送达、电子立案（eFiling）和出庭律师业务，以及市场、合规、财务等）开始自发构建自动化流程，无需任何人要求。

"我们的用户真的蜂拥而至，"Fuller 回忆道。"他们看到了 Connectors 和工具的易用性，突然间，整个组织里的人都开始自动化那些一直占用他们时间的任务。"

这正是任何 CTO 都希望看到的采用情况。但 Fuller 看到了更进一步的机会：如果 ABC Legal 还能运行一支经过版本管理、可观测且常驻的 AI 智能体集群呢？

这一雄心最终归结为基础设施。早期的智能体住在构建者碰巧放置它们的地方，作为个人桌面上的定时任务。把它们从个人机器上移走，就能让它们无人值守地运行，并让 Fuller 对已构建的内容、成本以及昨晚是否运行有一个统一的视图。

于是他部署了 [Claude Managed Agents](https://platform.claude.com/docs/en/managed-agents/overview)：一套通用的部署结构、共享工作区、统一的审计与计费界面，以及运行在云端而非个人笔记本电脑上的常驻智能体。

截至 2026 年 7 月，Fuller 和他在 ABC Legal 的团队已记录：

-   生产环境中使用 Managed Agents 构建的智能体超过 50 个
-   在重度优化之前，部分智能体所覆盖的人工任务成本最多降低约 50%
-   各部门约 310 名员工使用 Claude 进行日常工作

以下是他们如何走到这一步，以及在此过程中学到了什么。

## 从热情到工程化：把每个智能体当作软件来对待

在首次部署 Claude Managed Agents 时，Fuller 让团队把每个智能体都定义为代码。他认为这是智能体应有的自然形态。正如他所解释的，"智能体本质上就是结构化文本，一个提示词加上配置，而任何文本都可以放在一个仓库里，让全公司都能看到、审查和改进。"智能体的提示词、工具列表、调度、凭据和记忆都放入配置文件，与公司软件一起保存在 git 仓库中。智能体的任何变更都只能通过某人批准的拉取请求（PR）进行，这为每个智能体带来了版本历史、代码审查、回滚和审计轨迹。

他花了一周时间构建了一个包含两个模板的入门套件，存放在专用的 git 仓库中。一个用于事件驱动的智能体，在事情发生时立即启动，比如新任务到达或文书从法院返回。另一个用于定时智能体，按定时器运行：每小时、每天或每周。每个智能体都住在自己的文件夹中，具有标准结构：一个 JSON 配置文件、一个 Markdown 格式的系统提示词、部署脚本和运维文档。将变更合并到主分支即可自动部署智能体。构建者永远不需要编写软件。他们克隆仓库、复制一个入门模板、告诉 Claude Code 智能体应该做什么，然后就能得到智能体所需的一切：配置、提示词、凭据存储和记忆。

## 弥合技术鸿沟

Fuller 召集了公司 15 人指导委员会，成员来自财务、市场、运营和开发部门（没有一个是软件开发人员），让他们克隆仓库并使用 Claude Code 构建 Managed Agents。

目标是证明非开发人员可以自己构建生产级智能体。如果每个智能体都必须经过开发团队，这个瓶颈就会限制整个公司前进的速度。之所以安全，是因为他们不是在编写软件。相反，他们是在填写配置和提示词，而 Managed Agents 提供了运行时。

"我不得不向他们解释什么是 PR。很多（非软件工程师）以为它的意思是运行，就像 PR 一样，尽可能快，"他说。"现在他们在做拉取请求，并互相发送。"

一周之内，15 名员工都拥有了可用的智能体。这些构建者回到各自的团队并培训其他人。一个月之内，ABC Legal 大约有 50 多个智能体在运行。每个智能体都有一个名称、一个所有者和一项单一职责。

## 法律文书流程大多数阶段都有对应的智能体

ABC Legal 现在在法律立案流程及其周边运营的大多数阶段都有智能体。

AI Code Reviewer 审查四个代码库中的每个拉取请求，运行多模型分析以捕获安全漏洞、性能回退和已提交的凭据。工程师现在在合并前会等待它的审查。

EvidenceChain™ Delivery Agent 接管了一位客户经理过去手工完成的每周例行工作。ABC Legal 运营着一个专有网站 EvidenceChain.com，法院、原告和被告可以在上面查询现场完成的送达记录，包括送达员是谁、何时尝试送达以及文书送达的照片。一位客户希望持续从中提取特定记录。该智能体现在会为匹配的任务拉取数据库报告，使用 Managed Agent 内置的浏览器检索每个 PDF，并每天将其交付到客户的 FTP 服务器。设置它的客户经理从未自动化过任何东西，通过向 Claude Code 描述需求，大约一小时就构建完成了。

eFiling Rejection Diagnoser 在法院拒绝立案时自动触发，读取任务详情，检查法院规则，并在一分钟左右将诊断结果发布到 Slack，这项工作过去要消耗员工数小时的时间。一个任务验证智能体会对照法院检查每个传入的任务。它在浏览器中浏览法院网站，确认听证会或案件已适当立案并确实在所述日期进行，然后根据发现调整任务，标记司法管辖区、法院和诉讼时效时间范围。

Attorney Coverage Agent 在律师网络中工作以确保听证会有律师覆盖，检查可用性，给他们发邮件，并阅读关于可用性和价格的回复，以便协调员确认覆盖。

在财务部门，一个应收账款汇款智能体解析汇款邮件，构建 NetSuite 付款申请文件，并将其发布到 Slack 以供一键批准，然后导入；还有一个每日智能体对每个工程工单给出资本化或费用化的裁决。市场部门运行一个 Google Ads 分析师，每周为渠道负责人发布建议。在运营部门，一个名为 Charvis 的审查智能体检查已完成的服务任务，现在与合规团队的一致率约为 98%。

Service-Overdue-Nudger 处理 ABC Legal 运营积压的一线层，即一个人原本要做的重复性首轮处理，并起草分级的每日外联消息供人工批准。

## 让智能体更聪明：收集、调优、重复

ABC Legal 的智能体在人工监督下工作，将它们做了什么或建议什么发布到 Slack，人们在那里回复帖子并用表情符号做出反应。



Hank 是一个内部代码审查智能体，它将每次审查发布到一个共享的 Slack 频道。每条记录都标明了拉取请求以及由此产生的计数，因此智能体所做决定的轨迹是公开且可搜索的。

Fuller 认为所有这些反应数据都是被浪费的训练信号。不过，并非每个智能体都需要这个信号。集群中的大多数是单任务执行者，其输出无人评分，它们独自工作。对于确实收集评分反馈的智能体，ABC Legal 使用三角色架构：独立的智能体共享一个工作区、环境和凭据保险库，但按不同的时间表运行。这种模式将 Slack 中的消息转化为经过版本管理、人工批准的智能体变更：

1.  **初始智能体**完成工作，通常是在任务到达或文书返回时实时进行，并记录每个操作的审计轨迹。
2.  **收集器（Harvester）**每小时或每天运行，从 Slack 收集人工反馈，反馈以帖子回复和表情符号反应的形式到达。每一个都成为一个带标签的数据点。
3.  **调优器（Tuner）**每周运行，同时审视所有内容，并提出对提示词或配置的变更，而非模型权重。它只负责起草。由人工审查并合并拉取请求。



在 ABC Legal 的自我改进智能体循环中，初始智能体实时完成工作，收集器按每小时节奏从 Slack 收集人工反馈，每周调优器以拉取请求的形式提出提示词和配置变更。智能体通过开发者已经在使用的工作流得到改进。

一个例子是"deliveries-as-code"，这是 Fuller 用于调优工作路由方式的智能体式系统，始于 ABC Legal 的 50 人姊妹公司 Docketly。Docketly 围绕交付来组织工作，每个交付都有自己的路由和处理规则集。所有约 145 个规则集都是 git 中的单个 YAML 文件，而非管理屏幕中的记录，因此调优一个交付意味着编辑一个文件并打开一个拉取请求。

四个智能体构成了这个循环：一个每周向 Slack 发布裁决，收集器根据人工反馈将反应转化为标签，调优器在 YAML 上打开拉取请求，第四个智能体将合并后的配置推送到生产数据库。第四个智能体只执行人工已经审查和批准的内容。在实践中，一个标记错误路由交付的表情符号反应，可以在一周内变成对该交付路由规则的合并变更。审查是循环中唯一的手动步骤。

## 为什么选择 Claude Managed Agents

Fuller 在最终选择 Claude Managed Agents 作为其组织的智能体式执行框架（harness）之前，评估了多个框架。他的标准很具体：平台必须具有版本管理、可观测的会话、工作区计费、模型选择、记忆原语、MCP 接线，以及最关键的，无需照看的基础设施。

平台的责任划分与 Fuller 希望运营的方式清晰对应。Anthropic 的托管基础设施拥有让智能体运行的一切：执行循环、会话、记忆、控制台以及模型本身。ABC Legal 拥有提示词、工具列表、触发逻辑、审计轨迹以及基于结果的反馈循环。

有几项能力在大规模下被证明尤为重要：

-   **版本管理：** 每次推送都会创建一个带有乐观锁的新智能体版本。回滚轻而易举。
-   **模型灵活性：** 大多数智能体默认使用 Claude Sonnet，高容量和快速任务使用 Claude Haiku，当更深入的推理足以证明成本合理时使用 Claude Opus。切换模型只需改一行。
-   **MCP 接线和凭据保险库：** 智能体连接到 ABC Legal 自己的平台（有超过 100 个工具可用）、用于报告的 Metabase、用于人在环路交互的 Slack，以及用于项目管理的 Atlassian。
-   **定时部署：** 周期性智能体通过 Bitbucket Pipelines 按 cron 时间表运行，后者已经处理仓库访问、密钥和计费。

ABC Legal 追踪 AI 支出的每一美元，按供应商、工具、团队和用例细分。随着集群在春季上线，支出攀升，然后在 7 月开始下降，而使用量持续增长，这是下文所述效率工作的结果，许多智能体覆盖的任务成本降低约 50%，各部门约 310 名员工使用 Claude。

公司的成本策略是深思熟虑的：将支出推向垂直的运营工具和智能体，这些地方的回报可衡量，同时保持横向聊天和构思使用的广泛性并控制成本。大多数智能体从人在环路开始，智能体查看任务或工单并提出建议，供人在采取任何行动之前审查。建议要么存储在任务中并在横幅中显示，以便人们在工作流程中接受或拒绝，要么发布到 Slack 频道，人们可以在帖子中回复。这些回复构建了一个包含好坏判断的带标签数据集，为收集器和调优器循环提供输入，并让团队能够编写评估（eval）并在前沿模型之间对智能体进行基准测试。一旦智能体证明它在特定任务上与人类一样好或更好，它就会切换到自动化模式并自行行动，之后它仍留在同一测量框架内，以观察性能的任何变化。

ABC Legal 追踪的指标是效率比；即智能体交付的价值与其运行成本的比值。每个 Managed Agent 在每次运行时都会向数据仓库报告自己的价值，以小时和美元计。智能体遵循 J 曲线，通常在刚起步并使用较大模型时处于水下，然后随着团队编写评估、转向更便宜更快的模型并削减 token 而转为正值。

## 部署智能体集群的最佳实践

Fuller 部署 AI——特别是 Claude Managed Agents——的经验让他总结出几条关于使用该技术的工作原则：

‍

-   **把一切视为代码。** "代码只是结构化文本。LLM 是文本引擎，"他说。"你能把越多的业务转化为仓库中的文本，智能体给你的杠杆就越大。"这适用于传统软件，同样也适用于提示词、模式、调度规则、通知模板和业务配置。
-   **从人在环路开始。** 每个智能体一开始都发布建议供人工审查。只有在证明与人类决策持续一致之后，它才赢得独立行动的权利。"每个智能体在独自行动之前都要赢得信任。它不是从那里开始的。"
-   **把 PR 作为你的控制面。** "如果你想让智能体参与决策，就让决策看起来像一个拉取请求。"逐行评论、审批工作流和不可变审计轨迹随版本控制免费而来，并与 AI 和人工审查自然组合。
-   **投资于反馈循环。** 收集器-调优器模式意味着智能体无需重新训练即可改进。Slack 回复和表情符号反应成为结构化信号，反馈到提示词和配置变更中，全部通过人类已经在使用的同一拉取请求工作流进行。
-   **跳过定时任务的弯路。** ABC Legal 在转向 Managed Agents 之前花了真实时间构建定时任务和本地例程，很大程度上是因为该产品当时才刚刚发布 beta 版。Fuller 今天的建议是直接使用 Managed Agents。
-   **预期的是 git 障碍，而非 AI 障碍。** 困难的部分是让业务用户熟悉克隆仓库以及在 Git 和拉取请求中工作，而非 AI 本身。它奏效了，而且很快，但这确实是一个真实的障碍，Fuller 希望工具本身能使其更容易。
-   **并非每个任务都值得一个智能体。** 成本是真实的，所以每个团队都必须从价值高于成本的角度思考。工作是挑选真正节省时间或创造自动化的可处理问题，并愿意说某个任务不值得一个智能体。

## 下一步

ABC Legal 的智能体集群持续增长。进行中的项目包括一个服务照片审查器、一个 PagerDuty 分诊智能体、一份每日 KPI 摘要，以及在现有智能体上扩展的调优器循环。

团队还在识别更多"X-as-code"候选者：通知模板、事件路由规则和调度逻辑，这些都可以移入仓库，让智能体能够读取、推理并提出改进。

正如 Fuller 所说："我们希望 AI 支持一个能够自我运行的业务，让员工自由地驾驭它。"
