# AI 智能体的常见工作流模式——以及何时使用它们
[AI 智能体](https://www.anthropic.com/research/building-effective-agents)自主做出决策，而工作流正是你为这种自主性赋予结构的方式。它们建立执行模式，将智能体的能力引导至需要协调步骤、可预测结果和编排时序的复杂问题。

当你需要多个智能体协同工作时，真正的决策在于哪种模式适合你的问题。

我们与数十个构建 AI 智能体的团队合作过，在生产环境中，三种模式覆盖了绝大多数用例：顺序式、并行式和评估器-优化器式。

每种模式解决不同的问题，选错一种会让你在延迟、token 或可靠性上付出代价。本文逐一拆解这三种模式，并给出每种模式适用时机的指导，以及如何将它们组合使用。

## **工作流与智能体如何协同**

如果你管理过团队，你就已经理解工作流了。

想想制造业的装配线：每个工位上都有一名熟练工人对自己的具体任务做出决策，但整体流程是预先设计好的——即便个别步骤涉及路由或重试这类动态决策。

智能体工作流的运作方式也是如此。

### **理解工作流与自主智能体**

工作流并不取代智能体的自主性；它们塑造的是智能体在何处、以何种方式运用自主性。

**完全自主的智能体决定一切**：使用哪些工具、以什么顺序执行任务、何时停止。

**工作流提供结构**：它建立整体流程、定义检查点，并为智能体在每一步的运作方式设定边界，同时仍允许在这些边界内进行动态行为。

工作流中的每一步仍然可以利用智能体的推理和工具调用，但整体编排遵循一条既定的路径。工作流模式让你在每一步内获得智能体的智能，同时让整个任务以可预测的过程流转。

## **智能体工作流模式**

在生产环境中，我们看到三种工作流模式出现得最为频繁。请把它们视为构建模块，而非僵化的模板——随着需求演进，你常常会将它们组合或嵌套使用：

1.  **顺序式工作流**——用于按固定顺序执行任务
2.  **并行式工作流**——用于跨智能体同时运行独立任务
3.  **评估器-优化器工作流**——用于需要迭代改进的输出

每种工作流类型解决特定的问题，并在复杂度、成本和性能方面有明确的权衡。

|  | 解决的问题 | 何时使用 | 权衡 | 优势 |
| --- | --- | --- | --- | --- |
| **顺序式** | 任务存在依赖关系：步骤 B 需要步骤 A 的输出 | 多阶段流程、数据流水线、起草-审查-润色循环 | 增加延迟（每一步都要等待前一步） | 通过让每个智能体专注于一件事，可以提升准确性 |
| **并行式** | 任务相互独立，但逐个执行太慢 | 跨多个维度的评估、代码审查、文档分析 | 成本更高（多个并发 API 调用），且需要聚合策略 | 可以更快完成，并实现工程团队之间的关注点分离 |
| **评估器-优化器** | 初稿质量不够好 | 技术文档、客户沟通、按特定标准生成代码 | 成倍增加 token 用量并增加迭代时间 | 通过结构化反馈循环可以生成更好的输出 |

‍
从能解决你问题的最简单模式开始。默认选择顺序式。当延迟成为瓶颈且任务相互独立时，转向并行式；只有当你能够衡量质量提升时，才加入评估器-优化器循环。

### **顺序式工作流**

顺序式工作流按预定顺序执行任务。

每个阶段的智能体处理输入、做出决策、按需发起工具调用，然后将结果传递给下一阶段。其结果是清晰的操作链条，输出以线性方式流经系统。



**何时使用：** 当任务自然分解为具有明确依赖关系的不同阶段时，顺序式工作流表现出色。你以一定的延迟换取更高的准确性，因为每个智能体专注于特定的子任务，而不是试图一次处理所有事情。

在以下情况下使用顺序式工作流：

-   多阶段流程，每一步都依赖前一步的输出
-   数据转换流水线，每个阶段都增加特定的价值
-   由于固有依赖关系而无法并行化的任务
-   迭代改进循环，如起草-审查-润色循环

**何时避免：** 当单个智能体能够有效处理整个任务时，或者当智能体需要协作而非顺序交接工作时，跳过顺序式工作流。如果你把任务强行塞进顺序步骤，而它并不自然契合这种结构，那你就是在增加不必要的复杂度。

**示例：** 当每一步涉及真正不同的工作时，顺序式工作流效果很好：

-   生成营销文案，然后将其翻译成多种语言——或者从文档中提取数据、按 schema 校验，再加载到数据库中
-   内容审核流水线也很适合顺序式：提取内容、分类、应用审核规则，然后适当地路由

**专业提示：** 首先把你的流水线当作单个智能体来尝试，各步骤只是提示词的一部分。如果这样就足够了，你就在不增加复杂度的情况下解决了问题。只有当单个智能体无法可靠处理时，才拆分为多步工作流。

### **并行式工作流**

并行式工作流将独立任务分配给多个同时执行的智能体。你不必等一个智能体完成后再开始下一个，而是同时运行多个智能体并合并它们的结果。

当任务之间互不依赖时，这种模式可以带来速度提升。

这种方法类似于分布式系统中的扇出/扇入（fan-out/fan-in）模式。你把相同或相关的工作发送给多个智能体，每个智能体独立处理，然后你聚合或综合它们的输出。

智能体之间不互相交接工作——它们自主运作，产出的结果共同贡献于整体任务。



**何时使用：** 当你可以将工作划分为受益于同时处理的独立子任务时，或者当你需要从多个视角审视同一问题时，并行化是合理的。它还实现了关注点分离：不同的工程师可以独立拥有和优化各自的智能体，彼此的工作互不干扰。对于复杂任务，用单独的 AI 调用处理每个考量点，往往优于试图在一次调用中兼顾所有事情。

考虑在以下情况使用并行式工作流：

-   分区式方法，不同智能体处理不同方面（比如一个处理查询，另一个筛查安全问题）
-   评估场景，每个智能体评估不同的质量维度
-   投票模式，多个智能体分析相同内容，你聚合它们的评估结果

**何时避免：** 当智能体需要累积上下文或必须基于彼此的工作继续构建时，不要使用并行式工作流。当 API 配额等资源限制使并发处理效率低下时，或者当你缺乏处理不同智能体矛盾结果的清晰策略时，跳过这种模式。如果结果聚合变得过于复杂或降低了输出质量，并行化就不值得。

**示例：** 并行式工作流适用于：

-   自动化评估（每个智能体检查不同的质量指标）或代码审查（多个智能体检查不同的漏洞类别）
-   文档分析是另一个强有力的用例：并行提取关键主题、情感分析和事实核查，然后合并这些洞察

**专业提示：** 在实现并行智能体之前先设计好你的聚合策略。你会采用多数投票吗？对置信度分数取平均？还是听从最专业的智能体？对如何综合结果有清晰的计划，可以防止你收集到相互冲突的输出却无从解决。

### **评估器-优化器工作流**

评估器-优化器工作流将两个智能体配对在一个迭代循环中：一个生成内容，另一个按特定标准评估它，生成器再根据反馈进行改进。这一过程持续到输出达到你的质量阈值或达到最大迭代次数。

关键洞察在于，生成和评估是不同的认知任务。将它们分离可以让每个智能体专业化——生成器专注于产出内容，评估器专注于应用一致的质量标准。



**何时使用：** 当你有清晰、可衡量的质量标准，且 AI 评估器能够一致地应用这些标准时，以及当首次尝试与最终质量之间的差距足够显著、值得额外的 token 和延迟时，这种模式有效。

考虑在以下情况使用评估器-优化器工作流：

-   有特定要求的代码生成（安全标准、性能基准、风格指南）
-   语气和精确性至关重要的专业沟通
-   任何初稿质量始终达不到要求的场景

**何时避免：** 当初次尝试的质量已经满足你的需求时，跳过评估器-优化器工作流——你只是在为不必要的迭代消耗 token。不要将这种模式用于需要即时响应的实时应用、像基础分类这样的简单常规任务，或者当评估标准过于主观、AI 评估器无法一致应用时。如果存在确定性工具（比如用于代码风格的 linter），就改用那些工具。当资源限制的代价超过质量提升时，也要避免这种模式。

**示例：** 评估器-优化器工作流适用于：

-   生成 API 文档（生成器编写文档，评估器对照代码库检查完整性、清晰度和准确性）
-   创建客户沟通内容（生成器起草邮件，评估器评估语气和政策合规性）
-   生成 SQL 查询（生成器编写查询，评估器检查效率和安全性问题）

**专业提示：** 在开始迭代之前设定清晰的停止标准。定义最大迭代次数和具体的质量阈值。没有这些护栏，你可能会陷入昂贵的循环：评估器不断发现小问题，生成器不断微调，但质量在你停止迭代之前早已进入平台期。要知道何时足够好就是足够好。

## **选择合适的工作流模式**

合适的工作流模式取决于你的任务结构、质量要求和资源约束。

在选择模式之前，先尝试将任务作为单次智能体调用来完成。如果这达到了你的质量标准，那就完成了。如果没有，找出它在何处不足——这会告诉你该选用哪种模式。

以下几个问题可以帮助你决策：

-   单个智能体能有效处理这个任务吗？如果能，就完全不要使用工作流。
-   任务是否有清晰的顺序依赖关系？使用顺序式工作流。
-   子任务能否独立且同时处理，更快的完成是否有帮助？考虑并行式工作流。
-   质量是否会通过迭代改进得到有意义的提升？考虑评估器-优化器模式。

选定模式后，考虑：

-   **失败处理：** 为每一步定义回退行为和重试逻辑。
-   **延迟和成本约束：** 这些决定了你能运行多少智能体、能负担多少次迭代。
-   **衡量改进：** 用单个智能体设定基线，这样你就能判断工作流是否真的有用。

**组合模式：** 这些模式并非互斥。你可以根据复杂度的需要嵌套它们。

-   评估器-优化器工作流可能使用并行评估，多个评估器同时评估不同的质量维度。
-   顺序式工作流可能在某些阶段包含并行处理，在进入下一步之前发生多个独立操作。

关键在于让模式的复杂度与实际需求相匹配。不要因为你能做并行处理就加入它——只有当并发执行带来明确好处时才加入。除非评估器-优化器循环能以你可以衡量的方式提升输出质量，否则不要实现它。

## **审慎地演进你的工作流**

我们最好的建议是：从能起作用的最简单模式开始。如果顺序式工作流能处理你的用例，就不要加入并行化。如果初稿质量已经足够好，就跳过评估器-优化器循环。

随着需求变化，这三种模式为你提供了清晰的升级路径。顺序式工作流可以在瓶颈阶段纳入并行处理。智能体式方法可以在质量标准收紧时加入评估，而且由于这些模式是模块化的，你无需彻底重写。
