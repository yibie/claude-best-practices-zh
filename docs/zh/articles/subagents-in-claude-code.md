# 如何在 Claude Code 中使用子智能体，以及何时使用
[Claude Code](https://claude.com/product/claude-code) 能很好地处理复杂的多步骤项目，但长会话会不断累积负担。每一次文件读取、每一次探索的岔路、每一个未完成的想法都留在上下文窗口中，拖慢响应速度并推高 token 成本。

设想在一个[大型 TypeScript monorepo](https://claude.com/resources/articles/how-claude-code-works-in-large-codebases-best-practices-and-where-to-start) 中构建一个新功能。主要工作是实现，但支线任务不断出现：追踪现有服务如何处理 auth、找到日期格式化的共享 util、检查设计系统里是否已有接近你所需功能的组件。这些都不需要完整的项目上下文，而在主会话中运行它们只会增加噪音。如果能并行运行它们呢？

于是[子智能体](https://code.claude.com/docs/en/sub-agents)登场了。子智能体是一个拥有自己上下文窗口的隔离 Claude 实例。它接受一个任务，完成工作，只返回结果。可以把子智能体想象成 Claude Code 会话的浏览器标签页：一个可以追逐岔路而不丢失主线程的地方。

在本文中，我们讨论何时使用子智能体是有意义的、如何调用它们，以及何时这种开销并不值得。

## 什么是子智能体？

子智能体是自包含的智能体，在各自的上下文窗口中运行。当 Claude 启动一个子智能体时，该助手会独立工作，读取文件、探索代码或进行修改。完成任务后，子智能体只把相关结果返回给主对话。

每个子智能体都从零开始，不受对话历史或已调用 Skills 的拖累。多个子智能体可以并行运行，每个可以有不同的权限：研究型子智能体可能只有只读访问权限，而实现型子智能体则拥有完整的编辑能力。

Claude Code 包含几种内置的子智能体类型，包括：

-   **通用智能体（General-purpose agents）**，用于复杂的多步骤任务
-   **计划智能体（Plan agents）**，在给出实现策略之前先研究代码库
-   **探索智能体（Explore agents）**，针对快速、只读的代码搜索进行了优化

Claude Code 经常自行启动子智能体来处理分配的任务。也可以显式地指挥这种行为，并定义可复用的专家，让 Claude 自动委派给它们。知道何时该使用子智能体，正是让这个功能有用的关键。

## 何时应该使用子智能体？

某些类别的工作明显受益于子智能体委派。学会识别它们会让这个功能有效得多。

### 研究密集型任务

当理解某事物如何运作是修改它的前提时，子智能体可以探索代码库并返回摘要，而不是把几十个文件倾倒进对话中。

**信号：** 收集上下文需要读取几十个文件。

**收益：** 主对话保持干净，到达的是综合后的发现，而不是原始内容。

### 多个独立任务

当修复多个文件中的错误、更新多个组件中的模式，或进行互不依赖的修改时，并行子智能体可以更快完成任务。

**信号：** 子任务之间没有依赖关系。

**收益：** 三个子智能体同时工作，通常能在更短时间内完成任务。

### 需要全新视角

当目标是对实现进行无偏见的审查时，子智能体提供一张白纸，因为它不会继承主对话中的假设、上下文或盲点。

**信号：** 需要在不受对话历史影响的情况下进行验证。

**收益：** 更干净、更客观的反馈。

**专业提示：** /clear 命令也会重置上下文和对话历史，提供类似的无偏见起点，但代价是完全丢失该历史。子智能体在保持主对话完整的同时实现同样的全新视角。

### 提交前验证

在最终确定修改之前，一个独立的子智能体可以验证实现没有过拟合测试或遗漏边界情况。

**信号：** 在提交代码前需要第二意见。

**收益：** 捕捉因熟悉代码而可能被忽视的问题。

### 流水线工作流

当任务有明确的阶段（例如，先设计，再实现，然后测试）时，每个阶段都受益于专注的注意力。

**信号：** 具有清晰交接的连续阶段。

**收益：** 每个子智能体专注于自己的阶段，不受其他阶段上下文造成的噪音干扰。

‍**专业提示：** 当任务需要探索十个或更多文件，或涉及三个或更多独立工作时，这是引导 Claude 使用子智能体的强烈信号。

## 如何指挥子智能体的使用

调用子智能体有多种方法，从简单的对话到自动化工作流。正确的起点取决于工作流，随着模式的出现可以逐步叠加复杂度。

### 对话式调用

最灵活的方法就是在对话中直接要求 Claude 使用子智能体。这在所有 Claude Code 界面中都有效：终端、VS Code、JetBrains、Web 和桌面应用。

能可靠调用子智能体的自然语言模式包括：

-   "Use a subagent to explore how authentication works in this codebase"
-   "Have a separate agent review this code for security issues"
-   "Research this in parallel. Check the API routes, database models, and frontend components simultaneously"
-   "Spin up subagents to fix these TypeScript errors across the different packages"

明确表达很重要。指定范围，在任务独立时请求并行执行，并描述期望的输出。

有效对话式调用的技巧包括：

-   **清晰界定任务范围。** "Explore how payments work" 胜过 "explore everything"。
-   **明确请求并行化。** 说 "these can run in parallel" 或 "work on all three simultaneously"。
-   **指定应返回什么。** 摘要、具体发现或建议。指明输出格式有助于 Claude 交付它。
-   **在无偏见分析重要时要求全新上下文。** "Use a subagent that does not see our previous discussion" 确保干净的评估。

**专业提示：** 当子智能体耗时较长时，Ctrl+B 将其发送到后台。对话可以在它运行时继续，完成后结果会自动浮现。/tasks 命令显示后台运行的所有内容。

### 自定义子智能体

当同一种子智能体被反复请求时（安全审查者、测试编写者、文档校对者），可以将其一次性定义为自定义子智能体。

之后，只要任务匹配其描述，Claude 就会自动委派给它，无需提示。

自定义子智能体以 markdown 文件形式存放在 `.claude/agents/`（项目级，与团队共享）或 `~/.claude/agents/`（用户级，在所有项目中可用）。每个都有自己的系统提示词、工具权限，并可选地拥有自己的模型。

### CLAUDE.md 指令

自定义子智能体定义专家是谁。CLAUDE.md 文件定义 Claude 何时应使用它们的规则。如果每次代码审查都应经过只读子智能体，或每个架构问题都应先触发一次研究，那么该策略就放在 CLAUDE.md 中。Claude 在每次对话开始时读取它，因此行为在会话和团队成员之间保持一致，无需任何人记得去要求。

CLAUDE.md 适合用于子智能体指令的情况：

-   代码审查应始终使用只读子智能体
-   项目有 Claude 应遵循的特定研究模式
-   需要在团队成员和会话之间保持一致的行为

### Skills

对于反复运行的复杂多步骤工作流，Skills（技能）提供了可复用的接口。在 .claude/skills/ 中定义一次技能，然后用 /skill-name 调用它，或让 Claude 在任务匹配其描述时自动加载它。

Skills 与 CLAUDE.md 文件的区别在于作用范围。CLAUDE.md 文件始终被加载，塑造每一次交互。技能是按需加载的，要么是因为被显式调用，要么是因为 Claude 将当前任务匹配到了技能的 description 字段。这使得技能成为那些应可用但不应应用于每个提示词的工作流的合适位置。

Skills 适合用于：

-   某些操作会定期运行
-   不同团队成员需要访问相同的复杂操作
-   在团队中标准化某些任务的执行方式很重要

### 钩子（hooks）

钩子（hooks）是用户定义的 shell 命令、HTTP 端点或 LLM 提示词，在 Claude Code 生命周期的特定点自动执行。[钩子](https://code.claude.com/docs/en/hooks-guide)可以基于事件自动化子智能体工作流。钩子在特定操作上触发，无需手动调用即可运行子智能体任务。

钩子是合适的工具，当：

-   每次提交都应在创建前自动审查
-   安全检查应在无人记得要求的情况下运行

## 何时不应该使用子智能体？

虽然子智能体是有用的功能，但它们带有开销。每个子智能体都会启动自己的上下文、消耗 token，并在开发者与工作之间增加一层间接。当上下文隔离、并行性或全新视角确实有帮助时，这种成本才值得。

对于较小或紧密顺序的任务，坚持使用主对话通常更简单，例如：

-   **顺序、依赖的工作。** 当第二步需要第一步的完整输出，而第三步需要两者时，单个会话处理这条链通常比通过文件传递状态的子智能体接力更干净。
-   **同一文件的编辑。** 两个子智能体并行编辑同一文件是冲突的配方。在这种情况下，将紧密耦合的修改保持在同一个上下文窗口中。
-   **小任务。** 对于快速修复或聚焦的问题，委派的开销超过收益。只需在主对话中提示或询问。
-   **太多专家智能体。** 为一切定义自定义子智能体很诱人，但用选项淹没 Claude 会让自动委派变得不那么可靠。大多数团队最终选择少数几个范围明确的智能体，而不是一个庞杂的名单。
-   **需要智能体相互协调的工作。** 子智能体向主对话报告，但不能相互交谈。对于子智能体需要通信的任务，请使用[智能体团队（agent teams）](https://code.claude.com/docs/en/agent-teams)。使用智能体团队时，子智能体在独立会话之间协调，而不是在一个会话内，这使它们更重、更昂贵。有关何时使用子智能体与 Agent Teams 的更多指导，请查看我们的 [Claude Code 智能体团队文档](https://code.claude.com/docs/en/agent-teams)。

前面描述的信号（即需要第二意见、子任务之间缺乏依赖关系，以及大量研究）清楚地表明何时委派给子智能体是值得的。

## 从对话开始，之后再自动化

子智能体在有意识地使用时才能发挥全部价值。Claude 提供的自动调用很有帮助，但知道何时委派研究、并行化工作并请求全新视角，比听天由命能产生更好的结果。

使用子智能体时，从对话式提示词开始。注意哪些请求反复出现，并在这些模式清晰时构建自动化。目标是让子智能体委派变得毫不费力，这样你的注意力就能留在重要的工作上。
