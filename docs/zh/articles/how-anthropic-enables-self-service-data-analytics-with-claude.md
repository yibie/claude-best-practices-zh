# Anthropic 如何借助 Claude 实现自助式数据分析

许多数据科学和数据工程团队都能证明，实现自助式数据分析历来是一件苦差事。

通过宽表和反规范化表让技术背景较少的同事更容易使用数据模型，往往会导致随着业务规模扩大而出现定义不一致、相互重叠的视图（而且对于毫无意愿学习 SQL 的员工来说，这几乎无助于弥合差距）。另一种做法是为用户创建更多圈定边界的环境，但这往往会遗漏长尾的业务问题，并随着各团队将工作孤立开来，导致指标和仪表盘膨胀。

LLM 的兴起为自助式分析提供了另一条路径，可以避开这些挑战。然而，把 Claude 指向数据仓库并让智能体去执行，可能会制造出一种虚假的精确感。

最初因摆脱临时请求而感到的解脱，会随着一个认识的到来而变成恐惧：这种设置让利益相关方与底层基础设施、文档和专业知识脱节，而这些正是此前引导他们走向精心整理的数据集的东西。

在 Anthropic，95% 的业务分析查询通过 Claude 实现自动化，总体准确率约为 95%。通过将这项往往枯燥重复的工作交给 Claude，我们的数据科学团队可以专注于更具战略性的工作，例如因果建模、预测和机器学习。

在与数十位 Anthropic 最顶尖的 Claude Code 用户会面，并见识了无数分析智能体的设计模式之后，我们为其他使用 LLM 的数据团队总结出了一些最佳实践。在本文中，我们将分享这些技巧和方法，以最大化 Claude 驱动自助式业务洞察的能力，包括：

-   为什么分析准确率是上下文与验证的问题，而不是代码生成的问题；
-   导致大多数错误的三类失败模式；
-   我们为应对这些错误而构建的智能体式分析技术栈；
-   我们如何衡量有效性；以及
-   我们创建大多数 Skills（技能）所使用的基本模板（见附录）

## **数据不是软件**

LLM 的生成能力是一把双刃剑：那些让模型能够创造性地解决复杂问题的机制，也可能产生幻觉性的错误输出。要全面理解分析智能体面临的挑战，将它们与编码智能体进行比较会很有帮助。

编码是一个开放式的解空间，会奖励模型的创造力，而文档和测试则提供了抵御幻觉的天然护栏。相比之下，对于分析用例，通常只有一个正确答案、一个正确来源，而且没有确定性的方法来证明其正确性。

对于自助式智能体业务分析而言，复杂性主要在于数据的模糊性。核心问题归结为**_我们能否将用户的问题映射到数据模型中具体且最新的实体，并知道与之交互的正确方式_**。如果我们能做到这一点，那么后续的执行和 SQL 就变得微不足道了。

我们识别出这个问题的三个特征，它们解释了绝大多数不准确的回答：

1.  **概念 <> 实体模糊性**：数据模型中有数百个可行选项（可能来自数百万个字段），智能体无法选择最能回答用户问题的正确字段。例如，在衡量活跃用户数量时：哪些行为构成“活跃”？是否包含欺诈用户？使用多长的回溯窗口？
2.  **数据陈旧**：数据源、业务定义和 schema 不断变化；资产和智能体知识会过时，并开始返回微妙错误的答案。
3.  **检索失败**：正确的信息可能确实存在于数据模型中，并且标注得当，但鉴于搜索空间的广阔，智能体就是找不到它。
