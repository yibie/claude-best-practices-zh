# 使用 Claude Fable 5.2 安全扩展多智能体团队
多智能体团队能够解决具有挑战性的长时程问题。[今年九月](https://www.anthropic.com/research/formalizing-fermats-last-theorem)，我们发表了费马大定理的首个端到端形式化证明，它由数十个运行内部研究模型的智能体编写，该模型大致相当于 Claude Fable 5.1。那项工作依赖 Prove2Me（一个用于数学形式化的平台）以及一位研究者的指导。在一项新的小型实验中，一支由 1,000 个智能体组成的团队运行 Claude Fable 5.2 的早期版本，在没有 Prove2Me 提供的脚手架、也没有研究者引导的情况下复现了该证明。该团队耗时 28.7 小时，使用的输出 token 只有原来的三分之一，写出的证明长度仅为原版的七分之一。

每个智能体都在一个无法访问互联网的沙箱中工作。一个分类器会在每条 shell 命令和每次文件编辑执行前进行检查，一个离线监控器则审查团队的每一个动作。我们给智能体提供了一份包含 60 条陈述的列表、一段对经典证明路线的一句话概述、这些陈述所使用的定义，以及我们此前形式化工作中已证明的 47 个引理，并分配了负责人和助手角色。除此之外，我们没有就如何证明该定理或如何组织自身提供任何其他指导。

这项小型实验表明，运行 Fable 5.2 这类模型的智能体团队，能够在精心设计的安全边界内完成雄心勃勃的长时程目标。

## 问题

费马大定理指出，对于任何大于 2 的 n，都不存在正整数 a、b、c 满足 aⁿ + bⁿ = cⁿ。它在其后 350 多年里一直未被证明，直到 1995 年 Andrew Wiles 爵士发表了 129 页的证明。对该证明进行形式化——使每一步都能由计算机检查——一直是数学界的一个[长期目标](https://lean-lang.org/use-cases/flt/)。

我们九月份的形式化工作由一位研究者和数十个智能体耗时 11 天、消耗约 60 亿输出 token 完成。他们用 Lean 编写了 1,300 万行代码，Lean 是一种由计算机检查证明每一步的编程语言。

智能体通过 Prove2Me 进行协调，该平台由彭天翼（现为 Anthropic 的技术人员）及其在哥伦比亚大学的合作者设计。Prove2Me 使用一张共享图，将每个待证明的陈述与其拆分出的更小陈述连接起来。任何智能体都可以拆分一个陈述，其他智能体可以向该图查询哪些未证明的部分已准备好处理，从而避免它们丢失对项目状态的跟踪。每个陈述及其证明都保存在一个可独立编译的单独文件中，因此许多智能体可以并行工作而无需编辑相同的文件。

## 执行框架

我们想看看，一支运行 Fable 5.2 这类模型的智能体团队，能否在没有 Prove2Me、也没有研究者指挥工作的情况下，使用由通用工具构建的执行框架（harness）产出这一结果。

### 工具

对于这项任务，我们给这支由 1,000 个智能体组成的团队提供了 60 条待证明的陈述，包括最终定理和 59 个中间里程碑。对于每条陈述，智能体必须用 Lean 编写证明，用 Lean 的工具构建并检查它，然后将其提交到 Git 上的共享主分支，由评分器在那里进行检查。我们为每个智能体提供了以下工具：

-   一个 shell 和一个文件编辑器，位于其自己的无网络访问沙箱中。
-   Lean 的工具链和 [Mathlib](https://github.com/leanprover-community/mathlib4)，已内置于沙箱镜像中。
-   其自己的 Git 分支，以及向主分支发起合并请求的能力。
-   一个共享的 Postgres 数据库，可从 shell 访问。

### 协作

证明工作可以被拆分，这使它成为适合多智能体团队的任务。但[智能体也需要协调](https://claude.com/resources/articles/multi-agent-coordination-patterns)，既要在他人的工作基础上继续推进，又要避免重复劳动。在我们[最初的形式化工作](https://www.anthropic.com/research/formalizing-fermats-last-theorem)中，Claude 的早期尝试失败了，因为智能体丢失了对项目状态的跟踪，无法有效协作。改用 Prove2Me 平台解决了这个问题。

在这次运行中，每个智能体都在自己轻量级虚拟机上拥有一个沙箱。单台共享机器在大约 100 个智能体时就达到了极限：在我们 100 个智能体的运行中，超过一半因内存、磁盘或 CPU 耗尽而不得不停止或重启。

有了 1,000 个独立沙箱，智能体需要一种共享工作的方式，因此我们给它们提供了一个 SQL 数据库（图 1）。我们选择 SQL，是因为它提供了用于组织信息的通用原语，其事务能够处理来自 1,000 个智能体的并发写入，而且 Claude 已经熟悉它。智能体使用该数据库来认领任务、共享笔记并记录已完成的工作。

![执行框架架构。一叠 1,000 个智能体沙箱（1 个负责人和 999 个助手），每个沙箱运行智能体循环，沙箱内的执行框架代码以 shell 和文件编辑器作为工具，以仓库、Lean 和数学库作为文件。API 请求和响应在智能体循环与沙箱外调用 Claude API 的网关之间传递。Git 和 SQL 请求及其结果通过同一网关传递到同样位于沙箱外的团队基础设施：一个存放 Lean 文件和计划的 Git 仓库，以及一个存放指令、任务和笔记的 Postgres 数据库。](https://claude.dev/media/13dca8328dafc6e21860d77255066340778ab6cecae719aefe31fad55a9b1c1c.png)

**图 1** 1,000 个智能体各自在自己的沙箱中运行，仅通过一条通往网关的管道与外界相连。网关调用 Claude API，并将 Git 和 SQL 请求传递到共享仓库和数据库。

### 提示

我们的提示词给 Claude 提供了一份包含 60 条待证明陈述的列表，每条都有一行非正式描述，并说明了可用的工具（如上所列）。

我们给团队提供的唯一结构是一个层级，由一名负责人和 999 名助手组成。我们告诉负责人将问题拆分为若干部分并分配给助手。我们告诉助手预期会收到来自负责人的工作，如果任务不明确就与负责人确认。

在运行过程中，执行框架向负责人发送了 19 条关于剩余时间的自动提醒，每条都鼓励负责人继续推进。

## 安全

正如我们[此前分享过的](https://www.anthropic.com/news/improving-alignment-security-efforts)，没有任何单一防御层足以约束一支智能体团队。在这项实验中，我们将沙箱与实时监控和离线监控相结合，使每个智能体都处于自己的虚拟机中且无网络访问，并检测任何试图逃逸沙箱或篡改监控的行为。

### 沙箱

我们通过以下方式保护每个智能体的沙箱（图 2）：

-   **通信**：智能体没有专用的消息传递工具，只能通过数据库和 Git 进行协调。
-   **代码变更**：智能体只能推送到自己的 Git 分支，并向主分支发起合并请求。随后由一个单独的任务将变更合并到主分支，仅在出现冲突或故障（例如无关历史）时拒绝合并。
-   **数据库访问**：数据库调用在共享的非特权角色下运行。每条 SQL 语句有 5 秒时限，写入超过 256 MiB 会被拒绝。
-   **网络控制**：沙箱没有网络访问。它们唯一的对外连接是一条通往网关的管道，由网关转发它们的请求。
-   **身份**：网关在沙箱外为每个请求标记智能体的身份，以防止一个智能体冒充另一个。
-   **内核**：每个沙箱的内核在构建时移除了让 root 用户获得直接进入路径的功能，例如可加载模块、kexec、原始内存访问和内核探针。它以内核锁定模式运行。
-   **最小权限**：每个智能体的命令在其沙箱内以非特权用户身份运行，并移除了 sudo 等可重新获得 root 权限的工具。智能体的工具经过设计，无法读取或更改运行它们的智能体循环。

![执行框架架构及其安全措施，分为三组标注。沙箱：每个智能体获得自己的轻量级 VM，无网络访问、无 API 密钥或凭据、无通往其他沙箱的直接路径、使用非特权用户账户，且无法通过工具访问执行框架代码。实时监控：网关对每次工具调用运行阻塞式分类器，采用故障关闭设计，设置每个智能体的身份并记录每次推送和查询；Git 仓库仅接受来自自身分支的推送，并通过合并任务处理主分支，Postgres 数据库使用共享的非特权角色并设有时间和大小限制。离线监控：保存在沙箱外的运行记录输入离线监控，离线监控将严重发现告知运行负责人。](https://claude.dev/media/ae9400390023085b8047fa4a7d7d2e486d1bb0c405152b884ef6e5579ec4abec.png)

**图 2** 三层安全措施环绕着团队：沙箱、实时监控和离线监控。分类器在每次工具调用执行前进行检查，离线监控器则审查团队的动作。

### 实时监控

为了让这类运行更安全，我们使用一个经过提示的 LLM 分类器，它可以阻止每次工具调用，包括 shell 命令和文件编辑。该分类器会监视试图逃逸沙箱、探测其边界或篡改监控的行为，以及模型若成功逃出沙箱后可能采取的任何有害动作。当分类器阻止一次工具调用时，整个智能体团队会停止，必须由人工审查该阻止后团队才能重启。这旨在防止另一个智能体执行被阻止的动作。

为了测试我们的分类器能否检测复杂的破坏行为，我们运行了多智能体侧任务和破坏评估，其中红队智能体使用分解攻击等策略，试图诱骗分类器允许沙箱逃逸。我们发现，能够查看智能体思维链（CoT）和智能体间通信的监控器在这些评估中能够检测到所有破坏尝试，因此我们现在使用它们来监控多智能体运行。与此同时，我们运行同一监控器的基于动作的版本——它只能看到动作，看不到 CoT——以防止智能体的推理说服监控器允许有害动作。

我们正在通过人工引导和自动红队、针对生产记录（包括过往事件）进行评估，以及扩展威胁模型，持续改进我们的监控栈。在本文所述的运行中，我们只使用了基于动作的监控器。只有对负责人的阻止才会结束运行；对助手的阻止只会移除该助手。

在这次运行之后不久，我们添加了并行的 CoT 监控器。我们在可能尚未完成发布前对齐评估的模型上运行此类实验，因此我们的监控设计考虑了模型未对齐的可能性。我们发布的模型会先完成该评估，这降低了风险，但并未消除风险。

在超过一百万次工具调用中，本次运行没有任何一次达到被阻止的标准。当我们用 CoT 监控器和当前的评分标准重放这些调用时，只有一次（一次 root 访问检查）接近被阻止。

### 离线监控

除实时监控外，我们还运行一个离线监控器。该监控器依据与实时监控器相同的威胁模型分析智能体团队的动作，但拥有额外的能力，例如能够查询其他智能体的动作。

## 结果

### 没有 Prove2Me，团队构建了自己的协调系统

这项证明的工作在多个层面进行：

-   **证明**：对于任何大于 2 的 n，都不存在正整数 a、b、c 满足 aⁿ + bⁿ = cⁿ。
-   **陈述**：我们给团队提供了 60 条待证明的陈述，包括最终定理和 59 个中间里程碑。
-   **更小的陈述**：智能体将困难的陈述拆分为更小的陈述，即引理。
-   **Lean**：每条陈述和引理都是 Lean 中的一个定理。

每条陈述在 [Lean](https://lean-lang.org/use-cases/flt/) 中都以一个证明占位符开始，只有当 Lean 的检查器接受完整证明后，它才算被证明。我们让负责人决定如何攻克该证明，以及如何在这些工作层面上协调团队。

在最初的 10 分钟里，负责人在数据库中建立了五张表（图 3）：

-   **Announce**：负责人向整个团队下达的命令（例如如何拆分工作）。
-   **Assign**：谁负责什么（例如哪位助手拥有或代理每条陈述）。
-   **Notes**：一块开放的公告板（例如用于认领某项工作或报告进度）。
-   **Subtasks**：一份待办清单，任何智能体都可以添加任务，第一个认领的助手即拥有它。
-   **Landed**：已完成工作的日志。

![1 个负责人和 999 个助手之间的五张共享数据库表。Announce，负责人向所有人下达的命令，例如如何拆分工作或减少数据库使用：负责人写入和读取，助手读取，有一次助手写入。Assign，谁负责什么，例如哪位助手拥有或代理每条陈述：负责人写入和读取，助手读取，有一次助手写入。Notes，一块开放的公告板，助手在此说明自己正在接手哪一部分或报告进度：负责人和助手都写入和读取。Subtasks，一份共享待办清单，任何人都可以添加任务，第一个抢到的助手拥有它：助手写入和读取，负责人读取，有两次负责人写入。Landed，已完成工作的日志，记录哪条陈述或哪一部分已完成、其提交以及是否通过团队检查：助手写入和读取，负责人读取。](https://claude.dev/media/3f0caf7f3e1dd17ad5ca3c9cb8bc584707404c40d3ba143cf21d348ef2dd48e8.png)

**图 3** 在最初的 10 分钟里，负责人建立了五张共享数据库表来协调团队。负责人写入命令和分配，助手记录已完成工作并管理 subtasks 表，双方都写入 notes 表。

### 负责人分配了陈述

负责人创建好这些表后，做了三件事。首先，它通过向 assign 表写入 999 行（每个助手一行），将每条陈述分配给一个由 16–17 名助手组成的小组。其次，它让每个小组中的一名助手担任队长，负责向 notes 表发布计划，并将工作拆分为任务供小组从 subtasks 表认领。第三，它向 announce 表发布指令，告诉每个助手先判断其陈述的难度，并在 notes 表中发布结论。

从提示词中，助手们知道数据库的存在。它们找到了 announce 表并开始进行评估。大多数将结论发布到了 notes 表。大约 27 分钟时，已有三条陈述被证明，负责人读取了发布的结论。随后，它将大多数助手判定在运行预算内不可行的 47 条陈述搁置一旁，并将几乎所有助手重新分配到剩余的 10 条陈述上，它认为这些可以完成。各小组从约 17 名助手扩大到 46 至 139 名。

每个助手在一个循环中工作，其中大部分内容都在负责人的命令中规定：

-   在 notes 表中找到该陈述的计划。
-   从 subtasks 表中认领一个任务。
-   用 Lean 编写证明，用 Lean 的工具检查它，并提交到 Git 上的主分支。
-   将任务标记为完成。
-   向 notes 表发布更新。

大约 45 分钟时，10 条陈述中已有约 5 条被证明，负责人写道：

> “团队的吞吐量远高于早期‘预算内不可行’结论的假设”

全部 10 条陈述在大约 70 分钟内被证明。

### 随后负责人将助手转移到更难的陈述

这最初的 10 条陈述完成后，负责人写道：“没有理由闲着”，并将助手重新分配到它最初放弃的更难陈述上。随着更多陈述被证明，它不断将助手转移到新的任务上，主要集中在前六个小时（见图 4 中以红色显示的 assign 表写入）。

![从第 0 小时到第 30 小时，1,000 个智能体与共享数据库表（announce、assign、notes、subtasks、landed 以及一组其他表）之间读写的时间推移图。写入以红线表示，从顶部的负责人和助手 1 到 999 一行向下延伸到各表；读取以绿线表示，从各表向下延伸到同一批智能体所在底行。到第 30 小时，计数攀升至 36,612 次写入和 311,734 次读取。几乎所有写入都流向 notes 表（约 20,600 次）和 subtasks 表（约 14,800 次），这些线在第 18 小时附近趋于平静，此时运行被重启。](https://claude.dev/media/c317ae355bbb5ddc955fd234a84ac7700fa41a3fd70ae16c32ac63817f276a57.png)

**图 4** 运行期间对共享表的读取（绿色）和写入（红色）。几乎所有写入都是助手的笔记和任务更新，包括认领任务。总计未包含大多数脚本调用。活动在第 18 小时附近停止，此时我们从上次保存处重启运行，并给智能体额外 12 小时。

起初，负责人指示队长将工作拆分为 subtasks 表中的任务。随着工作推进，助手在解决每条陈述上承担了更多责任。它们开始编写任务，有时是在队长发出求助之后。到第 5.6 小时，73 名助手已编写了 756 个任务，其中只有 16 名助手是队长。图 4 显示了许多助手对 subtasks 表的写入（红色），尽管其中大多数写入是为了认领任务或将其标记为完成。完成任务的助手也会主动承担更多工作：

> “空闲……我能端到端完成各部分……指定一个深入的部分……我立刻开始”

起初，负责人还会将助手分配到特定陈述。这在第一个小时内开始改变，到第三个小时，负责人告诉空闲的助手“不要等我”。这让空闲助手无需等待负责人就能接手不同陈述的工作，即便负责人仍在继续编写新的分配。

### 负责人将团队分配到 Langlands–Tunnell

大约第 18 小时，剩下的只有 Langlands–Tunnell（Wiles 的证明所依赖的一个经典结果），以及依赖它的陈述和另一条陈述，后者团队在过程中顺带证明了。在运行早期，Langlands–Tunnell 任务的队长曾持悲观态度，估计该证明至少需要 0.7 到 100 万行 Lean 代码，按时完成的可能性不到 1%。负责人将该陈述搁置一旁。

当几乎所有其他工作完成后，负责人将团队重新聚焦于 Langlands–Tunnell。在一次最后的自上而下分配中，它将约 750 名助手转移到该陈述上，并写道：“说实话，胜算很低。”

Langlands–Tunnell 远大于智能体处理过的任何其他陈述，所需任务数约为其九倍，新代码量超过其两倍。助手们再次使用 subtasks 表来拆分工作，但许多最初的任务对单个助手来说太大，无法独自完成。

于是团队将工作组织成一棵树。队长制定了一个计划，将该陈述划分为 10 个领域，并将每一部分列为一个任务。发现某一部分太大、无法独自处理的助手可以将其拆分，在其下添加更小的任务。每当某一部分对单个智能体来说过于困难时，这棵树就会生长，最终达到 2,418 个任务、深达 10 层（图 5）。每一部分都可以假定其下方的部分成立，因此数百名助手可以在这些部分被证明之前并行工作。

## 结论

这项小型实验让我们得以研究一支由 1,000 个智能体组成的团队如何完成一项漫长而困难的任务。仅使用 Git 和一个共享数据库，智能体就设计出用于分配角色和共享结果的表，组建了团队，并构建了一棵任务树来分解最具挑战性的陈述——而该陈述的队长曾估计其按时完成的可能性不到 1%。

这一结果并不否定领域专用执行框架或平台的必要性。例如，Prove2Me 仍可能通过帮助智能体更快地编译 Lean 代码、让它们搜索并复用人类成果来提高效率。

人类指导在某些节点上仍然有用。智能体往往会在困难问题上放弃，并误判其难度。早期，助手们判定 60 条陈述中有 47 条在运行预算内不可行，然而团队最终证明了其中大多数。在这种时刻给予人类鼓励，可以防止智能体过早停止。

精心设计的安全边界让我们最初有底气开展这项实验。Claude 可以用我们提供的工具以任何它选择的方式攻克问题，但只能在无网络访问的沙箱内、并在两个独立监控器的监视下进行。

我们预计这些方法会迅速演进，而随着像这样的团队承担更困难的工作，围绕它们的安全边界也需要同步跟进。我们相信，在安全扩展的前提下，多智能体团队将在未来几年帮助解决我们一些最具挑战性的问题。
