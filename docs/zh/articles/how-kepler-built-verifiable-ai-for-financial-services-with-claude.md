# Kepler 如何借助 Claude 为金融服务构建可验证的 AI
_在我们的 **How startups build with Claude** 系列中，我们重点介绍初创公司如何借助 AI 变革所在行业。本文分享 Kepler 如何为金融服务领域的 AI 构建信任与验证层。_

| 快速概览 |
| --- |
| 名称 | Kepler |
| 成立时间 | 2025 |
| 创始人 | Vinoo Ganesh（CEO）与 John McRaven（CTO） |
| 技术栈 | AWS、Rust、Python、用于编排的容器 |
| 增长 | 在不到三个月内索引了 2600 万+ 份 SEC 文件、5000 万+ 份公开文档、100 万+ 份私有文档，以及覆盖 27 个全球市场的 14,000+ 家公司。 |

金融公司运营在高度监管的环境中，其报告必须可审计、可问责。监管文件、交易推介材料或研究报告中的每一个数字，都需要能够对照源文件进行验证。

金融行业传统上依赖的工具可以提取数据，但验证过程仍然需要分析师来完成。分析系统无法理解自由形式的问题，无法将其分解为多个步骤，也无法推断出某个单一指标需要跨特定财年提取三个不同的行项目。AI 系统可以完成这种解读，但它们将解读与计算放在同一步骤中处理，因此产出的数字是由模型生成的，而模型可能会出错。

Vinoo Ganesh 和 John McRaven 曾在 Palantir 工作多年，为国防、能源和金融公司构建数据系统。这段经历塑造了他们对「答案必须可验证」的环境中信任问题的思考方式。在创立 [Kepler](https://kepler.ai/) 之前，他们与 147 家金融公司进行了交流，包括私募股权、对冲基金和投资银行，几乎在所有公司都听到了同样的声音：每个人都想用 AI 做研究，但没有人信任其输出。正如一位董事总经理对他们所说：「我怎么能信任一个我无法审计的东西？」

两人的答案是构建确定性的基础设施，作为 AI 的信任与验证层。该基础设施与作为推理和解读层的 Claude 相结合，驱动了 Kepler Finance：一个面向金融服务的研究平台，分析师可以用自然语言提问，并即时获得可验证的答案。

## 处理长时程、多步骤任务并标记歧义

金融分析涉及复杂的多步骤计算、密集的数据和含义过载的术语，且不容许任何错误。因此，Kepler 需要一个能够保持长时程计划不偏离、并能标记歧义的模型。

例如，如果分析师询问某家公司过去八个季度的存货周转天数，模型需要弄清楚答案需要什么：正确的公式、正确的财年期间，以及可能影响数字的任何重述。

团队对所有前沿模型进行了基准测试。他们发现，在简单查询上，各模型表现相当。但当涉及具有相互依赖关系的长时程多步骤计划时，除了 Claude 之外，所有模型在第四或第五步时都开始走捷径或丢失约束条件。「在我们的工作负载上，Claude 是始终能将计划保持完整的模型，」Ganesh 说。「其他模型一开始表现很强，但到第五步就会悄悄丢掉一个约束条件。」

最明显的差异在于每个模型如何处理不确定性以及如何让人类参与其中。例如，在某个术语可能有两种不同含义的情况下，大多数模型会选择一种含义然后继续。Claude 会停下来，请分析师做出决定。「这种行为比任何基准测试分数都重要，」Ganesh 说。「在金融分析中，早期的一个错误假设会破坏下游的一切。」

## 围绕 Claude 进行上下文工程

Kepler 团队发现，当给 Claude 提供精确定义的任务，并辅以结构化的领域知识、定义，以及关于哪些该解决、哪些该上报的硬性边界时，Claude 能产出更好的结果。「在金融领域，模型不能是整个系统。我们把它视为流水线中的一个阶段，其职责是恰好在该阶段把模型成功所需的一切交给它，」McRaven 说。「提示词工程优化的是单次调用，而内容工程优化的是围绕它的整个系统。」

团队构建了确定性执行环境，Claude 可以为每个需要可证明正确的操作调用它，例如计算比率或确定财年期间。他们开发了一套专有本体，将金融概念映射到精确定义和公式，可按用例定制。安全与访问控制限制在每一步都得到执行，管控每个用户可以拉取哪些数据源。在此基础上，他们为流水线中最常见的工作流构建了可复用的、可定制的 Skills（技能），例如跨复杂资本结构的企业价值计算（如处理优先股、可转换证券和少数股东权益），以及跨报告期变更的分部收入瀑布对账。这些 Skills 在确定性阶段和非确定性阶段之间进行协调，并且按设计是幂等的：相同的输入始终产生相同的输出。

接下来，他们将工作流分解为多阶段流水线，将不同的 Claude 模型匹配到不同阶段：Opus 4.7 用于复杂推理，如分解意图、解决歧义和生成结构化执行计划；Sonnet 4.6 用于任务约束更强、吞吐量更高的阶段。他们还训练了自己的专用模型用于召回（部分以 Claude 为基础，部分为 Kepler 专有），在将财务报表标签映射到标准化分类代码等任务上达到 94% 的准确率，而其他模型的准确率为 38-46%。

团队在投入生产之前，会针对数千个用例测试每一次提示词变更、模型升级和上下文修改。他们构建了自动化评估（eval）流水线，在每个阶段将 Claude 的输出与已知正确答案进行对比，同时检查结构化计划和最终计算结果。当测试失败时，他们可以追踪问题出在 Claude 的推理、提供的上下文，还是下游执行。当 Anthropic 发布新模型版本时，Kepler 会在数小时内完成基准测试，并确切知道哪些阶段有所改善、哪些出现退化、哪些需要调整提示词。

## 借助 Claude 扩展规模

Kepler Finance 已索引了覆盖 14,000+ 家公司的 2600 万+ 份 SEC 文件、5000 万+ 份公开文档和 100 万+ 份私有文档，横跨 27 个全球市场。Claude 使这一体量的非结构化数据变得可用，能够针对整个语料库解读问题，并调和不同公司和不同时期之间的术语差异。随后 Kepler 的检索层从经过验证的 SEC 文件中提取数字，计算结果，并将结果组装到分析台的 Excel 模板中，分析师只需点击一下，就能将每个数字追溯到源文件中高亮显示的确切行项目。

Claude 的推理与 Kepler 的确定性基础设施之间的分离，让一个小团队能够以这样的规模构建产品。Claude 承担了解读层的工作，否则这需要许多领域特定的 NLP 工程师，而 Kepler 的基础设施处理其余部分。由于架构是模块化的，原本需要大团队花费数月才能交付的新能力可以在数周内构建完成：团队改进某个阶段的推理，而无需触碰流水线的其余部分。

由于金融机构在合作之前需要合规基础设施，Kepler 从一开始就构建了完整的审计日志、隔离的客户环境和端到端的溯源能力，并已获得 SOC 2 Type II 认证，ISO 27001 认证正在进行中。

Kepler 的平台在设计上是领域无关的。团队刻意从金融领域起步，因为这是对 AI 要求最苛刻的环境之一：数据密集、术语含义过载、计算复杂，且不容许任何错误。为经受这种审视而构建的架构，适用于任何需要从大量文档集合中获得可验证答案的专业场景。从医疗服务提供方将临床试验数据与治疗方案进行核对，到法律团队在数十年的判例法中追溯先例，模式都是一样的：Claude 对问题进行推理，基础设施保证答案。

「Kepler Finance 是我们的第一个产品，」Ganesh 说。「但不会是最后一个。」
