# 构建常驻智能体

过去几个月里，我们看到常驻智能体（always-on agent）重新兴起。

常驻智能体是有状态的、主动的，这意味着它们跨会话管理上下文，并在没有直接监督的情况下采取行动。在底层，它们与其他智能体运行在同一个[核心循环](https://www.anthropic.com/research/building-effective-agents)之上。区别在于外围架构，它由若干原语构成，这些原语控制智能体何时醒来、运行轮次之间保留什么，以及它们的工作如何触达用户。

这轮复兴很大程度上归功于近期的模型进步，这些进步让常驻智能体在运行上更加实用。首先，最新模型具备更好的判断力：它们在理解用户意图、判断何时该主动联系方面更加可靠。其次，智能能力正变得越来越便宜，而长时程任务受益最大。例如，在[一个长时程编程基准测试](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)中，Opus 5.5 每解决一个任务的成本比 Opus 5 低 78%，而在典型工作负载上只低 40%。

客户已经开始问我们，如何将这类体验集成到他们自己的产品中。一些公司希望让现有智能体更具主动性，另一些则希望从零开始构建。

本文拆解常驻智能体背后的原语，并说明它们如何协同工作。

## 常驻智能体背后的循环

常驻智能体实际上并不是“一直在线”。这只是对用户体验的一种描述。

在现实中，智能体大部分时间都在休眠，周期性地醒来工作。每一段工作称为一个**运行轮次（run）**：智能体接收一个事件，完成任务，然后保存关于所发生事情的信息。运行轮次在**会话**（session）内进行，会话是消息与工具调用的记录。运行轮次结束后，智能体重新进入休眠，这个循环无限重复。

![常驻智能体时间线的动画示意图：长时间休眠、不消耗 token，其间穿插着短暂运行轮次。每个运行轮次有四个步骤：事件到达、会话开始、智能体循环运行、运行轮次写回在轮次之间保留的存储状态。](https://assets.claude.com/5dc803bf06d6e92e4aecae762da096626e2fa9ec.gif)

## 核心原语

常驻智能体的外围架构有五个核心原语：事件收件箱、定时器、记忆、权限和发件箱。我们逐一来看。

### 事件收件箱

大多数 AI 智能体只在用户发送消息时运行。相比之下，常驻智能体可以由多种类型的事件触发，包括 webhook、定时任务和后台任务。

一种诱人的做法是让每个事件源直接调用智能体，但这存在几种失败模式。例如，两个同时到达的事件可能启动相互竞争的运行轮次，而一次崩溃可能彻底丢失一个事件。

这正是事件收件箱的用武之地。每个来源不再直接调用智能体，而是把事件发送到收件箱，由工作进程（worker）从中取出。

最简单的版本包含三个组件：

-   一个持久化的事件列表，通常是数据库表；
-   一个处理器（handler），通常是 HTTP 端点，负责把事件写入列表；以及
-   一个工作进程，通常是后台服务，负责从列表中读取。

收件箱应跟踪每个事件的状态，并可以基于来源提供的唯一标识符对事件去重。关系型数据库很适合用作收件箱，每个事件作为新行追加。我们建议从每个用户一个收件箱开始，但如果需要更高的并行度，可以进一步拆分。

![事件收件箱示意图。处理器（HTTP 端点）把每个事件写入收件箱（一张跟踪状态并丢弃重复项的数据库表），并唤醒工作进程。工作进程读取待处理事件，启动运行轮次，等待其完成，并将事件标记为完成。](https://assets.claude.com/bb08543a505cea3a24c88c718ceec4405e9c0a79.png)

当新事件到来时，处理器把事件写入收件箱并唤醒工作进程。工作进程读取所有待处理事件并启动一个运行轮次。延续先前工作的事件（例如用户的回复）会恢复已有会话，而其他所有事件都会启动新会话。

随后，工作进程把事件传给智能体循环，等待运行轮次结束，并将对应事件标记为完成。实现细节可能很棘手，因此这里给出几条最佳实践：

-   **处理器应快速确认事件**。某些来源（例如 webhook 提供方）会把缓慢的响应视为失败。处理器仍可执行轻量检查，但任何更深入的验证（例如检查提示词注入）都应在运行轮次期间完成。
-   **收件箱应是唯一事实来源**。当工作进程被唤醒时，它应首先从收件箱拉取最新事件。这样，如果工作进程在运行轮次中途死亡，新的工作进程可以取到同一事件并重试。
-   **一个收件箱同一时间只应有一个活跃的工作进程**。这可以防止两个运行轮次重复工作或相互覆盖。当运行轮次中途出现新事件时，你可以把它推到下一个运行轮次、合并进当前运行轮次，或者中断并重启。
-   **工作进程应把待处理事件批量合并**。例如，如果用户连续发送多条消息，工作进程可以把它们合并为单个运行轮次，这样智能体只需回复一次。

### 定时器

与事件收件箱配合，定时器让常驻智能体具备主动性。定时器通常分为两类：跟进（follow-up）或计划（schedule）。跟进是智能体为自己设定的截止时间，例如检查某个回复。而计划则是按已知节奏重复发生的任务，例如每日简报。

定时器存放在自己的持久化存储中，通常是另一张数据库表，与收件箱分开。收件箱只应存放已准备好处理的事件。跟进和计划可以共用相似的 schema，但计划还需要跟踪其重复规则。

![定时器示意图。运行轮次在数据库表中设置定时器，要么是智能体设定的跟进，要么是用户设定的计划。调度器找出到期项，并向事件收件箱添加事件，从而启动下一个运行轮次。](https://assets.claude.com/c16694e6d979a2ace84d03da0544297b7245c0a8.png)

定时器本身不会发起运行轮次。相反，调度器（通常是后台服务）以固定间隔轮询存储，并触发所有到期项。每一轮，调度器会：

1.  扫描存储，找出到期的定时器。
2.  根据类别更新每个定时器。
    1.  跟进应被标记为完成。
    2.  计划应把到期时间更新为下一次发生时间。
3.  向收件箱添加事件并唤醒工作进程。

对于调度器，你可以自行构建服务，也可以使用持久化执行引擎。

### 记忆

常驻智能体在多个彼此不连续的运行轮次中工作，依赖记忆来保持连续性。

与事件收件箱和定时器类似，记忆应有自己的存储。在我们的产品中，例如 Claude Code 的[自动记忆](https://code.claude.com/docs/en/memory)和 Messages API 的[记忆工具](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)，这是以文件目录的形式实现的。对于常驻智能体，这些目录应映射到持久化存储，通常是数据库或对象存储。这样记忆的生命周期就能长于工作进程。

一条经验法则是，记忆只应保存智能体无法再次查询到的内容。如果某些内容已存在于另一个系统（例如问题跟踪器）中，你应保存一个指针。以下是常驻智能体应存储的记忆类型细分：

-   **用户指令：** 用户关于智能体行为的任何指令都应保存在单独文件中，并在每次运行轮次开始时加载。用户不会总在身边引导智能体，因此指令必须在运行轮次之间延续。
-   **用户笔记：** 智能体应保存它了解到的关于用户的信息，例如用户的角色、偏好，或用户给出的任何纠正。你可以从一个文件开始，随着笔记增多再拆分为多个小文件。在后一种情况下，每次运行轮次开始时只加载一个索引，但智能体可以在需要更多细节时把各个文件拉入上下文。
-   **过往消息：** 智能体应跟踪它已经告诉过用户的内容，以免重复。它可以将其保存在每次运行轮次开始时加载的单独文件中，也可以让工作进程加载智能体与用户最近的几条消息。
-   **任务进度：** 对于每个进行中的任务，智能体应维护一个进度文件，涵盖已完成和剩余的工作。任何新的运行轮次都可以读取该文件，并从上一个运行轮次中断的地方继续。与用户笔记类似，每次运行轮次开始时只加载一个索引，但智能体可以在需要更多细节时把各个文件拉入上下文。

![示例记忆设置的示意图，以文件目录形式呈现。instructions.md、index.md 和 reported.md 在每次运行轮次开始时加载，而 notes/ 和 progress/ 文件夹在需要时读取。智能体在运行轮次期间写入记忆。](https://assets.claude.com/e5d209d7ef9b3455dec8a27b777dc12bdf806699.png)

#### 上下文窗口内部

在做任何工作之前，智能体会加载系统提示词、工具定义和记忆文件。这部分初始上下文“开销”会包含在每个运行轮次中，因此我们建议保持精简，并使用[提示词缓存](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)来降低成本。

新会话开始时只有这部分上下文开销以及触发该运行轮次的事件。而已有会话则会带回其先前运行轮次中的消息和工具调用。

如果会话变得过长，你可以[压缩较早的消息](https://platform.claude.com/docs/en/build-with-claude/compaction)，或者启动新会话。两种方式都会丢失细节，因此任何需要持久保留的内容都应在过程中保存到记忆。

![上下文随时间使用的动画图表。系统提示词、工具和记忆的固定区段出现在每个运行轮次中。已有会话会带回其完整记录并不断增长，直到上下文压缩把较早的记录转为摘要。](https://assets.claude.com/48757f0a147acfe841c943674c6214d34ed4405a.gif)

### 权限

权限是常驻智能体风险最大的地方。运行轮次持有用户的访问权限，并且按设计是在无人值守下运行的。对于每次工具调用，智能体都需要决定是自行继续、阻止，还是等待批准。

权限所用的组件与其他智能体相同：

-   **凭据存储：** 常驻智能体通常需要敏感的用户凭据（如密码或访问令牌）才能发挥作用。[推荐模式](https://code.claude.com/docs/en/agent-sdk/secure-deployment#credential-management)是在智能体环境之外设置一个代理，由它把凭据添加到出站请求中。智能体发送不带凭据的请求，代理在转发前注入真实凭据。
-   **自动模式：** 常驻智能体应能在没有持续用户输入的情况下工作。我们已在 Claude Code 中通过[自动模式](https://www.anthropic.com/research/claude-code-auto-mode)解决了这个问题的一个版本。自动模式使用分类器审查风险较高的操作，并阻止其判定为危险的操作，以便 Claude 找到更安全的做法。不过，对于最重要的决策，用户审查仍然必要。
-   **延迟工具调用：** 在 Claude Code 中，[钩子可以延迟一次工具调用](https://code.claude.com/docs/en/hooks#defer-a-tool-call-for-later)，等待用户提供更多输入。同样的模式适用于常驻智能体，它们可能需要在采取某些操作前获得澄清或批准。当一次调用被延迟时，运行轮次结束，会话在调用中途被保存。请求会展示给用户（例如通过用 [MCP Apps](https://modelcontextprotocol.io/extensions/apps/overview) 构建的交互式卡片），用户的回答会作为事件回到收件箱。该事件启动新的运行轮次，用用户的输入恢复已保存的会话。在延迟调用等待响应期间，工作进程可以处理其他事件，因此智能体不会被阻塞。

### 发件箱

对于大多数 AI 智能体，响应在生成时就会流式传输给用户，因此用户可以跟随 Claude 推理问题、调用工具并写出答案的全过程。

相比之下，常驻智能体的大部分工作都在后台完成。用户得到的是结果和少量细节，而不是完整的逐步拆解。

![发件箱示意图。运行轮次以三种方式之一结束：无话可说、一次发送工具调用，或一次向用户提问的延迟工具调用。消息进入发件箱（一张数据库表），由调度器投递给用户。延迟请求可以经由发件箱，也可以在你自己的界面中展示。](https://assets.claude.com/700b5f3a446f22493c0307ec65751b6b2f82ccb7.png)

运行轮次可以以三种方式之一结束：

-   智能体向发件箱发送一条消息，
-   智能体判定无需发送任何内容，或
-   智能体使用延迟工具调用请求权限或额外输入。

大多数常驻智能体用一个直接把消息投递给用户的“发送”工具就足够了。只有当你希望控制智能体消息的节奏，或允许智能体从错误中恢复时，才需要正式的发件箱。

发件箱是一张单独的外发消息表，类似于事件收件箱。还有一个调度器，通常是后台服务，类似于工作进程。调度器读取待处理消息，决定投递哪些，并把它们发送给用户。来自延迟工具调用的请求既可以经由发件箱，也可以直接在界面中展示。

除了投递之外，调整智能体发送多少条消息也很重要。发送过多的智能体会变得嘈杂，而发送不足的智能体会漏掉用户需要知道的事情。我们建议构建评估（eval）来找到合适的平衡。在实践中，智能体最好先保持安静，然后随着时间推移赢得用户更多的注意力。

## 各部分如何协同

以下是五个原语如何协同工作：

![五个原语如何协同工作的动画示意图。定时器和事件收件箱启动运行轮次，运行轮次在会话内与记忆和权限协作，发件箱把消息投递给用户，用户的回答又作为事件返回。](https://assets.claude.com/9f8df7b2dcc9d4637d27f37dae6e40a2a5851c8a.gif)

每个运行轮次都始于收件箱中的一个事件，无论是用户消息、webhook 还是定时器。当工作进程取到一个事件时，它会启动一个运行轮次，并在新会话或已有会话中唤醒智能体。智能体读取记忆以获得基线，在权限范围内采取行动，然后把它学到的任何内容更新到记忆中。运行轮次结束后，智能体向发件箱推送一行记录，调度器把消息投递给用户。

这些部分共同构成一个循环。运行轮次可以设置一个定时器，稍后再次唤醒智能体；而当用户回复消息时，其回答会作为事件回到收件箱。每个运行轮次都很短暂，但这个循环会无限持续下去，这正是让智能体感觉始终在线的关键。
