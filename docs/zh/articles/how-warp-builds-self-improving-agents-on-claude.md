# Warp 如何在 Claude 上构建自我改进的智能体
_在我们的系列文章中，我们重点介绍初创公司如何借助 AI 变革所在行业。本文分享 Warp 如何将无状态的用户反馈转化为智能体的自我改进循环。_

智能体需要可靠且有效地处理重复性任务。一个初版提示词即使能把任务做对 80%，也可能给用户带来嘈杂而烦人的体验。Warp 在这方面吃过大亏，并以此为依据制定了其产品策略，为全球近 100 万开发者打造了更好的体验。

Warp 是用于构建和度量自我改进型云软件工厂的开放平台，构建在 Claude Platform 之上。团队在其内部代码审查智能体上遇到了这种“嘈杂体验”问题。工程师们抱怨说，他们的智能体给出的评论没有帮助，输出质量低下。

团队最初尝试了一些权宜之计，比如根据观察到的代码审查失败案例手动重写提示词。这让输出更可用，但无法规模化。改进 AGENTS.md 之类的上下文文件也有帮助，但远非彻底的修复。

最终他们意识到，真正的问题在于：无论智能体的用途是什么，对它的反馈通常都会在会话结束时消失，从而使智能体循环失去关键的上下文。他们的解决方案是：一个基于 [Agent Skills](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview) 的框架，用来创建自我改进的智能体，让反馈随时间不断累积，持续优化和提升智能体的输出。

继续阅读，了解他们如何在 Claude Platform 之上用 Skills（技能）构建这一方案。

## **基于 Skills 的智能体自我改进循环**

核心技术是使用 [**Skills**](https://support.claude.com/en/articles/12512176-what-are-skills) 构建的自我改进循环，Skills 是以文件形式编码的知识，可让指令不必直接写进原始提示词。Warp 演化出了一套自我改进的智能体架构，由两个 Skills 组成，中间夹着人类反馈。



**内层/基础 Skill** 承载功能领域的知识和指令。例如，当有 PR 被打开时，Warp 的代码智能体就使用该基础 Skill 和上下文执行，产出它的审查意见。

**人类对智能体输出的反馈**是自我改进循环的关键组成部分。对于代码审查来说，这可能简单到只是一个点赞，但越明确越好。

“人类可以确认‘这是一条很好、很有用的评论’，”Warp 创始人 Zach Lloyd 解释道，“但人类也可以详细说明为什么某次代码审查不好。像‘你建议重命名这个变量，但我们代码库的约定是这类全局变量使用这种特定的命名上下文’这样的具体说明，能告诉智能体下次如何做对。”

**外层/改进器 Skill** 充当观察者智能体，它按计划运行，而不是按任务运行。它拉取累积的人类反馈，将智能体给出的建议与人类的回应进行对比，并对基础 Skill 提出一个小而聚焦的修改。

由于 Skills 是纯文件，智能体非常擅长更新它们。这些更新可审查、可批准、可合并，能够走正常的 PR/代码审查工作流；一旦合并，内层 Skill 的下一次运行就会继承这项改进。

Warp 现在在其整个开源仓库中运行这一模式，分别设有规格编写、审查和分诊智能体，每个都带有自己的自我改进循环。

“基于文件的 Skills 是一种为智能体编码知识的方式，不必把这些知识直接放进提示词，而是让智能体在完成工作的过程中随时查阅，”Zach 说。“这个框架其实非常简单：一个是基础领域专用 Skill，另一个是改进该领域专用 Skill 的改进器 Skill。这种简单正是该方法的魅力所在。”

## **如何为智能体编写自我改进的 Skills**

以下是 Warp 团队为智能体循环编写自我改进 Skills 的一些经过验证的技巧：

-   **写原则，而不是规则。**“构建 Skill 时要像在指导一个聪明人，而不是像在给计算机编程，”Zach 说。“在 Skill 中写入‘寻找重复代码’这样的方向，比详尽的变量命名规则能提供更好的指引。”
-   **解释原因。**给出规则背后的理由，能让智能体对问题加以推理，而不是死板地遵循指令，这同样有助于更好的泛化。
-   **让反馈的给出毫不费力。**在人们已经在工作的地方采集反馈，比如直接在 PR 或 issue 上评论。同时让它自动发生，不需要额外的提交步骤。“低摩擦才能让信号持续流动，”Zach 指出。“如果门槛太高，你就拿不到反馈，也就无法改进 Skill。”
-   **保持 Skills 小巧，并使用渐进式披露。**[好的 Skill](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices) 文件并不大；它会引用资源文件和脚本，而不是一次性把所有内容都塞进上下文。
-   **反馈质量 > 数量，但数量也有帮助。**来自资深工程师的少量详细、领域专用的反馈，可能比大量草率的反馈更有价值，因为二元的点赞/点踩并不能说明_为什么_。“即使样本量相对较小，只要是一位具备领域专用知识的人给出的非常详细的反馈，你也能获得非常好的信号，而这些知识智能体本来无从获取，”Zach 继续说道。“话虽如此，高质量信号的语料库越大越好。在 Warp，我们用一个循环来管理整个开源仓库。我们有数百人贡献，进行着数千次代码审查。”
-   **在改进器 Skill 上多下功夫**。在编写改进器 Skill（观察者智能体）上多下功夫，其回报会超出眼前的智能体循环，因为改进器 Skills 在不同用例之间非常可复用。“除了领域专用知识这一部分，这是一个相当可复用的机制——代码审查智能体的改进器 Skill 与其他任何智能体的改进器 Skill 并没有太大差别。”

## **循环实践：Warp 的 issue 分诊智能体**

[Warp 的 issue 分诊智能体](https://github.com/warpdotdev/warp-agents-demo-github-issue-triage)演示了自我改进的智能体 Skills 框架。每当有人提交新的 GitHub issue 时，这一模式就会被触发：一个 GitHub Action 启动智能体，分析该 issue 的复杂度和可行性，分配标签，并建议修复方向。该分诊智能体运行在一个内层 Skill 文件上，该文件承载着关于每个标签含义以及行动前如何调研代码库的领域知识。

在一个示例 issue 上，第一阶段的内层 Skill 做得不错，但漏掉了一个标签：ready to spec，它表示贡献者可以开始针对该 issue 编写产品和技术规格。Warp 团队的一位维护者发现了这一缺口，并直接在该 issue 上留下反馈，正好是在工作发生的地方。关键在于，他既解释了自己的预期，也解释了为什么有这样的预期：这是便于智能体日后吸收的可操作反馈。

外层改进器 Skill 在 [Oz，Warp 的智能体编排平台](https://docs.warp.dev/)中作为定时的“update triage”智能体运行。该智能体通过 GitHub 认证，运行随 Skill 打包的 Python 脚本，拉取近期带有反馈的 issue，将它们汇总成一个 JSON 文件，再读回上下文。打包脚本本身就是一项最佳实践；Skills 可以引用资源文件，而不必在每次运行时重新编写代码。

在此基础上，智能体识别出维护者评论中的具体反馈信号，并提出了能捕捉这些信号的最小修改。它开了一个 PR，修改内层 Skill，使其在 issue 描述的是真实问题、即使确切的 UI 或 UX 形态尚未确定时，也应用“ready to spec”标签。

由于整个更新就是一个 Skill 文件，它走的是正常的代码审查工作流。PR 附带了一段说明，解释是哪些信号促成了这次修改以及修改了什么。由人进行审查、批准并合并，分诊 Skill 的下一次运行就会继承这项新知识。最后这一步人工环节闭合了循环，并让人始终掌控实际发生的变化。

这正是 Warp 现在在其开源仓库中大规模运行的同一机制，其中规格编写智能体、审查智能体和分诊智能体各自带有自己的自我改进循环。

任何智能体，无论任务是什么，只要你从一开始就为它构建这样一个循环——采集人类反馈信号、将其转化为 Skill 更新——它就会随时间变得更好，并从一次性的帮手扩展为能在整个组织内不断累积能力的系统。

| Warp 团队的最佳实践 |
| --- |
| 你是否把 Skills 与记忆混为一谈了？ | Skills 是程序性的、稳定的——“如何做 X”，与运行轮次无关，需刻意修改。记忆则由智能体在推理时自动写入，且始终在变化。 |
| 你需要一个改进器循环，还是每个智能体一个？ | 折中处理：用一个模板化的基础循环覆盖各智能体的共性，再叠加领域专用的权重。少数几个改进器可以各自负责一个；上百个则应当共享。 |
| 当反馈是错的怎么办？ | 假定它一定会错。不要让智能体盲目接受反馈——给它上下文去做合理性检查，筛选哪些人的输入算数，并在筛选或最终审查阶段保留人工介入。 |
| 你的领域可验证吗？ | 先构建验证执行框架（harness），再让智能体据此调优：生成参考语料库，将输出与参考对比，修复，重复。 |
| 如果领域不可验证呢？ | 在存在黄金输出的地方，依靠针对它们的确定性评估（eval）。在必须使用人类反馈的地方，将其限制在领域专家范围内——不要敞开大门。 |
| 你如何知道整个系统在改进？ | 跟踪人们已经在关注的全局指标——合并时间、贡献者数量、成本——并把它们反馈给改进器智能体。部署上采取爬行—行走—奔跑的渐进方式。 |
