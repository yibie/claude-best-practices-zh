# 快速模式

> **分类**：成本与性能 ｜ **英文**：fast mode ｜ **出现于 2 篇文章**

## 摘要

快速模式（fast mode）是 Claude API 上的一项选项：在保持同一模型能力的前提下，通过支付溢价换取更高的输出速度。它的意义在于把“更快”和“更强”解耦——需要低延迟时不必退回到能力更弱的模型，而是用成本换时间。

## 关键做法

- 把快速模式当作延迟预算工具：先确认瓶颈是模型输出速度，而不是任务设计或上下文长度，再考虑开启。
- 在能力与速度之间做显式取舍：同一模型下，快速模式不牺牲能力，只提高单价，因此适合对响应时间敏感、但对成本不敏感的调用。
- 优先在交互式、用户等待的链路上启用，把批处理、离线评测等对时延不敏感的流量留在标准模式，以控制总体成本。
- 结合长时程任务的使用方式：把“完成”的定义和停止条件写清楚，减少来回追问，本身就能显著缩短端到端时间，可与快速模式叠加使用。

## 在 Claude 里的用法

在 Claude API 上，Opus 5.5 和 Fable 5.2 均提供快速模式，按溢价计费获得更高输出速度。在 Claude Code 中，它适用于需要快速迭代的编码会话；而在长时间、多步骤的仓库级改动中，Opus 5.5 本身已能持续运行数小时，是否额外付费提速应视交互节奏而定。

## 常见误区

- 误以为快速模式会降低模型能力：它是在同一模型上购买速度，而不是切换到更小、更弱的模型。
- 误以为所有场景都该开启：对时延不敏感的批处理流量开启快速模式只会增加成本，不带来实际收益。
- 把速度问题误判为模型问题：若延迟来自任务描述含糊、反复澄清，应先改提示与停止条件，而非直接付费提速。
